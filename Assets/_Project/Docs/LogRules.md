# 로그 규칙

**문서 역할**
- **목적·질문:** 어떤 로그를 어떻게 기록·공유·보관하고 QA-Fix 과정을 남길지 정한다.
- **포함:** 런타임 기록·private 원시 로그 보관·사용자 수동 정리와 QA-Fix Log.md 운영 규범.
- **제외·담당:** 날짜별 정책 원문은 [LogHistory](LogHistory.md), 회차별 실행 영수증은 기존 Task/Log, 일반 작업 절차는 [WORKFLOW](WORKFLOW.md).
- **원본·참조:** 로그 정책의 단일 원본. §1.10과 §2의 보호·승인 조건을 다른 문서 요약으로 대체하지 않는다.
- **갱신:** 승인된 로그 정책·절차가 바뀌면 현행 조항을 고치고 이전 원문을 이력에 보존한다. 정책 문서화가 업로드·삭제 실행 승인은 아니다.

이 문서는 Hexiege 프로젝트에서 사용하는 두 종류의 로그 파일 규칙을 정의합니다.

| 종류 | 파일명 | 목적 | 작성 주체 |
|------|--------|------|----------|
| 런타임 로그 | 에디터: `RuntimeLog.txt` (1.10) / 실기기 캡처: `RuntimeLog_device.txt` (1.12) | 게임 실행 중 디버깅 + 라이브 운영 지표 수집 | game-programmer 에이전트 |
| QA-Fix 로그 | `Log.md` | QA ↔ DEV 버그 수정 이터레이션 기록 | qa-tester / game-programmer 에이전트 |

기존 규약으로 만들어진 로그 파일과 문서 인용은 계속 유효합니다. 새 명명 규약은 앞으로 생성하는 파일에만 적용합니다. 파일명 변경 원문: [LogHistory H01](LogHistory.md#h01).

---

## 이 문서를 왜 개정했는가

현행 판단은 심각도와 출시본 존속을 독립적으로 정합니다. 심각도가 높아도 UI로 대체 가능한 로그는 운영에 불필요할 수 있고, 조용히 삼킨 실패는 낮은 심각도라도 원인 보존이 필요합니다. 두 축 정의는 1.2, 적용 우선순위는 1.3이 권위 원본입니다.
날짜별 개정 표·구현/PASS·미검증 기록은 [LogHistory H02](LogHistory.md#h02)에 원문 보존합니다. 서버 수집은 향후 작업이며 구현 완료로 읽지 않습니다. 2026-09-08·09-14·09-15 개정 행 3건은 [LogHistory H14a](LogHistory.md#h14a)에 있습니다.

### 2026-08-13 개정 — 한 축에서 두 축으로

이 제목은 기존 참조를 유지합니다. 과거 설명 원문은 LogHistory H02, 현재 의무는 아래 1.1–1.14를 따릅니다.

# 1. 런타임 로그

게임 실행 중 발생하는 동작을 기록하는 로그입니다.

---

## 1.1 목적

런타임 로그는 두 가지 목적을 동시에 수행한다.

1. **개발 중 디버깅** — 버그 재현과 원인 파악. Claude(QA 에이전트 포함)가 로그 파일을 읽고 흐름을 추적한다.
2. **라이브 운영 지표 수집** — 출시본에서 플레이어에게만 발생하는 문제를 파악한다. (서버 수집은 향후 작업)

이 두 목적은 요구가 서로 다르다. 그래서 축을 나눈다.

---

## 1.2 두 축 — 심각도와 존속

모든 런타임 로그는 **두 축의 값을 각각 정한 뒤** 작성한다. 하나만 정하는 것은 규칙 위반이다.

### 축 A — 심각도

판정 질문: **"복구되었나?"**

| 값 | 정의 | 판정 |
|----|------|------|
| `Error` | 복구 경로가 **없다.** 기능이 죽고, 사용자는 그 기능을 더 이상 쓸 수 없다 | 복구 안 됨 |
| `Warn` | 예상 밖이지만 **대체 경로로 계속 진행**된다 (폴백 값 사용, 재시도 성공, 요청만 거부하고 게임은 계속) | 복구됨 |
| `Info` | 의도된 흐름 | 애초에 문제 아님 |

> "심각해 보이니까 Error" 는 판정이 아니다. **복구되었으면 Warn, 안 되었으면 Error.** 그것뿐이다.

### 축 B — 존속

판정 질문: **아래 두 문장 모두 "예"** 여야 `운영`이다. 하나라도 "아니오"면 `개발`이다.

1. **플레이어 기기에서만 벌어지는가?** (개발자가 에디터에서 재현할 수 없는가)
2. **이 로그가 없으면 원인을 추적할 수단이 없는가?** (UI 통지·다른 로그로 대체 불가능한가)

| 값 | 정의 |
|----|------|
| `운영` | 릴리스 빌드에 **남긴다.** 나중에 서버 수집 대상이 된다 |
| `개발` | 에디터·개발 빌드 전용. 릴리스에서는 **컴파일 단계에 사라진다** (1.7 참조) |
| `임시` | 특정 버그 추적용. **작업이 끝나면 코드 자체를 제거한다** |

| 생산 버튼 — 골드 부족으로 거부 | `Presentation/UI/ProductionPanelUI.cs` `ValidateProduction` → `ProductionFailReason.GoldInsufficient` | `Warn` | **개발** | 존속 2번이 "아니오". 같은 클래스가 실패 사유를 토스트로 이미 알린다 — 로그가 없어도 무슨 일이 있었는지 안다 |

## 1.3 분류 원칙

축 두 개만으로 갈리지 않는 경계 사례가 있다. 아래 네 가지가 그 경계를 확정한다.

**원칙 1 — 예외를 던지는 쪽은 로그하지 않는다.**
최종적으로 처리(`catch`)하는 쪽에서 **한 번만** 남긴다.
던지는 쪽과 받는 쪽이 모두 남기면 같은 사건이 두 줄로 기록되어, 서버 집계에서 **발생 건수가 부풀려진다.**

**원칙 2 — UI로 이미 알린 실패는 `개발`이다.**
단, **서버가 거부했는데 클라이언트가 그걸 몰랐던 경우는 `운영`** 이다.
클라이언트가 미리 막았는데도 서버가 거부했다는 것은 **클라·서버 상태 불일치**를 뜻하고, 그건 화면에 뜬 문구로는 절대 알 수 없는 정보다.

**원칙 3 — `Error`는 항상 `운영`이다.**
단, **Inspector 배선 누락 같은 설정 오류는 `Warn` + `개발`** 로 낮춘다.
설정 오류는 플레이어 기기의 문제가 아니라 개발 환경의 문제이고, 빌드 전에 잡히기 때문이다.

**원칙 4 — 삼킨 예외(`catch { }`)는 반드시 `운영` 로그를 남긴다.**
예외를 삼키면 **흔적이 전혀 남지 않는다.** 폴백이 조용히 성공한 것처럼 보이기 때문에,
로그를 남기지 않으면 "실패했다는 사실 자체"를 아무도 알 수 없다.

### 원칙 간 우선순위 (2026-08-14 추가)

한 자리에 원칙이 함께 걸리면 아래의 명시된 우선순위·최종 처리 지점·사건 단위를 적용합니다. 원칙 1~4 자체는 바꾸지 않습니다. 개정 당시 배경은 [LogHistory H03a](LogHistory.md#h03a)에 보존합니다.

#### ① 확정된 순서 — **원칙 1이 원칙 3보다 우선한다**

`Error`이면서 같은 사건이 두 계층에서 로깅되는 자리에서는 **원칙 1을 먼저 적용한다.**
즉 **원인을 가진 계층을 `운영`으로 두고, 중복되는 상위 호출부는 `개발`로 내린다.**

**근거 — 반대로 읽으면 원칙 1이 통째로 무효가 된다.**
원칙 3을 *"모든 `Error` 호출문이 각각 `운영`이어야 한다"* 로 읽으면,
예외는 결국 어딘가에서 `Error`로 잡히므로 **중복 금지 규칙이 적용될 자리가 아예 없어진다.**
규칙 하나를 살리려고 다른 규칙 하나를 죽이는 해석은 채택하지 않는다.

**이 순서로 잃는 정보는 없다.** 세 가지를 확인했다.

- **원인과 예외 타입·스택은 그대로 남는다.** 하위 계층 로그가 `운영`이므로 릴리스와 서버 수집에 계속 올라간다
- **화면 통지는 그대로다.** 상위 호출부는 `OnError` 등으로 사용자에게 계속 알린다 — 로그 축 값을 내리는 것이지 통지를 없애는 것이 아니다
- **`개발`이라도 개발 중에는 보인다.** 에디터·개발 빌드에서는 그대로 출력되고, **릴리스에서만 빠진다** (1.7)

#### ② "최종 처리 지점"의 정의 (원칙 1)

원칙 1은 *"최종적으로 처리(`catch`)하는 쪽에서 한 번만"* 이라고만 적고 **그게 어디인지 정의하지 않았다.**
위 3건이 막힌 진짜 원인이 이 모호함이다. 아래로 확정한다.

> **최종 처리 지점 = 예외의 원인 정보(예외 객체 · `e.Message` · 예외 타입 · 스택)를 실제로 손에 쥔 계층.**
> 즉 **`catch` 블록이 예외 객체를 직접 받는 그 자리**다.

**갈릴 수 있었던 반대 해석:** *"사용자에게 알리고 흐름을 끝내는 상위 호출부"* 도 "최종 처리"라 부를 수 있다.
그쪽을 택하지 않은 이유는 하나다 — **원인을 모르는 로그는 장애 추적에 쓸모가 없다.**

상위 호출부에는 원인이 도달하지 않는 경우가 흔하다. 실측 예로, `LobbyManager`의 두 메서드는
`catch (LobbyServiceException e)` 안에서 로그를 남긴 뒤 **`return null`** 만 한다.
호출부가 받는 것은 `null` 뿐이라, 호출부의 로그는 *"실패했다"* 만 말하고 *"왜"* 를 말하지 못한다.
그 줄만 릴리스에 남기면 **원인이 세상에서 사라진다.**
반대로 원인 계층을 택하면 화면 통지는 상위에서 그대로 유지되므로(① 참조) **잃는 것이 없다.**

#### ③ 원칙 3의 "항상 `운영`"은 **사건 단위**다

원칙 3은 **"그 *사건* 이 `운영`으로 기록되어야 한다"** 는 뜻이다.
**"모든 `Error` *호출문* 이 각각 `운영`이어야 한다"** 는 뜻이 아니다.

→ 한 사건이 여러 계층에서 감지되더라도, **원인을 가진 계층 한 곳이 `운영`으로 남으면 원칙 3은 충족된다.**
나머지 호출문은 `개발`로 내려도 원칙 3을 어기는 것이 아니다.

#### ④ 실제로 갈렸던 자리 — 2026-08-13 감사 3건

날짜별 적용 표는 [LogHistory H03b](LogHistory.md#h03b)에 보존합니다. 실제 원인 정보를 가진 catch를 운영으로 남기고 동일 사건의 상위 중복을 개발로 내리는 판정 예시이며, 새 호출경로를 추정으로 중복 처리하는 근거가 아닙니다.

#### ⑤ 순서를 매기지 않은 쌍 — 검토 결과

**실제로 충돌이 확인되지 않은 쌍에는 순서를 매기지 않는다.** 근거 없는 순서는 나중에 잘못된 판정을 낳는다.

| 쌍 | 판단 | 근거 |
|----|------|------|
| **1 ↔ 3** | **순서 지정 (1 > 3)** | 2026-08-13 감사 3건에서 정면 충돌이 실제로 확인됨 (④) |
| 1 ↔ 2 | 순서 미지정 | 두 원칙이 함께 걸린 자리(호출부 중복)에서 **결론이 같았다** — 둘 다 `개발`. 반대 결론 사례 미확인 |
| 1 ↔ 4 | 순서 불필요 | 원칙 4가 로그를 요구하는 자리(`catch` 블록)는 ②가 정의한 "원인 정보를 가진 계층"과 **같은 자리**다. 구조적으로 어긋날 수 없다 |
| 2 ↔ 3 | 순서 미지정 (단서만 명시 ↓) | ④의 3건에서 원칙 2도 `개발`을 가리켜 원칙 3과 반대지만, **결론이 원칙 1과 같아 1 > 3으로 함께 해소된다.** 원칙 2가 **단독으로** 원칙 3과 갈린 사례는 확인되지 않았다 |
| 2 ↔ 4 | 순서 불필요 | 전제가 서로 배타적이다. 원칙 4의 대상은 **아무 흔적도 남지 않는** 삼킨 예외이고, 원칙 2의 대상은 **화면에 이미 뜬** 실패다 |
| 3 ↔ 4 | 순서 불필요 | 둘 다 `운영`을 가리킨다. 반대 방향이 될 수 없다 |

**2 ↔ 3 에 붙는 단서 (새 규칙이 아니라 1.2가 이미 그렇게 판정한 내용의 명문화):**
원칙 2의 `개발` 하향은 **같은 사건의 `운영` 기록이 다른 계층에 남아 있을 때만** 성립한다.
UI로 알렸더라도 **원인이 그 로그에만 있으면 `개발`로 내리지 않는다.**
1.2 조합표의 *"매칭 로비 생성/참가 실패"* 행이 그 예다 — 호출부가 *"다시 시도해주세요"* 를 띄우는데도 `운영`으로 확정되어 있다.

> 미확인 쌍은 충돌이 없다는 증명이 아닙니다. 새 충돌은 실제 근거를 확인한 뒤 판단합니다. 과거 감사 범위 원문: [LogHistory H03c](LogHistory.md#h03c).

## 1.4 형식

형식은 개정 전 규정을 그대로 유지한다. **이 형식이 이미 서버 전송의 기반이기 때문이다.**

### 로그 라인

```
[HH:MM:SS.ms] [LEVEL] [System/Class] 메시지 | key=value, key=value
```

예시:
```
[10:53:23.124] [INFO] [Network/NetworkUnit] OnNetworkDespawn | IsServer=False, UnitType=Pistoleer
[10:53:23.125] [WARN] [Network/NetworkUnit] 예상치 못한 상태 감지 | IsServer=False, Reason=AlreadyDespawned
[10:53:23.126] [ERROR] [Network/NetworkUnit] Despawn 실패 | IsServer=False, Reason=ObjectNotFound
```

### `key=value`가 곧 전송 데이터다

`| key=value, key=value` 부분은 사람이 읽으라고 붙인 꼬리표가 아니다.
**운영 로그를 서버로 보낼 때 그대로 구조화 필드가 되는 부분**이다.

| 로그 라인의 조각 | 서버 전송 시 역할 |
|-----------------|------------------|
| `[LEVEL]` | 심각도 필드 |
| `[System/Class]` | 발생 지점 필드 |
| 메시지 | 사람이 읽을 설명 (집계 키로 쓰지 않는다) |
| `key=value` | **집계·필터링용 구조화 필드** |
| 이벤트 키 (1.5) | **집계의 기본 단위** |

그래서 `key=value`를 쓸 때 지켜야 할 것:

- **값은 집계 가능한 형태로 쓴다.** `Reason=ObjectNotFound` (○) / `Reason=이상하게도 오브젝트가 없었음` (✗)
- **키 이름을 그때그때 바꾸지 않는다.** `UnitType=` 과 `unitType=` 이 섞이면 집계가 조용히 둘로 갈라진다
- **같은 키의 값 표기도 파일마다 바꾸지 않는다 (2026-08-17 추가).** 위 항목은 **키** 이름에 관한 것이고, 이것은 **값** 쪽이다.
  갈라지는 방식과 결과가 같으므로 함께 지킨다 — 같은 키에 `Host` 와 `host` 가 섞이면 **한 지표가 조용히 둘로 갈라진다.**
- **자유 문장은 메시지 쪽에 넣는다.** `key=value`에는 넣지 않는다
- **값 안에 구분자 `, ` 를 넣지 않는다 (2026-08-18 추가).** 이 형식은 `key=value` 쌍을 `, ` 로 잇는다.
  값에 같은 문자열이 들어가면 **파싱이 그 자리에서 쪼개져 필드 하나가 둘로 보인다.**
  특히 `string.Join(", ", ...)` 결과를 그대로 값에 넣는 실수가 나기 쉽다 —
  목록을 담아야 하면 **다른 구분자(`|` 등)를 쓰거나 개수만 남긴다**(`Count=3`).

값 표기가 갈렸던 날짜별 사례는 [LogHistory H04a](LogHistory.md#h04a)에 보존합니다. 원본 로그는 소급 수정하지 않습니다.

### 카테고리 규칙

`[System/Class]` 형식으로 작성한다.

- **System**: 기능별 기존 영역에서 먼저 고릅니다. 예: `Network` · `Auth` · `Bootstrap` · `UI` · `Cloud` · `Factory` · `Audio` · `Input` · `HexGrid` · 전투용 `Combat`.
  **닫힌 집합이 아니며**, 기존 영역에 담기지 않을 때만 새 값을 추가합니다. 같은 기능에 다른 이름을 만들면 집계가 갈라집니다. 당시 사용 개수/예약 상태: [LogHistory H04b](LogHistory.md#h04b).
- **Class**: 정확히 어느 클래스에서 출력하는지 (예: `NetworkUnit`, `UnitView`, `ProductionPanelUI`)
- **System 은 그 로그가 다루는 「기능」으로 정한다. 파일이 놓인 폴더로 정하지 않는다 (2026-08-18 추가).**
  아래 예시 셋이 **전부 `Presentation/` 하위 클래스인데 System 이 셋으로 갈리는 것**이 그 뜻이다.
  즉 `Presentation/UI/LobbyUI` 의 **방 참가 실패**는 `UI` 가 아니라 **`Network`** 다 — 그래야
  매칭 실패를 추적할 때 `System=Network` 필터 하나로 그 사건이 전부 잡힌다.

예시:
```
[Combat/UnitView]        Presentation/Unit/  → Combat
[HexGrid/HexTileView]    Presentation/Grid/  → HexGrid
[UI/ProductionPanelUI]   Presentation/UI/    → UI
[Network/NetworkUnit]    Infrastructure/Network/ → Network
```

폴더 기준 분류를 되돌린 당시 경위는 [LogHistory H04c](LogHistory.md#h04c)에 보존합니다. 위 기능 기준 규범과 예시를 함께 적용합니다.

### 파일 헤더

파일 최상단에 **필수 2줄 + 선택 줄**을 작성하고, **빈 줄로 본문과 구분**한다.

| 줄 | 필수 여부 | 형식 |
|----|----------|------|
| 1줄째 | **필수** | `=== [작업명 또는 로그 목적] ===` |
| 2줄째 | **필수** | `=== [시각의 종류]: YYYY-MM-DD HH:MM:SS ===` |
| 3줄째 이후 | 선택 | `=== [출처 항목]: [값] ===` — 그 파일에만 존재하는 출처 정보 |
| 그다음 | **필수** | 빈 줄 (헤더 끝 표시) |

에디터 파일 예시 (2줄):
```
=== 유닛 사망 NGO 버그 픽스 검증 로그 ===
=== 세션 시작: 2026-06-08 10:52:40 ===

[10:53:23.124] [INFO] [Network/NetworkUnit] ...
```

실기기 파일 예시 (3줄 — 기기 정보 추가):
```
=== Android Logcat 캡처 ===
=== 저장 시각: 2026-08-13 14:07:11 ===
=== 대상 기기: SM_G981N (R3CN90ABCD) ===

08-13 14:06:52.310  8421  8455 I Unity   : ...
```

> **왜 줄 수를 고정하지 않는가 (2026-08-13 개정)**
> 개정 전 규칙은 헤더를 **정확히 2줄**로 못박았고, 실기기 캡처 도구는 `=== 대상 기기: ... ===` 를 붙여 3줄을 쓴다.
> 도구를 2줄로 깎지 않고 규칙을 넓힌 이유는 셋이다.
> ① **기기 정보는 에디터 로그에 대응물이 없다.** 3줄로 고정하면 에디터 파일에 의미 없는 빈 필드를 강요하게 되고, 의미 없는 필드는 곧 안 쓰이면서 규칙 전체를 무너뜨린다.
> ② **그 줄을 지우면 안전장치가 무효가 된다.** 캡처 도구는 기기가 여러 대일 때 사용자에게 대상을 직접 고르게 만들어 두었는데, 고른 결과를 파일에 남기지 않으면 그 확인 절차가 파일 단계에서 사라진다. 기기 여러 대 환경에서 "어느 기기의 로그인지 모르는 파일"은 형식만 멀쩡한 최악의 자료다.
> ③ **줄 수를 고정할 이유가 애초에 없었다.** 헤더는 `=== 키: 값 ===` 줄의 목록이고 본문은 `[` 로 시작한다. 헤더 끝은 **빈 줄**로 구분되므로, 줄 수를 세지 않아도 경계가 모호해지지 않는다.
> → 결론: **코드 수정 없음.** 현행 캡처 도구의 3줄 헤더는 이 규칙에 그대로 부합한다.

## 1.5 이벤트 키 — `LogEvent`

**운영 로그는 반드시 이벤트 키를 함께 남긴다.**

| 항목 | 규정 |
|------|------|
| 정의 방식 | **`enum LogEvent`**. 임의 문자열·문자열 상수 금지 |
| 전송 키 | enum 멤버 이름을 **그대로**(PascalCase) 쓴다. 변환 규칙(스네이크케이스화 등)을 두지 않는다 |
| 적용 범위 | **`운영` 로그만** 키를 받는다. `개발`·`임시`는 전송 대상이 아니므로 불필요하다 |

### 왜 enum인가

문자열 상수나 리터럴을 쓰면 **키가 조금씩 달라지면서 집계가 조용히 갈라진다.**
`"MatchmakingFailed"` 와 `"matchmaking_failed"` 와 `"MatchmakingFail"` 이 서로 다른 세 지표가 되고,
어느 쪽도 실제 발생 횟수를 나타내지 못한다. 게다가 이 오류는 **컴파일러가 잡아 주지 않는다.**
enum이면 오타는 컴파일 에러고, 이름을 바꾸면 IDE가 전부 따라 바꾼다.

### 왜 이름을 그대로 쓰는가

변환 규칙을 하나 두면, 그 규칙을 **양쪽(클라이언트 전송 코드 / 서버 집계 코드)이 똑같이 구현해야** 한다.
한쪽만 바뀌는 순간 지표가 통째로 사라지고, 사라진 사실조차 눈에 안 띈다.
이름을 그대로 쓰면 맞출 것 자체가 없다.

### 이름 짓기

- **무엇이 일어났는지**를 적는다. 어디서 일어났는지는 `[System/Class]`가 이미 담고 있다
- 이름은 **한 번 정하면 바꾸지 않는다.** 이름이 바뀌면 서버에 쌓인 과거 지표와 연결이 끊긴다
- 예: `MatchmakingLobbyJoinFailed`, `ServerRejectedUpgradeInsufficientGold`, `CloudSaveValueParseFailed`, `UnhandledException`

> 전역 훅은 Exception을 `UnhandledException`, Error를 `UnhandledEngineError`로 구별합니다(1.9).
> **`UnhandledException` 에 섞지 않고 나눈 이유**는 1.5 의 신설 기준 두 개를 **둘 다** 충족하기 때문이다.
> ① **집계가 섞이면 안 된다** — `UnhandledException` 은 *"try-catch 없이 터진 예외"* 다. 엔진의 `Debug.LogError` 는 **예외가 아니라** 스택이 풀리지도 흐름이 끊기지도 않는다. 한 키로 묶으면 **크래시 건수 지표가 크래시 아닌 사건으로 부풀어** 출시 판단에 못 쓴다.
> ② **조치가 다르다** — 미처리 예외는 **그 자리에 `try-catch` 를 두거나 원인 코드를 고치는** 일이고, 엔진 Error 는 대개 **우리가 SDK 를 잘못된 상태·순서로 호출한 것**이라 **호출 시점 가드 추가**가 조치다.
> `key=value` 는 기존 `Source=UnityLogHook` 을 그대로 쓰고 **`LogType=` 필드는 두지 않는다** — 키가 이미 둘을 가르고 있어 잉여 필드다.


키 개수·신설 이력: [LogHistory H05](LogHistory.md#h05). 2026-09 맵 준비·투영 키 4종 · 맵 전송 키 5종 신설과 `Round=` 필드 신설 블록: [LogHistory H14b](LogHistory.md#h14b).

## 1.6 민감 데이터

**로그 파일은 개발자 간 공유되고, 채팅에 인용되며 Release에 보관된다.** 기존 리포지토리 로그도 있어 유출 경로가 여럿이다.

| 데이터 | 규정 | 이유 |
|--------|------|------|
| **이메일** | **넣지 않는다. 부분 마스킹도 금지** | 부분 마스킹(`a***@gmail.com`)은 재식별이 너무 쉽다. 도메인 + 첫 글자 + 길이만으로 특정되는 경우가 흔하다 |
| **UID · PlayerId** | **해시로 치환해서 넣는다** | 완전히 지우지 않는 이유가 있다 — 아래 참조 |
| 인증 토큰 · 세션 키 · 비밀번호 | **어떤 형태로도 금지** | 그대로 계정 탈취 수단이 된다 |

### UID를 지우지 않고 해시로 바꾸는 이유

라이브 운영에서 답해야 하는 질문은 "누가 겪었나"가 아니라 이것들이다.

- **몇 명이 겪었나?** (한 사람이 100번 겪은 것과 100명이 한 번씩 겪은 것은 완전히 다른 문제다)
- **같은 사용자가 반복해서 겪나?** (일시적 오류인지, 특정 계정이 망가진 상태인지)

이 질문에 답하려면 **안정적인 익명 식별자**가 필요하다. 통째로 지우면 두 질문 모두 답할 수 없다.
해시는 "같은 사람인지"는 알려 주되 "누구인지"는 알려 주지 않는다 — 정확히 필요한 만큼만 남긴다.

### 2단 방어 — 규율만으로는 반드시 샌다

| 단계 | 책임 | 내용 |
|------|------|------|
| 1단 | **호출부** | 마스킹 헬퍼를 거쳐서 값을 넣는다 (`HashId(uid)` 등) |
| 2단 | **facade (`GameLog`)** | 최종 조립된 문자열에서 **이메일 패턴을 감지해 차단**한다 |

1단만 두면 언젠가 누군가 헬퍼를 빠뜨린다. 사람이 매번 기억해야 하는 규칙은 결국 깨진다.
2단은 그 실수를 마지막 지점에서 잡는 그물이다.

### 에디터 포함 항상 적용

**에디터에서도 똑같이 마스킹한다.** 경로를 갈라 에디터에서만 원본을 보이게 하면
"에디터에선 보였는데 빌드에선 안 보인다" 는 혼란이 생기고, 그 혼란을 없애려고
누군가 마스킹을 임시로 끄는 순간 방어가 무너진다.

## 1.7 릴리스 스트리핑

`개발` 로그를 출력하는 메서드에는 **두 개의 `[Conditional]` 특성을 모두** 붙인다.

```
[Conditional("UNITY_EDITOR")]
[Conditional("DEVELOPMENT_BUILD")]
```

| 항목 | 규정 |
|------|------|
| 적용 대상 | **`개발` 로그 메서드** |
| 적용 금지 | **`운영` 로그 메서드에는 붙이지 않는다** (릴리스에서 살아야 하므로) |

### 왜 둘 다 붙이는가

여러 개의 `[Conditional]`은 **OR**로 동작한다. 즉 "에디터 **또는** 개발 빌드에서 살아 있고, 그 외에는 사라진다".
한쪽만 붙이면 구멍이 생긴다.

| 붙인 것 | 생기는 구멍 |
|---------|-----------|
| `UNITY_EDITOR`만 | **실기기 테스트에서 로그가 사라진다.** 개발 빌드로 기기에 올려도 아무것도 안 나온다 |
| `DEVELOPMENT_BUILD`만 | **에디터에서 로그가 안 보인다.** 이 심볼은 에디터에 정의되어 있지 않다 |

### 런타임 분기와 다르다

`if (Debug.isDebugBuild)` 로 감싸는 것과 같지 않다.

- **런타임 분기**: 호출은 남아 있고, **인자는 이미 평가된 뒤** 조건을 검사한다.
  → 문자열 보간(`$"unit={id}, hp={hp}"`)이 릴리스에서도 매 호출마다 실행되어 문자열이 새로 만들어진다.
- **`[Conditional]`**: 컴파일러가 **호출 자체와 인자 평가까지 통째로 제거**한다.
  → 문자열 보간 비용이 **0**이 된다.

프레임마다 도는 코드에 개발 로그를 넣을 수 있는 것은 이 차이 때문이다.

### ⚠️ 람다에 넣으면 스트리핑이 무효가 된다 (2026-08-18 추가)

C# 컴파일러가 `[Conditional]` 로 지우는 것은 **문(statement) 자리의 호출**뿐이다.
**식(expression) 자리의 호출은 지우지 않는다.**

| 형태 | 릴리스에서 |
|---|---|
| `GameLog.Dev.Info(...);` (문) | **사라진다** ✅ |
| `() => GameLog.Dev.Info(...)` (**식 본문 람다**) | **살아남는다** ❌ |
| `() => { GameLog.Dev.Info(...); }` (**블록 본문 람다**) | **사라진다** ✅ |

식 본문 람다는 그 호출이 **람다의 반환식**이라 문이 아니고, 컴파일러가 지울 수 없다.
→ **콜백·이벤트 핸들러에 `Dev` 로그를 넣을 때는 반드시 블록 본문(`{ }`)으로 쓴다.**
겉보기 차이가 중괄호 두 개뿐이라 리뷰에서 놓치기 쉽고, **증상은 릴리스 빌드에서만 나타난다.**

## 1.8 sink 구조

로그를 "어디에 쓸 것인가"는 로그를 "남긴다"는 행위와 분리한다.

| 항목 | 규정 |
|------|------|
| 인터페이스 | `ILogSink` |
| 전달 방식 | `GameLog`가 **등록된 sink에 순서대로** 전달 |
| 등록 방식 | **정적 등록** — `GameLog.AddSink(...)` |
| 등록 주체 | **`LogSessionOwner`**(`Infrastructure/Debug/`) — sink 를 만들어 등록하는 곳은 **앱 전체에서 이 정적 클래스 하나뿐**이다. 부트스트래퍼(`LoginBootstrapper` / `GameBootstrapper`)는 `Awake` 첫 줄에서 **진입점 `EnsureInitialized()` 를 호출할 뿐**이며, 두 번째 호출부터는 아무 일도 하지 않는다(멱등) |

**조합 루트와 단일 소유권:** LogSessionOwner는 만든 sink를 자기 안에 보유하고 외부에 의존성을 주입하지 않습니다. Bootstrap 레이어만 진입점을 호출하며, 숨은 RuntimeInitializeOnLoadMethod 초기화를 두지 않습니다. 상태는 static 한 곳에 모아 씬을 건너 유지합니다. Login/Game bootstrap이 열고, UnityEngine.Application.quitting에서 한 번 닫습니다. 씬 OnDestroy로 앞 씬의 스트림을 닫지 않습니다.

주체 변경·과거 누락 로그 수는 [LogHistory H06](LogHistory.md#h06)에 보존합니다.

### sink가 하나도 없으면 콘솔로 폴백한다

등록 전에 발생한 로그를 버리면 안 된다.
**초기화 순서 문제로 로그가 사라지면, 그 사실 자체를 추적할 수단이 없기 때문이다.**
"로그가 안 나온다"의 원인이 "로그 시스템이 아직 안 켜졌다"인 경우, 로그로는 절대 알 수 없다.
sink 목록이 비어 있으면 **콘솔로 출력**한다.

### sink 하나가 실패해도 다음 sink는 계속 진행한다

각 sink 호출을 **개별적으로 `try-catch`로 감싼다.**

- 파일 sink가 디스크 권한 문제로 던져도, 콘솔 sink는 정상 출력되어야 한다
- **로그 때문에 게임이 멈추면 본말전도다.** 로그는 게임을 돕는 도구지 게임의 일부가 아니다

## 1.9 예외 · 엔진 오류 처리

절 제목 변경 이력은 [LogHistory H07a](LogHistory.md#h07a)에 보존합니다.

### `Exception` 오버로드를 둔다

`GameLog`는 `Exception`을 인자로 받는 **오버로드를 제공**한다.
예외를 `e.Message` 문자열로 눌러 담지 않는다 — **예외 타입이 텔레메트리 집계의 핵심 축**이기 때문이다.
`TimeoutException` 300건과 `NullReferenceException` 300건은 완전히 다른 사건이고,
메시지 문자열만 남기면 그 구분이 사라진다.

### `ConsoleSink`는 `Debug.LogException`으로 내보낸다

**`Debug.LogError(e.ToString())`을 쓰지 않는다.**
크래시 리포터가 그것을 **예외로 인식하지 못해 스택 심볼화(symbolication)가 되지 않는다.**
난독화·최적화된 릴리스 빌드에서 심볼화가 안 된 스택은 사실상 읽을 수 없는 주소 나열이다.

### 전역 훅 수집 — ~~미처리 예외~~ **미처리 예외 + 엔진 오류**

`Application.logMessageReceived` 훅을 걸어, **계측하지 않은 곳에서 터진 예외까지** 수집한다.
아무리 규율을 지켜도 `try-catch`를 두지 않은 자리는 남고, 실제 크래시는 대개 그런 자리에서 난다.

### 수집 범위 — Exception + Error
>
> **Exception 또는 Error를 수집**합니다. Info/Warning 및 Assert는 제외합니다.
>
> **`LogType.Assert` 는 제외한다** — `UNITY_ASSERTIONS`(에디터·개발 빌드) 에서만 살아 있어 **릴리스에서 발화 자체가 불가능**하다. 즉 운영 지표에 기여할 수 있는 양이 **원리적으로 0**이다. 나중에 `Debug.Assert` 를 실제로 쓰기 시작하면 이 판정을 다시 연다.
>
> 키는 `type` 으로 갈린다 — `Exception` → `UnhandledException` / `Error` → **`UnhandledEngineError`**(구별 근거는 **1.5**).
>
> ### 되먹임 방어 — 4겹
>
> | 겹 | 내용 | 무엇을 막는가 |
> |:-:|---|---|
> | ① | `type` 이 `Exception` \|\| `Error` 가 아니면 반환 (`Assert` 제외) | Info/Warning 이 훅을 통과하는 것 — 되먹임 표면 축소 |
> | **②** | **`RuntimeLogger.IsEmittingToConsole` 이면 반환** | `GameLog` 경유 + **`RuntimeLogger` 직접 호출** 양쪽의 **자기 출력** |
> | ③ | `GameLog.IsEmitting` 이면 반환 | `ConsoleSink` · sink 0개 폴백 포함 `GameLog` 전 경로 |
> | ④ | 직전과 동일한 `condition` + `stackTrace` 면 반환 | 훅 전달이 비동기일 경우의 1회 메아리 |
>
> ### 방어 ②를 유지해야 하는 이유
>
> - **되먹임 경로는 실재한다:** `GameLog.Ops.Error` → `FileSink` → `RuntimeLogger` → `Debug.LogError` → 훅.
> - Error 수집도 허용하므로 타입 필터만으로 자기 출력 고리를 막을 수 없습니다. 방어 ②·③을 함께 유지합니다.
> - **⚠️ 방어 ④는 우리 출력에 대해 애초에 작동한 적이 없다.** `RuntimeLogger` 가 만드는 줄은 **`[HH:mm:ss.fff]` 밀리초 타임스탬프로 시작**해 두 줄이 같아질 수 없기 때문이다. **④에 의존하지 말 것.** ④가 실제로 막는 것은 「남이 낸 같은 오류의 1회 메아리」뿐이다.
> - **방어 ③에는 구멍이 있다** — **1.11** 이 명시적으로 허용하는 **`RuntimeLogger` 직접 호출**(축 B `임시` 로그) 경로는 `GameLog` 를 거치지 않아 `IsEmitting` 이 거짓이다. 무한 루프까지는 가지 않지만 **같은 사건이 2줄로 남아 1.14 금지 9 위반**이 된다. **②가 그 구멍을 덮는다.**
> - **플래그는 반드시 `try` / `finally` 로 내린다.** 걸린 채 남으면 **이후 모든 엔진 오류를 영구히 놓친다.** `GameLog.Emit` 의 `finally` 와 같은 이유다.
>
> ### 스팸 억제 — `condition` 단위 1초 스로틀
>
> 엔진 오류는 `Update` 안에서 나면 **매 프레임 반복**되고, 수집된 줄은 `AutoFlush` 로 그때마다 디스크에 쓰인다. 방어 ④는 직전 1건만 비교하므로 A→B→A→B 교대를 못 막는다.
>
> | 항목 | 방침 |
> |---|---|
> | 판정 키 | **`condition` 문자열**(스택 제외) |
> | 통과 규칙 | 같은 `condition` 은 **1초에 1건**만 통과 |
> | 시계 | **`Stopwatch`**(단조 증가) — 시스템 시각 변경에 흔들리지 않는다 |
> | 억제분 표기 | 다음 통과 줄에 **`Suppressed=n`** 을 함께 남긴다. **처음 통과하는 줄에도 `Suppressed=0` 을 항상 붙인다** — 필드를 조건부로 빼면 같은 로그가 두 구성으로 갈려 파싱이 어려워진다(**1.4**) |
> | 자료구조 | `Dictionary` + **상한 32개.** 넘으면 통째로 비우고 다시 시작 — 상한이 없으면 매번 다른 문자열이 들어올 때 **로그 시스템 자신이 메모리 누수원**이 된다(**1.8** *"로그 때문에 게임이 멈추면 본말전도"*) |
> | 적용 범위 | **훅이 수집한 줄에만.** 우리가 직접 남기는 로그는 **1.14 금지 8** 이 이미 규율한다 |
>
> **⚠️ `Suppressed=` 는 실제 발생 횟수의 「하한」이다.** 방어 ④가 먼저 버린 줄은 스로틀에 도달하지 않으므로 카운트에 잡히지 않는다. **정확한 발생 횟수로 읽거나 과대 표기하지 말 것**(CLAUDE.md 규칙 10).
>
> **1.14 금지 8 과의 관계:** 금지 8은 *"우리가 로그를 **작성**할 때"* 의 규칙이라 남의 출력을 **수집**하는 이 자리는 문자 그대로의 대상이 아니다. 그러나 결과(*"스팸은 정작 필요한 줄을 묻어 버린다"*)가 동일하므로 **취지를 수집 자리에도 적용한 것**이다.

확대 당시 변경·미검증 원문: [LogHistory H07b](LogHistory.md#h07b). 과거 오류 0건을 hook 자연 실행 성공으로 읽지 않습니다.

훅 등록·해제 및 중복 방지 상태의 소유자는 LogSessionOwner입니다. sink와 동일한 세션 범위를 가져야 로그인·로비의 예외 수집이 누락되지 않습니다. 로그 클래스 이름은 `[Runtime/LogSessionOwner]`를 사용하며 과거 `[Runtime/GameBootstrapper]` 기록과 검색 범위를 구별합니다. 소유자 이동 원문: [LogHistory H07c](LogHistory.md#h07c).

> ⚠️ **재진입 가드 필수**
> sink가 `Debug.Log`를 호출하고, 그 호출이 다시 `logMessageReceived` 훅으로 들어오면
> **무한 루프로 앱이 죽는다.** 훅 처리 중임을 나타내는 플래그를 두고, 처리 중 재진입은 즉시 반환한다.
> 이 가드가 없으면 로그 시스템이 크래시의 **원인**이 된다.

## 1.10 파일 기록 — 에디터 상시 활성

### 에디터에서는 파일 기록을 항상 켠다

**세션을 수동으로 열고 닫지 않는다.** 플레이 모드에 들어가면 파일이 자동으로 쌓인다.

상시 기록은 세션 배선 누락·소유권 충돌을 막기 위한 계약입니다. Login→Lobby→Game은 한 세션으로 이어집니다. **Lobby.unity 직접 진입은 사용자 결정으로 커버하지 않는 범위**이며 자동 활성화나 씬 배선을 추가하지 않습니다. 당시 검증 수치: [LogHistory H08a](LogHistory.md#h08a).

### `FileSink`는 기존 `RuntimeLogger`를 재사용한다

파일 기록 구현을 **둘로 두지 않는다.** 이미 검증된 파일 쓰기 코드(append + AutoFlush, 예외 시 게임 중단 없음)가 있는데
새로 만들면 두 구현이 서로 다르게 동작하기 시작하고, 어느 쪽이 진짜인지 알 수 없게 된다.

### 파일 누적 관리 방침

| 항목 | 방침 |
|------|------|
| **경로** | `Assets/_Project/Docs/_Logs/_editor/{yyyy-MM-dd}/RuntimeLog.txt` — **파일명에 역할(host/client)을 넣지 않는다** (아래) |
| **누적 단위** | **일 단위 이어쓰기.** 하루에 파일 1개 |
| **실행 구분** | 파일을 나누지 않고, 플레이 모드 진입 시 **헤더를 다시 기록**해 구분선으로 삼는다 |
| **공유** | 선택 raw 테스트 로그는 월별 Release의 독립 ZIP으로 검증·보관한다 (아래) |
| **`.gitignore`** | raw만 좁은 경로로 분리하는 정책; 전체 `_Logs/` 제외 금지. 실제 pattern 적용은 별도 승인 (아래) |
| **정리** | **자동 삭제하지 않는다.** 사용자가 원할 때만 수동 메뉴로 지운다 (아래) |

**근거:**

- **왜 역할별 파일이 아닌가** — FileSink는 UNITY_EDITOR 경로이므로 파일 작성 프로세스는 에디터입니다. 역할은 파일명이 아닌 로그의 `Role=Host` / `Role=Client`로 기록합니다. 날짜별 변경 원문: [LogHistory H08b](LogHistory.md#h08b).
- **왜 `_editor/` 라는 별도 하위 트리인가** — 기존 `_Logs/YYYY-MM-DD/HH_MM_[작업명]/` 은 작업에 귀속된 **영구 보존물**이고,
  상시 로그는 **언제 버려도 되는 소모품**이다. 성격이 정반대인 둘이 같은 폴더에 섞이면
  "지워도 되는 파일"과 "지우면 안 되는 파일"을 구분할 수 없게 된다.
- **왜 실행 단위가 아니라 일 단위인가** — 플레이 모드 진입/종료는 하루에 수십 번 일어난다.
  실행마다 파일을 만들면 하루에 파일이 수십 개 생기고, "어느 파일이 그 재현이었나"를 다시 찾아야 한다.
  **상시 활성으로 없애려던 왕복이 형태만 바꿔 돌아오는 셈이다.**
  날짜는 사용자가 "어제 그거"처럼 말할 때 그대로 쓰는 좌표이고, `_Tasks`/`_Logs` 폴더 규칙도 이미 날짜를 1차 축으로 쓰고 있다.

### 원시 테스트 로그 공유·보관

원시 테스트 로그는 **로그 전용 private 저장소 `rmsepskek02/Hexiege-Logs`의 월별 Release ZIP**에 보관합니다. 저장 위치는 `https://github.com/rmsepskek02/Hexiege-Logs`이며 소스 저장소의 공개 Release에는 전송하지 않습니다. 이전 직접 커밋·ignore 금지 정책 원문은 [LogHistory H13](LogHistory.md#h13)에 보존합니다. 보관 절차의 정의와 실제 ZIP·Git·업로드·삭제 실행 권한은 구분하며, 실행에는 해당 범위의 사용자 승인이 필요합니다.

- **매 업로드 직전** 인증된 대상 확인으로 정확한 owner/repo와 `private=true`를 확인합니다. 확인 실패·불명확·public 또는 익명 공개 접근 가능한 대상으로 판명되면 ZIP/manifest 전송을 중단합니다. 인증 성공이나 이전 private 확인을 새 업로드의 private 검증으로 대신하지 않습니다. 다른 public 저장소로 fallback하지 않습니다.
- 로그 저장소를 **별도 clone할 필요는 없습니다**. 권한 있는 Release 업로드·다운로드로 보관하며, 소스 Git에는 코드·assets·Log.md·Task·doc/meta 근거를 유지합니다. 인증값·시크릿·인증 header/command line을 문서·로그·manifest에 출력하거나 저장하지 않습니다.

- 월별 Release 제목은 **`로그 보관 YYYY-MM`**입니다. 새 테스트 ZIP은 **`YYYY-MM-DD_HH_MM_작업명_회차.zip`**으로 구별합니다.
- 기존 로그 일회성 보관은 **`YYYY-MM-DD_기존로그.zip`**입니다. 크기 때문에 나눌 필요가 있을 때만 `_part01`, `_part02` suffix를 붙이며 각 파일은 **독립적으로 해제 가능한 ZIP**입니다. 분할 스트림이 아닙니다.
- **플랫폼 파일명 정규화 예외:** 로컬 원래 이름과 한글 Release label은 유지합니다. 플랫폼이 한글을 제거하는 경우 의미를 보존하는 remote ASCII 이름으로 대응시키고(예: `기존로그` ↔ `legacy-logs`), 영수증에 로컬 원래 이름·실제 remote 이름·label·asset ID·안정적인 위치/URL mapping을 기록합니다. 새 작업명·날짜·회차 의미를 잃지 않으며 ZIP/manifest의 **bytes·SHA256은 이름 변경 전후 불변**이어야 합니다. 인증이 포함된 임시 다운로드 URL은 기록하지 않습니다. 이름 대응은 보관 내용 변경이나 다른 저장 정책을 허용하지 않습니다.
  기존 로그의 대응 예는 로컬 `YYYY-MM-DD_기존로그.zip` → remote `YYYY-MM-DD_legacy-logs.zip`, 대응 remote manifest `YYYY-MM-DD_legacy-logs.manifest.json`입니다. ZIP label은 원래 한글 파일명을 유지하고 실제 날짜를 포함한 구체 이름·검증 영수증은 해당 Task에 기록합니다.
- 내부 경로는 원래 repository-relative 경로를 보존합니다. 선택한 Editor daily는 캡처 시점의 snapshot임을 기록하며 append 중인 원본의 기록 시점·크기·hash를 구분합니다. 포맷/내용을 재작성하지 않습니다.
- 새 회차는 기존 보관 manifest의 경로·hash와 대조해 이미 보관한 동일 로그를 반복 포함하지 않습니다. 동일 경로의 새 내용은 snapshot 시각/hash로 구별합니다.
- manifest에는 선택 원본 경로, 파일 수·크기·개별 SHA256, ZIP 크기·SHA256, Release/다운로드 위치, 세션·역할(확인된 경우), **빌드 상태와 미확정 경계**를 기록합니다. 빌드 시작을 완료로, 과거 PASS를 새 실행으로 승격하지 않습니다.
- 업로드 완료 응답만으로 보관 성공을 판정하지 않습니다. 지정 private 저장소에서 **ZIP과 manifest를 실제 다운로드**하고 각 크기·SHA256, ZIP 전체 entry의 상대경로·개수·크기·개별 SHA256을 manifest와 대조한 뒤 보관 확인을 기록합니다. 누락·추가·충돌 또는 검증 미완료 시 추적 해제하지 않습니다. 로컬 정리는 그 뒤에도 **대상별 사용자 승인**이 필요합니다.
- 로컬·remote archive를 자동/주기 삭제하지 않습니다. 선택하지 않은 소모품 Editor 로그의 기존 사용자 수동 메뉴 계약은 그대로 유지하며, 보관 대상으로 선택된 파일을 검증/승인 없이 그 메뉴로 지우지 않습니다.
- raw 테스트 로그 공유는 검증된 private Release ZIP 방식을 사용합니다. **신규 RuntimeLog txt 본문이 소스 Git에 재추적되지 않도록** 승인된 정확 원본 경로/파일명 pattern을 적용하며 ignore를 우회해 raw를 다시 추가하지 않습니다. 기존 추적 파일은 private 업로드·전체 다운로드 검증과 별도 사용자 승인 뒤에만 좁은 원본 목록으로 추적 해제합니다. 로컬 raw 원본은 그대로 보존하고 Git 이력은 남기며 **history rewrite는 하지 않습니다**.
- **Log.md·Task·raw txt.meta 및 실제 코드/asset/doc/folder metadata는 소스 Git에 유지**합니다. `CrossAuditResult.txt`처럼 RuntimeLog가 아닌 결과 txt도 유지합니다. `_Logs/` 전체 또는 전체 txt ignore 금지입니다. raw txt 본문만 좁게 분리하는 pattern을 적용하며, 적용 전 확정 경로 검토와 사용자 승인을 받습니다. 로그 문서/meta를 광범위한 제외 패턴에 함께 넣거나 orphan 이름만으로 삭제하지 않습니다.

도구: `Assets/Editor/Tools/LogArchiveZip.cs`. 사양은 2026-10-20 사용자 승인. **구현·메뉴 실행 확인 상태: 확인 전 (2026-10-20)** — 현재 상태는 [Task Plan](_Tasks/2026-10-20/12_02_log-archive-zip-tool/Plan.md) §8을 따르며, 아래 사용법은 동작 확인을 뜻하지 않습니다. 이 도구는 ZIP과 manifest를 **만들기만** 하고 업로드는 사용자가 합니다(클라우드 세션은 사용자 PC 파일에 접근할 수 없고, 공개 소스 저장소를 거치면 로그가 Git 이력에 영구 공개되기 때문).

3. `Assets/_Project/Docs/_Logs/_zip/YYYY-MM-DD/`에 `YYYY-MM-DD_HH_MM_<작업명>_<NN>.zip`과 같은 이름의 `.manifest.json`이 생깁니다(`NN`은 같은 날짜+작업명 기준 회차). ZIP 내부는 저장소 상대 경로이고 manifest에는 위 manifest 항목과 업로드 예정 Release, 「업로드는 사용자 수행」 표기가 들어갑니다. 빌드 상태는 `not inferred`입니다.

5. 사용자가 ZIP과 manifest를 **둘 다** 월별 Release(제목 `로그 보관 YYYY-MM`, tag `logs-YYYY-MM`)에 올립니다. 업로드 직전 private 확인(위 첫 항목)은 업로드하는 사용자에게 그대로 적용됩니다. 그 달 Release가 아직 없으면 같은 제목·tag로 만듭니다.

### 자동 삭제하지 않는다

개정 전 방식(폐기): ~~"날짜 폴더 단위로 보존 기간(기본 7일) 초과분을 자동 삭제한다"~~

보존 기간 기반 자동 삭제를 **철회한다.** 근거는 둘이다.

- **커밋한 파일을 자동으로 지우면 `git status`에 삭제로 잡힌다.** 공유하려고 커밋해 둔 파일이
  며칠 뒤 도구에 의해 조용히 사라지면, 사용자는 자기가 지우지 않은 삭제 목록을 마주하게 된다.
  되돌릴지 말지를 매번 판단해야 하는 상태가 되어 오히려 손이 더 간다.
- **이 프로젝트에는 자동 삭제로 사고를 겪은 이력이 있다.** `CLAUDE.md` 규칙 5(git — 읽기만 허용, 변경은 사용자 지시가 있을 때만)는
  2026-03-03에 `git restore` 를 무단 실행해 커밋되지 않은 작업 전체가 복구 불가로 소실된 사건에서 나왔다.
  **되돌릴 수 없는 삭제를 사용자 확인 없이 수행하지 않는다**는 원칙이 이 프로젝트에는 이미 서 있다.

과거 소용량 사례는 [LogHistory H08c](LogHistory.md#h08c)에 보존합니다. 당시 크기로 현재 저장 부담이나 삭제 필요성을 단정하지 않습니다.

## 1.11 `RuntimeLogger`의 위치

`RuntimeLogger`는 **없애지 않는다.** 두 가지 역할을 겸한다.

| 역할 | 내용 |
|------|------|
| `FileSink`의 파일 쓰기 구현체 | 1.10 참조 — 파일 기록 구현을 둘로 두지 않기 위해 |
| **축 B의 `임시` 계층** | 특정 버그 추적용으로 **직접 호출**하는 현행 방식이 그대로 유효하다 |

`임시` 로그는 `GameLog`를 거치지 않아도 된다. 이벤트 키도, 스트리핑 특성도 필요 없다.
**작업이 끝나면 코드째로 사라질 것**이기 때문이다. 사라질 코드에 규격을 씌우는 것은 비용만 늘린다.

단, `임시` 로그에도 **민감 데이터 규정(1.6)은 그대로 적용된다.** 선택된 원시 증거는 1.10의 검증된 Release 보관 대상으로 남으며, 업로드 검증과 별도 로컬 정리 승인은 구분한다.

> **⚠️ 이 「직접 호출」 경로가 전역 훅의 방어 ③을 우회한다 (2026-08-19 · 커밋 `cc864054`)**
> `GameLog` 를 거치지 않으므로 `GameLog.IsEmitting` 이 거짓이다. **1.9** 의 방어 **②(`RuntimeLogger.IsEmittingToConsole`)** 가 정확히 이 구멍을 막으려고 신설되었다.
> **호출하는 쪽이 할 일은 없다** — 플래그는 `RuntimeLogger` 안에서 세우고 내린다. 다만 **`RuntimeLogger` 의 콘솔 출력부를 손대는 사람은 그 플래그를 지우면 안 된다.**

현행 직접 세션 API는 **`BeginSession(string folderPath, string purpose)`**입니다. 목적은 그때의 작업명을 전달하고 비어 있으면 기본 문구로 헤더 형식을 방어합니다. 변경 이력: [LogHistory H09a](LogHistory.md#h09a).

### 캡처 도구 사용 절차

도구: `Assets/Editor/Tools/LogcatCapture.cs`

1. 기기를 USB로 연결한다 (USB 디버깅 ON)
2. 메뉴 **`Hexiege > Logs > Clear Device Buffer (Deletes Logs)`** 실행
3. 기기에서 **버그를 재현**한다
4. 메뉴 **`Hexiege > Logs > Save Device Logs`** 실행

`Clean Old Editor Logs (Deletes Assets)`는 1.10의 Editor 수동 정리용이며 실기기 캡처 절차에 포함하지 않습니다. 버퍼 비우기·저장 메뉴와 구분선으로 분리합니다. 이력: [LogHistory H09b](LogHistory.md#h09b).

> **왜 먼저 버퍼를 비우는가**: Logcat은 링 버퍼라 과거 로그가 계속 쌓여 있다.
> 비우지 않으면 예전 로그가 섞여 들어와 **어디부터가 이번 재현인지 알 수 없다.**

| 항목 | 값 |
|------|-----|
| 저장 경로 | `Assets/_Project/Docs/_Logs/{yyyy-MM-dd}/{HH_mm}_logcat/RuntimeLog_device.txt` |
| 덮어쓰기 | 하지 않는다. 같은 파일이 있으면 `RuntimeLog_device_2.txt` 처럼 번호가 붙는다 |
| 헤더 | 3줄 (`캡처` / `저장 시각` / `대상 기기`) — 1.4 헤더 규칙에 부합 |
| 빈 로그 | 받아온 로그가 비어 있으면 **파일을 만들지 않는다** (빈 파일이 남으면 혼란만 생긴다) |
| 기기 여러 대 | 자동 진행하지 않는다. 목록을 보여 주고 사용자가 대상을 고른 뒤에만 진행한다 |

채팅 복사 대신 파일 전체로 전달해 분량 제한에 따른 증거 누락을 피합니다. 이전 방식 원문: [LogHistory H09c](LogHistory.md#h09c).

- 실기기 로그는 Logcat 원본 형식(`-v threadtime`)으로 저장되며, 그 안에 담긴 게임 로그 줄은 에디터 파일과 동일한 형식이다
  ```
  [HH:MM:SS.ms] [LEVEL] [System/Class] 메시지 | key=value, key=value
  ```

## 1.13 현행 코드와의 차이

날짜별 코드 상태·개수·PASS·미실행 및 변경 전 기록은 [LogHistory H10](LogHistory.md#h10)를 참조합니다. 아래는 현행 아키텍처 계약이며 날짜별 실행 결과가 아닙니다. `LogEvent` 개수 행 두 곳에 붙었던 2026-09-08 갱신 단서는 [LogHistory H14c](LogHistory.md#h14c)에 있습니다.

### `GameLog` 배치 위치 (확정)

| 파일 | 레이어 | 계약 |
|---|---|---|
| `Application/Interfaces/ILogSink.cs` | Application | 인터페이스 및 중립 enum |
| `Application/GameLog.cs` | Application | 정적 facade |
| `Infrastructure/Debug/ConsoleSink.cs` | Infrastructure | 콘솔 구현; exception 객체 보존 |
| `Infrastructure/Debug/FileSink.cs` | Infrastructure | RuntimeLogger 파일 구현 재사용 |
| `Infrastructure/Debug/LogSessionOwner.cs` | Infrastructure | sink·파일 세션·전역 hook 단일 static 소유자 |
| `LoginBootstrapper` / `GameBootstrapper` | Bootstrap | Awake 첫 줄 EnsureInitialized 진입 호출 |

**Infrastructure→Application 의존 방향을 유지하며 Application→Infrastructure 역참조는 금지합니다.** Application/NetworkContext의 정적 홀더 선례를 따릅니다. Domain의 당시 사용처 0건은 과거 측정일 뿐 새 참조 허가가 아닙니다.

- Editor는 FileSink, Build는 ConsoleSink **하나만** 등록하여 콘솔 이중 출력을 방지합니다.
- EnsureInitialized는 멱등이며 상태·sink·hook cache는 static으로 씬을 건너 유지합니다. bootstrap은 진입만 호출하고 owner는 외부 의존성을 주입하지 않습니다(1.8).
- 가장 먼저 실행된 Login/Game bootstrap이 세션을 열고 Application.quitting에서 한 번 닫습니다. **씬 OnDestroy에서 세션을 닫지 않습니다. Lobby 직접 진입은 비적용 범위**입니다.
- FileSink는 인자 없는 BeginSession으로 일별 RuntimeLog.txt를 열고 RuntimeLogger에 목적 `에디터 상시 런타임 로그`를 전달합니다. append/AutoFlush, 예외 시 게임 중단 없음, FileSink 세션 소유권 가드와 빈 목적 fallback을 유지합니다.
- Role 기록 위치는 NetworkCombatController.OnNetworkSpawn의 **NetworkContext.Set 직후, IsServer 분기 바깥**입니다. Host/Client 양쪽을 남깁니다.
- 로거 자체의 console fallback·hook 재귀 방어는 1.8/1.9의 필요 동작입니다. 과거 Assets/Editor 미적용 건수는 **규칙 예외가 아닙니다**.
- 오류가 없다는 것과 hook이 자연 실행되었다는 것은 다릅니다. 미실행, 실행했으나 대상 없음, 실제 fault 경로 성공을 구별합니다. 회차 비교는 먼저 peer/Role 구성을 맞춥니다. 과거 PASS를 새 source/native/runtime PASS로 승격하지 않습니다.

## 1.14 금지 사항

1. **진단용 raw `Debug.Log` 직접 호출 금지** — 반드시 `GameLog`(구현 전까지는 `RuntimeLogger`)를 경유한다.
   콘솔에만 남은 로그는 파일이 되지 않아 **Claude가 읽을 수 없다.**
2. **축을 하나만 정하고 로그 작성 금지** — 심각도(축 A)와 존속(축 B)을 **둘 다** 정한다 (1.2)
3. **의미 없는 메시지 작성 금지** — 예: `[INFO] [Network/NetworkUnit] 여기`
4. **이메일 출력 금지 (부분 마스킹 포함)**, **UID·PlayerId 원본 출력 금지**, **토큰·세션 키 출력 금지** (1.6)
5. **레벨 표기 생략 금지** — 모든 로그 라인에 `[INFO]` / `[WARN]` / `[ERROR]` 중 하나를 반드시 명시
6. **운영 로그에 이벤트 키 생략 금지** (1.5)
7. **운영 로그 메서드에 `[Conditional]` 부착 금지** — 릴리스에서 사라지면 안 된다 (1.7)
8. **매 틱·매 프레임 로깅 금지** — 상태 **전이** 시점에만 남긴다. 스팸은 정작 필요한 줄을 묻어 버린다
9. **같은 사건을 두 곳에서 로깅 금지** — 최종 처리 지점에서 한 번만 (분류 원칙 1)
   - **"최종 처리 지점"의 정의는 1.3 「원칙 간 우선순위」 ② 참조** — **예외 객체(`e.Message`·예외 타입·스택)를 직접 손에 쥔 `catch` 블록**이다. "사용자에게 알리고 흐름을 끝내는 상위 호출부"가 아니다.
   - 이 금지가 **원칙 3(`Error`는 항상 `운영`)과 충돌할 때는 원칙 1이 우선**한다 — 같은 절 ①·③ 참조. 원인을 가진 계층을 `운영`으로 두고, 중복되는 상위 호출부를 `개발`로 내린다.
   - **중복 판정은 실제 호출경로를 끝까지 따라 확인합니다.** 하위 호출 전 return하거나 하위 catch가 없으면 대응 원인 로그가 없으므로 중복이 아닙니다. 그런 로그를 개발로 내리면 원인을 잃습니다. 당시 사례는 [LogHistory H11](LogHistory.md#h11)에 보존합니다.
10. **`임시` 로그 코드를 남긴 채 작업 종료 금지** — 코드는 제거하되 원시 증거는 **1.10의 검증된 Release 보관 계약**으로 보존한다. 업로드/다운로드 검증과 별도 사용자 승인 전 로컬 원본을 지우지 않는다.

# 2. QA-Fix 로그 (Log.md)

QA 에이전트가 버그를 발견했을 때 생성하며, QA ↔ DEV 버그 수정 과정을 Round 단위로 기록합니다.
에이전트(qa-tester, game-programmer) 전용 문서입니다.

## 폴더 구조

```
Assets/_Project/Docs/_Logs/
├── _editor/                            ← 에디터 상시 로그 (소모품 · 수동 정리, 1.10)
│ └── YYYY-MM-DD/
│   └── RuntimeLog.txt                  ← 파일을 쓰는 프로세스는 항상 에디터 1개 (1.10)
│
├── YYYY-MM-DD/
│ ├── HH_MM_[작업명]/                   ← _Tasks와 동일 경로명; raw 보관은 1.10, Log.md는 Git 유지
│ │ ├── RuntimeLog.txt                  ← 런타임 로그 (임시 진단 세션 · 1.11)
│ │ └── Log.md                          ← QA ↔ DEV 이터레이션 이력 (에이전트 전용)
│ │
│ └── HH_mm_logcat/                     ← 실기기 Logcat 캡처 위치; raw 보관은 1.10
│   └── RuntimeLog_device.txt
```

예시:
```
Assets/_Project/Docs/_Logs/
└── 2026-03-05/
  └── 18_05_network-input-fix/
    ├── RuntimeLog.txt
    └── Log.md
```

기존 규약의 RuntimeLog_host.txt/RuntimeLog_client.txt 및 해당 문서 인용은 유효합니다. 새 진단 세션은 RuntimeLog.txt, Device 캡처는 RuntimeLog_device.txt를 사용합니다. 파일명 정정 원문: [LogHistory H12](LogHistory.md#h12).

## 위치 및 생성 시점
- 경로: `Assets/_Project/Docs/_Logs/YYYY-MM-DD/HH_MM_[작업명]/Log.md`
- **_Tasks와 동일한 날짜/시간/작업명 폴더**를 사용 (대응 관계 유지)
- QA 에이전트가 FAIL을 처음 발견한 시점에 생성
- 모든 TC가 PASS이면 생성 불필요

## 작성 주체
| 섹션 | 작성 주체 |
|------|----------|
| `[QA]` | qa-tester 에이전트 |
| `[DEV]` | game-programmer 에이전트 |

## 형식

```markdown
# QA-Fix 반복 로그 — [작업명]

## Round 1 — YYYY-MM-DD HH:MM

### [QA] 발견된 문제
- BUG-001: [TC-ID] — [증상 설명]
  - 관련 파일: [파일 경로:라인]
  - 원인 분석: [분석 내용]
- BUG-002: [TC-ID] — [증상 설명]
  - ...

### [DEV] 수정 내용
- BUG-001: [수정 파일:라인] — [수정 내용]
- BUG-002: [수정 파일:라인] — [수정 내용]

## Round 2 — YYYY-MM-DD HH:MM

### [QA] 발견된 문제
...
```

## 운영 규칙
- DEV 수정 완료 후 반드시 `[DEV]` 섹션 채운 뒤 QA에게 재요청
- Round는 순서대로 append — 이전 Round 내용 수정 금지
- 최종 전체 PASS 시 Log.md에 별도 종료 표기 불필요 (Testcase.md 최종 판정으로 대체)
- 런타임 로그 파일을 근거로 인용할 때는 **파일 경로와 줄 번호**를 함께 적는다
