그런데 실제로 로그를 짤 때 가장 자주 부딪히는 질문은 그게 아니라 **"이 로그를 출시된 게임에도 남길 것인가"** 다.

# 1. 런타임 로그

게임 실행 중 발생하는 동작을 기록하는 로그입니다.

---

## 1.1 목적

런타임 로그는 두 가지 목적을 동시에 수행한다.

1. **개발 중 디버깅** — 버그 재현과 원인 파악. Claude(QA 에이전트 포함)가 로그 파일을 읽고 흐름을 추적한다.
2. **라이브 운영 지표 수집** — 출시본에서 플레이어에게만 발생하는 문제를 파악한다. (서버 수집은 향후 작업)

이 두 목적은 요구가 서로 다르다. 그래서 축을 나눈다.

---

## 1.2 두 축 — 심각도와 존속

모든 런타임 로그는 **두 축의 값을 각각 정한 뒤** 작성한다. 하나만 정하는 것은 규칙 위반이다.

### 축 A — 심각도

판정 질문: **"복구되었나?"**

| 값 | 정의 | 판정 |
|----|------|------|
| `Error` | 복구 경로가 **없다.** 기능이 죽고, 사용자는 그 기능을 더 이상 쓸 수 없다 | 복구 안 됨 |
| `Warn` | 예상 밖이지만 **대체 경로로 계속 진행**된다 (폴백 값 사용, 재시도 성공, 요청만 거부하고 게임은 계속) | 복구됨 |
| `Info` | 의도된 흐름 | 애초에 문제 아님 |

> "심각해 보이니까 Error" 는 판정이 아니다. **복구되었으면 Warn, 안 되었으면 Error.** 그것뿐이다.

### 축 B — 존속

판정 질문: **아래 두 문장 모두 "예"** 여야 `운영`이다. 하나라도 "아니오"면 `개발`이다.

1. **플레이어 기기에서만 벌어지는가?** (개발자가 에디터에서 재현할 수 없는가)
2. **이 로그가 없으면 원인을 추적할 수단이 없는가?** (UI 통지·다른 로그로 대체 불가능한가)

| `임시` | 특정 버그 추적용. **작업이 끝나면 코드 자체를 제거한다** |

## 1.3 분류 원칙

축 두 개만으로 갈리지 않는 경계 사례가 있다. 아래 네 가지가 그 경계를 확정한다.

**원칙 1 — 예외를 던지는 쪽은 로그하지 않는다.**
최종적으로 처리(`catch`)하는 쪽에서 **한 번만** 남긴다.
던지는 쪽과 받는 쪽이 모두 남기면 같은 사건이 두 줄로 기록되어, 서버 집계에서 **발생 건수가 부풀려진다.**

**원칙 2 — UI로 이미 알린 실패는 `개발`이다.**
단, **서버가 거부했는데 클라이언트가 그걸 몰랐던 경우는 `운영`** 이다.
클라이언트가 미리 막았는데도 서버가 거부했다는 것은 **클라·서버 상태 불일치**를 뜻하고, 그건 화면에 뜬 문구로는 절대 알 수 없는 정보다.

**원칙 3 — `Error`는 항상 `운영`이다.**
단, **Inspector 배선 누락 같은 설정 오류는 `Warn` + `개발`** 로 낮춘다.
설정 오류는 플레이어 기기의 문제가 아니라 개발 환경의 문제이고, 빌드 전에 잡히기 때문이다.

**원칙 4 — 삼킨 예외(`catch { }`)는 반드시 `운영` 로그를 남긴다.**
예외를 삼키면 **흔적이 전혀 남지 않는다.** 폴백이 조용히 성공한 것처럼 보이기 때문에,
로그를 남기지 않으면 "실패했다는 사실 자체"를 아무도 알 수 없다.

### 원칙 간 우선순위 (2026-08-14 추가)

쉬운 말로 먼저 설명한다.

위의 원칙 네 개는 각각은 분명한데, **한 자리에 두 개가 동시에 걸리면 서로 반대 답을 내놓는 경우가 있다.**
실제로 그런 일이 벌어졌다 — 2026-08-13 로그 감사에서 205건을 판정하는 동안, **3건에서 원칙 1과 원칙 3이 정면으로 반대 결론**을 냈다.
어느 쪽을 따라야 하는지 규칙에 적혀 있지 않아 판정이 멈췄다.

그래서 아래에 **① 어느 원칙이 우선하는지**, **② 원칙 1이 말하는 "최종 처리 지점"이 정확히 어디인지**,
**③ 원칙 3의 "항상 운영"이 무엇의 단위인지**를 확정해 둔다.

> **아래 내용은 원칙 1~4의 문구를 바꾸지 않는다.** 원칙 본문은 그대로 두고 **적용 순서와 용어 정의만 덧붙인 것**이다.

#### ① 확정된 순서 — **원칙 1이 원칙 3보다 우선한다**

`Error`이면서 같은 사건이 두 계층에서 로깅되는 자리에서는 **원칙 1을 먼저 적용한다.**
즉 **원인을 가진 계층을 `운영`으로 두고, 중복되는 상위 호출부는 `개발`로 내린다.**

**근거 — 반대로 읽으면 원칙 1이 통째로 무효가 된다.**
원칙 3을 *"모든 `Error` 호출문이 각각 `운영`이어야 한다"* 로 읽으면,
예외는 결국 어딘가에서 `Error`로 잡히므로 **중복 금지 규칙이 적용될 자리가 아예 없어진다.**
규칙 하나를 살리려고 다른 규칙 하나를 죽이는 해석은 채택하지 않는다.

**이 순서로 잃는 정보는 없다.** 세 가지를 확인했다.

- **원인과 예외 타입·스택은 그대로 남는다.** 하위 계층 로그가 `운영`이므로 릴리스와 서버 수집에 계속 올라간다
- **화면 통지는 그대로다.** 상위 호출부는 `OnError` 등으로 사용자에게 계속 알린다 — 로그 축 값을 내리는 것이지 통지를 없애는 것이 아니다
- **`개발`이라도 개발 중에는 보인다.** 에디터·개발 빌드에서는 그대로 출력되고, **릴리스에서만 빠진다** (1.7)

#### ② "최종 처리 지점"의 정의 (원칙 1)

원칙 1은 *"최종적으로 처리(`catch`)하는 쪽에서 한 번만"* 이라고만 적고 **그게 어디인지 정의하지 않았다.**
위 3건이 막힌 진짜 원인이 이 모호함이다. 아래로 확정한다.

> **최종 처리 지점 = 예외의 원인 정보(예외 객체 · `e.Message` · 예외 타입 · 스택)를 실제로 손에 쥔 계층.**
> 즉 **`catch` 블록이 예외 객체를 직접 받는 그 자리**다.

**갈릴 수 있었던 반대 해석:** *"사용자에게 알리고 흐름을 끝내는 상위 호출부"* 도 "최종 처리"라 부를 수 있다.
그쪽을 택하지 않은 이유는 하나다 — **원인을 모르는 로그는 장애 추적에 쓸모가 없다.**

상위 호출부에는 원인이 도달하지 않는 경우가 흔하다. 실측 예로, `LobbyManager`의 두 메서드는
`catch (LobbyServiceException e)` 안에서 로그를 남긴 뒤 **`return null`** 만 한다.
호출부가 받는 것은 `null` 뿐이라, 호출부의 로그는 *"실패했다"* 만 말하고 *"왜"* 를 말하지 못한다.
그 줄만 릴리스에 남기면 **원인이 세상에서 사라진다.**
반대로 원인 계층을 택하면 화면 통지는 상위에서 그대로 유지되므로(① 참조) **잃는 것이 없다.**

#### ③ 원칙 3의 "항상 `운영`"은 **사건 단위**다

원칙 3은 **"그 *사건* 이 `운영`으로 기록되어야 한다"** 는 뜻이다.
**"모든 `Error` *호출문* 이 각각 `운영`이어야 한다"** 는 뜻이 아니다.

→ 한 사건이 여러 계층에서 감지되더라도, **원인을 가진 계층 한 곳이 `운영`으로 남으면 원칙 3은 충족된다.**
나머지 호출문은 `개발`로 내려도 원칙 3을 어기는 것이 아니다.

#### ④ 실제로 갈렸던 자리 — 2026-08-13 감사 3건

추상적인 서술만으로는 다음에 또 막힌다. 규칙이 실제로 적용된 모습을 그대로 남긴다.

| 사건 | 원인을 가진 계층 → **`운영`** | 중복되는 상위 호출부 → **`개발`** |
|------|------------------------------|--------------------------------|
| UGS 초기화 실패 | `Infrastructure/Network/UnityServicesInitializer.cs:139` — `catch (Exception e)` 안에서 `e.Message`를 남긴다 | `Infrastructure/Network/NetworkGameManager.cs:201` — `onFailure` 콜백에서 **같은 예외의 같은 `e.Message`** 를 다시 남기고 `OnError`로 화면에 알린다 |
| Lobby 생성 실패 | `Infrastructure/Network/LobbyManager.cs:111` — `catch (LobbyServiceException e)` 안에서 `e.Message`를 남기고 `return null` | `Infrastructure/Network/NetworkGameManager.cs:233` — `null`을 받아 **고정 문구**로 남긴다. 예외 객체를 받지도 못한다 |

세 건 모두 **하위 계층이 이미 원인과 함께 기록**하고, 상위 호출부가 **같은 사건을 한 번 더** 기록하던 자리다.
②의 정의를 적용하면 최종 처리 지점은 왼쪽 열이고, ①에 따라 오른쪽 열은 `개발`로 내려간다.

#### ⑤ 순서를 매기지 않은 쌍 — 검토 결과

**실제로 충돌이 확인되지 않은 쌍에는 순서를 매기지 않는다.** 근거 없는 순서는 나중에 잘못된 판정을 낳는다.

## 1.4 형식

형식은 개정 전 규정을 그대로 유지한다. **이 형식이 이미 서버 전송의 기반이기 때문이다.**

### 로그 라인

```
[HH:MM:SS.ms] [LEVEL] [System/Class] 메시지 | key=value, key=value
```

예시:
```
[10:53:23.124] [INFO] [Network/NetworkUnit] OnNetworkDespawn | IsServer=False, UnitType=Pistoleer
[10:53:23.125] [WARN] [Network/NetworkUnit] 예상치 못한 상태 감지 | IsServer=False, Reason=AlreadyDespawned
[10:53:23.126] [ERROR] [Network/NetworkUnit] Despawn 실패 | IsServer=False, Reason=ObjectNotFound
```

### `key=value`가 곧 전송 데이터다

`| key=value, key=value` 부분은 사람이 읽으라고 붙인 꼬리표가 아니다.
**운영 로그를 서버로 보낼 때 그대로 구조화 필드가 되는 부분**이다.

| 로그 라인의 조각 | 서버 전송 시 역할 |
|-----------------|------------------|
| `[LEVEL]` | 심각도 필드 |
| `[System/Class]` | 발생 지점 필드 |
| 메시지 | 사람이 읽을 설명 (집계 키로 쓰지 않는다) |
| `key=value` | **집계·필터링용 구조화 필드** |
| 이벤트 키 (1.5) | **집계의 기본 단위** |

그래서 `key=value`를 쓸 때 지켜야 할 것:

- **값은 집계 가능한 형태로 쓴다.** `Reason=ObjectNotFound` (○) / `Reason=이상하게도 오브젝트가 없었음` (✗)
- **키 이름을 그때그때 바꾸지 않는다.** `UnitType=` 과 `unitType=` 이 섞이면 집계가 조용히 둘로 갈라진다
- **같은 키의 값 표기도 파일마다 바꾸지 않는다 (2026-08-17 추가).** 위 항목은 **키** 이름에 관한 것이고, 이것은 **값** 쪽이다.
  갈라지는 방식과 결과가 같으므로 함께 지킨다 — 같은 키에 `Host` 와 `host` 가 섞이면 **한 지표가 조용히 둘로 갈라진다.**
- **자유 문장은 메시지 쪽에 넣는다.** `key=value`에는 넣지 않는다
- **값 안에 구분자 `, ` 를 넣지 않는다 (2026-08-18 추가).** 이 형식은 `key=value` 쌍을 `, ` 로 잇는다.
  값에 같은 문자열이 들어가면 **파싱이 그 자리에서 쪼개져 필드 하나가 둘로 보인다.**
  특히 `string.Join(", ", ...)` 결과를 그대로 값에 넣는 실수가 나기 쉽다 —
  목록을 담아야 하면 **다른 구분자(`|` 등)를 쓰거나 개수만 남긴다**(`Count=3`).

> **실제로 갈렸던 사례 — `Role=` (2026-08-17 · 커밋 `73574a23`)**
> 실기 로그를 열어 보니 같은 `Role=` 키가 두 표기로 갈려 있었다 —
> `NetworkGameManager` **5곳**은 `Role=Host` / `Role=Client`, `NetworkCombatController` **1곳**은 `Role=host` / `Role=client`.
> **소수인 `NetworkCombatController` 쪽을 `Host` / `Client` 로 맞췄다.**
> 근거 로그: `_Logs/_editor/2026-08-17/RuntimeLog.txt` — 통일 **전** 시점의 파일이라
> `Role=Host`(88행)와 `Role=host`(4·98행)가 한 파일 안에 그대로 남아 있다.
> **이 파일은 소급 수정하지 않는다** — 이력 기록이고, 갈렸다는 사실 자체가 이 항목의 근거이기 때문이다.

### 카테고리 규칙

`[System/Class]` 형식으로 작성한다.

- **System**: 어느 시스템 영역인지 (예: `Network`, `Combat`, `UI`, `HexGrid`, `Auth`)
- **Class**: 정확히 어느 클래스에서 출력하는지 (예: `NetworkUnit`, `UnitView`, `ProductionPanelUI`)
- **System 은 그 로그가 다루는 「기능」으로 정한다. 파일이 놓인 폴더로 정하지 않는다 (2026-08-18 추가).**
  아래 예시 셋이 **전부 `Presentation/` 하위 클래스인데 System 이 셋으로 갈리는 것**이 그 뜻이다.
  즉 `Presentation/UI/LobbyUI` 의 **방 참가 실패**는 `UI` 가 아니라 **`Network`** 다 — 그래야
  매칭 실패를 추적할 때 `System=Network` 필터 하나로 그 사건이 전부 잡힌다.

예시:
```
[Combat/UnitView]        Presentation/Unit/  → Combat
[HexGrid/HexTileView]    Presentation/Grid/  → HexGrid
[UI/ProductionPanelUI]   Presentation/UI/    → UI
[Network/NetworkUnit]    Infrastructure/Network/ → Network
```

> **왜 본문에 문장으로 못 박는가 (2026-08-18 · 커밋 `589c2fcf`)**
> 위 예시 셋은 원래도 있었지만 **예시만으로는 읽는 사람마다 해석이 갈렸고, 실제로 갈렸다.**
> 나머지 계층 이관 배치 3 이 원본 `[Network]` 태그를 달고 있던 UI 4파일의 System 을
> **폴더 기준으로 `"UI"` 로 바꿨다가**, 위 근거에 따라 `589c2fcf` 로 되돌렸다.
> **규칙 번호를 새로 만들지 않고 이 절 본문에 한 문장으로 넣은 이유**는, 이것이 새 규칙이 아니라
> 예시가 이미 말하고 있던 것의 명문화이기 때문이다(번호를 늘리면 코드 주석의 기존 참조와 어긋난다).

### 파일 헤더

파일 최상단에 **필수 2줄 + 선택 줄**을 작성하고, **빈 줄로 본문과 구분**한다.

| 줄 | 필수 여부 | 형식 |
|----|----------|------|
| 1줄째 | **필수** | `=== [작업명 또는 로그 목적] ===` |
| 2줄째 | **필수** | `=== [시각의 종류]: YYYY-MM-DD HH:MM:SS ===` |
| 3줄째 이후 | 선택 | `=== [출처 항목]: [값] ===` — 그 파일에만 존재하는 출처 정보 |
| 그다음 | **필수** | 빈 줄 (헤더 끝 표시) |

에디터 파일 예시 (2줄):
```
=== 유닛 사망 NGO 버그 픽스 검증 로그 ===
=== 세션 시작: 2026-06-08 10:52:40 ===

[10:53:23.124] [INFO] [Network/NetworkUnit] ...
```

실기기 파일 예시 (3줄 — 기기 정보 추가):
```
=== Android Logcat 캡처 ===
=== 저장 시각: 2026-08-13 14:07:11 ===
=== 대상 기기: SM_G981N (R3CN90ABCD) ===

08-13 14:06:52.310  8421  8455 I Unity   : ...
```

> **왜 줄 수를 고정하지 않는가 (2026-08-13 개정)**
> 개정 전 규칙은 헤더를 **정확히 2줄**로 못박았고, 실기기 캡처 도구는 `=== 대상 기기: ... ===` 를 붙여 3줄을 쓴다.
> 도구를 2줄로 깎지 않고 규칙을 넓힌 이유는 셋이다.
> ① **기기 정보는 에디터 로그에 대응물이 없다.** 3줄로 고정하면 에디터 파일에 의미 없는 빈 필드를 강요하게 되고, 의미 없는 필드는 곧 안 쓰이면서 규칙 전체를 무너뜨린다.
> ② **그 줄을 지우면 안전장치가 무효가 된다.** 캡처 도구는 기기가 여러 대일 때 사용자에게 대상을 직접 고르게 만들어 두었는데, 고른 결과를 파일에 남기지 않으면 그 확인 절차가 파일 단계에서 사라진다. 기기 여러 대 환경에서 "어느 기기의 로그인지 모르는 파일"은 형식만 멀쩡한 최악의 자료다.
> ③ **줄 수를 고정할 이유가 애초에 없었다.** 헤더는 `=== 키: 값 ===` 줄의 목록이고 본문은 `[` 로 시작한다. 헤더 끝은 **빈 줄**로 구분되므로, 줄 수를 세지 않아도 경계가 모호해지지 않는다.
> → 결론: **코드 수정 없음.** 현행 캡처 도구의 3줄 헤더는 이 규칙에 그대로 부합한다.

## 1.5 이벤트 키 — `LogEvent`

**운영 로그는 반드시 이벤트 키를 함께 남긴다.**

| 항목 | 규정 |
|------|------|
| 정의 방식 | **`enum LogEvent`**. 임의 문자열·문자열 상수 금지 |
| 전송 키 | enum 멤버 이름을 **그대로**(PascalCase) 쓴다. 변환 규칙(스네이크케이스화 등)을 두지 않는다 |
| 적용 범위 | **`운영` 로그만** 키를 받는다. `개발`·`임시`는 전송 대상이 아니므로 불필요하다 |

### 왜 enum인가

문자열 상수나 리터럴을 쓰면 **키가 조금씩 달라지면서 집계가 조용히 갈라진다.**
`"MatchmakingFailed"` 와 `"matchmaking_failed"` 와 `"MatchmakingFail"` 이 서로 다른 세 지표가 되고,
어느 쪽도 실제 발생 횟수를 나타내지 못한다. 게다가 이 오류는 **컴파일러가 잡아 주지 않는다.**
enum이면 오타는 컴파일 에러고, 이름을 바꾸면 IDE가 전부 따라 바꾼다.

### 왜 이름을 그대로 쓰는가

변환 규칙을 하나 두면, 그 규칙을 **양쪽(클라이언트 전송 코드 / 서버 집계 코드)이 똑같이 구현해야** 한다.
한쪽만 바뀌는 순간 지표가 통째로 사라지고, 사라진 사실조차 눈에 안 띈다.
이름을 그대로 쓰면 맞출 것 자체가 없다.

### 이름 짓기

- **무엇이 일어났는지**를 적는다. 어디서 일어났는지는 `[System/Class]`가 이미 담고 있다
- 이름은 **한 번 정하면 바꾸지 않는다.** 이름이 바뀌면 서버에 쌓인 과거 지표와 연결이 끊긴다
- 예: `MatchmakingLobbyJoinFailed`, `ServerRejectedUpgradeInsufficientGold`, `CloudSaveValueParseFailed`, `UnhandledException`

## 1.6 민감 데이터

**로그 파일은 개발자 간 공유되고, 채팅에 붙여지고, 리포지토리에 커밋된다.** 유출 경로가 이미 여럿이다.

| 데이터 | 규정 | 이유 |
|--------|------|------|
| **이메일** | **넣지 않는다. 부분 마스킹도 금지** | 부분 마스킹(`a***@gmail.com`)은 재식별이 너무 쉽다. 도메인 + 첫 글자 + 길이만으로 특정되는 경우가 흔하다 |
| **UID · PlayerId** | **해시로 치환해서 넣는다** | 완전히 지우지 않는 이유가 있다 — 아래 참조 |
| 인증 토큰 · 세션 키 · 비밀번호 | **어떤 형태로도 금지** | 그대로 계정 탈취 수단이 된다 |

### UID를 지우지 않고 해시로 바꾸는 이유

라이브 운영에서 답해야 하는 질문은 "누가 겪었나"가 아니라 이것들이다.

- **몇 명이 겪었나?** (한 사람이 100번 겪은 것과 100명이 한 번씩 겪은 것은 완전히 다른 문제다)
- **같은 사용자가 반복해서 겪나?** (일시적 오류인지, 특정 계정이 망가진 상태인지)

이 질문에 답하려면 **안정적인 익명 식별자**가 필요하다. 통째로 지우면 두 질문 모두 답할 수 없다.
해시는 "같은 사람인지"는 알려 주되 "누구인지"는 알려 주지 않는다 — 정확히 필요한 만큼만 남긴다.

### 2단 방어 — 규율만으로는 반드시 샌다

| 단계 | 책임 | 내용 |
|------|------|------|
| 1단 | **호출부** | 마스킹 헬퍼를 거쳐서 값을 넣는다 (`HashId(uid)` 등) |
| 2단 | **facade (`GameLog`)** | 최종 조립된 문자열에서 **이메일 패턴을 감지해 차단**한다 |

1단만 두면 언젠가 누군가 헬퍼를 빠뜨린다. 사람이 매번 기억해야 하는 규칙은 결국 깨진다.
2단은 그 실수를 마지막 지점에서 잡는 그물이다.

### 에디터 포함 항상 적용

**에디터에서도 똑같이 마스킹한다.** 경로를 갈라 에디터에서만 원본을 보이게 하면
"에디터에선 보였는데 빌드에선 안 보인다" 는 혼란이 생기고, 그 혼란을 없애려고
누군가 마스킹을 임시로 끄는 순간 방어가 무너진다.

## 1.7 릴리스 스트리핑

`개발` 로그를 출력하는 메서드에는 **두 개의 `[Conditional]` 특성을 모두** 붙인다.

```
[Conditional("UNITY_EDITOR")]
[Conditional("DEVELOPMENT_BUILD")]
```

| 항목 | 규정 |
|------|------|
| 적용 대상 | **`개발` 로그 메서드** |
| 적용 금지 | **`운영` 로그 메서드에는 붙이지 않는다** (릴리스에서 살아야 하므로) |

### 왜 둘 다 붙이는가

여러 개의 `[Conditional]`은 **OR**로 동작한다. 즉 "에디터 **또는** 개발 빌드에서 살아 있고, 그 외에는 사라진다".
한쪽만 붙이면 구멍이 생긴다.

| 붙인 것 | 생기는 구멍 |
|---------|-----------|
| `UNITY_EDITOR`만 | **실기기 테스트에서 로그가 사라진다.** 개발 빌드로 기기에 올려도 아무것도 안 나온다 |
| `DEVELOPMENT_BUILD`만 | **에디터에서 로그가 안 보인다.** 이 심볼은 에디터에 정의되어 있지 않다 |

### 런타임 분기와 다르다

`if (Debug.isDebugBuild)` 로 감싸는 것과 같지 않다.

- **런타임 분기**: 호출은 남아 있고, **인자는 이미 평가된 뒤** 조건을 검사한다.
  → 문자열 보간(`$"unit={id}, hp={hp}"`)이 릴리스에서도 매 호출마다 실행되어 문자열이 새로 만들어진다.
- **`[Conditional]`**: 컴파일러가 **호출 자체와 인자 평가까지 통째로 제거**한다.
  → 문자열 보간 비용이 **0**이 된다.

프레임마다 도는 코드에 개발 로그를 넣을 수 있는 것은 이 차이 때문이다.

### ⚠️ 람다에 넣으면 스트리핑이 무효가 된다 (2026-08-18 추가)

C# 컴파일러가 `[Conditional]` 로 지우는 것은 **문(statement) 자리의 호출**뿐이다.
**식(expression) 자리의 호출은 지우지 않는다.**

| 형태 | 릴리스에서 |
|---|---|
| `GameLog.Dev.Info(...);` (문) | **사라진다** ✅ |
| `() => GameLog.Dev.Info(...)` (**식 본문 람다**) | **살아남는다** ❌ |
| `() => { GameLog.Dev.Info(...); }` (**블록 본문 람다**) | **사라진다** ✅ |

식 본문 람다는 그 호출이 **람다의 반환식**이라 문이 아니고, 컴파일러가 지울 수 없다.
→ **콜백·이벤트 핸들러에 `Dev` 로그를 넣을 때는 반드시 블록 본문(`{ }`)으로 쓴다.**
겉보기 차이가 중괄호 두 개뿐이라 리뷰에서 놓치기 쉽고, **증상은 릴리스 빌드에서만 나타난다.**

## 1.8 sink 구조

로그를 "어디에 쓸 것인가"는 로그를 "남긴다"는 행위와 분리한다.

| 항목 | 규정 |
|------|------|
| 인터페이스 | `ILogSink` |
| 전달 방식 | `GameLog`가 **등록된 sink에 순서대로** 전달 |
| 등록 방식 | **정적 등록** — `GameLog.AddSink(...)` |
| 등록 주체 | **`LogSessionOwner`**(`Infrastructure/Debug/`) — sink 를 만들어 등록하는 곳은 **앱 전체에서 이 정적 클래스 하나뿐**이다. 부트스트래퍼(`LoginBootstrapper` / `GameBootstrapper`)는 `Awake` 첫 줄에서 **진입점 `EnsureInitialized()` 를 호출할 뿐**이며, 두 번째 호출부터는 아무 일도 하지 않는다(멱등) |

> **등록 주체 변경 (2026-08-17 · 커밋 `a253232e`)**
> 이 항목은 직전 판까지 ~~*"`GameBootstrapper` 가 초기화 시 호출 (유일한 의존성 조합 루트)"*~~ 였다.
> **바뀐 것은 주체의 이름과 구조이고, 규칙의 취지 — 「등록 주체를 하나로 못 박는다」 — 는 그대로다.**
>
> **왜 옮겼는가:** `GameBootstrapper` 는 **`Game.unity` 에만** 배치되어 있다(실측: `Login.unity` 0 / `Lobby.unity` 0 / `Game.unity` 1).
> 그래서 로그인·로비 구간의 로그는 sink 가 하나도 없는 상태로 흘러 **아래 「콘솔 폴백」만 타고 파일에 남지 않았다** — 실측 **73건**.
>
> **조합 루트 원칙과 충돌하지 않는 근거:**
> ① `LogSessionOwner` 는 **의존성을 남에게 주입하지 않는다.** 자기가 만든 sink 를 자기 안에 들고 있을 뿐이다.
> ② **호출 주체는 여전히 Bootstrap 레이어뿐**이라, "누가 로그를 켰는가"가 코드에서 그대로 추적된다.
>    (아무도 부르지 않았는데 켜지는 `[RuntimeInitializeOnLoadMethod]` 방식을 쓰지 않은 이유다.)
> ③ **상태를 `static` 한 곳에 모은 것이 이 변경의 핵심이다.** sink 를 인스턴스 필드에 두면
>    "이미 열려 있는가?"라는 판단이 **씬 경계를 건너가지 못해**, 뒤 씬이 앞 씬의 파일 스트림을 닫아 버린다
>    (2026-08-10 에 실제로 겪은 사고 — **1.10** 근거 문단 참조).
>
> 여닫는 시점은 **여는 쪽 둘 / 닫는 쪽 하나**다 — 두 부트스트래퍼가 열고, 닫는 것은 `UnityEngine.Application.quitting` 1회다.
> 상세는 `_Tasks/2026-08-17/11_07_scene-independent-logging/Plan.md`.

### sink가 하나도 없으면 콘솔로 폴백한다

등록 전에 발생한 로그를 버리면 안 된다.
**초기화 순서 문제로 로그가 사라지면, 그 사실 자체를 추적할 수단이 없기 때문이다.**
"로그가 안 나온다"의 원인이 "로그 시스템이 아직 안 켜졌다"인 경우, 로그로는 절대 알 수 없다.
sink 목록이 비어 있으면 **콘솔로 출력**한다.

### sink 하나가 실패해도 다음 sink는 계속 진행한다

각 sink 호출을 **개별적으로 `try-catch`로 감싼다.**

- 파일 sink가 디스크 권한 문제로 던져도, 콘솔 sink는 정상 출력되어야 한다
- **로그 때문에 게임이 멈추면 본말전도다.** 로그는 게임을 돕는 도구지 게임의 일부가 아니다

## 1.9 예외 처리

### `Exception` 오버로드를 둔다

`GameLog`는 `Exception`을 인자로 받는 **오버로드를 제공**한다.
예외를 `e.Message` 문자열로 눌러 담지 않는다 — **예외 타입이 텔레메트리 집계의 핵심 축**이기 때문이다.
`TimeoutException` 300건과 `NullReferenceException` 300건은 완전히 다른 사건이고,
메시지 문자열만 남기면 그 구분이 사라진다.

### `ConsoleSink`는 `Debug.LogException`으로 내보낸다

**`Debug.LogError(e.ToString())`을 쓰지 않는다.**
크래시 리포터가 그것을 **예외로 인식하지 못해 스택 심볼화(symbolication)가 되지 않는다.**
난독화·최적화된 릴리스 빌드에서 심볼화가 안 된 스택은 사실상 읽을 수 없는 주소 나열이다.

### 전역 미처리 예외 수집

`Application.logMessageReceived` 훅을 걸어, **계측하지 않은 곳에서 터진 예외까지** 수집한다.
아무리 규율을 지켜도 `try-catch`를 두지 않은 자리는 남고, 실제 크래시는 대개 그런 자리에서 난다.

> **훅 소유자 이동 (2026-08-17 · 커밋 `a253232e`)**
> 등록·해제와 중복 방지 상태는 직전 판까지 ~~`GameBootstrapper.Setup.cs`~~ 안에 **인스턴스 멤버**로 있었고,
> 지금은 **`LogSessionOwner`**(`Infrastructure/Debug/`) 의 `static` 으로 옮겨졌다. **되먹임 방어 3겹은 한 겹도 빼지 않고 그대로 이관**되었다
> (예외만 수집 / `GameLog.IsEmitting` / 직전 동일 예외 무시).
>
> **왜 sink 커버리지와 함께 옮겼는가:** 훅이 `GameBootstrapper` 에만 걸려 있으면
> **로그인·로비 구간에서 터진 미처리 예외는 아무 데도 수집되지 않는다.** sink 만 고치고 훅을 두고 가면 같은 구멍이 예외 쪽에 그대로 남는다.
>
> **⚠️ 부수 영향 — 로그 라인의 클래스 이름이 바뀐다.**
> 미처리 예외 로그의 `className` 이 ~~`GameBootstrapper`~~ → **`LogSessionOwner`** 가 되었다.
> 즉 로그 라인이 `[Runtime/GameBootstrapper]` → **`[Runtime/LogSessionOwner]`** 로 바뀐다.
> Infrastructure 인 이 클래스가 Bootstrap 레이어의 `GameBootstrapper` 를 참조하면 의존 방향이 뒤집히므로 **불가피한 변경**이다.
> **로그를 `grep` 하는 쪽(스크립트·과거 검색 습관)에 영향이 있다** — 옛 이름으로 찾으면 이후 로그가 잡히지 않는다.

> ⚠️ **재진입 가드 필수**
> sink가 `Debug.Log`를 호출하고, 그 호출이 다시 `logMessageReceived` 훅으로 들어오면
> **무한 루프로 앱이 죽는다.** 훅 처리 중임을 나타내는 플래그를 두고, 처리 중 재진입은 즉시 반환한다.
> 이 가드가 없으면 로그 시스템이 크래시의 **원인**이 된다.

## 1.10 파일 기록 — 에디터 상시 활성

### 에디터에서는 파일 기록을 항상 켠다

**세션을 수동으로 열고 닫지 않는다.** 플레이 모드에 들어가면 파일이 자동으로 쌓인다.

**근거 (실제 겪은 왕복):** MistShrine 힐 검증 작업에서
*로그 코드 추가 → 세션 배선 → 배선 오류로 파일 미생성 → 그 원인을 추적 → 재배선* 이라는 왕복이 발생했다.
상시 활성이면 이 왕복이 통째로 사라진다 — **그냥 읽으면 된다.**
세션 소유권 문제(어느 쪽이 세션을 닫을 것인가)도 구조적으로 없어진다.

### 공유는 복사가 아니라 그 파일을 그대로 커밋한다

개정 전 방식(폐기): ~~"남길 파일은 `_Logs/YYYY-MM-DD/HH_MM_[작업명]/` 으로 복사한 뒤 커밋한다"~~

복사 단계를 **없앤다.** 공유할 로그가 생기면 `_editor/` 에 있는 그 파일을 그대로 커밋한다.

```
git add Assets/_Project/Docs/_Logs/_editor/2026-08-13/RuntimeLog.txt
```

- **복사는 기존 방식보다 오히려 더 번거롭다.** 상시 활성으로 세션 배선 왕복을 없애 놓고
  그 자리에 "어느 파일을 어디로 복사할지 고르는" 새 왕복을 집어넣으면 개정의 목적이 무너진다.
  그대로 커밋하면 **지금까지의 수고와 동일**하고, 달라지는 것은 세션 배선이 필요 없다는 점뿐이다.
- **커밋하지 않은 날의 파일은 로컬에 그대로 남는다.** git은 커밋을 강제하지 않으므로 문제되지 않는다.

### `.gitignore`에 넣지 않는다

`_Logs/_editor/` 를 `.gitignore`에 넣으면 **`git add` 자체가 막혀** 위의 공유 방법이 성립하지 않는다.
로그 공유는 사용자가 커밋해서 푸시해야 이루어지므로, 무시 대상으로 지정하는 순간 목적이 무너진다.

> **알아 둘 점 — 커밋하지 않은 파일은 `git status`에 계속 뜬다.**
> `.gitignore`에 넣지 않는 이상 `_editor/` 의 새 파일은 추적되지 않은 파일로 계속 표시된다.
> 이것은 **의도된 동작**이다. 목록에 보이는 덕분에 "공유할 로그가 있다"는 사실을 놓치지 않는다.
> 표시가 거슬리면 지우는 것이 아니라 **아래 수동 정리 메뉴로** 처리한다.

### 자동 삭제하지 않는다

개정 전 방식(폐기): ~~"날짜 폴더 단위로 보존 기간(기본 7일) 초과분을 자동 삭제한다"~~

보존 기간 기반 자동 삭제를 **철회한다.** 근거는 둘이다.

- **커밋한 파일을 자동으로 지우면 `git status`에 삭제로 잡힌다.** 공유하려고 커밋해 둔 파일이
  며칠 뒤 도구에 의해 조용히 사라지면, 사용자는 자기가 지우지 않은 삭제 목록을 마주하게 된다.
  되돌릴지 말지를 매번 판단해야 하는 상태가 되어 오히려 손이 더 간다.
- **이 프로젝트에는 자동 삭제로 사고를 겪은 이력이 있다.** `CLAUDE.md` 규칙 5(git 명령 절대 금지)는
  2026-03-03에 `git restore` 를 무단 실행해 커밋되지 않은 작업 전체가 복구 불가로 소실된 사건에서 나왔다.
  **되돌릴 수 없는 삭제를 사용자 확인 없이 수행하지 않는다**는 원칙이 이 프로젝트에는 이미 서 있다.

그리고 애초에 지워야 할 만큼 쌓이지 않는다. **로그는 텍스트라 작다.**
실측 근거: MistShrine 힐 검증 로그(`_Logs/2026-08-10/14_12_mistshrine-heal-implementation/RuntimeLog_host.txt`)는
**310줄 / 약 54KB** 였다.

## 1.11 `RuntimeLogger`의 위치

## 1.12 실기기 로그

### 캡처 도구 사용 절차

도구: `Assets/Editor/Tools/LogcatCapture.cs`

1. 기기를 USB로 연결한다 (USB 디버깅 ON)
2. 메뉴 **`Hexiege > Logcat > 1. 버퍼 비우기`** 실행
3. 기기에서 **버그를 재현**한다
4. 메뉴 **`Hexiege > Logcat > 2. 파일로 저장`** 실행

> **메뉴 항목은 3개다 (2026-08-17 갱신)** — 같은 도구 파일에 **`3. 오래된 에디터 로그 정리`** 가 추가되었다.

> **왜 먼저 버퍼를 비우는가**: Logcat은 링 버퍼라 과거 로그가 계속 쌓여 있다.

1. **진단용 raw `Debug.Log` 직접 호출 금지** — 반드시 `GameLog`(구현 전까지는 `RuntimeLogger`)를 경유한다.
   콘솔에만 남은 로그는 파일이 되지 않아 **Claude가 읽을 수 없다.**
2. **축을 하나만 정하고 로그 작성 금지** — 심각도(축 A)와 존속(축 B)을 **둘 다** 정한다 (1.2)
3. **의미 없는 메시지 작성 금지** — 예: `[INFO] [Network/NetworkUnit] 여기`
4. **이메일 출력 금지 (부분 마스킹 포함)**, **UID·PlayerId 원본 출력 금지**, **토큰·세션 키 출력 금지** (1.6)
5. **레벨 표기 생략 금지** — 모든 로그 라인에 `[INFO]` / `[WARN]` / `[ERROR]` 중 하나를 반드시 명시
6. **운영 로그에 이벤트 키 생략 금지** (1.5)
7. **운영 로그 메서드에 `[Conditional]` 부착 금지** — 릴리스에서 사라지면 안 된다 (1.7)
8. **매 틱·매 프레임 로깅 금지** — 상태 **전이** 시점에만 남긴다. 스팸은 정작 필요한 줄을 묻어 버린다
9. **같은 사건을 두 곳에서 로깅 금지** — 최종 처리 지점에서 한 번만 (분류 원칙 1)
   - **"최종 처리 지점"의 정의는 1.3 「원칙 간 우선순위」 ② 참조** — **예외 객체(`e.Message`·예외 타입·스택)를 직접 손에 쥔 `catch` 블록**이다. "사용자에게 알리고 흐름을 끝내는 상위 호출부"가 아니다.
   - 이 금지가 **원칙 3(`Error`는 항상 `운영`)과 충돌할 때는 원칙 1이 우선**한다 — 같은 절 ①·③ 참조. 원인을 가진 계층을 `운영`으로 두고, 중복되는 상위 호출부를 `개발`로 내린다.
   - **⚠️ 중복 판정은 호출 경로를 끝까지 따라가서 한다 (2026-08-18 추가).** *"같은 하위 계층을 부르니 중복일 것"* 이라는 추정은
     2026-08-18 이관에서 **두 번 연속 빗나갔다.** 하위를 부르기 전에 `return` 하거나, 하위에 `catch` 가 없으면
     **대응하는 하위 로그가 애초에 존재하지 않으므로 중복이 아니다** — 그 자리를 `개발`로 내리면 **원인이 세상에서 사라진다.**
     | 실제 사례 | 결과 |
     |---|---|
     | `RelaySetupFailed` 가 `RelayManager`(원인)와 `NetworkGameManager`(호출자) 양쪽에서 발생 | **3곳 중 2곳만** 같은 사안이었다. `Stage=CodeMissing` 은 하위를 **호출하지 않고 `return`** 해 대응 로그가 존재할 수 없어 **`운영` 유지** |
     | `PlayerProfileService` 를 부르는 View **4곳** | **4곳 중 3곳만** 같은 사안이었다. `ProfileView` 로그아웃은 `FirebaseAuthService.SignOutAsync` 에 **`catch` 가 없어** 하위 로그가 없다 → **`운영` 유지** |
10. **`임시` 로그 코드를 남긴 채 작업 종료 금지** — 코드는 제거하되, **로그 파일 자체는 `_Logs/`에 보존**한다

# 2. QA-Fix 로그 (Log.md)

QA 에이전트가 버그를 발견했을 때 생성하며, QA ↔ DEV 버그 수정 과정을 Round 단위로 기록합니다.
에이전트(qa-tester, game-programmer) 전용 문서입니다.

## 폴더 구조

```
Assets/_Project/Docs/_Logs/
├── _editor/                            ← 에디터 상시 로그 (소모품 · 수동 정리, 1.10)
│ └── YYYY-MM-DD/
│   └── RuntimeLog.txt                  ← 파일을 쓰는 프로세스는 항상 에디터 1개 (1.10)
│
├── YYYY-MM-DD/
│ ├── HH_MM_[작업명]/                   ← _Tasks와 동일 경로명 (대응 관계) · 영구 보존
│ │ ├── RuntimeLog.txt                  ← 런타임 로그 (임시 진단 세션 · 1.11)
│ │ └── Log.md                          ← QA ↔ DEV 이터레이션 이력 (에이전트 전용)
│ │
│ └── HH_mm_logcat/                     ← 실기기 Logcat 캡처 · 영구 보존
│   └── RuntimeLog_device.txt
```

예시:
```
Assets/_Project/Docs/_Logs/
└── 2026-03-05/
  └── 18_05_network-input-fix/
    ├── RuntimeLog.txt
    └── Log.md
```

> **파일명 정정 (2026-08-17)** — 이 구조도의 task 폴더 가지는 직전 판까지
> ~~`RuntimeLog_host.txt` / `RuntimeLog_client.txt`~~ 두 줄이었다.
> `RuntimeLogger.BeginSession` 에서 `role` 인자가 사라졌으므로(1.10 · 1.11 · 커밋 `4e027e68`),
> **진단용 임시 세션이 만드는 파일도 `RuntimeLog.txt` 하나**가 된다.
>
> **단, 이미 커밋된 기존 로그 파일은 그대로 유효하다.**
> `_Logs/2026-08-10/14_12_mistshrine-heal-implementation/RuntimeLog_host.txt` 처럼 이전 규약으로 만들어진 파일과
> 그 파일을 가리키는 문서 링크는 **계속 살아 있다.** 규약 변경은 **앞으로 새로 만들어지는 파일에만** 적용된다.
>
> `RuntimeLog_device.txt` 는 실기기 Logcat 캡처 도구(1.12)의 산출물이라 **변경 대상이 아니다.**

## 위치 및 생성 시점
- 경로: `Assets/_Project/Docs/_Logs/YYYY-MM-DD/HH_MM_[작업명]/Log.md`
- **_Tasks와 동일한 날짜/시간/작업명 폴더**를 사용 (대응 관계 유지)
- QA 에이전트가 FAIL을 처음 발견한 시점에 생성
- 모든 TC가 PASS이면 생성 불필요

## 작성 주체
| 섹션 | 작성 주체 |
|------|----------|
| `[QA]` | qa-tester 에이전트 |
| `[DEV]` | game-programmer 에이전트 |

## 운영 규칙
- DEV 수정 완료 후 반드시 `[DEV]` 섹션 채운 뒤 QA에게 재요청
- Round는 순서대로 append — 이전 Round 내용 수정 금지
- 최종 전체 PASS 시 Log.md에 별도 종료 표기 불필요 (Testcase.md 최종 판정으로 대체)
- 런타임 로그 파일을 근거로 인용할 때는 **파일 경로와 줄 번호**를 함께 적는다
