## 공통 UI 규칙

모든 UI 시스템에 예외 없이 적용되는 공통 규칙이다.
새로운 UI를 제작하거나 기존 UI를 수정할 때 이 섹션을 기준으로 삼는다.

> **[2026-09-21 추가 — 위 두 줄은 그대로 두고 덧붙인다]**
> 🔴 **멀티플레이 화면에는 규칙 번호보다 위에 있는 원칙이 하나 더 있다 — 「플레이어는 자신이 Host 인지 Client 인지 알 수 없다.」**
> 그러므로 **UI/UX 도 승패 기록도 역할과 무관하게 항상 일관되게 동작해야 하며**, 같은 상황에서 **Host 화면과 Client 화면이 다르면 그것은 결함**이다.
> **원칙의 단일 소스는 [TechnicalDesignDocument.md](../TechnicalDesignDocument.md) 「🔴 최상위 원칙 — 플레이어는 자신이 Host 인지 Client 인지 알 수 없다」 절**이며,
> **그 내용을 이 문서에 옮겨 적지 않는다** — 사본은 원본이 바뀌는 순간 조용히 거짓이 된다.
> 이 섹션의 규칙(특히 `D-` 접두사의 「경기 종료 후 상대 이탈 UI」 절)은 **그 원칙을 어기지 않는 범위에서만 성립**한다.

### 반응형 UI

**규칙 1. Canvas Scaler 설정**
모든 씬의 Canvas는 아래 값으로 통일한다.

| 항목 | 값 |
|------|-----|
| Scale Mode | Scale With Screen Size |
| Reference Resolution | 1080 × 1920 |
| Match Width Or Height | 0 (가로 너비 기준) |

Match Width Or Height=0은 가로 너비를 기준으로 스케일링한다.
세로가 긴 기기(21:9 등)에서는 캔버스 논리 높이가 기준보다 자연스럽게 늘어나는 방식으로 대응한다.

**규칙 2. 앵커 기반 배치 원칙**
모든 UI 요소는 고정 픽셀 크기 대신 앵커 비율 기반으로 배치한다.
sizeDelta, offsetMin, offsetMax 등 고정 픽셀값 사용 금지.

앵커(Anchor)란 부모 오브젝트를 기준으로 자식 오브젝트의 위치와 크기를 비율로 지정하는 방식이다.
화면 크기가 달라져도 비율이 유지되므로 어떤 해상도에서도 레이아웃이 일관되게 표시된다.

Layout Group 내부 반응형 패턴:
GridLayoutGroup의 CellSize는 고정 픽셀값이므로 사용하지 않는다.
대신 VerticalLayoutGroup + HorizontalLayoutGroup 중첩 구조를 사용하고,
Control Child Size + Child Force Expand를 활성화하면 CellSize 없이
가용 공간을 자동으로 균등 분배한다.

**규칙 3. Filled/Simple 이미지 자식 앵커 규칙**
Image.Type.Filled 또는 Simple 타입 이미지 안에 자식 이미지가 있는 경우,
자식 이미지도 부모와 같은 비율로 앵커를 설정해야 한다.
고정 offsetMin/offsetMax를 사용하면 해상도마다 자식 이미지의 크기와 위치가 달라진다.

예: 게이지 바(부모, Filled) 안에 fill 이미지(자식)가 있을 때,
fill 이미지의 앵커를 0.14~0.86처럼 비율로 설정해야 모든 해상도에서 동일하게 표시된다.

### Safe Area

**규칙 4. SafeArea 컨테이너 구조**
노치, 펀치홀, 하단 홈바가 있는 기기에서 UI가 가려지지 않도록 모든 씬에 SafeAreaContainer를 배치한다.
SafeAreaContainer에는 SafeAreaFitter 컴포넌트를 부착하여 Safe Area 범위에 맞게 자동으로 조정한다.

```
[UI] Canvas
  ├─ Background               ← 전체화면 배경 등 Safe Area 적용이 불필요한 요소
  └─ SafeAreaContainer        ← SafeAreaFitter 컴포넌트 부착
       └─ (모든 실제 UI 요소)  ← 팝업, HUD, 버튼 등 전부 이 안에 배치
```

- 실제 UI 요소(팝업, HUD 등)는 전부 SafeAreaContainer 안에 배치한다.
- 전체화면을 채워야 하는 배경 요소는 SafeAreaContainer 밖(Canvas 직속)에 배치한다.
- 독립 Canvas를 가진 UI(ToastUI 등)는 해당 Canvas에도 SafeAreaFitter를 적용한다.
- **반투명 배경 오버레이(BlockingOverlay)도 전체화면 배경과 동일하게 SafeAreaContainer 밖(UIManager Canvas 직속)에 두어야 한다.**
  팝업 컴포넌트가 직접 소유하지 않고, `UIManager.ShowBlockingOverlay()` / `HideBlockingOverlay()`를 통해 제어한다.
  (각 팝업이 SafeAreaContainer 안에 개별 오버레이를 소유하면 노치/홈바 영역이 가려지지 않는 구조적 문제가 발생하므로, UIManager가 단일 소유한다.)

**전체화면 배경 오브젝트 구현 방법**

배경 오브젝트를 Canvas 직속에 올바르게 배치하기 위해 아래 4가지를 반드시 지킨다.

1. **RectTransform 설정**: anchorMin=(0,0), anchorMax=(1,1), offsetMin=offsetMax=(0,0) → Canvas 전체를 빈틈없이 채움
2. **raycastTarget=false**: Image 컴포넌트의 Raycast Target을 반드시 꺼야 한다. 켜두면 배경이 터치 이벤트를 모두 가로채 하위 UI 버튼이 눌리지 않는다.
3. **Hierarchy 순서**: 배경 오브젝트를 SafeAreaContainer보다 위(앞)에 배치한다. Unity UI는 Hierarchy 위쪽 오브젝트를 먼저(뒤에) 그리므로, 배경이 SafeAreaContainer 아래에 있으면 모든 UI를 가린다.
4. **기존 Image 처리**: SafeAreaContainer 안에 있던 오브젝트에 배경 역할의 Image가 붙어 있었다면, 별도 배경 오브젝트를 생성한 뒤 기존 Image는 삭제 대신 `enabled=false`로 비활성화한다. 실기 테스트 통과 후 최종 삭제한다.

### UI 숨김/표시

**규칙 5. CanvasGroup 숨김/표시 패턴**
UI 요소를 숨길 때 SetActive(false) 대신 CanvasGroup을 사용한다.

| 상태 | alpha | blocksRaycasts | interactable |
|------|-------|----------------|--------------|
| 숨김 | 0 | false | false |
| 표시 | 1 | true | true |

SetActive(false)를 사용하면 두 가지 문제가 발생한다.
- Layout Group(버튼들이 나란히 정렬되는 구조) 안에서 해당 요소가 차지하던 공간이 사라져 나머지 요소들이 이동한다.
- 오브젝트 내부 로직(Update 등)이 함께 멈춘다. DontDestroyOnLoad 오브젝트(ToastUI 등)에서 이 방식을 쓰면 이후 동작이 전혀 일어나지 않는다.

**DOTween / AnimatedPanel 사용 시 추가 주의사항**:
- DOTween 애니메이션이 진행 중인 오브젝트를 SetActive(false)로 비활성화하면 Tween 시퀀스가 강제 중단되고, 이후 Show() 호출 시 초기화 타이밍이 꼬일 수 있다.
- `AnimatedPanel` 컴포넌트가 붙은 오브젝트는 **항상 active 상태로 유지**한다. `EnsureInitialized()`에서 CanvasGroup을 `alpha=0 / blocksRaycasts=false / interactable=false`로 초기 설정하여 시각적으로 숨긴다.
- 배경 오버레이(`_backgroundOverlay`)도 GameObject는 항상 active 상태 유지. Show() 시 `alpha=1 / blocksRaycasts=true / interactable=true`, Hide() 시 `alpha=0 / false / false`로 즉시 전환한다.

**반투명 배경 오버레이(BlockingOverlay) 단일 소유 패턴**:
- 반투명 배경 오버레이는 **UIManager가 단일 소유**한다. 개별 팝업이 자체 오버레이를 들고 있지 않으며, `UIManager.ShowBlockingOverlay(onTap)` / `UIManager.HideBlockingOverlay()`로만 제어한다.
- 두 가지 모드로 구분한다.
  - **Modal 모드** — `ShowBlockingOverlay()` (콜백 없음): 뒤쪽 입력만 차단한다. 오버레이를 터치해도 닫히지 않는다. (ConfirmPopup, AnonymousWarningPopup, RematchRequestPopup)
  - **Popup 모드** — `ShowBlockingOverlay(() => Close())` (콜백 있음): 오버레이를 터치하면 등록된 콜백(팝업 닫기)이 실행된다. (InGameSettingsUI, BuildingPlacementUI, 생산/건물 패널)
- 팝업이 중첩될 수 있으므로 UIManager는 **참조 카운터**로 표시 횟수를 누적 관리한다. `HideBlockingOverlay()`가 호출되어 카운터가 0이 될 때에만 실제로 숨겨진다.
- 호출은 항상 null-safe 패턴 `UIManager.Instance?.ShowBlockingOverlay(...)`를 사용한다 (씬 직접 진입 시 Instance가 null일 수 있음).
- **팝업 Hide와 오버레이 Hide는 항상 짝을 이룬다.** 조준 모드 진입 등을 위해 팝업만 숨기는 경로에서도 오버레이를 그대로 두지 말고 `HideBlockingOverlay()`로 함께 내린다. 반대로 조준 완료/취소 처리가 `Close()`를 거치지 않고 끝나는 경로는, `Close()`가 대신 반납해 주던 참조 카운터를 해당 경로에서 직접 `HideBlockingOverlay()`를 호출해 반납해야 한다. (동일 결함이 스킬 패널·랠리포인트 두 곳에서 반복 발생했던 사례 — `_Tasks/2026-08-08/13_33_rally-point-blocking-overlay-bug/`)

### 폰트

**규칙 6. 기본 폰트**
TextMeshPro 텍스트 컴포넌트에 사용하는 폰트는 아래 두 가지다.

| 폰트 | 경로 | 용도 |
|------|------|------|
| Maplestory Light SDF | `Assets/_Project/Fonts/Maplestory Light SDF.asset` | 기본 폰트 (일반 본문, 라벨, 수치 등) |
| Maplestory Bold SDF | `Assets/_Project/Fonts/Maplestory Bold SDF.asset` | 강조 폰트 (헤더, 버튼 등 굵은 표현 필요 시) |

기본값은 Maplestory Light SDF이며, 강조가 필요한 경우 Bold SDF를 사용한다.
에디터 스크립트로 UI를 생성할 때도 폰트 에셋을 명시적으로 설정해야 한다.
이 두 폰트 외의 폰트는 사용하지 않는다.

### 골드 부족 UI

**규칙 7. 비용 텍스트 색상**
보유 골드가 해당 항목(유닛, 건물)의 비용보다 적으면 빨간색, 충분하면 흰색으로 표시한다.
골드가 변경될 때마다 자동으로 재평가한다.
팝업이 닫히면 흰색으로 초기화한다.

골드와 비용을 비교해서 색상을 결정하는 로직은 각 UI에서 동일하게 적용되어야 하며,
이 규칙을 따르는 개별 섹션에서는 해당 규칙을 별도로 기술하지 않고 이 규칙을 참조한다.

### 팝업

**규칙 8. 팝업 타입 구분**
모든 팝업은 아래 두 가지 타입 중 하나로 반드시 분류한다.
새로운 팝업을 제작할 때 어떤 타입인지 명확히 결정하고 구현해야 한다.

| 타입 | 설명 | 배경 탭 닫기 |
|------|------|-------------|
| 팝업 (Popup) | 정보 확인 또는 조작 패널 | 가능 |
| 모달 (Modal) | 사용자의 명시적 응답이 필요한 팝업 | 불가 |

> **[🔴 2026-09-16 개정 — 모달 정의 확장]** 종전 모달 설명은 *"사용자의 명시적 Y/N 선택이 필요한 팝업"* 이었다. **버튼이 1개뿐인 알림 팝업(규칙 D-5)이 위 두 타입 어디에도 들어가지 못한다**는 것이 확인되어 정의를 넓혔다 — 버튼이 하나라 「Y/N 선택」이 아니고, 그렇다고 팝업 (Popup)으로 분류하면 **배경 탭으로 닫혀** 아무 선택지도 없는 화면만 남는다. 🔴 **넓힌 것은 「응답의 선택지가 몇 개인가」뿐이고 판정 기준 자체는 바뀌지 않았다** — *화면을 진행시키려면 사용자가 팝업 안에서 무언가를 눌러야 하는가*, 그것이 여전히 모달의 기준이다. 따라서 **이미 모달로 분류돼 있던 팝업의 타입은 하나도 바뀌지 않는다.**

현재 예시:
- 팝업: 생산 패널, 건물 배치 패널, 인게임 설정 메뉴
- 모달: ConfirmPopup (포기 확인 등), 맵 준비 실패 UI (멀티 최초 경기 · 싱글 최초 경기), 재경기 요청, **알림 팝업** (규칙 D-5 — 재경기 맵 준비 실패 알림(규칙 M-3·M-4)과 재경기 요청자 이탈 알림(규칙 D-6)이 이 팝업을 쓴다)

**규칙 9. 팝업 닫기 — 배경 탭**
팝업(Popup) 타입은 배경을 탭하면 닫힌다.
모달(Modal) 타입은 배경 탭이 비활성화되며, 반드시 확인/취소 버튼으로만 닫힌다.

> **[🔴 2026-09-16 보강 — 위 두 줄은 원문 그대로다]** 규칙 8 이 모달의 정의를 「명시적 응답」으로 넓히면서 **버튼이 1개인 모달**(알림 팝업 — 규칙 D-5)이 생겼다. 위 둘째 줄의 *"확인/취소 버튼"* 은 **버튼이 반드시 2개라는 뜻이 아니라 「배경이 아니라 팝업 안의 버튼으로만 닫힌다」는 뜻**으로 읽는다. 🔴 **배경 탭 불가라는 규정 자체는 바뀌지 않았다.**

**규칙 10. 팝업 중첩**
팝업이 중첩되어 열릴 수 있으며 다음 규칙을 따른다.
- 중첩 팝업이 열리면 하위 팝업은 즉시 입력이 차단된다.
- 닫기 순서는 LIFO (마지막에 열린 팝업부터 순서대로 닫힌다).
- 배경(Background)은 하나의 공유 배경을 사용한다.

**규칙 11. 건물 팝업 — 대상 건물 파괴 시 자동 닫힘 (2026-08-08 신설)**
건물을 대상으로 열리는 모든 건물 패널(생산/건물액션/스킬/연구 — 공통 베이스 `BuildingPanelBase`)은, **현재 표시(또는 스킬 조준) 중인 그 건물이 파괴되면 즉시 닫혀야 한다.** 파괴된 건물의 패널·조준 UI가 화면에 남는 유령 상태를 허용하지 않는다.

- 판정은 팝업의 가시성(`IsOpen`)이 아니라 **현재 대상 건물의 Id 일치**로 한다. 스킬 조준 모드에서는 패널 팝업이 숨겨져(`IsOpen=false`) 가시성만으로는 조준 중 케이스를 놓치기 때문이다.
- 닫힘은 각 패널의 정리 훅(`OnBeforeClose`)을 반드시 경유해, 스킬 조준 취소·랠리 마커 숨김 등 패널별 정리가 함께 실행되도록 한다.
- 파괴 인지는 서버 권위 사망 이벤트(`GameEvents.OnBuildingDied`)를 기준으로 하며, 멀티플레이 클라이언트에서도 동일 이벤트가 재발행되어 싱글/호스트/순수 클라 모두 동일하게 동작한다.
- 게임 상태 판정(발동·철거 등)은 서버 재검증이 권위를 가지며, 본 규칙은 **UI 원복만** 담당한다.

### 로딩 인디케이터 (LoadingIndicator)

**규칙 L-1. LoadingIndicator는 UIManager.ShowLoading()으로만 제어**
- `UIManager.Instance?.ShowLoading(true, "메시지")` / `ShowLoading(false)`
- 직접 LoadingIndicator GameObject를 활성/비활성 금지.

**규칙 L-2. 씬 전환이나 비동기 작업 시작 시 반드시 ShowLoading(true) 호출**
- 해당하는 상황: 씬 전환(LoginScene/LobbyScene/GameScene), 로그아웃, 로비 복귀, 재경기.
- 게임 포기(싱글/멀티 모두)는 씬 전환 없이 같은 씬 안에서 GameEndUI만 표시하므로 해당 없음.

**규칙 L-3. ShowLoading(false) 책임은 목적지 씬 Bootstrapper**
- 씬을 시작하는 호출부는 ShowLoading(true)만 담당한다.
- ShowLoading(false)는 각 씬의 초기화 완료 시점에 호출한다.
  - Login 씬: LoginBootstrapper(ShowLoginSelect / 자동 로그인 분기).
  - Lobby 씬: LobbyRootView.Start() 완료 시점.
  - Game 씬: GameBootstrapper.LoadMap() 완료 시점.
- 어디서 켰든 목적지 씬이 준비되면 자동으로 꺼지므로 ShowLoading(false) 누락 버그를 방지한다.
- 예외 경로(비동기 작업 실패로 씬 전환이 무산된 경우)에서는 켠 호출부가 직접 ShowLoading(false)로 끈다.

**규칙 L-4. null-safe 패턴 필수**
- `UIManager.Instance?.ShowLoading(...)` — Lobby/Game 씬 단독 실행 시 Instance가 null일 수 있으므로 null-safe를 보장한다.

> Infrastructure(NetworkBehaviour)에서 발생하는 씬 전환(재경기 등)은 UIManager(Presentation)를 직접 참조하지 않고
> GameEvents(Application)를 경유해 Presentation(GameEndUI)이 ShowLoading을 호출하도록 한다(레이어 방향 보호).

### 무작위 맵 준비 실패 UI

**규칙 M-1. 내부 정보 비공개**

맵 준비 실패 팝업에는 seed, 맵 유형, `MapVersion`, 내부 error code를 표시하지 않는다. 이 정보는 로그에만 기록한다.

**규칙 M-2. 멀티플레이 최초 경기 실패**

- loading UI를 닫고 기존 로비와 network connection을 유지한다.
- 모달 (Modal) 타입이며, 문구는 `맵 준비에 실패했습니다`다.
- action은 `Retry`와 `Leave Match`다.
- 어느 플레이어든 Retry를 누를 수 있고 Host에 재시도 요청을 보낸다. 중복 요청은 같은 준비 상태에서 한 번만 처리한다.
- Retry는 기존 package 재전송이 아니라 새 root seed부터 맵 관련 추첨·생성·전송을 다시 시작한다.

**규칙 M-3. 멀티플레이 재경기 맵 준비 실패**

- 이전 `MapDefinition`과 결과 화면을 유지하고 rematch pending 상태를 초기화한다.
- 자동 로비 복귀 countdown을 전체 길이로 다시 시작한다.
- **결과 화면의 기존 선택지를 모두 복원한다.**
  > **[🔴 2026-09-14 개정]** 종전 문구는 *"`SameMap`, `NewMap`, `Lobby` action을 모두 복원한다"* 였다. 재경기 맵 조건 선택(`SameMap`/`NewMap`)이 없어졌으므로(`GameSystemRules_RandomMap.md` 규칙 14 의 개정 블록이 단일 소스) **복원 대상을 「결과 화면의 기존 선택지」로 바꿨다.** 🔴 **규정의 뜻은 바뀌지 않았다 — 실패해도 화면을 실패 이전 상태로 되돌린다는 것이 이 규칙이며, 바뀐 것은 그 선택지가 무엇인지뿐이다.** 규칙 제목의 `NewMap` 표기도 함께 걷어냈다.
- ⚠️ **팝업 여부 미정 — 구현 시 확정한다.** 위 세 줄은 결과 화면을 되돌리는 것만 규정할 뿐, **실패를 알리는 별도 팝업이 뜨는지 결과 화면만 복원되는지는 정해진 바 없다.** 이 미정은 **규칙 M-4 의 재경기 새 맵 실패에도 그대로 적용된다**(둘이 같은 문제다). **팝업으로 확정되면 공통 UI 규칙 8(팝업 타입 구분)에 따라 팝업/모달 타입을 함께 정해야 한다.**
  > **[🔴 2026-09-16 확정 — 위 ⚠️ 미정 표시는 원문 그대로 둔다]** 위 「팝업 여부 미정」을 **닫는다. 실패를 알리는 별도 팝업을 띄운다** — 결과 화면만 복원하고 끝내지 않는다. 팝업은 **알림 팝업**(구조·닫기 규정은 규칙 D-5)이며 타입은 규칙 8 의 **모달 (Modal)** 이라 **배경 탭으로 닫히지 않는다.** 같은 미정을 공유하던 **규칙 M-4 의 재경기 맵 준비 실패도 이 확정을 그대로 따른다**(둘이 같은 문제라는 위 서술 그대로다). ⚠️ **표시 문구와 버튼 라벨은 여전히 미정 — 구현 시 확정한다.** 이번에 정해진 것은 **팝업이 뜨는가와 그 타입뿐**이며, 무엇이라고 쓸지는 정해진 바 없다.
  > 🔴 **위 두 번째 불릿(자동 로비 복귀 countdown 을 전체 길이로 다시 시작)은 이번 확정으로 바뀌지 않는다.** 상대 이탈로 인한 countdown 재시작은 **시점도 길이도 다르며** 그 규정은 규칙 D-4 가 따로 가진다.
  > **[🔴 2026-09-22 (2차) 개정 — 실패를 알리는 수단을 「알림 팝업」에서 「상태 줄」로 바꾼다. 🔴 위 ⚠️ 미정 표시와 2026-09-16 확정 블록은 원문 그대로 둔다(`.claude/MEMORY.md` B-7)]**
  > **바뀌는 것은 「무엇으로 알리는가」 하나뿐이다.** 🔴 **이 규칙의 본문 세 불릿(맵 정의·결과 화면 유지 / 카운트다운 전체 길이 재시작 / 선택지 복원)은 한 글자도 바뀌지 않는다.**
  >
  > **알리는 자리** — **알림 팝업(규칙 D-5)을 띄우지 않고, 결과 화면의 상태 줄**(= 규칙 D-1 이 쓰는 타이머 텍스트 자리, 규칙 D-7 이 재경기 상태를 얹은 그 자리)**에 문구를 띄운다.**
  >
  > | 구분 | 2026-09-16 확정 | 이번 개정 |
  > |------|----------------|----------|
  > | 알리는 수단 | 알림 팝업(규칙 D-5) · 모달(규칙 8) | **상태 줄**(규칙 D-1 의 자리 · 규칙 D-7 의 네 번째 상태) |
  > | 표시 문구 | ⚠️ 미정 | ✅ **확정** — `재경기를 시작할 수 없습니다. {0}초 후 로비로 돌아갑니다.` (`{0}` = 남은 초) |
  > | 버튼 라벨 | ⚠️ 미정 | 🔴 **무효 — 팝업을 쓰지 않으므로 라벨을 가질 버튼이 없다**(아래 「미정 표시 두 개를 어떻게 처리했는가」) |
  > | 카운트다운 | 전체 길이로 재시작 | **그대로** — 이번 개정은 타이머 처리를 건드리지 않는다 |
  > | 「다시하기」 버튼 | 복원 | **그대로**(상대가 살아 있으면 다시 시도할 수 있다) · 「로비로」는 항상 활성(규칙 D-3) |
  >
  > **🔴 개정 사유 3가지**
  > 1. **모달 팝업은 「로비로」 버튼을 가린다.** 모달은 입력을 막으므로 규칙 D-3 이 *「두 버튼이 동시에 꺼지면 사용자가 스스로 화면을 빠져나갈 방법이 없어진다」* 고 막으려던 상황을 만든다. ✅ **2026-09-16 확정이 틀렸던 것이 아니다 — 그때는 규칙 D-3 의 이 조항이 아직 없었다.** 그 조항은 「경기 종료 후 상대 이탈 UI」 절과 함께 자리를 잡았고, **새로 생긴 규칙과 부딪혀서 개정하는 것**이다.
  > 2. **재경기가 안 되는 길이 셋인데 사용자는 셋을 구분할 수 없다** — ① 수락을 서버로 보내지 못했다 ② 맵 준비가 실패했다 ③ 맵 준비 한도가 만료됐다(규칙 D-7). 사용자에게는 전부 **「재경기가 안 됐다」** 하나다. 팝업은 ②에만 붙던 것이라 그대로 두면 **같은 결과인데 ②만 팝업이 뜨고 ①③ 은 조용하다.** 🔴 **같은 결과면 같은 화면**이어야 한다.
  > 3. **상태 줄이 이미 이 화면의 알림 자리다** — 규칙 D-1 이 선례를 세우고 규칙 D-7 이 세 번째 상태를 얹었다. **네 번째 상태를 같은 자리에 두는 것**이 팝업이라는 다른 수단을 하나 더 늘리는 것보다 일관된다.
  >
  > **미정 표시 두 개를 어떻게 처리했는가 (판단과 근거)**
  > - **「표시 문구 미정」은 닫힌다** — 위 표의 문구가 사용자 승인으로 확정됐다.
  > - 🔴 **「버튼 라벨 미정」은 닫지 않고 「이 규칙에서 무효가 됐다」고 적는다.** 「닫혔다」고 쓰면 **라벨이 정해졌다는 뜻이 되어 거짓**이고, 그대로 두면 **아직 정할 것이 남은 것처럼 읽힌다.** 실제로 일어난 일은 **가리킬 대상(버튼)이 없어진 것**이라 둘 다 아니다. ⚠️ **단, 규칙 M-4 가 팝업 확정을 유지하는 동안 그쪽의 버튼 라벨 미정은 살아 있다**(아래 규칙 M-4 의 2026-09-22 (2차) 블록).
  >
  > **상태 줄의 네 상태와 우선순위의 단일 소스는 규칙 D-7** 이며 여기에 옮겨 적지 않는다.
  > ⚠️ **상태: 사용자 확정 · 🔴 실기 검증 0건.** 구현은 game-programmer 가 병렬로 진행 중이다.

**규칙 M-4. 싱글플레이 실패**

- 최초 경기 준비 실패는 모달 (Modal) 타입이며, `Retry`/`Lobby`를 표시한다. ⚠️ **표시 문구 미정 — 구현 시 확정한다.** 멀티 최초 실패(규칙 M-2)의 `맵 준비에 실패했습니다`를 그대로 쓸지 다른 문구를 쓸지는 **정해진 바 없다.** ⚠️ **loading UI 처리 미정 — 구현 시 확정한다.** 규칙 M-2 는 첫 불릿에서 loading UI를 닫는다고 규정하지만 이 규칙에는 그 서술이 없으며, `TechnicalDesignDocument.md` 「복구 상태」 절의 싱글 항목도 같은 자리가 비어 있다. **채워 넣지 않고 미정으로 둔다 — 새 사양 추가이기 때문이다.**
- 재경기 맵 준비 실패는 **결과 화면의 기존 선택지를 복원한다.** ⚠️ **팝업 여부 미정 — 구현 시 확정한다.** 상세와 근거는 위 규칙 M-3 의 같은 미정 표시를 따른다.
  > **[🔴 2026-09-14 개정]** 종전 문구는 *"재경기 새 맵 실패는 결과 화면의 기존 같은 맵/새 맵/로비 선택을 복원한다"* 였다. 규칙 M-3 과 같은 사유이며(`GameSystemRules_RandomMap.md` 규칙 14 의 개정 블록) **뜻은 바뀌지 않았다.** ⚠️ **위 「팝업 여부 미정」 표시는 이번 개정과 무관하며 그대로 남는다** — 무엇을 복원하는지가 바뀌었을 뿐, **실패를 알리는 팝업이 뜨는지는 여전히 정해진 바 없다.**
  > **[🔴 2026-09-16 확정 — 위 ⚠️ 미정 표시는 원문 그대로 둔다]** 위 「팝업 여부 미정」을 **닫는다 — 재경기 맵 준비 실패는 알림 팝업(구조는 규칙 D-5, 타입은 규칙 8 의 모달)으로 알린다.** 근거와 상세는 위 규칙 M-3 의 같은 자리 확정 블록을 따른다(둘이 같은 문제다). ⚠️ **표시 문구와 버튼 라벨은 여전히 미정**이며, **첫 불릿의 최초 경기 실패 「표시 문구 미정」·「loading UI 처리 미정」도 그대로 남는다** — 이번 확정은 그 둘을 건드리지 않았다.
  > 🔴 **이 규칙은 싱글플레이다 — 상대가 없다.** 따라서 「경기 종료 후 상대 이탈 UI」 절의 **이탈 관련 규정(규칙 D-1 · D-2 · D-4 의 이탈 재시작 · D-6)은 이 규칙에 적용되지 않는다.** 이번에 닫힌 미정은 **맵 준비 실패 시 팝업이 뜨는지 하나뿐**이고, 싱글플레이에서 알림 팝업을 쓰는 자리도 **그 실패 알림뿐**이다.

  > **[🔴 2026-09-22 (2차) — 위 규칙 M-3 의 「상태 줄로 알린다」 개정이 이 규칙에도 번지는가: **번지게 하지 않았다.** 🔴 위 블록들은 원문 그대로 둔다]**

  > | ② 실패 경로가 셋인데 구분할 수 없다 | ❌ **적용되지 않는다** — 「수락 전송 실패」도 「맵 준비 한도」도 **상대가 있어야 성립**한다(규칙 D-7). 싱글에는 경로가 하나뿐이다 |
  > | ③ 상태 줄이 이미 알림 자리다 | ⚠️ **자리는 있으나 도달 경로를 확인하지 못했다** — 아래 실측 |
  >
  > **메인 세션 실측(코드 · 이 문서 작업 중 직접 확인)**
  > - **상태 줄 자리 자체는 싱글에도 있다** — 결과 화면과 자동 복귀 카운트다운은 `GameEndUI` 의 **싱글·멀티 공용 경로**이며, 로비 복귀도 싱글 분기를 갖는다.
  > - 🔴 **그러나 싱글 재경기 맵 준비 실패가 그 상태 줄까지 닿는 경로는 찾지 못했다** — 실패 통보 채널이 **네트워크 통보**(`GameEvents.OnNetworkRematchMapFailed`, 발행처는 `NetworkGameEndController`)이고, 싱글 맵 준비는 `GameBootstrapper` 의 맵 준비 경로에서 이뤄지며 실패는 **로그와 폴백 템플릿**으로 처리된다. ⚠️ **「찾지 못했다」이지 「없다고 증명했다」가 아니다.**
  >
  > ⚠️ **그래서 남는 미정 2가지 — 구현 시 확정한다.**
  > 1. **싱글 재경기 맵 준비 실패를 상태 줄로 알릴 것인가**(= 이 개정을 여기까지 번지게 할 것인가).
  > 2. **알린다면 그 실패가 결과 화면까지 닿는 경로를 만들 것인가** — 위 실측대로 현재는 그 경로를 확인할 수 없다.
  >
  > 🔴 **그 결과 지금은 두 규칙이 서로 다른 수단을 갖는다 — M-3 은 상태 줄, M-4 는 팝업이다.** **이것을 그대로 두는 것 자체가 결정이므로 적어 둔다**(종전에는 *「규칙 M-4 의 재경기 맵 준비 실패도 이 확정을 그대로 따른다」* 로 한 덩어리였다). ⚠️ **그 결과 이 규칙의 「표시 문구 미정」·「버튼 라벨 미정」은 둘 다 살아 있다** — 규칙 M-3 에서 문구가 확정되고 버튼 라벨이 무효가 된 것은 **그 규칙에서만** 일어난 일이다.

### 경기 종료 후 상대 이탈 UI

경기가 끝나 결과 화면이 떠 있는 동안 **상대가 게임을 떠난 경우** 화면을 어떻게 바꿀지 규정한다.

**무엇을 왜 정하는가** — 지금은 결과 화면에서 상대가 나가도 그 사실이 화면에 전혀 전달되지 않는다.
그래서 재경기를 요청한 사람은 두 버튼이 모두 꺼진 채 갇혀 있다가, 카운트다운이 만료되면 **이유도 모른 채 로비로 끌려간다.**
이 절은 「상대가 떠났다」는 사실을 화면에 드러내고, 사용자가 언제든 **스스로** 로비로 나갈 수 있게 하는 것을 목표로 한다.

> 이 절의 규칙은 `D-`(Disconnect) 접두사를 쓴다 — 로딩 인디케이터 절의 `L-`, 무작위 맵 준비 실패 절의 `M-` 과 같은 방식이며,
> 「공통 UI 규칙」의 숫자 규칙 번호와 섞이지 않게 하기 위함이다.

> 🔴 **이탈을 무엇으로 판정하는지는 이 문서의 규칙이 아니다.**
> 무반응이 얼마나 이어져야 이탈로 보는지 · 이탈로 판정했을 때 연결을 어떻게 처리하는지 ·
> 사용자가 로비 복귀 버튼으로 나가는 **정상 퇴장**을 상대에게 어떻게 알리는지는 **네트워크 세션 동작 규정의 몫**이며,
> **그 값을 이 문서에 옮겨 적지 않는다** — 사본은 원본이 바뀌는 순간 조용히 거짓이 된다.
> 이 절은 **그 판정 결과를 받아 화면을 어떻게 바꿀지만** 규정한다.
> ⚠️ ~~**가리킬 문서명 미정 — 판정 규정을 어느 문서가 담을지 확정되면 이 자리에 그 문서명을 적는다.**~~
> **[✅ 2026-09-16 확정 — 원문은 취소선으로 남긴다]** 판정 규정의 단일 소스는 **[GameSystemRules_RandomMap.md](GameSystemRules_RandomMap.md) 규칙 17(결과 화면에서의 상대 이탈 — 판정과 통보)** 이다. 무엇을 이탈로 볼 것인가·언제 알릴 것인가는 그 규칙이 정하고, **설정값과 그 자리는 [TechnicalDesignDocument.md](../TechnicalDesignDocument.md) 「결과 화면 이탈 판정·통보 구조」 절**이 단일 소스다. 맵 전송 중 이탈은 같은 문서 **규칙 18**, 씬 재로드 중 이탈이 범위 밖이라는 결정은 **규칙 19** 다.

**규칙 D-1. 상대 이탈 시 결과 화면의 타이머 텍스트를 교체한다**

상대가 이탈한 것으로 판정되면 결과 화면의 **타이머 텍스트를 아래 문구로 교체**한다.

| 상태 | 타이머 텍스트 |
|------|--------------|
| 평시 | 남은 시간만 안내하는 기존 문구 |
| 상대 이탈 | `상대방이 떠났습니다. n초 뒤 로비로 이동합니다.` (`n` = 남은 초) |

별도 팝업을 새로 띄우지 않고 **이미 떠 있는 결과 화면의 타이머 텍스트 자리**를 쓴다.
이탈 사실을 알리는 것과 남은 시간을 알리는 것은 사용자에게 **한 덩어리의 정보**라, 두 자리로 나누면 서로를 가린다.

**규칙 D-2. 상대 이탈 시 재경기 버튼을 비활성화한다**

상대가 이탈한 것으로 판정되면 결과 화면의 **재경기(다시하기) 버튼을 비활성화**한다.
상대가 없으므로 요청해도 받을 사람이 없고, 누를 수 있게 두면 응답이 오지 않는 요청으로 사용자를 다시 기다리게 만든다.

**규칙 D-3. 로비 복귀 버튼은 항상 활성 상태를 유지한다**

결과 화면의 **로비 복귀 버튼은 어떤 상태에서도 비활성화하지 않는다.**
재경기를 요청하고 상대의 응답을 기다리는 동안에도 끄지 않으며, 상대 이탈 판정 뒤에도 켜 둔다
(이탈로 꺼지는 것은 규칙 D-2 의 재경기 버튼뿐이다).

근거: 두 버튼이 동시에 꺼지면 사용자가 **스스로 화면을 빠져나갈 방법이 없어** 카운트다운 만료까지 갇힌다.
로비 복귀는 상대의 상태와 무관하게 언제나 성립하는 선택이므로 끌 이유가 없다.

> **[✅ 2026-09-21 구현 완료 — 위 규칙 본문은 한 글자도 고치지 않고 결과만 덧붙인다]**
> `Presentation/UI/GameEndUI.cs` 의 `SetupRematchButton(bool)` 이 설치하던 리스너에서 **`_backToLobbyButton.interactable = false` 한 줄을 제거**했다(커밋 `d881d23`).
> **잔존 0건 — 그 자리를 `false` 로 되돌리는 동작 코드는 리포지토리 전체에 없다**(주석만 남아 제거 이유를 설명한다. 문서 작업 중 직접 실측).
> **꺼진 상태를 되돌리는 안전망 `RestoreRematchButton()` 의 `_backToLobbyButton.interactable = true` 는 그대로 남겼다** — 켜는 쪽이라 이 규칙과 충돌하지 않는다.
> ⚠️ **이 규칙의 후반부(「상대 이탈 판정 뒤에도 켜 둔다」)는 아직 확인되지 않았다** — 이탈 판정 자체가 미구현(단계 5·6)이라 그 상황이 만들어진 적이 없다.

**규칙 D-4. 자동 로비 복귀 카운트다운 — 기본 60초, 이탈 판정 시 30초로 재시작**

| 시점 | 카운트다운 |
|------|-----------|
| 결과 화면 표시 | 60초 |
| 상대 이탈 판정 | 30초로 **다시 시작** |

- 이탈 판정 시점의 남은 시간이 얼마였든 **30초로 다시 시작**한다. 남은 시간을 그대로 두면 이탈을 인지한 직후에 화면이 사라져 버릴 수 있기 때문이다.
- 카운트다운이 만료되면 로비로 이동하는 동작 자체는 기존 그대로다.
- ⚠️ **맵 준비 실패로 인한 카운트다운 재시작은 이 규칙이 아니라 규칙 M-3 이 규정한다** — 그쪽은 **전체 길이**로 다시 시작하고, 이 규칙의 이탈 재시작은 **30초**다. **재시작 시점도 길이도 서로 다르므로 두 규칙을 섞어 읽지 않는다.**

> **[⚠️ 2026-09-21 — 위 표의 두 행 중 첫 행만 구현됐다. 규칙 본문은 그대로 둔다]**

**규칙 D-5. 알림 팝업 — 타이틀 + 본문 + 버튼 1개, 배경 탭으로 닫히지 않는다**

사용자에게 **선택을 요구하지 않고 사실 하나를 알리기만 하는** 팝업을 신설한다.

| 구성 | 내용 |
|------|------|
| 타이틀 | 한 줄 제목 |
| 본문 | 알릴 내용 |
| 버튼 | **1개** |

- 호출은 `UIManager.ShowAlert` 로 한다. 씬이 팝업을 직접 참조하지 않으며, 호출은 항상 null-safe 패턴 `UIManager.Instance?.ShowAlert(...)` 를 쓴다(로딩 인디케이터의 규칙 L-4 와 같은 이유 — 씬에 직접 진입하면 `Instance` 가 null 일 수 있다).
- 타입은 **모달 (Modal)** 이다(규칙 8). 🔴 **배경을 탭해도 닫히지 않으며 반드시 버튼으로만 닫는다**(규칙 9). 배경 탭으로 닫히면 **상대가 없는 결과 화면만 남아** 사용자가 아무것도 할 수 없는 상태가 되기 때문이다.
- 반투명 배경 오버레이는 개별 팝업이 소유하지 않고 `UIManager` 가 단일 소유한다(규칙 4·5). 이 팝업은 배경 탭으로 닫히지 않으므로 **Modal 모드**(콜백 없는 `ShowBlockingOverlay()`)로 표시한다.
- 이 팝업을 쓰는 자리는 현재 두 곳이다 — **재경기 맵 준비 실패 알림**(규칙 M-3·M-4)과 **재경기 요청자 이탈 알림**(규칙 D-6).

> **[⚠️ 2026-09-21 구현 완료 · 화면에 띄워 본 적은 없다 — 위 규칙 본문은 한 글자도 고치지 않고 결과만 덧붙인다]**
>
> **무엇이 됐나** — 위 「신설한다」는 **새 팝업을 만드는 것이 아니라 기존 `ConfirmPopup` 을 확장하는 방식으로** 충족됐다(사용자 승인. 경위와 근거는 `_Tasks/2026-09-16/06_27_post-game-leave-ui/Plan.md` §3-1 의 확정 블록이 단일 소스다).
> `ConfirmPopup` 에 `_titleText` 필드와 `ShowAlert(title, message, buttonLabel, onClick)` 가 생겼고, `IUIManager` 에 `ShowAlert` 선언 · `UIManager` 에 위임 구현이 추가됐다(커밋 `d881d23`).
> **기존 `ShowConfirm` 의 시그니처와 동작은 바꾸지 않았고 실호출처도 변경 전과 같은 5건이다**(문서 작업 중 직접 실측).

> 🔴 **아직 아무도 이 팝업을 본 적이 없다 — `UIManager.ShowAlert` 의 실호출처가 0건이기 때문이다.** 실제로 띄우는 것은 규칙 D-6(단계 8)과 규칙 M-3·M-4(단계 10)이며 둘 다 미착수다. **「구현됐다」와 「동작이 확인됐다」는 다른 말이고, 이 항목은 앞쪽까지만 참이다.**
> ✅ **확인된 것은 회귀가 없다는 쪽이다** — 제목 없는 기존 확인/취소 팝업 2건(앱 종료 확인 · 이메일 인증 취소)이 실기에서 종전과 같이 표시됐다. 나머지 1건(`ProfileView` 의 알림 표시)은 임의 재현이 어려워 **미확인**이나, `ShowConfirm(cancelLabel: string.Empty)` 로 호출해 **버튼 2개 구조가 확인된 2건과 같고** 버튼 배치를 담는 ButtonRow 가 무변경이다.

**규칙 D-6. 재경기 요청에 응답하기 전에 요청자가 이탈한 경우**

재경기 요청을 받아 요청 팝업이 떠 있는 상태에서 **응답하기 전에 요청자가 이탈**하면 다음 순서로 처리한다.

2. **알림 팝업(규칙 D-5)을 띄운다.**

   | 구성 | 값 |
   |------|-----|
   | 타이틀 | `알림` |
   | 본문 | `상대방이 떠났습니다.` |
   | 버튼 | `로비로` — 누르면 로비로 이동한다 |

버튼을 누르지 않아도 카운트다운이 만료되면 로비로 이동하므로(규칙 D-4), 사용자가 팝업을 방치해도 화면에 갇히지 않는다.

### 판단 기준 — 이 한 문장이 위 표를 결정한다

> **「사람을 기다리면 타이머가 돈다 / 시스템을 기다리면 타이머가 멈춘다」**

요청한 쪽은 **상대가 수락할지**(사람)를 기다린다. 상대가 요청 팝업을 띄워 둔 채 아무것도 누르지 않으면 **영영 답이 없으므로** 타이머가 돌아야 한다.
수락이 접수된 뒤에는 **서버가 맵을 만드는 것**(시스템)을 기다린다. 사람의 응답을 더 기다리는 것이 아니므로 타이머를 멈춘다.
🔴 **앞으로 이 화면에 새 대기 상태가 생기면 이 문장으로 판단한다.**

### 🔴 양쪽이 「수락 접수」 상태로 들어가는 경로가 서로 다르다 — 이것이 이 규칙의 핵심이다

| 누구 | 무엇을 계기로 바꾸는가 | 왜 그래야 하는가 |
|------|---------------------|----------------|
| **수락한 쪽** | **수락 버튼을 누른 즉시 자기 화면에서** 바꾼다. **서버 응답을 기다리지 않는다** | 수락을 서버로 보내는 경로가 `ServerRpc` 라 **수락자가 Client 이고 Host 가 이미 떠났으면 그 호출이 증발한다.** 서버 응답을 기다리게 만들면 그 경우 **화면이 영영 바뀌지 않아 역할에 따라 화면이 달라진다** |
| **요청한 쪽** | 서버가 **수락을 접수했다는 통보(`ClientRpc`)를 받으면** 바꾼다 | 요청자는 상대가 수락한 사실을 알 길이 없다. 그래서 **수락이 됐는데도 자기 타이머가 만료되면 혼자 로비로 나가 버린다.** 이 통보가 그 구멍을 메운다 |

🔴 **두 경로 모두 「플레이어는 자신이 Host 인지 Client 인지 알 수 없다」는 최상위 원칙을 지키기 위한 것이다.** 그 원칙의 단일 소스는 [TechnicalDesignDocument.md](../TechnicalDesignDocument.md) 「🔴 최상위 원칙 — 플레이어는 자신이 Host 인지 Client 인지 알 수 없다」 절이며 **여기에 옮겨 적지 않는다.**

### 맵 준비 한도 — 상태 줄을 되돌리기만 하는 시계

- **값은 `NetworkMapTransfer.TransferTimeoutSeconds` 를 참조한다. 🔴 숫자를 이 문서에 옮겨 적지 않는다** — 그 상수의 주석이 *「규칙 16 이 정한 값이라 이것은 잠정값이 아니다」* 라고 밝혀 **그 상수가 단일 소스**임을 이미 적고 있다.
- 🔴 **이 시계는 아무것도 판정하지 않는다 — 승패도, 이탈도, 연결 종료도 하지 않는다. 하는 일은 상태 줄 문구를 되돌리는 것 하나뿐이다.** 🔴 **나중에 이 시계에 다른 판정을 얹지 않는다.**
- **멈추는 자리는 다음 넷이 전부다** — ① 맵 준비 실패 통보 수신 ② 재경기 시작 통보 수신 ③ 상대 이탈 판정 ④ 결과 화면이 닫힐 때.
- ⚠️ **규칙 16 의 10초와 같은 값이지만 같은 구간이 아니다.** `GameSystemRules_RandomMap.md` 규칙 16 의 「timeout, 재전송, 실패 복구」 절은 **응답 대기 한 번이 10초이고 재전송 1회를 포함하면 최대 두 번**이라고 정한다. 따라서 **이 한도가 맵 준비 실패보다 먼저 만료될 수 있다.** 그래도 문제가 되지 않는 이유는 위 두 번째 불릿이다 — **이 시계는 판정하지 않으므로** 화면만 평시 문구로 돌아가고, 뒤늦게 도착한 통보는 위 표의 해당 행대로 처리한다.

### ⚠️ 카운트다운을 건드리는 규칙이 셋이다 — 섞어 읽지 않는다

### 🔴 이 규칙이 전제하는 네트워크 쪽 동작 (이 문서의 규칙이 아니다)

이 절 머리말대로 **이탈 판정과 통보는 이 문서의 몫이 아니다.** 아래는 **이 규칙이 성립하려면 네트워크 쪽에 있어야 하는 것**이며, 값이나 절차를 여기에 옮겨 적지 않는다.

- **수락 접수를 양쪽에 알리는 통보가 발행된다** — 위 표의 「요청한 쪽」 경로가 이것에 의존한다.
- 🔴 **「진행 중이던 맵 준비를 취소한다」는 요구는 이 규칙에 없다** — 이탈 판정이 연결을 끊을 때 전송 객체가 함께 사라진다는 실측이 있기 때문이다. **그 실측과 위 세 항목의 단일 소스는 [Plan.md](../_Tasks/2026-09-16/06_27_post-game-leave-ui/Plan.md) §13-3 의 2026-09-22 확정 블록**이다.

### 🔴 일부러 채택하지 않은 안

- **로딩 화면을 띄우는 안** — 로딩 화면은 **화면 전체를 덮고 입력을 차단**하므로 **로비 복귀 버튼을 누를 수 없게 되어 규칙 D-3 이 막으려던 상황(사용자가 스스로 화면을 빠져나갈 방법이 없어지는 것)을 그대로 만든다.** 게다가 로딩 화면은 「곧 된다」는 신호인데 맵 준비가 실패할 수도 있으므로 **거짓 신호**가 된다. ⚠️ **재경기가 실제로 성사된 뒤의 로딩은 자리가 맞으므로 그대로 둔다**(위 표의 마지막 행).
- **그 구간에 버튼을 아예 못 누르게 막는 안** · **수락·요청 실패를 알리는 별도 팝업을 띄우는 안** — 채택하지 않았다. **세 안의 기각 사유 전문의 단일 소스는 [Plan.md](../_Tasks/2026-09-16/06_27_post-game-leave-ui/Plan.md) §13-3 의 2026-09-22 확정 블록**이며 여기에 옮겨 적지 않는다. 다만 **팝업 안의 기각 사유 한 줄은 이 문서가 이미 갖고 있다** — 규칙 D-1 의 *「별도 팝업을 새로 띄우지 않는다」*.

### 🔴 왜 새 규칙으로 세웠는가 (기존 D-1·D-2·D-4 의 확장으로 적지 않은 이유)

1. **한 덩어리의 사양이 세 규칙으로 흩어진다.** 이 사양은 **상태 줄 · 타이머 · 진입 경로**가 서로를 근거로 삼는 하나의 규정이다. 규칙 D-1(문구) · D-4(타이머) · D-2(버튼)에 나눠 붙이면 **읽는 사람이 세 자리를 모아야 뜻이 완성되고, 세 자리 중 하나만 고쳐도 조용히 어긋난다.**
2. **기존 규칙이 규정하지 않는 동작이 새로 생긴다.** 규칙 D-4 가 아는 타이머 조작은 **재시작뿐**이고 이 사양은 **정지**를 도입한다. 규칙 D-1 이 아는 상태는 **평시와 이탈 둘뿐**이고 이 사양은 **세 번째 상태**를 더한다. 새 동작을 기존 규칙의 각주로 다는 것보다 **자기 번호를 주고 기존 규칙과의 관계를 명시하는 쪽**이 오독이 적다.
3. **계기가 다르다.** 규칙 D-1·D-2·D-4 는 전부 **상대 이탈 판정**이 계기이지만, 이 규칙의 계기는 **재경기 수락 접수**다. 같은 화면을 건드린다는 이유로 같은 규칙에 넣으면 **규칙 D-4 가 경고한 「섞어 읽기」를 규칙 문서가 스스로 유발한다.**
4. **규칙 번호는 재배열하지 않는다.** `D-7`·`D-8` 은 기존 번호의 뒤에 덧붙는 것이라 **기존 번호를 참조하는 코드 주석과 과거 Task 문서의 연결이 하나도 끊기지 않는다.**

> **[🔴 2026-09-22 (2차) 추가 확정 3건 — 위 규칙 D-7 본문·표·소절은 한 글자도 지우지 않고 덧붙인다(`.claude/MEMORY.md` B-7). 문서 편집은 세션이 날을 넘겨 2026-09-24 에 했다.]**
>
> **① 「수락 접수」는 재경기가 성사되는 두 경로를 **모두** 가리킨다.**
> 재경기가 성사되는 길은 둘이다(메인 세션 실측 · 이 문서 작업 중 내가 재측정).
>
> | 경로 | 어디서 | 수락 접수 통보를 발행하는가 |
> |------|--------|--------------------------|
> | 한쪽이 요청 → 다른 쪽이 **수락** | `AcceptRematchServerRpc` | ✅ **같은 통보를 발행한다** |
> | 양쪽이 각자 「다시하기」를 눌러 **상호 동의** | `RequestRematchServerRpc` 의 「상대도 이미 요청 → 상호 동의」 분기 | ✅ **같은 통보를 발행한다** |
>
> 🔴 **그래서 위 표의 「수락이 접수된 시점」은 두 경로 모두를 뜻한다.** 판단 근거: **서버가 양측 신호를 다 받은 시점이 곧 「성사 확정」**이며, 한 경로에만 붙이면 **같은 「맵 준비 중」인데 경로에 따라 상태 줄이 뜨기도 하고 안 뜨기도 하고 타이머도 한쪽에서만 멈춘다** — 그것이 곧 「역할·경로에 따라 화면이 달라지는 것」이다.

> **② 상태 줄의 네 번째 상태 — 「재경기 실패」와 우선순위**
> 상태 줄이 가질 수 있는 상태는 이제 **넷**이다 — **평시 / 재경기 준비 중 / 재경기 실패 / 상대 이탈.**
>
> | 상태 | 문구 |
> |------|------|
> | 재경기 실패 | `재경기를 시작할 수 없습니다. {0}초 후 로비로 돌아갑니다.` (`{0}` = 남은 초) |
>
> - **이 상태로 들어가는 계기는 셋이며 화면은 하나다** — ① 수락을 서버로 보내지 못했다 ② 맵 준비 실패 통보를 받았다 ③ 맵 준비 한도가 만료됐다. 🔴 **사용자에게는 전부 「재경기가 안 됐다」 하나이므로 같은 문구를 쓴다.** (①은 수락자 쪽에서 ③으로 드러난다.)

> - 🔴 **우선순위는 「이탈 > 실패 > 평시」다.** 실패보다 **이탈 판정이 나중에 오고 더 중요한 사실**이므로 **이탈 문구가 실패 문구를 덮는다**(실패 통보는 맵 준비 한도 안에서 오고, 이탈 판정은 그보다 늦다). 그 반대는 성립하지 않는다.

> **③ 🔴 맵 준비 한도의 길이 정정 — 「한 창」이 아니라 「창의 개수만큼」이다**
> 위 「맵 준비 한도」 소절의 ⚠️ 마지막 불릿은 *「한 창만 쓰므로 맵 준비 실패보다 먼저 만료될 수 있다」* 고 적었다. **그 지적이 받아들여져 사양이 정정됐다** — 한도는 **`NetworkMapTransfer.TransferTimeoutSeconds * (NetworkMapTransfer.MaxResendCount + 1)`**, 즉 **한 창의 길이 × 창의 개수(최초 전송 1회 + 재전송 상한)** 다. **여전히 숫자 리터럴을 쓰지 않는다**(메인 세션이 코드로 확인 · 이 문서 작업 중 내가 재측정 — `GameEndUI` 의 한도 코루틴이 두 상수의 곱을 쓴다).
> - ✅ **정정 덕에 Host 와 Client 의 대기 시간이 맞아떨어진다** — **Host 는 timeout + 재전송 1회로 실패를 확정**하고 **Client 는 같은 길이의 한도가 만료**되므로, 두 쪽이 **거의 같은 시점에 같은 화면**이 된다.
> - 🔴 **위 원문 불릿은 지우지 않았다** — 「한 창만 쓴다」는 **정정 전 사양에 대한 기록**으로 읽고, **현재 사양의 단일 소스는 이 ③ 항목**이다.
> - ⚠️ **이 시계가 아무것도 판정하지 않는다는 규정은 그대로다.** 바뀐 것은 **길이**와, 만료 시 **되돌아가는 문구가 평시 문구가 아니라 실패 문구**라는 것뿐이다.

### 팝업 열기/닫기

**규칙 1. 팝업 열기**

유닛 버튼을 0.5초 이상 누르면 해당 유닛의 자동 생산을 토글한다.

**규칙 5. 자동 생산 중인 유닛 탭**
이미 자동 생산 중인 유닛 타입을 탭하면 추가 등록 없이 자동 생산 토글(해제)로 처리한다.

---

### 큐 구조

**규칙 6. 슬롯 구성**
슬롯은 3개다. 슬롯0은 현재 생산 중, 슬롯1은 대기 1순위, 슬롯2는 대기 2순위다.
슬롯에 표시되지 않는 자동 순환 대기 항목이 그 뒤에 추가로 쌓일 수 있다.

**규칙 7. 큐 상한 계산**
큐 상한(3개)은 현재 생산 중 1개 + 골드가 이미 차감된 대기 항목 수의 합산으로 계산한다.
골드가 차감되지 않은 자동 대기 항목은 합산에서 제외한다.

**규칙 8. 슬롯 클릭 취소**
슬롯을 직접 클릭하면 해당 슬롯의 생산을 취소한다.

---

### 골드 차감 시점

**규칙 9. 수동 항목**
수동으로 등록한 항목은 등록 즉시 골드가 차감된다.

**규칙 10. 자동 항목**
자동으로 등록한 항목은 슬롯1 또는 슬롯2에 표시되는 시점에 골드가 차감된다.
슬롯 뒤에서 대기 중인 자동 항목은 골드가 차감되지 않은 상태다.

---

### 생산 등록 검증 순서

**규칙 11. 검증 우선순위**
수동 생산 등록 시 검증 순서는 큐 상한 초과 → 골드 부족 → 인구 초과다.
이 순서는 실제 등록 로직의 검증 순서와 반드시 일치해야 한다.

---

### 생산 실패 피드백

**규칙 12. 실패 피드백 방식**

| 실패 사유 | UI 반응 |
|-----------|---------|
| 큐 가득 (3개 초과) | 토스트만 표시 |
| 골드 부족 | 토스트만 표시 |
| 인구 가득 | 토스트만 표시 |

골드 부족 시 유닛 비용 텍스트 색상은 실패 시점이 아닌, 골드가 변경될 때마다 자동으로 재평가된다.
인구 가득 시 HUD 인구 텍스트 색상은 HUD가 자체적으로 처리한다. 생산 패널이 관여하지 않는다.

---

### 정보 바 (골드/인구/비용 텍스트)

**규칙 13. 골드 텍스트**
보유 골드가 변경될 때마다 자동 갱신된다.

**규칙 14. 유닛 비용 텍스트 색상**
보유 골드가 해당 유닛의 비용보다 적으면 빨간색, 충분하면 흰색으로 표시된다.
골드 변경 시마다 자동 재평가된다.

**규칙 15. 인구 텍스트**
"사용/최대" 형식으로 표시된다.

---

### HUD (골드/인구 상시 표시)

**규칙 16. 인구 가득 상태 표시**
인구가 가득 찬 상태(사용 >= 최대)이면 인구 텍스트를 빨간색으로 표시한다.
가득 차지 않으면 흰색으로 표시한다.

**규칙 17. 인구 텍스트 형식**
"사용 / 최대" 형식으로 표시된다.

---

### 자동 생산 규칙

**규칙 18. 수동 등록 시 자동 모드 해제**
수동 항목을 등록하면 자동 모드가 전체 해제된다.
단, 이미 골드가 차감된 자동 항목은 수동으로 이관되어 생산이 계속된다. 환불 없음.
아직 골드가 차감되지 않은 자동 항목은 제거된다. 환불 없음.

**규칙 19. 자동 생산 해제/취소 시**
자동 유닛 타입을 해제하거나 해당 슬롯을 취소했을 때:
- 이미 골드가 차감된 자동 항목 → 수동으로 이관. 환불 없음, 생산 계속.
- 아직 골드가 차감되지 않은 자동 항목 → 제거. 환불 없음.

**규칙 20. 자동 생산 중복 방지**
자동 타입을 새로 등록할 때, 같은 타입이 이미 슬롯0에서 수동 생산 중이거나
대기 큐의 마지막 항목이 수동으로 등록된 같은 타입이면,
중복 추가 없이 기존 항목을 자동으로 전환한다. 골드는 이미 차감된 상태를 유지한다.

단, 대기 큐에 다른 항목이 있는 경우에는 슬롯0 전환 대신 대기 큐 끝에 새로 추가한다.
중간에 다른 유닛이 있으므로 이 경우는 중복이 아니다.
예: [Assault(슬롯0)] [Pistoleer(슬롯2)] 상태에서 Assault 자동 등록 →
    슬롯3에 Assault 추가 → [Assault(슬롯1)] [Pistoleer(슬롯2)] [Assault(슬롯3)]

**규칙 21. 자동 생산 중 자원 부족 시**
생산 시작 시점에 골드 또는 인구가 부족하면 자동 모드를 전체 즉시 취소한다.
남은 자동 항목들은 규칙 19에 따라 처리된다.

**규칙 22. 생산 완료 후 자동 순환**
자동 항목이 완료되면, 해당 타입이 자동 목록에 아직 있으면 대기 큐 끝에 재추가된다.
재추가 시 골드 미차감 상태이며, 슬롯1/2에 표시될 때 차감된다.

---

### 슬롯 직접 취소 규칙

**규칙 23. 취소 시 환불**
슬롯을 직접 클릭해 취소할 때 골드가 이미 차감된 항목은 전액 환불된다.
골드가 차감되지 않은 항목은 환불 없다.

---

### 스폰 대기

**규칙 24. 스폰 불가 시 대기**
생산이 완료됐으나 배럭 인접에 빈 타일이 없으면 진행률 100% 상태로 대기한다.
빈 타일이 생기면 다음 프레임에 즉시 스폰된다.

---

### 토스트 메시지

**규칙 25. 토스트 표시 방식**
서로 다른 종류의 토스트가 동시에 요청되면 큐에 쌓아 순서대로 하나씩 표시한다.
같은 종류는 누적하지 않는다 — 이미 표시 중인 종류가 다시 요청되면 큐에 넣지 않고 표시 시간만 처음 값으로 되돌리고,
큐에서 대기 중인 종류가 다시 요청되면 무시한다.
근거: 같은 문구를 두 번 보여 줘도 새 정보가 없고, 버튼을 연타하면 같은 안내가 요청 횟수만큼 몇 초씩 이어져 오히려 방해가 된다.
진입 애니메이션 없이 즉시 표시되며, 설정된 시간이 지나면 페이드아웃으로 사라진다.

**규칙 26. 토스트 터치**
표시 중인 토스트를 터치하면 현재 메시지가 즉시 제거되고 다음 메시지가 표시된다.

**규칙 27. 토스트 자동 정리**
게임 시작 또는 종료 시 남아있는 토스트가 자동으로 초기화된다.

**규칙 28. 토스트 종류**

| 키 | 표시 상황 |
|----|-----------|
| GoldInsufficient | 골드가 부족해 수동 생산을 등록할 수 없을 때 |
| PopulationFull | 인구가 가득 차 수동 생산을 등록할 수 없을 때 |
| ProductionQueueFull | 큐가 이미 3개로 가득 차 추가 등록을 거부할 때 |
| UpgradeRequired | 건물 업그레이드가 필요해 현재 단계에서는 생산할 수 없는 유닛을 탭했을 때 |
| SkillOnCooldown | 스킬이 쿨다운 중이라 스킬 슬롯을 탭해도 발동할 수 없을 때 |
| BuildingNotAllowed | 이 타일에는 건설할 수 없어(자기 팀 소유 건설 불가 타일) 건물 배치 패널을 열지 않을 때 |

### 패널 구조

**규칙 1. `BuildingPanelBase`를 상속한 전용 패널을 신설한다**
MistShrine 패널은 `BuildingPanelBase`를 상속해 공통 프레임(헤더 제목 · 닫기[X] · 하단 철거 버튼+환불 표시 ·
대상 건물 파괴 시 자동 닫힘(공통 UI 규칙 11) · `IGameUI` 생명주기)을 그대로 물려받는다.
연구 패널(`ResearchPanelUI : BuildingPanelBase`)과 동일한 방식이다.

**규칙 2. `BuildingSkillPanelUI`는 재사용하지 않는다**
스킬 패널은 **종족 로드아웃 5슬롯 · 3×3 그리드 · 지점 조준**을 전제하는 UI다.
MistShrine은 슬롯도 조준도 없으므로 스킬 패널을 재사용하지 않고 전용 패널을 만든다.
여기서 "슬롯이 없다"는 것은 **종족 로드아웃 스킬 슬롯이 없다**는 뜻이며, 패널의 **3×3 그리드 9슬롯 규격 자체는 그대로 쓴다**(규칙 10).

**규칙 3. 패널 구성 요소**
- 사용(시전) 버튼 1개
- 쿨다운 표시 (규칙 7)
- 자동 모드 표시 (규칙 6)
- 철거 버튼 + 환불 금액 텍스트 (베이스가 제공 — 별도 구현 불필요)

> 이 요소들의 **배치**는 3×3 그리드 9슬롯을 따른다(규칙 10). 미사용 슬롯 숨김 방식은 규칙 11.

**규칙 4. 닫기 규칙은 공통 팝업 규칙을 따른다**
배경 탭 시 닫힘(공통 UI 규칙 8·9). 대상 건물 파괴 시 자동 닫힘(공통 UI 규칙 11).

### 조작 (생산 패널과 동일하게 통일)

**규칙 5. 탭 / 롱프레스 조작**
조작 방식은 **생산 패널 유닛 버튼과 동일하게 통일**한다(생산 패널 UI 규칙 3·4·5와 같은 UX).

| 입력 | 동작 |
|------|------|
| 짧은 탭 | 수동 시전 1회 |
| 길게 누르기(0.5초 이상) | 자동 모드 토글 |
| 자동 모드 상태에서 짧은 탭 | 자동 모드 **해제** (시전하지 않음) |

자동 모드 상태에서의 탭은 생산 패널의 `state.IsAutoMode && AutoTypes.Contains(type)` → `HandleToggleAuto` 분기와
동일한 분기 처리를 따른다.

**규칙 6. 자동 모드 기본값은 OFF**
건설 직후 MistShrine의 자동 모드는 **꺼진 상태**다.
근거: 수동 상태에서 사용자가 곧바로 사용하지 않기를 원할 수 있으므로, 켜진 상태를 기본으로 강제하지 않는다.
자동 모드 ON/OFF는 패널에서 즉시 구분되도록 시각 표시한다 — 생산 패널의 **자동 생산 테두리 회전 머티리얼 패턴**을 재사용한다.
표시 방식은 **테두리 회전 효과 하나로 확정**이며, 오버레이 배선 주의사항은 규칙 14를 따른다.

### 쿨다운 표시

**규칙 7. 쿨다운 오버레이는 `SkillCooldownOverlay`를 재사용한다**
사용 버튼 위 쿨다운 표시는 기존 `SkillCooldownOverlay`(시계방향 radial fill + 남은 초 텍스트, 남은 시간 0 이하면 자동 숨김)를 그대로 쓴다.
이 컴포넌트는 스킬 전용 로직 없이 `SetCooldown(remaining, total)`만 받는 **순수 표시 컴포넌트**이므로 재사용에 제약이 없다.
`total`(발동 시점 총 쿨다운)이 fill 비율에 필요하므로, 로직 측에서 남은 시간과 총 쿨다운을 함께 제공해야 한다
(`GameSystemRules_Buildings.md` MistShrine 물안개 힐 시스템 규칙 21).

### 범위 표시 UI

**규칙 8. 아군 MistShrine 패널이 열려 있는 동안에만 범위를 표시한다**
- 아군 MistShrine을 클릭해 **패널이 열려 있는 동안에만** 반투명 원형 UI로 회복 범위를 표시한다.
- **패널을 닫으면 즉시 사라진다.**
- **적 MistShrine은 클릭해도 범위를 표시하지 않는다** — 상대에게 정보 우위를 주지 않기 위함이다.
- 물안개가 지속되는 동안의 범위는 **물안개 VFX 자체로 확인**되므로, 물안개 지속 중이라는 이유로 범위 UI를 따로 켜지 않는다.
- 렌더링은 지면 데칼 셰이더 재사용을 우선 검토한다(`GameSystemRules_Buildings.md` MistShrine 물안개 힐 시스템 규칙 27 — **ZTest Always 금지**).
- 원의 **시각 사양(채움·외곽선)** 은 규칙 12를 따른다.

### 회복 텍스트

**규칙 9. 회복 텍스트는 회복이 실제로 발생한 대상만 · 표시 주기를 힐 틱과 분리한다**
- **실제로 체력이 회복된 대상에만** 표시한다(최대 체력이라 회복량 0인 대상은 표시하지 않는다).
- **회복 틱(1초)과 텍스트 표시 주기를 분리**한다. 범위 내 다수 대상에게 매초 텍스트가 뜨면 화면이 도배되기 때문이다
  (BloomFairy HoT가 "완료 시 1회 표시"로 억제한 선례 — `GameSystemRules_Units.md` 규칙 37 HoT 힐 텍스트 집계).
- **표시 주기는 임시로 3초 누적 1회 표시**로 하고, 밸런싱 단계에서 확정한다(**미확정**).
- 건물 위 회복 텍스트는 신규 UI 없이 기존 경로로 커버된다(`FloatingHpTextSpawner`가 `IsUnit` 분기로 건물 월드 좌표를 이미 지원).

### 패널 레이아웃 (2026-08-10 확정)

**규칙 10. 패널 레이아웃은 3×3 그리드 9슬롯을 유지한다 (A안 확정)**
MistShrine 패널은 비생산 건물 패널의 공통 규격인 **3×3 그리드 9슬롯**을 그대로 사용한다(전용 패널을 만들되 그리드 규격은 공통을 따른다).

| 슬롯 | 용도 |
|:-:|------|
| 1 | **사용(시전) 버튼** (규칙 3·5, 쿨다운 오버레이는 규칙 7) |
| 2~5 | 미사용(예약) |
| 6 | **철거 버튼** (`BuildingPanelBase`가 제공 — 규칙 1) |
| 7~9 | 미사용(예약) |

슬롯 6을 철거로 **고정**하는 이유: `BuildingSkillPanelUI`가 이미 "슬롯 1~5 = 스킬 / **슬롯 6 = 철거** / 7~9 예약"(스킬 규칙 9) 배치를 쓰고 있어,
**모든 건물 패널에서 철거 버튼 위치를 동일하게 유지**해야 오조작(잘못된 철거)을 줄일 수 있기 때문이다.

**규칙 11. 미사용 슬롯은 `CanvasGroup.alpha=0`으로 숨긴다 — `SetActive(false)` 금지**
`SetActive(false)`는 GridLayout의 셀 정렬을 무너뜨려 남은 버튼이 앞으로 당겨지므로 금지한다.
`BuildingActionPanelUI`·`BuildingSkillPanelUI`가 이미 쓰는 패턴(슬롯 버튼마다 `CanvasGroup` 캐시, 기본 `alpha=0`)과 동일하게 처리한다.
입력 차단이 필요하면 `blocksRaycasts`를 가시성과 함께 맞춘다.

### 범위 표시 원의 시각 사양 (2026-08-10 확정)

**규칙 12. 범위 표시 원은 반투명 채움 + 외곽선을 함께 사용한다**

- 표시 조건(아군 · 패널이 열려 있는 동안만)은 규칙 8 그대로다.
- **색상 · 투명도 · 외곽선 두께 값은 미확정**이며, 아트/밸런싱 단계에서 확정한다.

### 자동 모드 시각 표시 (2026-08-10 확정)

**규칙 14. 자동 모드 표시는 테두리 회전 효과만 사용하고, 오버레이 오브젝트는 하나만 둔다**
- MistShrine 패널의 자동 모드 ON/OFF 표시는 **테두리 회전 효과 하나로 확정**한다(별도 도트 인디케이터를 두지 않는다).
- 근거: 프로젝트에 **도트 인디케이터 UI가 실재하지 않는다.** 씬(`Assets/_Project/Scenes/Game.unity`) 확인 결과
  `ProductionPanelUI`의 `_unitAutoIndicators`(List\<GameObject\>)와 `_unitBorderOverlays`(List\<Image\>)는
  **같은 `BorderOverlay` 오브젝트**를 각각 GameObject/Image로 가리키는 **중복 배선**이다.
  코드 주석의 "기존 도트 인디케이터"는 과거 설계의 흔적이다.
- 그 결과 생산 패널에서는 같은 오브젝트에 `SetActive`와 `CanvasGroup.alpha`가 이중으로 걸린다(두 제어 방향이 같아 시각 버그는 없다).
- **MistShrine 패널은 이 중복 구조를 복제하지 않는다** — 자동 상태 표시용 오버레이 오브젝트를 **하나만** 두고 **단일 경로로만 on/off** 한다.

> `ProductionPanelUI`의 중복 배선 자체를 정리할지는 이 문서의 범위가 아니다(별도 판단 필요).

## 건물 배치 패널 UI

### 비용 텍스트

**규칙 1. 건물 비용 텍스트 표기 형식**
건물 비용은 숫자만 표시한다. 'G' 등 접미사를 붙이지 않는다.
(생산 패널 비용 텍스트와 동일한 표기 방식.)

---

### 건물 비용 텍스트 색상

**규칙 2. 색상 표시 기준**
팝업이 열린 동안 현재 보유 골드가 해당 건물의 건설 비용보다 적으면 빨간색으로 표시된다.
충분하면 흰색으로 표시된다.

**규칙 3. 색상 재평가 시점**
팝업이 열리는 순간과 골드가 변경될 때마다 자동으로 재평가된다.
팝업이 닫히면 흰색으로 초기화된다.

---

### 건물 배치 실패 피드백

**규칙 4. 골드 부족 시 피드백**
골드가 부족한 상태에서 건물 버튼을 탭하면 토스트 메시지를 표시하고 팝업을 유지한다.
팝업을 닫지 않는 이유: 사용자가 비용 텍스트 색상을 통해 어떤 건물이 불가능한지 직접 파악할 수 있도록 하기 위함이다.

> **멀티플레이 분기 제외**: 위 규칙은 싱글플레이 분기에만 적용된다. 멀티플레이 RPC 분기는 별도 작업 예정.

### 무작위 맵 타일 선택과 건설 패널

> **타일 상태 표기**: 타일의 상태는 `TileKind` 한 가지 값(`Normal` 일반 타일 / `NoBuild` 건설 불가 타일 / `Blocked` 막힌 타일)으로 표현한다. 세 값의 성질과 이 표기를 쓰는 이유의 단일 소스는 `GameSystemRules_RandomMap.md` 5장(규칙 9·10)이다.

**규칙 5. 판정 우선순위**

`InputHandler`(Presentation)와 `GridInteractionUseCase`(Application)가 함께 다음 순서로 클릭을 처리한다. 패널을 여는 1·2번은 `InputHandler`가 맡고, 타일 상태를 판정하는 3~5번은 `GridInteractionUseCase`가 맡는다. 건물 액션 패널과 채굴소 배치 팝업을 여는 일은 Presentation의 몫이라 Application에 둘 수 없기 때문이며(레이어 규칙), 이 분담을 하나로 합치면 Application → Presentation 역참조가 된다.

1. 기존 building action 분기
2. `MineKind`와 MiningPost 건설 자격 분기
3. `TileKind.Blocked`(막힌 타일) 차단
4. `TileKind.NoBuild`(건설 불가 타일) 처리
5. 일반 타일(`TileKind.Normal`) 처리

광산 분기가 건설 불가 처리보다 먼저이므로 광산 타일의 MiningPost 예외는 유지한다.

**규칙 6. 막힌 타일 또는 빈 공간 클릭**

- 논리 `HexGrid`에 좌표가 있어도 `TileKind.Blocked`는 선택할 수 없다.
- 기존 타일 선택을 해제하고 열린 건물 배치 패널을 닫는다.
- 토스트를 표시하지 않는다.
- 새 타일 선택 이벤트를 발행하지 않는다.

**규칙 7. 자기 팀 소유 건설 불가 타일 클릭**

- 타일을 정상 선택하고 highlight를 표시한다.
- 건물 배치 패널을 열지 않으며, 이전 타일에서 열린 패널이 남아 있으면 닫는다.
- `ToastKey.BuildingNotAllowed`로 `이 타일에는 건설할 수 없습니다`를 표시한다.

**규칙 8. 중립·적 소유 건설 불가 타일 클릭**

- 타일 선택과 highlight만 수행한다.
- 건물 배치 패널을 열지 않고 stale 패널을 닫는다.
- 건설 의도가 성립하지 않으므로 토스트를 표시하지 않는다.

## 인게임 설정 메뉴

### 메뉴 열기/닫기

**규칙 1. 메뉴 열기**
HUD의 설정 버튼을 탭하면 인게임 설정 메뉴가 열린다.
설정 메뉴 외부 영역(공유 Background)을 탭하면 메뉴가 닫힌다.
닫기(X) 버튼을 탭해도 메뉴가 닫힌다.

**규칙 2. 싱글플레이 일시정지**
싱글플레이에서 설정 메뉴가 열리면 게임이 즉시 일시정지된다 (Time.timeScale=0).
메뉴가 닫히면 일시정지가 해제된다 (Time.timeScale=1).
멀티플레이에서는 일시정지 기능이 없다.

**규칙 3. 포기 확인 팝업**
설정 메뉴에서 포기 버튼을 탭하면 확인 팝업(ConfirmPopup)이 표시된다.
포기 확인 팝업이 열려 있는 동안 공유 Background 클릭은 차단된다 (설정 메뉴가 닫히지 않음).

---

### 게임 포기

**규칙 4. 포기 결과**
포기 플레이어는 패배 처리된다.
싱글플레이: 항상 Red 팀(로컬 플레이어)이 패배.
멀티플레이: 포기를 요청한 클라이언트의 팀이 패배.

**규칙 5. 재경기**
포기 후 재경기는 일반 게임 종료와 동일하게 처리된다.
커스텀게임에서는 재경기 요청이 가능하다.

---

### 프로필 서브 패널

**규칙 6. 프로필 버튼 (서브 패널 열기/닫기)**
인게임 설정 메뉴의 메인 버튼 그룹에는 사운드/포기 버튼과 함께 **프로필 버튼**이 배치된다.
프로필 버튼은 사운드 버튼과 완전히 동일한 서브 패널 전환 패턴을 따른다.

- 프로필 버튼을 탭하면 메인 버튼 그룹의 CanvasGroup을 숨기고(공통 UI 규칙 5), 프로필 서브 패널의 CanvasGroup을 표시한다.
- 프로필 서브 패널의 뒤로가기 버튼을 탭하면 프로필 서브 패널을 숨기고 메인 버튼 그룹을 다시 표시한다.
- 표시/숨김은 SetActive가 아닌 CanvasGroup(alpha/blocksRaycasts/interactable)으로 처리한다(공통 UI 규칙 5).

> **미정 — 프로필 서브 패널 내부 구성**: 프로필 화면 안에 어떤 정보(전적, 계정 정보 등)를 어떤 형태로 표시할지는 아직 확정되지 않았다.
> 본 규칙은 "프로필 버튼이 사운드 버튼과 동일한 열기/닫기 패턴을 따른다"까지만 규정한다. 내부 구성은 별도 기획/논의 후 확정하여 이 노트를 삭제하고 규칙을 보완한다.

## 로비 설정/프로필 UI

Lobby.unity의 설정 및 프로필 관련 UI 구조 규칙이다.

**규칙 1. ProfilePanel / SettingPanel 최상위 탭 분리**
기존에는 로비 "설정" 탭 하나 안에서 프로필/사운드가 서브 화면으로 전환되는 구조였으나,

|------|------|

| SettingPanel | 사운드 등 게임 설정 |

**규칙 2. SettingPanel 사운드 탭 규칙 참조**
SettingPanel 내 사운드 탭의 슬라이더/버튼 규칙(슬라이더 색상, 전체 소리켜기/전체 음소거/초기화/뒤로 버튼 동작)은

중복 서술하지 않고 해당 규칙을 참조한다.
