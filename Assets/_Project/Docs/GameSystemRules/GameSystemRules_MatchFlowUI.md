# Game System Rules — 경기 흐름 UI

- **목적·답하는 질문:** 경기 준비 실패·결과·재경기에서 화면과 버튼이 어떻게 동작할지 판단한다.
- **포함:** M/D 규칙, 문구·타이머·팝업·버튼·레이아웃 전제 및 예외 이유
- **제외·담당 문서:** 공통 팝업은 [UI](GameSystemRules_UI.md), 맵·이탈 운영은 [MatchFlow](GameSystemRules_MatchFlow.md), 구현 구조는 [네트워크 TDD](../TechnicalDesignDocument_Network.md)
- **권위원본·주요 참조:** 경기 흐름 UI 규칙 원본이며 기존 섹션·M/D ID 유지
- **갱신 조건·방법:** 승인된 화면 동작·프리팹 전제 변경을 본문에 반영한다. Setup 실행·도구 이동·회차별 관측은 기존 Task/History, 현재 검증은 [PROJECT_STATUS](../PROJECT_STATUS.md)에 연결한다.

> 공통 UI 규칙 1~11·L-1~L-4는 [GameSystemRules_UI.md](GameSystemRules_UI.md#공통-ui-규칙), 역할 독립성은 [GameSystemRules_Network.md](GameSystemRules_Network.md)가 원본이다. 이 문서의 섹션별 규칙 번호는 재번호하지 않는다.

## 공통 UI 규칙

> 아래 규칙 M/D는 경기 준비 실패와 결과·재경기 화면 계약을 정의한다. 숫자 규칙 8·9·11 등 공통 팝업 규정은 공통 UI 원본을 참조한다.

### 무작위 맵 준비 실패 UI

**규칙 M-1. 내부 정보 비공개**

맵 준비 실패 팝업에는 seed, 맵 유형, `MapVersion`, 내부 error code를 표시하지 않는다. 이 정보는 로그에만 기록한다.

**규칙 M-2. 멀티플레이 최초 경기 실패**

- loading UI를 닫고 양쪽(Host·Client)이 즉시 방을 나간다. 연결을 종료하고 로비 메인으로 돌아가며 사용자 조작을 기다리지 않는다.
- 양쪽은 같은 알림 모달을 본다. 제목 `알림`, 본문 `경기를 시작할 수 없습니다.`, 버튼 `확인` 하나다. 버튼은 모달만 닫고 배경 탭은 닫지 않는다. 역할에 따른 화면 차이는 [네트워크 최상위 원칙](GameSystemRules_Network.md)을 위반한다.
- 실패 사유·seed·유형·내부 코드를 표시하지 않으며 재시도 버튼·요청도 없다. 다시 경기하려면 새 방을 만든다.
- 실패 통보를 보낸 뒤 연결을 끊는 기술 순서와 Client의 실패 통보/연결 끊김 경로는 [네트워크 TDD](../TechnicalDesignDocument_Network.md)와 [구현 계획](../_Tasks/2026-10-12/07_08_multi-first-map-failure-ui/Plan.md)5절을 따른다. 양쪽 즉시 이탈·Client 경로의 규정을 M-2와 네트워크 규칙 중 어느 쪽에서 소유할지 남긴 미정은 이번에 새 결정하지 않는다. 역할 독립성은 네트워크 규칙의 원본을 따른다.
- 구현·관측 범위는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다. 정상 경로·Host 자신의 실패·통보 수신 관측을 전송 객체 스폰 전 실패·Host 완전 사망·전송 계층60초 통보의 실기 확인으로 확대하지 않는다. 이전 연결 유지·두 버튼·구현 대기와 후속 관측 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-02)다.

**규칙 M-3. 멀티플레이 재경기 맵 준비 실패**

- 이전 `MapDefinition`과 결과 화면을 유지하고 rematch pending을 초기화한다.
- 자동 로비 복귀 countdown을 전체 길이로 다시 시작하고 결과 화면의 기존 선택지를 복원한다. 이탈30초 재시작은 별도 D-4 계약이다.
- 알림 팝업을 띄우지 않고 D-7의 상태 줄로 실패를 알린다. 문구·개행·사유 분기·우선순위는 D-7이 원본이다. 상대가 살아 있으면 다시 시도할 수 있고 `로비로`는 항상 활성이다(D-2·D-3).
- 상태 줄을 쓰는 이유는 모달이 로비 버튼을 가리기 때문이며, 수락 전송 실패·맵 준비 실패·한도 만료를 같은 실패 화면으로 일관되게 알리기 위해서다. 화면 복원·타이머 계약은 표시 수단 변경과 무관하게 유지한다.
- 이전 알림 팝업·미정값과 구현/관측 등급의 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-03), 현재 구현·실기 범위는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다.

**규칙 M-4. 싱글플레이 실패**

- 맵 생성 중 어떤 이유·시점의 실패든 맵 준비 실패로 취급한다. 무작위 생성/폴백 실패뿐 아니라 격자 투영 실패도 포함한다. 이 범위는 싱글 전용이며 멀티는 M-2·M-3을 따른다.
- loading UI는 실패 안내를 가리므로 닫는다. 최초 실패는 모달에 `경기를 시작할 수 없습니다.`와 `다시하기`/`로비로`를 표시한다. 배경 탭 닫기는 공통 모달 규칙을 따른다.
- 재경기 실패는 결과 화면의 기존 선택지를 복원하고 상태 줄에 `재경기를 시작할 수 없습니다.` 한 줄을 표시한다. 별도 팝업과 자동 복귀 타이머를 쓰지 않고 남은 초도 붙이지 않는다. 최초 실패에는 결과 화면이 없어 모달이 필요하고 재경기는 기존 화면을 사용한다.
- 재시도 횟수 제한은 없다. 사유를 세분한 문구를 만들지 않으며 `로비로`가 항상 열려 있어야 한다. 실패가 에셋 문제라 반복될 수 있어도 로비로 나갈 수 있고, 생성100회가 우연히 실패했다면 재시도 성공 가능성이 있다.
- 싱글 결과 화면은 평시·실패 모두 자동 로비 복귀 countdown이 없다. 평시 상태 줄은 빈 줄이다. D-1·D-2·D-4·D-6의 상대 이탈·자동 복귀 규정은 싱글에 적용하지 않고 D-3의 로비 버튼 활성은 적용한다.
- 실패 통보는 기존 싱글 전용 채널과 화면을 다시 켜는 계약을 재사용하며 새 채널을 만들지 않는다. 투영 실패는 준비 성공 이후에만 도달하므로 준비 실패 강제로 투영 실패 검증을 대신하지 않는다.
- 결과 화면 상태 줄·싱글 최초 실패 모달·멀티 로비 실패 안내의 세 값은 사건과 개정 책임이 달라 한 상수로 합치지 않는다. 같은 글자·마침표여도 거짓 단일 소스로 만들지 않는다. 멀티 로비 값 자체를 상수로 올릴지는 여기서 정하지 않는다.
- 현재 구현·실기 범위는 [PROJECT_STATUS](../PROJECT_STATUS.md), 날짜별 확정·과거 미정·문구 변경·강제 실패·회차별 로그/사용자 화면 등급은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-04)다. 실제 자연 투영 실패 발생 빈도와 심각도는 강제 실패 관측으로 확정하지 않는다. 2026-10-13 멀티 실패 관측은 새 싱글 문구의 화면 확인이 아니다.

### 경기 종료 후 상대 이탈 UI

경기 종료 뒤 상대가 떠났을 때 그 사실을 결과 화면에 알리고, 사용자가 언제든 스스로 로비로 나갈 수 있도록 하는 UI 계약이다. D-(Disconnect)는 공통 숫자 규칙·M/L 규칙과 구별하는 접두사다.

결과 화면은 공용 반투명 배경 위에 승패·상태 줄·결과 버튼을 함께 표시하며 배경 탭으로 닫히지 않는다. 표시 중 게임 타일·건물·설정·랠리·스킬·카메라 입력을 차단하고 진행 중 조준을 정리한다. 재경기로 결과를 숨겨도 새 경기 UI 정리가 끝날 때까지 게임 입력은 차단하며, 준비 실패로 결과를 복원하면 같은 차단을 유지한다. 구체 점유 API와 상위 Modal 중 입력 차단은 [공통 UI 규칙](GameSystemRules_UI.md#공통-ui-규칙)을 따른다.

이탈 판정·정상 퇴장 통보는 [MatchFlow](GameSystemRules_MatchFlow.md) 규칙17, 맵 전송 중 이탈은 같은 문서 규칙18, 씬 재로드 중 제외는 규칙19가 원본이다. 이 절은 판정 결과를 받은 뒤의 결과 표시·입력 차단·문구·버튼·timer를 정하며 기술 설정·구조는 [네트워크 TDD](../TechnicalDesignDocument_Network.md)를 따른다. 과거 화면 미전달·문서명 미정·원본 위치 확정 당시 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-11)다.

**규칙 D-1. 상대 이탈 시 결과 화면의 타이머 텍스트를 교체한다**

상대 이탈을 판정하면 기존 결과 화면의 timer 텍스트 자리를 상태 줄로 사용해 이탈 사실과 남은 시간을 함께 알린다. 두 정보가 한 덩어리이므로 새 팝업이나 별도 텍스트 자리를 만들지 않는다. 현행 문구와 평시 한 줄/이탈 두 줄의 개행 형태는 **규칙 D-7의 상태 줄 표만** 원본으로 참조한다. 과거 한 줄 표기·개행 미정·평시 확정 포인터 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-12)다.

**규칙 D-2. 상대 이탈 시 재경기 버튼을 비활성화한다**

상대 이탈이 판정되면 결과 화면의 재경기 버튼을 비활성화한다. 상대가 없는 요청으로 다시 기다리게 하지 않기 위해서다.

| 다시하기 버튼 | 조건 |
|---|---|
|활성|상대가 떠나지 않았다 **AND** 실패 사유가 연결 끊김이 아니다|
|비활성|두 조건 중 하나라도 어긋난다|

연결 끊김 실패 문구를 띄우면서 재시도를 권하는 모순을 막기 위해 문구와 버튼은 같은 사유 판정을 사용한다. 이 표가 활성 조건의 원본이며 다른 규칙은 참조한다. M-3의 선택지 복원에서도 연결 끊김이면 다시하기를 복원하지 않고 그 밖의 사유에서 복원한다. D-3의 로비 버튼 활성과 D-8의 문구 복원은 유지한다.

한번 끈 버튼을 일정 시간 뒤 되살리지 않는다. 일시적 순단이면 재시도할 수 없는 대가가 있으나, 되살렸다 다시 끄는 깜빡임과 별도 타이머를 추가하지 않으며 화면 문구와 선택을 일관되게 한다. 과거 「새 요청이 오면 버튼·문구를 되돌릴 것인가」 안건은 새 복구 정책을 정한 것이 아니라, 연결 끊김 사유가 양쪽에 전달돼 양쪽 버튼이 꺼지므로 전제가 성립하지 않아 무효가 된 것이다. 그 밖의 사유는 원래 버튼이 켜져 있어 해당 안건의 전제가 없다.

양쪽 사유 전달과 RPC 요청 유무는 버튼 색·활성 모습의 직접 관측과 구분한다. 강제 실패 관측을 자연 연결 끊김 관측으로 확대하지 않는다. 당시 채택/기각·로그 실측·무효 판정·사용자 화면 확인 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-07), 현재 검증 범위는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다.

**규칙 D-3. 로비 복귀 버튼은 항상 활성 상태를 유지한다**

결과 화면의 **로비 복귀 버튼은 어떤 상태에서도 비활성화하지 않는다.**

이는 결과 화면의 선택지 활성 정책이다. 그 위에 응답을 기다리는 Modal이나 Loading이 실제 입력을 점유하면 결과 버튼의 개별 CanvasGroup 입력을 잠그고, 상위 점유 반납 뒤 기존 선택지 정책대로 복원한다. 버튼 자체의 활성 사유나 자동 복귀 timer를 변경하지 않는다.
재경기를 요청하고 상대의 응답을 기다리는 동안에도 끄지 않으며, 상대 이탈 판정 뒤에도 켜 둔다
(이탈로 꺼지는 것은 규칙 D-2 의 재경기 버튼뿐이다).

근거: 두 버튼이 동시에 꺼지면 사용자가 **스스로 화면을 빠져나갈 방법이 없어** 카운트다운 만료까지 갇힌다.
로비 복귀는 상대의 상태와 무관하게 언제나 성립하는 선택이므로 끌 이유가 없다.

D-2의 비활성 사유가 늘거나 D-7의 준비 상태에 들어가도 이 규칙은 유지한다. 사용자가 스스로 나갈 길이 열려 있어야 재시도 버튼을 계속 꺼 둘 수 있다. 구현·초기 코드 실측·후반부 화면 확인의 한계는 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-08)에 보존한다. 이탈 판정 경로가 구현된 사실을 이탈 뒤 로비 버튼의 화면 확인으로 합치지 않는다.

**규칙 D-4. 자동 로비 복귀 카운트다운 — 기본 60초, 이탈 판정 시 30초로 재시작**

**적용 범위는 멀티플레이 결과 화면이다.** 싱글은 평시·실패 모두 자동 복귀 countdown을 시작하지 않는다(M-4). 싱글에는 기다릴 상대가 없고 D-3의 로비 버튼이 항상 열려 있기 때문이다.

| 시점 | 카운트다운 |
|---|---|
|멀티 결과 화면 표시|60초|
|상대 이탈 판정|남은 시간과 관계없이30초로 다시 시작|

이탈을 알자마자 화면이 사라지지 않도록30초를 새로 부여하고 만료하면 로비로 이동한다. 맵 준비 실패의 **전체 길이 재시작**은 M-3, 수락 접수의 **정지**는 D-7이 원본이므로 계기·길이를 섞지 않는다. 싱글 상태 줄은 평시 빈 줄·실패 한 줄이며 남은 초를 붙이지 않는다.

실제60초 적용은 Inspector 직렬화 값과 코드 기본값을 함께 대조해야 한다. 초기 코드/씬 변경·싱글 분리·죽은 ShowResult 최종 삭제·회차별 타이머 측정 및 컴파일/성능/z-order/삭제 후 미검증 경계 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-09), 현재 검증 상태는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다. 로그 한 파일 안의 서로 다른 빌드/세션을 같은 검증으로 합치지 않으며 timer 로그와 사용자 화면 확인은 별도 증거다.

**규칙 D-5. 알림 팝업 — 타이틀 + 본문 + 버튼 1개, 배경 탭으로 닫히지 않는다**

사용자에게 **선택을 요구하지 않고 사실 하나를 알리기만 하는** 팝업을 신설한다.

| 구성 | 내용 |
|------|------|
| 타이틀 | 한 줄 제목 |
| 본문 | 알릴 내용 |
| 버튼 | **1개** |

- 호출은 `UIManager.ShowAlert` 로 한다. 씬이 팝업을 직접 참조하지 않으며, 호출은 항상 null-safe 패턴 `UIManager.Instance?.ShowAlert(...)` 를 쓴다(로딩 인디케이터의 규칙 L-4 와 같은 이유 — 씬에 직접 진입하면 `Instance` 가 null 일 수 있다).
- 타입은 **모달 (Modal)** 이다(규칙 8). 🔴 **배경을 탭해도 닫히지 않으며 반드시 버튼으로만 닫는다**(규칙 9). 배경 탭으로 닫히면 **상대가 없는 결과 화면만 남아** 사용자가 아무것도 할 수 없는 상태가 되기 때문이다.
- 반투명 배경 오버레이는 개별 팝업이 소유하지 않고 `UIManager` 가 단일 소유한다(규칙 4·5). 이 팝업은 배경 탭으로 닫히지 않으므로 **Modal 모드**(콜백 없는 `ShowBlockingOverlay()`)로 표시한다.
- 이 알림 팝업의 사용처는 **멀티 최초 경기 맵 준비 실패(M-2)**와 **재경기 요청자 이탈(D-6)**이다. M-3·M-4의 재경기 실패는 상태 줄을 사용하므로 이 사용처에 넣지 않는다. 사용처·실호출 집계의 변경과 이전 미구현 표시 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-10)에 보존하며 현재 구현/관측 범위는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다.

**프리팹 전제:** 제목이 비어 `SetActive(false)`로 숨겨질 때 자리도 사라지도록 `ConfirmPopup.prefab` Panel에 VerticalLayoutGroup이 있어야 한다. 없으면 제목 없는 기존 확인/취소 팝업 본문이 아래로 밀린다. 취소 버튼 숨김도 ButtonRow의 HorizontalLayoutGroup에 의존한다. 기존 `ShowConfirm` 시그니처·동작을 유지한다. 패딩·간격·높이는 실제 프리팹/Inspector를 기준으로 확인하고 코드 기본값만으로 판단하지 않는다.

ConfirmPopup 전용 Setup/Tools 복구 스크립트는 최종 삭제됐으며 현재 프리팹과 동작은 유지한다. `SetActive`를 CanvasGroup 규칙의 예외로 명문화할지는 별도 미결이며 [ROADMAP](../ROADMAP.md)을 따른다. 초기 적용·실호출 집계·실기 경계·보존/이동/삭제 결정 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-01)에 보존한다. 당시의 미착수·호출0건·도구 선택 대기를 현재 상태로 읽지 않는다.

**규칙 D-6. 재경기 요청에 응답하기 전에 요청자가 이탈한 경우**

재경기 요청을 받아 요청 팝업이 떠 있는 상태에서 **응답하기 전에 요청자가 이탈**하면 다음 순서로 처리한다.

1. 떠 있던 **재경기 요청 팝업을 닫는다.** 응답할 상대가 없어졌으므로 그대로 두면 수락을 눌러도 아무 데도 닿지 않는다.
2. **알림 팝업(규칙 D-5)을 띄운다.**

   | 구성 | 값 |
   |------|-----|
   | 타이틀 | `알림` |
   | 본문 | `상대방이 떠났습니다.` |
   | 버튼 | `로비로` — 누르면 로비로 이동한다 |

3. 이 시점의 자동 로비 복귀 카운트다운은 **30초**다 — 규칙 D-4 의 이탈 재시작과 **같은 시점·같은 값**이며, 여기에 별도의 타이머를 두지 않는다.

버튼을 누르지 않아도 카운트다운이 만료되면 로비로 이동하므로(규칙 D-4), 사용자가 팝업을 방치해도 화면에 갇히지 않는다.

요청 팝업이 떠 있지 않은 이탈에는 이 알림을 띄우지 않는다(D-1). 기존 팝업 숨김·로비 복귀와 D-4의30초 시계를 재사용하며 별도 타이머를 만들지 않는다. 팝업 파괴 시 자신이 소유한 overlay 점유를 해제하고, 잡은 적 없는 점유를 놓지 않아야 로비까지 입력 차단이 남지 않는다. 구현 구조는 [TDD](../TechnicalDesignDocument.md), 현재 검증 범위는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다. 이탈·시계·점유 로그와 사용자 팝업/로비 화면 확인은 서로 다른 증거다. 초기 호출/씬 실측·누수 예방·회차별 원문과 한계는 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-05)다.

**규칙 D-7. 재경기 수락이 접수되면 상태 줄을 「재경기 준비 중...」으로 바꾸고 자동 복귀 타이머를 멈춘다**

재경기 요청 뒤 상대 수락을 기다리는 동안은 사람을 기다리므로 타이머가 계속 돈다. 수락 접수 뒤 맵 준비는 시스템을 기다리므로 자동 복귀 타이머를 멈추고 기존 상태 줄에 `재경기 준비 중...`을 표시한다. 새 팝업·텍스트 자리를 만들지 않는다.

### 판단 기준 — 이 한 문장이 위 표를 결정한다

**사람을 기다리면 타이머가 돈다 / 시스템을 기다리면 타이머가 멈춘다.** 요청 직후는 버튼 문구만 바꾸며(D-8) 상대의 무응답으로 영구 대기하지 않도록 timer를 유지한다. 수락 접수 후는 다음 계약을 따른다.

### 🔴 양쪽이 「수락 접수」 상태로 들어가는 경로가 서로 다르다 — 이것이 이 규칙의 핵심이다

수락한 쪽은 버튼을 누른 즉시 자기 화면을 바꾸고 서버 응답을 기다리지 않는다. Client가 Host 이탈 뒤 ServerRpc를 보내지 못해도 화면이 갇히지 않아야 하기 때문이다. 요청한 쪽은 서버의 수락 접수 통보를 받아 진입한다. 수락 접수는 요청을 받은 상대가 수락하는 경로(`AcceptRematchServerRpc`)와 양쪽이 각자 다시하기를 눌러 상호 동의하는 경로(`RequestRematchServerRpc`) 모두를 포함하며 양쪽 통보를 보장한다.

### 맵 준비 한도 — 상태 줄을 되돌리기만 하는 시계

- 길이는 `NetworkMapTransfer.TransferTimeoutSeconds * (NetworkMapTransfer.MaxResendCount + 1)`이다. 한 응답 창이 아니라 최초 전송과 재전송 상한을 포함한 창 수의 곱이며 숫자 리터럴을 복제하지 않는다.
- 이 시계는 승패·이탈·연결 종료를 판정하지 않는다. 한도 만료 또는 맵 준비 실패/수락 전송 실패는 아래 실패 상태로 전환하고 자동 복귀 countdown을 전체 길이로 재시작한다.
- 준비 한도는 실패 통보 수신·재경기 시작 통보·상대 이탈·결과 화면 닫기의 네 계기로 중단한다. 실패 직후 늦은 준비 통보로 준비 상태에 재진입해 timer를 다시 멈추지 않도록 같은 회차 전환을 멱등 처리한다.

### ⚠️ 카운트다운을 건드리는 규칙이 셋이다 — 섞어 읽지 않는다

| 계기 | 자동 복귀 타이머 | 원본 |
|---|---|---|
| 상대 이탈 |30초로 재시작|D-4|
| 맵 준비 실패·준비 한도 만료|전체 길이로 재시작|M-3·D-7|
| 수락 접수|정지하고 준비 한도 시작|D-7|

### 🔴 이 규칙이 전제하는 네트워크 쪽 동작 (이 문서의 규칙이 아니다)

이탈 판정과 통보는 [경기 운영](GameSystemRules_MatchFlow.md)·[네트워크 규칙](GameSystemRules_Network.md)이 담당한다. 이탈 판정 후 서버는 재경기 요청·수락을 처리하지 않는다. 이탈 연결 종료로 전송 객체가 제거되는 기존 흐름을 사용하며, 별도 진행 중 맵 준비 취소 요구를 추가하지 않는다. 규칙 D-3에 따라 준비 중에도 로비 버튼은 항상 활성이다.

### 🔴 일부러 채택하지 않은 안

로딩 화면·전체 버튼 잠금·수락/요청 실패 별도 팝업은 로비 탈출을 막거나 같은 실패에 다른 화면을 주므로 사용하지 않는다. 실제 재경기 성립 후 로딩은 유지한다.

### 🔴 왜 새 규칙으로 세웠는가 (기존 D-1·D-2·D-4 의 확장으로 적지 않은 이유)

상대 이탈 표시·버튼 활성·자동 복귀와 별개로 시스템 준비 대기의 진입/종료를 정하는 계약이다. 이탈 판정·승패·기존 timer 규칙을 대체하지 않는다.

**상태 줄의 현재 문구·개행:** `n`은 남은 초이며 표의 줄바꿈을 그대로 사용한다. 문장 사이 공백 한 칸을 줄바꿈으로 바꾸고 줄바꿈 앞뒤에 공백을 남기지 않는다. 평시만 한 줄(앞 빈 줄 없음)이고 준비 중 문구에는 남은 초를 붙이지 않는다. 남은 초 없는 D-5·D-6 팝업 본문은 개행 대상이 아니며 새 남은 초를 추가하지 않는다.

| 상태 | 문구 |
|---|---|
|평시|`n초 후 로비로 돌아갑니다.`|
|상대 이탈|`상대방이 떠났습니다.` + 줄바꿈 + `n초 뒤 로비로 이동합니다.`|
|재경기 준비|`재경기 준비 중...`|
|연결 끊김으로 재경기 실패|`상대방이 나가서 재경기를 시작할 수 없습니다.` + 줄바꿈 + `n초 후 로비로 돌아갑니다.`|
|그 밖/사유 모름 재경기 실패|`재경기를 시작할 수 없습니다.` + 줄바꿈 + `n초 후 로비로 돌아갑니다.`|

실패는 네 번째 상태이며 원인이 갈려도 상태 수는 늘지 않는다. countdown 문구 우선순위는 **이탈 > 실패 > 평시**다. 연결 끊김이 명확한 경우만 상대 이탈 문구를 쓰고, 수락 전송 실패·한도 만료처럼 원인을 모르면 중립 기본 문구를 쓴다. 실패 사유는 상태 깃발 전에 보관해 첫 표시부터 일관되게 한다. 실패 상태에서도 D-2 조건 아래 다시하기를 복원하고 로비 버튼은 항상 활성이다.

표의 네 상태와 화면/로그 증거 등급, 레이아웃 수용·강제 실패·타이머 회차별 측정·수락전송 예외 관측 및 과거 사양은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-06), 현재 상태는 [PROJECT_STATUS](../PROJECT_STATUS.md)를 따른다. 좁은 화면 수용·로그 관측·빌드 판별을 전체 회귀 또는 미관측 실패의 PASS로 합치지 않는다.

**규칙 D-8. 「요청 중...」 문구는 버튼에 두고, 상대 이탈 뒤에는 문구만 되돌리고 버튼은 비활성으로 유지한다**

- 재경기 요청 직후 `요청 중...`은 버튼에 표시하고 상태 줄로 옮기지 않는다. 요청 진행 상태는 요청하는 버튼이 소유한다.
- 상대 이탈이 판정되면 버튼 문구는 `다시하기`로 되돌리되 버튼은 비활성으로 유지한다. 받을 사람이 없는 요청이 진행 중인 것처럼 보이지 않아야 한다. 문구 복원은 활성 조건과 분리하고 다시 누를 수 있는지는 D-2만 따른다.
- 로비 버튼은 D-3에 따라 항상 활성이다. D-7의 `재경기 준비 중...` 상태에서도 사용자가 나갈 수 있다.
- 과거 가드에 문구가 묶였던 코드 상태·활성 조건 추가·문구/버튼 분리 및 사용자 화면 확인의 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-matchflowui-13)다. 원래 코드 변경 커밋을 이번 정리로 특정하거나 로그를 버튼 색 직접 관측으로 해석하지 않는다.
