# Game System Rules — Network

- **목적·답하는 질문:** Host·Client 역할과 관계없이 플레이어에게 보장할 동작을 판단한다.
- **포함:** 역할 독립성 최상위 원칙, 이탈 시 승패 기록, 인게임 이탈 판정과 처리
- **제외·담당 문서:** Netcode·RPC·데이터 계약·치팅 방어는 [네트워크 TDD](../TechnicalDesignDocument_Network.md), 결과 화면 운영은 [MatchFlow](GameSystemRules_MatchFlow.md)
- **권위원본·주요 참조:** 사용자 확정 네트워크 제품 동작 규정의 원본
- **갱신 조건·방법:** 제품 동작이 승인 변경될 때 해당 규칙을 고친다. 구현 경위·실측 보고는 규정에 쌓지 않고 현재 상태/상세 근거로 연결한다.

최상위 원칙은 개별 규칙보다 우선하므로 번호를 붙이지 않으며 규칙1·2의 식별자와 기존 제목을 유지한다. 제품 동작 규정은 이 문서, 구조·구현 방법은 [네트워크 TDD](../TechnicalDesignDocument_Network.md), 결과 화면 운영은 [MatchFlow](GameSystemRules_MatchFlow.md)가 담당한다. 2026-10-12 이관·당시 참조 문맥과 배치 이유는 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-network-01)에 보존한다.

## 🔴 최상위 원칙 — 플레이어는 자신이 Host 인지 Client 인지 알 수 없다 (2026-09-21 사용자 확정)

**[쉬운 말로]** 이 게임은 P2P(Host-Client) 구조라 두 사람 중 한 명이 서버 역할을 맡지만, **플레이어에게는 자기가 어느 쪽인지 보이지 않는다.** 그러므로 **무슨 상황이든 화면도 승패 기록도 역할과 무관하게 항상 같게 동작해야 한다.**

> 사용자 확정 원문: *"host인지 client인지 플레이어는 파악할수 없잖아 / 무슨 상황이건 항상 일관되게 적용이 되어야 한다고 이게 제일 중요하다고"*

- 🔴 **이것은 개별 기능의 요구사항이 아니라 이 프로젝트의 네트워크 동작 전반에 적용되는 상위 규정이다.** 아래 네트워크 설계 절들과 `GameSystemRules/` 의 네트워크 관련 규칙은 **이 원칙을 어기지 않는 범위에서만 성립**한다. 개별 규칙이 이 원칙과 충돌하면 **고칠 대상은 개별 규칙이다.**
- **적용 범위 3가지** — ① 화면(UI/UX) ② 승패 기록 ③ 이탈·종료 처리. **어느 하나라도 역할에 따라 갈리면 그것은 결함이다.**
- Host 전용 처리에 의존하면 Host가 사라진 뒤 남은 Client의 판정·화면을 보장하지 못한다. 새 네트워크 처리는 Client에도 필요한 판정 경로가 있는지 확인한다.
- 화면의 공통 계약은 [UI](GameSystemRules_UI.md), 결과 화면 이탈은 [MatchFlow](GameSystemRules_MatchFlow.md) 규칙17, 인게임 이탈 판정은 아래 규칙2를 따른다. 구현 구조는 [네트워크 TDD](../TechnicalDesignDocument_Network.md)에서 확인한다.
- 과거 ReconnectionHandler/Relay 코드 실측·행번호 정정·역할 비대칭 판단 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-network-02)다. 과거 가드를 현재 코드에 재확인한 결과로 주장하지 않는다.

## 네트워크 동작 규칙

**규칙 1. 이탈 시 승패 기록 — 규칙 집합 (2026-09-21 사용자 확정 · 미구현 · 별건 작업)**

**적용 범위는 인게임 중 이탈의 승패 기록이다.** 나간 쪽은 패배, 남은 쪽은 승리로 기록하며 Host/Client 역할로 갈리지 않는다. 결과 화면은 승패가 이미 결정된 뒤이므로 그 화면에서 나가도 승패를 바꾸지 않는다. 아래 표와60초 시계는 인게임에만 적용한다.

| 상황 | 나간 쪽 | 남은 쪽 |
|---|---|---|
|로비 버튼/앱 정상 종료|나가기 직전 스스로 패배 기록|통보를 받고 즉시 승리 기록|
|회선 끊김|기록할 기회 없음|60초 뒤 승리 기록|
|앱 강제 종료|기록할 기회 없음|60초 뒤 승리 기록|

앱 강제 종료의 패배 회피를 막기 위해 경기 시작에 진행 중 표시를 저장하고 정상 종료 때 지운다. 다음 실행에 표시가 남으면 미완료 경기로 보고 패배를 기록한다.

**이탈 판정 절차:** 상대 신호가 없으면 상대와 무관한 인터넷 도달을 먼저 확인한다. Host/Client가 같은 절차를 따르며, 도달 가능하면 상대 이탈→내 승리, 불가능하면 내 이탈→내 패배로 판정한다. 확인 대상 후보는 기존 UGS(Relay·Lobby·Cloud Save)이며 후보를 확정 서비스로 승격하지 않는다. 단순 경로 유무는 실제 통신 성공과 다르므로 구현 방식은 [네트워크 TDD](../TechnicalDesignDocument_Network.md)에서 다룬다.

이 절차는 결과 화면의 이탈 판정에도 공유하지만 판정 뒤 행동은 다르다. 인게임은 승패 결정/기록, 결과 화면은 연결 종료와 화면 정리이며 구체 결과 화면 절차는 [MatchFlow](GameSystemRules_MatchFlow.md) 규칙17이다. 잠깐의 내 회선 문제를 상대 이탈로 오판하여 복구 가능한 연결을 스스로 종료하지 않아야 하므로 도달 확인은 결과 화면 작업에서 먼저 마련하고 전적 작업에서 재사용한다.

**남은 한계는 구분한다.** Relay 경로 장애는 양쪽 인터넷이 정상이어도 발생할 수 있어 별건 처리한다. 무효 경기 처리는 제안일 뿐 확정 방침이 아니다. 게임 트래픽만 차단하고 UGS API를 살려 도달 확인을 통과하는 승패 위조는 서버 검증 과제다. 두 항목을 같은 문제로 합치지 않는다.

인게임60초는 전송 계층이 끊김을 통보하는 시점과 같은 시계이며 규칙2를 따른다. 결과 화면30초는 별도 자체 감시로 승패를 정하지 않는다. 화면 문구는 [MatchFlowUI](GameSystemRules_MatchFlowUI.md)가 담당한다.

이 승패 기록 규칙은 기존 미구현·별건 계획 상태이며 최신 진행은 [ROADMAP](../ROADMAP.md)에서 확인한다. 과거 인터넷 도달0건·전적 쓰기 경로를 찾지 못한 코드 조사·초기 과한 한계 진술과 정정·시계 확정 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-network-03)다. 이번 문서 정리를 새 구현 검증으로 읽지 않는다.

**규칙 2. 인게임 이탈 처리 — `ReconnectionHandler` 정리 (2026-09-21 사용자 확정 · 미구현)**

경기 진행 중 상대 이탈의 판정 주체와 시점을 정한다. 기존 문서의 미구현 후속 계약이며 결과 화면 완료를 인게임 구현 완료로 옮겨 적지 않는다.

**확정 D — 인게임 판정도 양쪽이 각자 돌린다 (결과 화면과 같은 구조)**

Host와 Client가 각자 자기 쪽에서 판정한다. Host 전용 감시만 있으면 Host가 사라진 뒤 남은 Client에 판정 주체가 없어 최상위 원칙을 위반한다. 정상 퇴장 통보와 자체 감시는 보완 관계이며 상대 신호 상실 시 규칙1의 인터넷 도달 판정을 따른다. 상세 구조는 [네트워크 TDD](../TechnicalDesignDocument_Network.md)를 참조한다.

작업 순서는 결과 화면 UI·프로세스를 마무리한 뒤 인게임에 같은 구조를 재사용하는 것이다. 인게임 이탈은 결과 화면 단계1~10 범위가 아니며 [ROADMAP](../ROADMAP.md)의 별건 순서를 따른다. 기존 실행 로직의 비활성화·검증·최종 삭제는 [WORKFLOW](../WORKFLOW.md)의 작업 절차를 따른다.

**확정 E — 인게임 판정 시점은 t=60 이며 그 뒤의 유예는 없앤다**

`t=0`은 상대 앱 종료/회선 끊김이며 전송 계층이 연결을 붙드는 `t<60` 구간이 재접속 허용 시간이다. 끊김 통보 시점 `t=60`에서 승부를 결정하고 이후30초 유예를 추가하지 않는다. 일시적 끊김은 전송 계층의 재시도 구간에 포함되며, 완전히 죽은 앱의 상태 복구 구현이 없는 추가 유예는 기다리는 시간만 늘리기 때문이다.

기존 `_reconnectWaitSeconds`·`WaitAndForceWin()`·`OnClientReconnected()`는 함께 정리하는 대상이다. 코드 필드만 고치면 직렬화된 씬 값이 남을 수 있으므로 실제 Inspector/씬 값도 대조해야 한다. NGO 재접속 때 새 ClientId가 부여되는지 과거 조사에서 확인하지 못했으므로 가드 존재만으로 재접속 취소 실패를 단정하지 않는다.

이는 현재 불필요한 유예를 없애는 결정이며 [ROADMAP](../ROADMAP.md)의 향후 실제 재접속 대기 시간120초 제안·보류를 확정하거나 닫지 않는다. 과거 서버 전용 코드·씬 실측·Host 사망 재현·반대역할 ForceWin 미검증·착수순서 변경·필드 출처 원문은 [당시 원문·검증 근거](../History/ImplementationVerificationHistory.md#role-maintenance-20261016-rules-network-04)에 보존한다. 과거 재현 발췌와 직접 재측정한 증거의 범위를 합치지 않는다.

⚠️ **작업 항목은 [ROADMAP.md](../ROADMAP.md) 의 「인게임 이탈 처리 정리(`ReconnectionHandler`)」 행**이고, **구조·시점 규칙의 단일 소스는 이 절**이다 — **로드맵 행에 위 표를 옮겨 적지 않는다.**
