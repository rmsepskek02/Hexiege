# 작업 사이클 운영 규칙

이 파일은 **작업 사이클 메카닉의 단일 권위 소스**입니다.
에이전트 역할은 `CLAUDE.md` 규칙 3, 문서 인덱스는 루트의 `AGENTS.md` 참조.

---

## 작업 시작 전 확인

`CLAUDE.md` 작업 시작 전 체크리스트 [1]이 이 문서를 읽도록 지시하므로, **아래 두 가지는 사이클 [1]에 들어가기 전에 확인한다.**
둘 다 **시스템 프롬프트에 자동 주입되지 않는다** — 직접 열지 않으면 도달하지 못한다.

| 확인 대상 | 무엇을 보나 | 왜 |
|----------|-----------|-----|
| `AGENTS.md` — 문서 인덱스 | 이번 작업에 필요한 문서가 어디 있는지 | 프로젝트 전체 문서의 단일 인덱스다. 여기를 거치지 않으면 관련 규칙 문서를 빠뜨린 채 착수하게 된다 |
| `.claude/mistakes.md` — AI 실수 기록 | 이번 작업과 성격이 비슷한 과거 실수가 있는지 | 같은 실수가 반복되는 것을 막기 위한 누적 기록이다. **목차가 한 건당 한 줄**이라 훑는 비용이 작고, 걸리는 항목이 있을 때만 그 본문을 펼쳐 읽는다 |

- **두 문서 모두 전문을 읽지 않는다.** `AGENTS.md`는 인덱스에서 필요한 문서만 골라 열고, `.claude/mistakes.md`는 목차를 훑은 뒤 해당 항목만 펼친다.
- 「성격이 비슷하다」의 기준은 기술 분야가 아니라 **실수의 모양**이다 — 수치를 다음 사람에게 넘기는 작업이면 인계 수치 항목을, 문서·메모리를 정리하거나 옮기는 작업이면 소실 항목을 본다.
- **작업 중 실수를 인지하면 그 자리에서 `.claude/mistakes.md`에 덧붙인다.** [7]~[11] 문서 반영 단계까지 미루지 않는다 — 미루면 경위가 흐려져 교훈을 만들 수 없다. **사건은 지우지 않는다.**
- **수치나 목록을 사용자·다른 에이전트에게 보고하는 작업이거나 코드 주석·문서의 사실 주장을 판정하는 작업이면, 아래 「검수·판정 작업과 수치 보고의 절차」를 따른다.**

## 폴더 구조

```
Assets/_Project/Docs/_Tasks/         ← 사용자용 작업 문서
└── YYYY-MM-DD/
  └── HH_MM_[작업명]/
    ├── Research.md    ← 코드 파악, 영향 범위, 현재 상태
    ├── Plan.md        ← 구현 접근법, 파일별 변경 내용, 위험 요소
    └── Testcase.md    ← 테스트 시나리오 + 사용자 실기 결과 기록

Assets/_Project/Docs/_Logs/          ← 런타임 로그 + QA-Fix 로그 (상세 규칙: LogRules.md 참조)
```

예시:
```
Assets/_Project/Docs/_Tasks/
└── 2026-03-05/
  └── 18_05_network-input-fix/
    ├── Research.md
    ├── Plan.md
    └── Testcase.md
```

> **시간(HH_MM) 확인 방법**: 폴더 생성 시 현재 시간을 모르는 경우, Bash 도구로 `date +%H_%M` 명령을 실행하여 확인한다. 시간 접두사 생략은 규칙 위반이다.

## 전체 작업 사이클

```
[1] 사용자 작업 요청 → 계획 설명
      ↓
[2] 사용자 승인 ("진행해") → "task 문서 작성을 진행할까요?" 반드시 확인
      ↓
[3] Research.md 작성
      ↓
[4] Plan.md 작성 → 사용자에게 공유 → 명시적 승인 후에만 구현 시작
      ↓
[5] 에이전트 위임 결정 → 컨텍스트 공유 → 구현
      ↓ ← 구현 완료 후 바로 [6]으로 이동 (TC/QA는 사용자가 명시적으로 지시한 경우에만 진행)
[5-1] Testcase.md 작성  ← 사용자가 명시적으로 요청한 경우에만 진행
      ↓
[5-2] Inspector 작업이 필요한 경우: Editor 1회성 스크립트 작성 → 사용자에게 실행 요청 → 사용자 확인
(별도의 Inspector 작업이 없는 경우 생략하고 다음 단계 바로 진행)
      ↓
[5-3] qa-tester 에이전트에게 테스트 요청 및 테스트 진행하여 문서에 반영  ← [5-1] 완료 즉시 진행 (이미 사용자 승인 완료)
      ↓
[6] 구현 내용을 사용자가 테스트하여 작업 완료 여부 확인
(버그 발견 또는 부족한 구현의 경우 재작업)
      ↓
[7] 테스트 완료 확인 즉시 → "문서/메모리 업데이트를 진행할까요?" 반드시 확인
(사용자가 다음 작업으로 넘어가려 해도 이 확인 단계를 생략하지 않음)
      ↓
[8] Testcase.md 결과 업데이트
      ↓
[9] 에이전트 MEMORY.md 업데이트
      ↓
[10] 업데이트 내용 검토
      ↓
[11] 문서 전체 검토 및 반영
      ↓
[12] 변경 파일 리스트업
```

### ⚠️ 절대 금지 사항
- **[2] 승인 후 바로 Edit/Write/Agent 호출 금지** — 반드시 "task 문서 작성할까요?" 먼저 확인
- **[5-1~5-3] TC 작성 및 QA 테스트는 사용자 명시적 지시 없이 진행 금지** — 사용자가 먼저 요청하지 않는 한 TC/QA 제안·진행 불가
- **[6] 테스트 완료 후 다음 작업 전 [7] 업데이트 확인 생략 금지** — "나중에", "다음 세션에" 불가
- **규모/복잡도 무관 — 한 줄 수정도 포함 — 예외 없음**

## 단계별 상세 운영 규칙

### [1] 작업 요청 및 계획 설명
- 착수 전 확인 대상은 상단 **「작업 시작 전 확인」** 참조 (`AGENTS.md` 인덱스 · `.claude/mistakes.md` 목차)
- 사용자 요청 분석 후 작업 범위·접근법 설명
- 승인 전 Edit/Write/Agent 호출 일체 금지

### [2] 사용자 승인 + 문서 작성 여부 확인
- 사용자가 "진행해" 등으로 승인 → 즉시 **"task 문서(Research.md / Plan.md) 작성을 진행할까요?"** 질문
- 사용자가 명시적으로 "문서 생략해도 돼"라고 말하지 않는 한 반드시 확인

### [3] Research.md 작성
- 관련 코드 읽기, 영향 범위 파악
- 현재 버그/상태 분석
- 작업 중 발견한 부가 이슈도 여기에 기록

### [4] Plan.md 작성 및 승인
- **`Assets/_Project/Docs/GameSystemRules.md` 읽기 필수 — 예외 없음. Plan.md 작성 전 반드시 읽을 것.**
  - 세부 규칙은 `Assets/_Project/Docs/GameSystemRules/` 하위 파일에 있다. 인덱스를 먼저 읽고 작업과 관련된 파일을 추가로 읽는다.
- **Plan의 각 수정 항목은 GameSystemRules의 어떤 규칙에 근거하는지 명시할 것.**
- 구체적인 구현 방법, 수정할 파일 목록
- 예상 위험 요소, 아키텍처 제약 사항
- Plan.md 내용을 사용자에게 공유 → **명시적 승인 확인 후에만** 구현 시작
- 계획 변경 시 변경 이유도 추가 기록

#### ⚠️ 기존 로직 제거 규칙 (예외 없음)
Plan에 "기존 로직 제거"를 명시할 때는 반드시 제거해도 안전한 근거를 함께 기술해야 하며, 검증 전까지는 "제거" 대신 "비활성화(주석 처리)" 방식을 기본으로 한다. 또한, 사용자가 바로 파악할 수 있도록 **Plan 문서 최상단에 기술한다**.
주석 처리된 기존 로직의 **최종 삭제는 [6] 사용자 테스트 통과 후, [7] 문서/메모리 업데이트 전**에 수행한다.

### [5] 에이전트 위임 및 구현

어느 에이전트를 부르는지는 `CLAUDE.md` 규칙 3 참조. 전달할 컨텍스트는 아래 표를 따른다.

| 에이전트 | 담당 | 전달 필수 컨텍스트 |
|---------|------|-----------------|
| **game-programmer** | 코드 구현 / 버그 수정 | 관련 파일 경로, 증상, 아키텍처 규칙 |
| **game-design-lead** | 게임플레이 설계 / 밸런스 결정 | 현재 구현 상태, 관련 수치 |
| **qa-tester** | 구현 검증 / 버그 체크 | 변경된 파일 목록, 예상 동작 |
| **asset-prompt-crafter** | 3D 모델 / UI 에셋 생성 | 에셋 스펙, FBX 파이프라인 요구사항 |
| **document-manager** | 모든 문서 생성·수정·동기화 | 변경 내용, 관련 문서 경로 |

> **작업 분해·에이전트 조율은 위 표에 없다 — 메인 세션이 직접 한다.** 서브에이전트는 다른 에이전트를 호출할 수 없으므로(하네스 제약, 설정으로 변경 불가) 조율을 에이전트에게 위임할 수 없다. 종전에 이 표에 있던 `project-orchestrator` 행은 그래서 2026-09-02에 제거됐다. 메인 세션은 최상위라 위 5개 에이전트를 직접 호출할 수 있다.

#### 조율이 필요한 작업의 기준

아래에 해당하면 **메인 세션이 조율·단계 분할·결과 검토를 직접 수행한다.** 개별 실무는 위 표의 전문 에이전트에게 위임하되, 무엇을 어떤 순서로 맡길지와 돌아온 결과의 검토는 메인 세션의 몫이다.

| 상황 | 메인 세션이 직접 조율·검토 |
|------|----------|
| 단일 파일 버그 수정 | 선택 (game-programmer 직접 위임 가능) |
| 설계 결정 + 코드 구현이 함께 필요 | **필수** |
| 3개 이상 파일에 걸친 기능 추가 | **필수** |
| 에이전트 결과 검토 필요 | **필수** |
| 전체 현황 파악 및 다음 작업 결정 | **필수** |

- 구현 완료 후 [6] 사용자 테스트로 바로 이동
- **TC 작성([5-1]) 및 QA 테스트([5-3])는 사용자가 명시적으로 지시한 경우에만 진행** — 먼저 제안하거나 묻는 것도 금지

#### 조율 진행 절차 (7단계)

위 기준에 해당해 메인 세션이 직접 조율할 때는 아래 순서를 밟는다.

1. **이해** — 사용자가 실제로 달성하려는 것이 무엇인지 먼저 확정한다. 모호하면 추측하지 말고 되묻는다.
2. **분해** — 더 쪼갤 수 없는 하위 작업 단위로 나누고, 작업 간 선후 의존을 함께 적는다.
3. **배정** — 각 하위 작업을 담당 에이전트에 배정한다. 어느 에이전트가 무엇을 맡는지는 `CLAUDE.md` 규칙 3과 위 위임 표를 따른다. **이 자리에 에이전트 목록을 옮겨 적지 않는다** — 사본은 에이전트가 늘거나 줄면 조용히 거짓이 된다.
4. **순서 결정** — 의존 관계를 기준으로 순차/병렬 실행 순서를 정한다. 착수 전 분해 결과를 사용자에게 공유하고 승인을 받는다([4]와 같이 승인 전 구현 착수 금지).
5. **실행** — 메인 세션이 전문 에이전트를 **직접 호출**한다. 각 호출은 아래 위임 포맷을 쓰고, 위 표의 「전달 필수 컨텍스트」 열을 빠짐없이 채운다.
6. **검증** — 돌아온 결과를 검토한다. 기대와 다르면 무엇이 어긋났는지 붙여 다시 위임한다. **검토 자체는 위임 대상이 아니다.**
7. **종합** — 결과를 합쳐 사용자에게 보고하고, 남은 항목을 함께 알린다.

- 하위 작업 하나로 끝나는 일을 억지로 여러 단계로 쪼개지 않는다 — 단일 에이전트로 충분하면 바로 위임한다.
- 맞는 에이전트가 없으면 임의로 대신 처리하지 말고 사용자에게 알린다.

#### 위임 포맷

에이전트를 호출할 때의 지시는 아래 5칸을 채워 전달한다.

```
[작업 목표]: 구체적인 목표
[컨텍스트]: 필요한 배경 정보
[범위]: 정확히 무엇을 해야 하는지
[제약사항]: 지켜야 할 규칙이나 제한
[기대 결과물]: 어떤 형태의 결과를 기대하는지
```

### [5-1] Testcase.md 작성
- 구현 완료 후 `Testcase.md`를 작업 폴더에 작성
- 설계 스펙 기반으로 테스트 케이스 목록 작성 (Inspector 작업 완료 여부와 무관)

#### TC 본문 형식
각 TC는 아래 4개 항목으로 구성하며, **반드시 자연어로 작성** (코드 스니펫, 메서드명, 변수명 사용 금지):

```
### TC-N: 테스트 이름

**전제:** 테스트 시작 전 시스템 상태

**동작:**
1. 사용자가 수행하는 조작 순서

**기댓값:**
- 예상되는 결과

**결과:** (사용자 실기 테스트 후 기록 — AI와 문서로 소통하는 채널)
```

- 예시: ~~`unitProductionUseCase.StartProduction()`을 호출하면~~ → "생산 버튼을 누르면 생산이 시작된다"
- TC ID 접두사로 컨텍스트 구분:
  | 접두사 | 대상 |
  |--------|------|
  | `SINGLE-` | 싱글플레이 / 에디터 단독 |
  | `MULTI-` | 멀티플레이 (Host + Client 구성) |
  | `PERF-` | 성능 (프레임, 이벤트 빈도, 대량 오브젝트 등) |

#### QA 섹션 형식
TC 목록과 **별도 섹션**으로 문서 하단에 작성. qa-tester 에이전트 전용 공간:
- 코드, 근거, 버그 ID 등 구체적인 표현 사용
- 정적 분석 결과 + 실기 테스트 결과(가능한 경우) 모두 포함

#### 판정 기준 (3단계)
| 판정 | 의미 |
|------|------|
| `PASS` | 기댓값과 완전히 일치 |
| `FAIL` | 기댓값 미충족, 버그 존재 |
| `CONDITIONAL PASS` | 최종 수렴은 보장되나 조건부 확인 필요 (실기 재확인 요구) |

### [5-2] Inspector 에디터 스크립트 (Inspector 작업이 있는 경우)
- Inspector에서 수동으로 해야 하는 작업이 있을 경우 Editor에서 실행 가능한 1회성 스크립트 작성

#### 검사 범위

역할별 분할 문서의 기존 위치 안내는 실제 규칙 본문과 구별해 집계하고 목적지의 규칙 존재를 확인한다. 숫자·소번호·M/D/L·R 계열·NET-/U-* 식별자를 지원한다. 문자 식별자나 허용된 부분 번호 집합에 임의의 숫자 연속성을 강제하지 않는다. 본문의 완전 보존과 게임 구현 일치는 별도 검토 대상이다.

**매 실행의 `[검사 범위]` 블록이 실제 범위의 권위 소스다.** 탐색 문서와 정의 해석 문서, 원본과 이전 위치 안내, 정의 없는 시나리오, 형식별 정의, 참조·명명 ID·링크·앵커 및 이력보정 수를 구분한다. 그룹·namespace 인용은 정확 ID 검사에서 제외한 수를 표시한다. 이 자리에 실행 숫자를 옮겨 적지 않는다.

```
규칙 정의 원본 : Assets/_Project/Docs/GameSystemRules 하위
참조 검색 대상 : Assets/_Project/Docs 하위 + 루트 AGENTS.md · CLAUDE.md + .claude 하위 (skills/ · plugins/ · worktrees/ 제외)
제외           : _Tasks/ · _Logs/ (이력 기록이라 소급 수정하지 않는다)
```

#### 규칙 정의와 참조 형식

일반 규칙은 `**규칙 ID. 제목**`으로 쓴다. 기존 H3 형식의 `### 규칙 R1 — 제목`, `### NET-AUTH-001. 제목`, `### U-MOV-PHASE. 제목`과 굵은 소번호 정의도 지원한다. 식별자는 전체 문자열로 판정하므로 `20-1`은 하나의 소번호이며 `20~21` 범위와 다르다. 기존 식별자·번호를 검사기에 맞추려고 재배열하지 않는다.

- H2는 섹션명이다. 지원하지 않는 규칙 정의처럼 보이는 줄이나 빈 규칙 검사 범위는 조용히 통과시키지 않고 진단한다. 코드 예시는 실제 정의로 집계하지 않는다.
- 섹션마다 번호가 반복되면 정확한 H2 섹션명을 함께 인용한다. 같은 줄의 다른 섹션 언급으로 그 참조를 대신 특정할 수 없다. 여러 번호 나열과 범위도 각 식별자의 존재를 확인한다.
- 파일 링크와 같은 문서·다른 문서의 앵커를 검사한다. 인라인 Markdown 링크와 제목/HTML id 앵커가 대상이며, 외부 URL 접근·raw 출처 파일·참조식 링크는 검사하지 않는다. 그룹·namespace 인용은 개별 ID 검증을 대신하지 않는다.
- 문서명을 명시한 규칙 참조는 그 문서명에서 80자 이내를 검사하며 마침표 뒤 공백에서 문맥을 끝낸다. `규칙` 접두사 없는 숫자 인용은 검사하지 않는다. 접두사 없는 NET/U ID는 문서명 뒤 공백·인용·조사·목록으로 직접 이어질 때 해당 문서에 결속하고, 중간에 일반 서술이 끼면 ID의 전역 원본을 찾는다. 따라서 모든 자연어 규칙 인용을 빠짐없이 검사한다는 뜻은 아니다.
- 날짜별 보존 원문의 잘못된 섹션 인용은 원문을 고치지 않고 `historical-section` 주석과 눈에 보이는 참조 보정을 덧붙일 수 있다. 주석은 문서명·ID 집합·정확한 섹션을 지정하며 **바로 다음 물리 한 행의 일치하는 참조에만** 적용한다. 빈행을 끼우지 않는다. 문서·섹션·식별자 존재 검사는 유지하며, 잘못된 주석·미적용 주석은 오류다. 전체 이력을 검사에서 제외하는 용도로 쓰지 않는다. 구체 문법은 검사기와 회귀 테스트가 원본이다.
- 과거 변경 기록: 2026-08-25에는 Map·RandomMap·Upgrade 문서를 당시 숫자·굵은 글씨 형식으로 통일해 검사에 넣었다. 2026-10-15 정비로 기존 문자·소번호 형식과 앵커까지 지원하고 정의 해석 누락을 진단하도록 바꿨다.

- **0건을 확인한 뒤 [12]로 넘어간다.** 남은 항목이 있으면 참조하는 쪽을 고쳐 해소하고, 고칠 수 없는 항목은 그 이유를 사용자에게 보고한다.
- **규칙 번호 자체는 고치지 않는다** — 코드 주석과 과거 Task 문서가 그 번호를 참조하고 있어 재배열하면 연결이 끊긴다. 고칠 대상은 항상 참조하는 쪽이다.

## 검수·판정 작업과 수치 보고의 절차

> **이 절이 아래 8개 절차의 단일 소스다.** 2026-10-06, 코드 주석 전수 판정 작업(`_Tasks/2026-10-01/05_19_rules-implementation-audit/`)이 만든 절차 6개와 그 회차의 실수에서 나온 2개를 그 작업의 `Plan.md` §2-5 에서 이 상시 문서로 옮겼다.
> 옮긴 이유: **task 문서는 그 작업 당시의 과정을 남기는 용도라 다음 회차가 찾아보지 않는다 — 거기에만 있으면 효력이 없다.** 그쪽 목록은 그 시점의 기록이고, 앞으로의 개정은 **이 절에서만** 한다(사본은 원본이 바뀌면 조용히 거짓이 된다).
> 근거와 사례(왜 이 절차가 필요했는지)는 그 작업의 `Research.md` §12-6 이하와 `.claude/mistakes.md` 의 2026-10-06 항목들에 있다.

**적용 대상:** 코드 주석·문서의 「사실 주장」(구현 상태·위치·수치·구조·판단)을 판정하거나 고치는 작업 — 그리고 **수치나 목록을 사용자·다른 에이전트에게 보고하는 모든 작업**(7·8번은 검수가 아니어도 적용된다).

1. **고친 문장도 사실 주장이면 판정 대상이다.** 쓴 담당과 **다른 담당**이 같은 파일을 읽는다. 「고쳤다」는 보고는 검증이 아니다 — 거짓을 고치다 새 거짓을 써 넣은 자리가 이 작업에서 3건 나왔고, 담당을 바꿔 전수 재독했을 때 비로소 걸렸다.
2. **규칙 인용은 「그 절에 낱말이 있다」가 아니라 「이 조항이 이 동작을 규정한다」로 확인한다.** 낱말로 찾으면 한 동작이 두 규칙에 흩어져 있을 때 틀린 규칙으로 간다.
3. **범위를 숫자로 좁혀 지시하지 않는다.** 고치려는 **주장**을 정하고 그 주장을 파일 전수로 검색한다. 숫자로 좁히면 알려진 한 자리만 고치고 같은 거짓을 남기며, 한 파일 안에서 앞뒤가 반대가 되는 상태가 새로 생긴다.
4. **문장 안에 참과 거짓이 섞여 있으면 구절 단위로 판정한다.** 문장째 바꾸면 참인 구절까지 지워 과거 버그를 되살릴 수 있다 — 거짓 판단을 지울 때 사실이 함께 사라지면 사실을 남기는 방식으로 고친다.
5. **판정하려는 파일이 순수 C#(Unity·UniRx·TMPro·DOTween·Netcode 를 참조하지 않는 파일)이면 `mcs` 로 컴파일하고 `mono` 로 실행해 먼저 확정한다.** 읽어서 「판정 불가」로 남기기 전에 이 수단을 먼저 쓴다. 한계: 컴파일되고 실행되는 순수 C# 만 덮는다(UI 계층 파일은 대상이 아니다).
6. **동작 코드 무변경은 해시로 증명한다** — 주석과 문자열 리터럴을 걷어낸 코드 본문의 해시를 변경 전과 대조한다. 단 **역검증 네 갈래를 먼저 돌려 도구가 거짓 통과를 내지 않는지** 본다: 주석 한 줄 추가 → 같음 · 공백·개행만 변경 → 같음 · 숫자 표기 변경 → 달라짐 · 문자열 리터럴 한 글자 변경 → 리터럴을 보존하는 해시만 달라짐. 갈래마다 사본이 원본과 실제로 다른지 먼저 확인한다. 공백 변경은 **이미 공백이 있는 자리의 칸 수만** 넓힌다(없던 자리에 넣으면 정규화가 코드 차이로 잡는다).
7. **판정 불가·미해결 항목은 수가 아니라 자리 목록으로 보고받는다** — 파일·행 번호 + 그 주장 + 왜 판정하지 못했는지. 근거: 판정 불가 41자리의 **목록을 잃어 재탐색이 필요해졌고**, 특히 화면 담당 14자리는 목록이 아예 없다. 수만 받으면 나중에 그 항목들을 다시 찾을 수 없다.
8. **숫자를 보고할 때 문서에 적힌 값을 옮기지 않고 그 자리에서 다시 센다.** 근거: 「8자리」를 문서에서 옮겨 보고했으나 다시 세어 보니 실제는 3자리였다(문서값이 낡아 있었다). 다시 셀 수 없는 값은 「전달값」이라고 출처와 함께 적는다.
