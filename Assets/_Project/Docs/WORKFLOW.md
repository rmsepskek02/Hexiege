# 작업 사이클 운영 규칙

이 파일은 **작업 사이클 메카닉의 단일 권위 소스**입니다.
에이전트 역할 정의 및 문서 인덱스는 루트의 `AGENTS.md` 참조.

---

## 폴더 구조

```
_Tasks/                              ← 사용자용 작업 문서
└── YYYY-MM-DD/
  └── HH_MM_[작업명]/
    ├── Research.md    ← 코드 파악, 영향 범위, 현재 상태
    ├── Plan.md        ← 구현 접근법, 파일별 변경 내용, 위험 요소
    └── Testcase.md    ← 테스트 시나리오 + 사용자 실기 결과 기록

_Logs/                               ← 에이전트용 QA-Fix 반복 로그
└── YYYY-MM-DD/
  └── HH_MM_[작업명]/                ← _Tasks와 동일 경로명 (대응 관계)
    └── Log.md         ← QA ↔ DEV 이터레이션 이력 (에이전트 전용)
```

예시:
```
_Tasks/
└── 2026-03-05/
  └── 18_05_network-input-fix/
    ├── Research.md
    ├── Plan.md
    └── Testcase.md

_Logs/
└── 2026-03-05/
  └── 18_05_network-input-fix/
    └── Log.md
```

## 전체 작업 사이클

```
[1] 사용자 작업 요청 → 계획 설명
      ↓
[2] 사용자 승인 ("진행해") → "task 문서 작성을 진행할까요?" 반드시 확인
      ↓
[3] Research.md 작성
      ↓
[4] Plan.md 작성 → 사용자에게 공유 → 명시적 승인 후에만 구현 시작
      ↓
[5] 에이전트 위임 결정 → 컨텍스트 공유 → 구현
      ↓ ← 구현 완료 후 반드시 "TC 작성 및 QA 테스트를 진행할까요?" 사용자 확인
      ↓   승인 시 [5-1]로 진행 / 미승인 시 [6]으로 바로 이동
[5-1] Testcase.md 작성  ← 사용자 승인 후 진행
      ↓
[5-2] Inspector 작업이 필요한 경우: Editor 1회성 스크립트 작성 → 사용자에게 실행 요청 → 사용자 확인
(별도의 Inspector 작업이 없는 경우 생략하고 다음 단계 바로 진행)
      ↓
[5-3] qa-tester 에이전트에게 테스트 요청 및 테스트 진행하여 문서에 반영  ← [5-1] 완료 즉시 진행 (이미 사용자 승인 완료)
      ↓
[6] 구현 내용을 사용자가 테스트하여 작업 완료 여부 확인
(버그 발견 또는 부족한 구현의 경우 재작업)
      ↓
[7] 테스트 완료 확인 즉시 → "문서/메모리 업데이트를 진행할까요?" 반드시 확인
(사용자가 다음 작업으로 넘어가려 해도 이 확인 단계를 생략하지 않음)
      ↓
[8] Testcase.md 결과 업데이트
      ↓
[9] 에이전트 MEMORY.md 업데이트
      ↓
[10] 사용자 MEMORY.md 업데이트 (C:\Users\rmsep\.claude\projects\...\memory\)
      ↓
[11] 업데이트 내용 검토
      ↓
[12] PROJECT_STATUS.md / ROADMAP.md 반영
```

### ⚠️ 절대 금지 사항
- **[2] 승인 후 바로 Edit/Write/Agent 호출 금지** — 반드시 "task 문서 작성할까요?" 먼저 확인
- **[5] 구현 완료 후 TC/QA 확인 생략 금지** — 반드시 "TC 작성 및 QA 테스트를 진행할까요?" 사용자에게 확인할 것
- **[6] 테스트 완료 후 다음 작업 전 [7] 업데이트 확인 생략 금지** — "나중에", "다음 세션에" 불가
- **규모/복잡도 무관 — 한 줄 수정도 포함 — 예외 없음**

## 단계별 상세 운영 규칙

### [1] 작업 요청 및 계획 설명
- 사용자 요청 분석 후 작업 범위·접근법 설명
- 승인 전 Edit/Write/Agent 호출 일체 금지

### [2] 사용자 승인 + 문서 작성 여부 확인
- 사용자가 "진행해" 등으로 승인 → 즉시 **"task 문서(Research.md / Plan.md) 작성을 진행할까요?"** 질문
- 사용자가 명시적으로 "문서 생략해도 돼"라고 말하지 않는 한 반드시 확인

### [3] Research.md 작성
- 관련 코드 읽기, 영향 범위 파악
- 현재 버그/상태 분석
- 작업 중 발견한 부가 이슈도 여기에 기록

### [4] Plan.md 작성 및 승인
- **`Assets/_Project/Docs/GameSystemRules.md` 읽기 필수 — 예외 없음. Plan.md 작성 전 반드시 읽을 것.**
- **Plan의 각 수정 항목은 GameSystemRules.md의 어떤 규칙에 근거하는지 명시할 것.**
- 구체적인 구현 방법, 수정할 파일 목록
- 예상 위험 요소, 아키텍처 제약 사항
- Plan.md 내용을 사용자에게 공유 → **명시적 승인 확인 후에만** 구현 시작
- 계획 변경 시 변경 이유도 추가 기록

#### ⚠️ 기존 로직 제거 규칙 (예외 없음)
Plan에 "기존 로직 제거"를 명시할 때는 반드시 제거해도 안전한 근거를 함께 기술해야 하며, 검증 전까지는 "제거" 대신 "비활성화(주석 처리)" 방식을 기본으로 한다. 또한, 사용자가 바로 파악할 수 있도록 **Plan 문서 최상단에 기술한다**.
주석 처리된 기존 로직의 **최종 삭제는 [6] 사용자 테스트 통과 후, [7] 문서/메모리 업데이트 전**에 수행한다.

### [5] 에이전트 위임 및 구현
에이전트 위임 기준은 `AGENTS.md` 참조.
- 구현 완료 후 반드시 **"TC 작성 및 QA 테스트를 진행할까요?"** 사용자에게 확인
- 승인 시 즉시 [5-1]로 진행 / 미승인 시 [6] 사용자 테스트로 바로 이동

### [5-1] Testcase.md 작성
- 구현 완료 후 `Testcase.md`를 작업 폴더에 작성
- 설계 스펙 기반으로 테스트 케이스 목록 작성 (Inspector 작업 완료 여부와 무관)

#### TC 본문 형식
각 TC는 아래 4개 항목으로 구성하며, **반드시 자연어로 작성** (코드 스니펫, 메서드명, 변수명 사용 금지):

```
### TC-N: 테스트 이름

**전제:** 테스트 시작 전 시스템 상태

**동작:**
1. 사용자가 수행하는 조작 순서

**기댓값:**
- 예상되는 결과

**결과:** (사용자 실기 테스트 후 기록 — AI와 문서로 소통하는 채널)
```

- 예시: ~~`unitProductionUseCase.StartProduction()`을 호출하면~~ → "생산 버튼을 누르면 생산이 시작된다"
- TC ID 접두사로 컨텍스트 구분:
  | 접두사 | 대상 |
  |--------|------|
  | `SINGLE-` | 싱글플레이 / 에디터 단독 |
  | `MULTI-` | 멀티플레이 (Host + Client 구성) |
  | `PERF-` | 성능 (프레임, 이벤트 빈도, 대량 오브젝트 등) |

#### QA 섹션 형식
TC 목록과 **별도 섹션**으로 문서 하단에 작성. qa-tester 에이전트 전용 공간:
- 코드, 근거, 버그 ID 등 구체적인 표현 사용
- 정적 분석 결과 + 실기 테스트 결과(가능한 경우) 모두 포함

#### 판정 기준 (3단계)
| 판정 | 의미 |
|------|------|
| `PASS` | 기댓값과 완전히 일치 |
| `FAIL` | 기댓값 미충족, 버그 존재 |
| `CONDITIONAL PASS` | 최종 수렴은 보장되나 조건부 확인 필요 (실기 재확인 요구) |

### [5-2] Inspector 에디터 스크립트 (Inspector 작업이 있는 경우)
- Inspector에서 수동으로 해야 하는 작업이 있을 경우 Editor에서 실행 가능한 1회성 스크립트 작성
- 메뉴 경로(`Hexiege/...`) 형태로 작성, 사용자에게 실행 요청
- 사용자가 실행 완료를 확인한 후 다음 단계 진행
- 스크립트 실행 완료 후 해당 파일 삭제해도 무방 (1회성)
- 별도의 Inspector 작업이 없는 경우 생략하고 다음 단계 바로 진행

### [5-3] QA 요청
- qa-tester 에이전트에게 Testcase.md와 함께 테스트 요청
- QA 에이전트는 **정적 분석 + 실기 테스트(가능한 경우)** 모두 수행하여 결과를 문서에 반영
- 판정은 `PASS` / `FAIL` / `CONDITIONAL PASS` 3단계 사용
- **멀티플레이 TC**: 에디터(Host) + 빌드(Client) 구성이 필요하여 QA 에이전트 단독 실기 불가 → 해당 TC에 "에이전트 실기 불가 — 사용자 확인 필요" 표기 후 정적 분석만 수행
- 발견된 버그는 BUG-ID로 명시하여 QA 섹션에 기록
- **FAIL 발견 시**: `_Logs/` 하위 동일 경로에 Log.md 생성(없는 경우) 후 해당 Round [QA] 섹션에 버그 기록 → game-programmer에게 Log.md 경로와 함께 수정 요청
- **재QA 시**: Log.md에 다음 Round 섹션 추가 후 동일 절차 반복

## Log.md 운영 규칙

### 위치 및 생성 시점
- 경로: `_Logs/YYYY-MM-DD/HH_MM_[작업명]/Log.md`
- **_Tasks와 동일한 날짜/시간/작업명 폴더**를 사용 (대응 관계 유지)
- QA 에이전트가 FAIL을 처음 발견한 시점에 생성

### 작성 주체
| 섹션 | 작성 주체 |
|------|----------|
| `[QA]` | qa-tester 에이전트 |
| `[DEV]` | game-programmer 에이전트 |

### Log.md 형식

```markdown
# QA-Fix 반복 로그 — [작업명]

## Round 1 — YYYY-MM-DD HH:MM

### [QA] 발견된 문제
- BUG-001: [TC-ID] — [증상 설명]
  - 관련 파일: [파일 경로:라인]
  - 원인 분석: [분석 내용]
- BUG-002: [TC-ID] — [증상 설명]
  - ...

### [DEV] 수정 내용
- BUG-001: [수정 파일:라인] — [수정 내용]
- BUG-002: [수정 파일:라인] — [수정 내용]

## Round 2 — YYYY-MM-DD HH:MM

### [QA] 발견된 문제
...
```

### 운영 규칙
- 모든 PASS → Log.md 생성 불필요
- DEV 수정 완료 후 반드시 [DEV] 섹션 채운 뒤 QA에게 재요청
- Round는 순서대로 append — 이전 Round 내용 수정 금지
- 최종 전체 PASS 시 Log.md에 별도 종료 표기 불필요 (Testcase.md 최종 판정으로 대체)

### [6] 사용자 테스트
- 구현 내용을 사용자가 직접 테스트하여 완료 여부 확인
- 버그 발견 또는 부족한 구현의 경우 재작업

### [7] 문서/메모리 업데이트 확인 ← 절대 생략 불가
- 테스트 완료 확인 즉시 → **"문서/메모리 업데이트를 진행할까요?"** 반드시 질문
- 사용자가 다음 작업을 언급해도 이 확인을 먼저 한 뒤 넘어감

### [8] Testcase.md 업데이트
- 사용자 테스트 최종 결과를 `Testcase.md`에 반영 (PASS/FAIL)
- Plan.md 별도 체크리스트 불필요 — Testcase.md로 통합

### [9] 에이전트 MEMORY.md 업데이트
`AGENTS.md`의 완료 후 업데이트 체크리스트 참조.

### [10] 사용자 MEMORY.md 업데이트
- `C:/Users/rmsep/.claude/projects/.../memory/MEMORY.md`: 아키텍처 결정, 중요 교훈, 핵심 제약 반영

### [11] 업데이트 내용 검토
- 각 에이전트가 작성한 MEMORY.md 변경 내용을 확인
- 잘못 기록된 내용, 누락된 항목 수정

### [12] 문서 반영
- `PROJECT_STATUS.md`: 완료된 시스템/버그 수정 항목 갱신
- `ROADMAP.md`: 완료된 항목 제거, 다음 우선순위 조정
- `WORK_HISTORY.md`: 완료된 작업 마일스톤 추가

## 규칙

- 작업 폴더는 삭제하지 않음 (히스토리로 보존)
- **계획 단계(Research/Plan 작성 시)**: 에이전트(Agent) 호출 허용 — 코드 파악, 설계 검토, 의견 수렴에 활용
- **승인 전 금지**: Edit/Write(파일 수정/생성) 일체 금지 — 코드 변경은 반드시 사용자 승인 후에만
- **승인 후 즉시 구현 금지**: 승인 → "task 문서 작성할까요?" 확인 → 문서 작성 → 구현 순서 준수
- **테스트 완료 후 다음 작업 이동 전**: 반드시 "문서/메모리 업데이트를 진행할까요?" 확인 먼저
- project-orchestrator는 단일 에이전트 작업이든 복합 작업이든 계획·조율·검토가 필요할 때 언제든 사용
- 위 사이클의 어떤 단계도 "간단하니까", "한 줄이니까" 등의 이유로 생략 불가 — 예외 없음
