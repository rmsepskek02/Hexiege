이 계획은 게임 문서를 역할별로 정리하고, 서로 다른 수치와 상태 설명을 근거에 맞춰 통일하기 위한 것이다. 같은 본문은 기준 문서 한 곳으로 모으고, 여러 목적이 섞인 문서는 나누되 기존 규칙과 과거 기록을 계속 찾을 수 있게 한다. 사용자 실행 승인을 받은 뒤 아래 계획을 적용했으며 말미에 실제 실행 판정을 기록한다.

## 3. 기존 참조가 끊기지 않도록 하는 조건

1. 새 규칙 파일은 `GameSystemRules/` 바로 아래에 둔다. 검사기의 규칙 파일 glob은 비재귀라는 메인 확인을 반영하며, 하위 폴더를 새로 만들어 조용히 검사에서 빠뜨리지 않는다.
2. 규칙 번호와 NET-/U-* 식별자는 재번호하지 않는다. 기존 문서 경로·원래 H2·규칙 번호별 목적지 대응표를 먼저 작성한다.
3. 원본 경로는 파일로 유지한다. 이동한 H2·기존 앵커를 남기고 각 규칙의 새 원본으로 안내한다. 이 안내는 규칙 본문 사본을 재생성하지 않는다.
4. 같은 번호가 여러 섹션에 있으면 문서명+섹션명+규칙 번호로 가리킨다. 기존 UI/Buildings 참조의 섹션 식별을 유지한다.
5. 코드 주석·과거 Task/Log·에이전트 메모리의 참조는 읽기 조사 목록에 포함하되, 이번 본문 정리 승인만으로 코드·기존 Task/Log를 수정하지 않는다. 옛 경로에 안내가 남아 목적지에 도달하는지 확인한다.
6. 규칙 정의의 굵은 형식과 검사 범위를 WORKFLOW [11]에 맞춰 확인한다. 이동된 번호가 원본에서 안내만 남으면 검사기가 옛 번호를 결번으로 볼 가능성을 실측한다. checker와 호환 안내가 충돌하면 분할을 강행하지 않고 해당 이관을 보류한다. 검사기 변경은 별도 범위 결정 사항이다.

근거: WORKFLOW [11] 번호·형식·검사 범위, doc-conventions §53. 메인이 전달한 기존 GameEvents 및 GameBootstrapper.Map의 UI/RandomMap 참조 사례도 보존 조건에 포함한다.

상태는 사양 확정 여부, 에셋 준비·연결, 구현·구조 이행, 자동 검증(실행 범위/날짜), 사용자 실기(단독/멀티/역할·대상 범위)로 구분한다. 기존 상태값의 의미를 바꾸지 않고 필요한 열을 추가한다. `MigrationRequired`를 미테스트로, native PASS를 실제 경기 수용으로, 일부 유닛 수용을 full migration으로 바꾸지 않는다.

시간은 초를 기준으로 하고, 프레임 표기가 필요한 경우 `초:프레임(FPS)`와 확인 근거를 붙인다. 30fps가 확인된 값만 환산한다. 타격 시점·공격 주기·클립 길이·발동 후 쿨다운은 서로 다른 값으로 유지한다. 표 셀에 긴 실행 기록을 넣지 않고 근거 링크를 둔다.

## 6. 위험·롤백·검증 범위

- **참조 단절:** 규칙 번호와 옛 섹션 대응표·안내 경로가 통과하기 전 이관을 완료 처리하지 않는다.
- **유일 정보 소실:** 이관 전 블록 사본과 목적지 비교·주장 목록을 작업 근거로 보존. 맞지 않으면 해당 단계만 다시 편집하여 원상 배치한다. 자동 Git restore/reset은 사용하지 않는다.
- **사양 변경 혼입:** 기술 구조 정리와 제품 사양 정정을 분리해 검토한다. 밸런스나 게임 기능 변경이 필요하면 별도 결정/작업으로 분리한다.
- **상태 확대:** 과거 PASS 범위와 전체 미완료 조건을 같은 항목에서 추적한다. OPEN이 무엇인지 위치와 근거를 보고한다.
- **검사기 사각지대:** WORKFLOW [11]의 `[검사 범위]` 및 형식을 확인한다. Task 제외·NET-* 규약·앵커·사실 진위는 별도로 검토한다. 0건을 전체 정확성으로 전달하지 않는다.
- **현재 검사 환경:** WindowsApps python3 별칭 실패로 Research 작성 시 검사 미실행. 실행 단계에서는 사용 가능한 실제 런타임으로 검사하며 불가하면 원인·미검증 범위를 보고한다. 임의 설치·baseline 직접 편집 없음.

이번 계획 문서에는 Testcase를 만들거나 게임 QA를 실행하지 않는다. 문서 자체 링크·변경 범위·근거 재독은 계획 산출물 검토이며 게임 실기 완료 판정이 아니다.

## 10. 실제 구현값 기준 정정 — 사용자 추가 결정

구조 정리 후 사용자가 유닛 스탯·공격 시간·건물 기획 문서를 **실제 구현 기준으로 맞추도록** 지시했다. 스탯 밸런싱은 추후 진행하고, 공격 시간은 이미 교정한 실제 생산 연결값을 기준으로 기록한다. 이는 코드·클립·설정 변경이나 새 게임 QA 승인이 아니라 문서 사본 정정이다.

- StatsReference의 문서/config 충돌은 구현 저장값으로 정정하고, 설정 fallback과 실제 UnitFactory가 선택·추출하는 production clip 값은 분리한다. Fox 피해와 VFX marker, Torrent 발사와 접촉, Bloom 발동 후 쿨다운 예외를 유지한다.
- 현재 연결된 25개 유닛의 타격·주기는 game-programmer의 읽기 전용 생산 연결·설정·소비 경로 조사와 메인 독립 검토를 근거로 반영한다. 기존 날짜 기록과 원래 시간 표기는 보존한다.
- 건물은 현재 실행 경로에서 지원하는 기능만 현행 GDD 본문에 둔다. 유일한 선택적 기획은 별도 미확정 기획 절로 보존하고 원문을 지우지 않는다. 이름 검색에 없다는 이유만으로 구현이 없다고 판단하지 않고 배치·업그레이드·수입·공격·수리 소비 경로를 확인한다.
- AI 종족 시나리오는 수지 숫자·빌드오더를 바꾸지 않고 새 논의 백로그로 둔다.
- 현재 Task의 Research/Plan에 이 추가 결정과 old→new 값·근거·검증을 반영한다. 기존 Task/Log·원문 History·코드·에셋·메모리·Unity·Git 변경은 수행하지 않는다.

이 절의 추가 결정은 앞 §8~§9에 기록된 첫 정리 완료 당시의 보류 범위를 갱신한다. 실제 정정 결과와 남은 확인 항목은 Research의 후속 절에 기록한다.

### 추가 결정의 적용 결과

실제 config25개와 연결된 생산 클립·Factory 소비 경로를 확인해 Stats를 정정했다. Rabbit 공격 연구표도 기존8% 계산식으로 동기화했다. GDD 채굴소·본기지는 현재 지원 기능으로 정리하고 이전 선택적 기획을 별도 절에 원문 보존했다. AI 시나리오 재논의는 ROADMAP 백로그로 남겼다.

문서 담당 비교에서 기본25행·기존 시간 원문25행 mismatch0 및 checker exit0·문제 없음이다. EagleArcher는 실제 클립 열거 순서를 실행 관측하지 않아 두 주기 가능성을 표시했다. 메인의 독립 검토와 기존 전체 migration·정밀·네트워크 미결은 별도다. 값·원문·근거와 정확한 검증 범위는 Research §11을 따른다.
