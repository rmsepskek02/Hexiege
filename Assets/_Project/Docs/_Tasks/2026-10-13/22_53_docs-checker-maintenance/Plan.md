# 문서 검사기 정비 — 계획

문서가 분할되거나 규칙 이름이 달라져도 잘못된 참조를 빠뜨리지 않도록 검사기를 정비한다. 현재 확인된 누락을 작은 단계로 고치고, 일부 문서를 읽지 못했는데도 문제가 없다고 보고하는 상황을 막는다. 기존 문서 이력과 메모리 보호 기능은 유지한다.

**현재 상태: 구현·검증·상시 안내 동기화 완료, main 병합 대기.** 사용자가 승인한 검사기 구현과 실제 문서 점검을 마쳤다. 코드 세대별 검증 범위와 main의 마지막 실행 확인은 Research §10에 기록했다. *(2026-10-15 — 구현 승인 이후 실제 검증 완료 결과를 반영했다.)*

**작업 위치 갱신(2026-10-15):** 다른 유닛 작업의 미커밋 변경을 보호하기 위해 main 기반 별도 worktree `D:/Projects/Hexiege/Hexiege/.utmp/docs-checker-finalize`, 브랜치 `codex/docs-checker-finalize`에서 재개했다. 공유 작업 경로에서는 수정하지 않는다. 최초 조사 브랜치와 준비된 변경의 복원 경위는 Research §8에 기록한다.

**기존 로직 제거 계획:** 검사 항목·CLI·메모리 보호 동작의 폐지는 제안하지 않는다. 잘못된 숫자·섹션 판정은 같은 검사 목적을 충족하는 판정으로 교정한다. 기존 경로를 교체할 때는 `WORKFLOW.md` [4]의 비활성화 우선 원칙에 따라 검증 전 원본 경로를 보존하고, 정상·오류 회귀 검증 후 최종 처리한다. 되돌릴 수 없는 조기 삭제와 검사 회피용 규칙 번호 변경은 하지 않는다.

## 3. 실행 순서

### 단계 1 — 누락을 드러내는 회귀 입력 확보

- 숫자 정상·잘못된 번호, 문서 미등록, 잘못된 섹션, 섹션 간 결번 은폐, 나열된 뒤 번호 누락을 합성 입력으로 재현한다.
- 실제 사용 중인 소번호·문자 ID·숫자 ID 형식을 재현하고, 지원해야 하는 정상 입력과 실패해야 하는 입력을 구분한다.
- 이력 제외, 기본 읽기 전용과 메모리 보호의 현재 정상 동작을 테스트로 고정한다.
- 테스트는 실제 규칙·메모리 파일을 깨뜨리지 않고 임시 저장소·임시 기준값에서 실행한다.

### 단계 2 — 정의와 참조의 정확한 연결

- 실제 정의를 문서·필요한 섹션·전체 식별자로 구분한다. 소번호를 범위로 쪼개지 않는다.
- 동일 줄의 여러 문서·섹션·번호 목록을 각각 연결한다. 다른 섹션의 번호·제목으로 통과하지 않도록 한다.
- 최대 번호 비교 대신 해당 식별자의 존재를 확인한다. 범위 표기는 의도한 번호 집합을 검사하고 뒤집힌 범위·잘못된 구문을 조용히 무시하지 않는다.
- NET-/U-*는 `규칙` 접두사가 없는 기존 식별자 인용도 대상으로 삼되, 일반 단어·예시·정의 자기 자신을 참조 오류로 오인하지 않는다.
- 반복 번호 문서의 섹션별 결번을 해당 섹션 정의로 판정한다. 동일 영역 내 중복은 의도된 다른 섹션 반복과 구별한다.

### 단계 3 — 원본·안내와 검사 범위 진단

- 분할된 원본과 기존 위치 안내를 구별하고 안내가 연결하는 목적지 존재를 확인한다. 안내 삭제나 번호 재배열로 문제를 숨기지 않는다.
- MatchFlow의 부분 번호 집합을 정상적으로 검사한다. 문자 ID를 임의로 연속 번호로 간주하지 않는다.
- 규칙 문서 탐색 수, 실제 정의 해석 수, 안내와 형식별 검사 범위, 해석되지 않은 후보를 확인할 수 있게 출력한다.
- 규칙 폴더 소실·빈 정의·규칙처럼 보이는 미지원 형식·알 수 없는 대상 문서를 조용한 성공으로 처리하지 않는다. 시나리오 등 원래 번호 정의가 없는 문서는 이유를 구별한다.
- 기존 `--root` 등의 의미와 정상 호출을 유지하고, 판정 불가·생략과 통과를 구분한다.

### 단계 4 — Markdown 연결과 앵커

- 같은 문서의 `#앵커`, 다른 Markdown 문서의 `파일.md#앵커`, 명시적 HTML 앵커 및 실제 제목 앵커를 검사한다.
- 한글·이모지·중복 제목·인코딩·공백 경로와 외부 URL 제외를 회귀 입력으로 고정한다. 코드 예시나 UI 표시 문구로 인한 오탐을 확인한다.
- 비 Markdown raw 출처·모든 확장자 링크·외부 사이트 연결 검사까지 무조건 확대하지 않는다. 첫 범위는 현재 문서의 Markdown 연결과 앵커이며, 남는 미지원 형식은 명시한다.

### 단계 5 — 독립 검수·운영 문서 동기화·병합 준비

- game-programmer가 회귀 입력을 검증하고 메인 세션이 코드와 실행 근거를 독립 검토한다. 별도 TC/QA 단계는 사용자 지시가 있을 때만 진행한다.
- 실제 저장소에서 새 검사를 실행하고 새 보고를 검사기 오탐·실제 참조 문제·의도된 이력/예시로 분류한다. 오류를 없애려고 검사 대상이나 번호를 임의 축소하지 않는다.
- 승인 범위의 상시 운영 안내만 document-manager가 동기화한다. 현재 Task에 실제 수정 목록·검증 출력과 한계를 남긴다.
- main 병합 전에 변경 범위와 회귀 결과를 확인한다. 사용자 지시한 별도 브랜치 작업 후 main 병합 순서를 지키며 푸시는 별도 사용자 지시에 따른다.

## 4. 검증 기준

| 검증 묶음 | 통과 기준 |
|---|---|
| 식별자·참조 | 정상 숫자/소번호/문자 ID는 통과. 없는 번호·ID·문서, 나열 끝의 오류와 잘못된 소번호 해석은 진단. |
| 섹션 | 다른 섹션에 같은 번호가 있어도 결번을 탐지. 같은 줄의 다른 섹션 언급으로 잘못된 참조가 면제되지 않음. |
| 분할·안내 | 기존 위치 안내와 올바른 목적지는 통과. 깨진 목적지 및 필요한 정의 누락은 진단. 실제 원본의 비연속 집합을 무조건 결번 처리하지 않음. |
| 범위 | 규칙 폴더·정의가 없거나 미지원 정의가 있어도 무조건 0건으로 끝나지 않음. 숫자가 아닌 문서의 검사 포함 여부가 출력으로 드러남. |
| 링크 | 실제 파일·앵커는 통과. 존재하는 파일의 없는 앵커, 같은 문서 없는 앵커는 진단. 명시 HTML·제목 앵커와 공백·인코딩 처리 확인. |
| 이력 제외 | 임시 `_Tasks/`·`_Logs/` 및 외부 문서 제외에 오류를 넣어도 상시 검사에 섞이지 않음. |
| 메모리 | 고아 토픽·기준값 소실·1행 감소를 탐지. 증가 안내는 오류와 분리. 사유 없는 감소 갱신 거부 및 사유 있는 임시 갱신 이력 보존 확인. |
| 읽기 전용 | 기본 실행 전후 문서·메모리·실제 기준값 해시 동일. 테스트용 갱신 경로는 임시 기준값에만 적용. |
| 실제 저장소 | 새 보고의 모든 항목을 근거로 분류·해소 또는 이유를 보고. 0건과 함께 실제 검사 범위·남은 한계를 명시. |

검사기 정비는 Unity 게임 동작을 변경하지 않으므로 Unity 빌드·기기 경기 테스트가 기본 검증에 필요하지 않다. Python 회귀 테스트와 실제 문서 입력 검증으로 도구의 행동 계약을 확인한다. 본문 의미 및 게임 구현 일치까지 검증 완료로 확대하지 않는다.

## 5. 구현 전 남은 선택과 위험

- 원본·안내·비연속 번호 집합의 표현 방식은 구현 담당자가 제안하고 근거를 남긴다. 파일명·본문 문구 추측만으로 광범위하게 예외 처리하지 않는다.
- 제목 앵커 규칙과 구문 인용 처리 기준을 테스트 및 운영 안내에 함께 고정한다. 지원하지 않는 Markdown 구문을 정상 검사로 주장하지 않는다.
- 강화된 검사에서 발견한 실제 상시 문서 문제는 해당 위치만 고친다. 기존 이력·기획 정책까지 수정해야 한다면 별도 논의한다.
- [5]의 낱말 겹침은 보조 진단이다. 의미 정확성 판정처럼 표현하지 않으며 검사 강화를 위해 기존 규칙 내용을 임의 재작성하지 않는다.
- 실제 메모리 기준값은 이번 계획에서 갱신하지 않는다. 낡은 기준값 안내와 검사기 결함을 분리한다.
