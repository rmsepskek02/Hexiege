## 이 조사가 무엇이고 왜 필요한가 (자연어 설명 — 기술 용어 없이)

> **[보존 — 2026-08-13 07:27 작성 시점의 설명이다.]**
> 아래 설명은 *"쪽지를 떼는 작업"* 이라는 당시 인식을 그대로 담고 있다.
> **확정된 방향은 "떼기"가 아니라 "두 축으로 갈라 `GameLog`로 옮기기"다**(§0).
> 그럼에도 이 설명을 남기는 이유는, **"왜 남길 로그와 뗄 로그를 갈라야 하는가"** 라는
> 이 문서의 핵심 문제의식이 개정 후에도 그대로 유효하기 때문이다.
> 달라진 것은 **가르는 축의 개수와, 가른 뒤에 무엇을 하는가**뿐이다.

게임을 만들다 보면 개발자가 프로그램 안에 **"지금 여기까지 왔다"** 는 쪽지를 잔뜩 붙여 둡니다.
문제가 생겼을 때 어디서 잘못됐는지 찾기 위한 것입니다.

지금 이 게임의 **접속·방 만들기·로그인** 부분에는 그런 쪽지가 **209장** 붙어 있습니다.
그런데 이 중 상당수는 **이미 테스트가 끝나서 더 볼 이유가 없는 쪽지**입니다.
예를 들면 *"건물 만들기 성공"* 같은 것인데, 건물이 만들어졌는지는 **화면을 보면 바로 알 수 있으므로**
굳이 쪽지로 남길 이유가 없습니다.

사용자가 **"이미 테스트가 끝난 불필요한 쪽지는 떼는 것을 원칙으로 하자"** 고 정했습니다.
이건 새로운 규칙이 아니라, **원래 있던 규칙을 이제야 지키는 것**입니다
(`LogRules.md` 금지사항 1이 이미 이런 쪽지를 진단용으로 쓰지 말라고 정해 두었습니다).

### 그런데 전부 떼면 안 됩니다 — 이 조사의 핵심

쪽지 중에는 **성격이 완전히 다른 것이 섞여** 있습니다.

- **떼야 하는 쪽지**: *"건물 만들기 성공"*, *"화면 켜짐"* — 개발 중에만 쓰던 흔적
- **남겨야 하는 쪽지**: *"인터넷 서버에 연결 실패했음"*, *"로그인 서버가 응답을 안 함"* —
  이건 **플레이어 기기에서만 벌어지는 일**이라, 이 쪽지가 없으면 나중에 *"게임이 안 켜져요"* 라는
  문의가 왔을 때 **원인을 알아낼 방법이 아예 없어집니다.**

그래서 **이번 작업의 본체는 "지우기"가 아니라 "가르기"** 입니다.
어떤 쪽지가 어느 쪽인지 **판단하는 기준을 먼저 세우는 것**이 이 조사의 목적입니다.

### 이 조사에서 새로 밝혀진 것 네 가지

**첫째, 상위 조사가 준 숫자에 오차가 있었습니다.**
일부는 **이미 주석 처리되어 실행되지 않는 줄**이고, 일부는 **설명글 안에 적힌 글자**였습니다.
실제로 실행되는 쪽지만 다시 셌습니다. (§2-2)

**둘째, 조사 도중에 파일이 바뀌었습니다.**
동시에 진행 중이던 다른 작업이 **07:16에 완료**되면서 로그인 관련 파일 두 개의 숫자가 달라졌습니다.
바뀐 뒤 기준으로 다시 쟀고, **어느 시점 기준인지 문서에 명시**했습니다. (§2-3)

**셋째, "다른 방식으로 옮겨 쓰면 된다"는 전제가 성립하지 않습니다.**
규칙 문서는 쪽지를 `RuntimeLogger`라는 다른 도구로 옮겨 쓰라고 되어 있는데,
실제로 그 도구를 확인해 보니 **특정 작업을 디버깅하는 동안에만 잠깐 쓰는 도구**였고,
지금 이 프로젝트에서 **그 도구를 쓰는 곳은 한 군데도 없습니다.** (§6)

**넷째, 쪽지를 떼면 프로그램이 깨지는 자리가 있습니다.**
쪽지가 **"만약 ~라면"의 유일한 내용물**인 자리가 **9곳** 있습니다.
쪽지만 떼면 빈 껍데기가 남아 **프로그램이 아예 컴파일되지 않거나, 오류를 조용히 삼키게** 됩니다. (§8)

## 0. 방향 전환 경위 (2026-08-13 갱신 시 신설)

### 0-0. 쉬운 말로 먼저

이 조사를 끝냈을 때의 결론은 **"쪽지를 진단용과 운영용으로 나눠서, 진단용은 떼자"** 였다.
그런데 그 뒤 사용자와 로그 규칙 전반을 이야기하면서 **그 한 가지 잣대로는 판정이 안 된다**는 것이 드러났다.

문제가 된 예는 이렇다.

- **골드가 모자라 생산이 거부됨** — 심각해 보이지만(경고), 화면에 이미 *"골드가 부족합니다"* 가 뜬다.
  → **출시본에는 남길 필요가 없다.**
- **랜덤 매칭이 실패함** — 대수롭지 않아 보이지만, 실패 **이유**가 이 쪽지에만 들어 있다.
  → **출시본에 반드시 남겨야 한다.**

**심각한 쪽이 오히려 필요 없고, 안 심각한 쪽이 필수다.** 잣대 하나로는 이 둘을 가를 수 없다.
그래서 잣대를 **두 개**로 나눴다 — *"얼마나 심각한가"* 와 *"출시본에 남길 것인가"* 는 **서로 다른 질문**이다.

여기에 하나가 더 붙었다. 사용자가 **라이브 운영 중에 버그 지표를 서버로 모을 계획**이라고 밝혔다.
그러면 남길 쪽지는 **나중에 서버가 알아볼 수 있는 형태**여야 한다.
쪽지를 그냥 두고 나중에 전부 뜯어고치면 늦으므로, **지금부터 그 이음매를 만들어 두기로** 했다.

**결론: 이 작업은 "지우는 일"이 아니라 "두 축으로 갈라서 새 통로(`GameLog`)로 옮기는 일"이 되었다.**

### 3-3. 가르는 질문 (기준을 한 줄로 압축)

> **"이 로그가 없는 상태에서 플레이어가 *'게임이 안 돼요'* 라고 문의했을 때, 원인을 좁힐 수 있는가?"**

## 8. 영향 범위 — 제어 흐름과 얽힌 로그 **9곳**

로그를 지우면 **컴파일이 깨지거나 동작이 달라지는** 자리다. 전수 스캔 결과다.

### 8-1. 중괄호 없는 `if`/`else`의 **유일한 본문** — 3쌍 (6건)

**① `LobbyManager.cs:271~274`**
```csharp
if (lobby != null)
    Debug.Log($"[Matchmaker] 매칭 Lobby 발견! Name={lobby.Name}, Id={lobby.Id}");
else
    Debug.Log($"[Matchmaker] FirstOrDefault null — 비교 실패");

return lobby?.Id;
```
> 두 로그만 지우면 `if (lobby != null) else` 가 남아 **컴파일 오류(CS1525)** 다.
> **`if`/`else` 구문 전체(4줄)를 함께 지워야 한다.** `return lobby?.Id;`는 로그와 무관하므로 동작은 불변이다.

**② `NetworkGameManager.cs:718~721` / ③ `:739~742`**
```csharp
bool result = NetworkManager.Singleton.StartHost();
if (result)
    Debug.Log("[Network] NetworkManager.StartHost() 성공.");
else
    Debug.LogError("[Network] NetworkManager.StartHost() 실패.");

return result;
```
> **성공 쪽(`Debug.Log`)은 진단, 실패 쪽(`Debug.LogError`)은 운영**이다 — **한 구문 안에서 분류가 갈린다.**
> 성공 로그만 지우려면 `if (result) ... else ...` 를 `if (!result) Debug.LogError(...)` 로 **반전**해야 한다.
> **단순 삭제가 불가능한 자리다.**

### 8-2. `catch` 본문이 **로그 1줄뿐** — 5곳

로그를 지우면 `catch { }` 가 되어 **예외를 조용히 삼킨다.**

| 파일:라인 | 예외 종류 | 분류 |
|-----------|-----------|:-:|
| `NetworkGameManager.cs:400~403` | `StartMatchmakingAsync` 예외 | 운영 |
| `NetworkGameManager.cs:629~632` | 티켓 삭제 오류 (무시) | 운영 |
| `LobbyManager.cs:379~382` | Relay Join Code 업데이트 실패 | 운영 |
| `LobbyManager.cs:444~447` | Lobby 나가기 실패 | 운영 |
| `LoginUseCase.cs:387~390` | UGS SignOut 예외 (무시) | 운영 |

> **5곳 모두 운영 로그로 판정되어 이번 제거 대상이 아니다.** 즉 **실제 충돌은 발생하지 않는다.**
> 다만 *"catch 안의 로그는 지우지 않는다"* 는 것을 **작업 지침으로 명시**해야 사고를 막는다.

### 8-3. `catch` 본문에 다른 문장이 함께 있는 곳 — 21곳

`Debug.LogError(...)` + `OnError?.Invoke(...)` 또는 `return null;` 형태다.
로그만 지워도 컴파일·동작에 문제가 없다. **다만 전부 운영 로그로 판정되어 제거 대상이 아니다.**

### 8-4. 얽힘 없음이 확인된 항목

| 확인 항목 | 결과 |

**① 두 축이 코드 구조로 강제된다**

| 축 | 코드에서의 표현 | 강제되는 방식 |
|----|----------------|--------------|
| **A — 심각도** | **메서드 이름** — `Info` / `Warn` / `Error` | 셋 중 하나를 고르지 않으면 호출할 수 없다 |
| **B — 존속** | **중첩 클래스** — `GameLog.Ops` (운영) / `GameLog.Dev` (개발) | **둘 중 하나를 지나야만 메서드에 닿는다.** 즉 *"축 B를 깜빡한다"* 는 실수가 성립하지 않는다 |

호출 형태:
```
GameLog.Ops.Error(LogEvent.UnhandledException, "Runtime", nameof(GameBootstrapper), "메시지", "key=value");
GameLog.Dev.Warn("UI", nameof(ProductionPanelUI), "메시지");
```

**두 축의 차이가 컴파일 단계에서 갈리는 지점 2개:**

1. **`Ops`는 `LogEvent`를 필수 첫 인자로 받고, `Dev`는 아예 받지 않는다.**
   → *"운영 로그에 이벤트 키 생략"*(`LogRules.md` **1.14 금지 사항** 6)이 **컴파일 불가**가 된다.
2. **`Dev`의 4개 메서드에만 `[Conditional("UNITY_EDITOR")]` + `[Conditional("DEVELOPMENT_BUILD")]` 가 붙어 있다.**
   `Ops`에는 붙어 있지 않다 — 릴리스에서 살아야 하기 때문이다(**금지 사항** 7).

**② 재진입 가드가 3겹이다**

`ConsoleSink`는 최종적으로 `Debug.Log*`를 호출하고, `GameBootstrapper`는 미처리 예외 수집을 위해
`UnityEngine.Application.logMessageReceived` 훅을 걸어 두었다. 두 개를 그대로 두면 고리가 만들어진다.

```
GameLog.Emit → sink → Debug.LogError → logMessageReceived 훅 → GameLog.Emit → ...
```

이 고리를 **세 겹으로** 끊는다 (`GameBootstrapper.Setup.cs` `OnUnityLogMessageReceived`):

| 겹 | 방어 | 내용 |
|:-:|------|------|
| 1 | **종류 필터** | `LogType.Exception` 이 아니면 즉시 반환. sink의 평범한 출력(Log/Warning/Error)은 훅을 통과조차 못 한다 |
| 2 | **재진입 플래그** | `GameLog.IsEmitting` 이 참이면 즉시 반환 — 지금 들어온 것은 우리가 방금 만든 출력이 되돌아온 것이다 |
| 3 | **직전 값 비교** | 메시지 + 스택이 직전과 동일하면 무시. 훅 전달이 동기가 아닐 경우 2겹이 뚫리는 것에 대비한 그물이다 |

여기에 더해 **`GameLog.Emit` 자체가 `_isEmitting` 플래그를 `try/finally`로 관리**한다.
`finally`에서 반드시 내리는 이유는, 한 번이라도 못 내리면 **그 뒤의 모든 로그가 영구히 차단**되기 때문이다.

**③ 레이어 분리 — 의존 방향이 뒤집히지 않는다**

- **계약(`ILogSink`)과 facade(`GameLog`)는 Application에**, **구현체(`ConsoleSink`/`FileSink`)는 Infrastructure에** 둔다.
  운영 로그는 모든 레이어에서 호출되는데 facade를 Infrastructure에 두면 `Application → Infrastructure` 참조가 생긴다.
- **sink 등록은 `GameBootstrapper`만 수행한다** — `.claude/MEMORY.md`의 *"GameBootstrapper가 유일한 의존성 조합 루트"* 그대로다.
- **`LogLevel` enum이 두 네임스페이스에 존재한다.** `Hexiege.Application.LogLevel`(신규)과
  `Hexiege.Infrastructure.LogLevel`(기존 `RuntimeLogger` 용). Infrastructure 쪽 파일에서 수식 없이 `LogLevel`이라고 쓰면
  **자기 네임스페이스 것으로 해석되어 인터페이스 구현이 성립하지 않는다.**
  그래서 `ConsoleSink`/`FileSink`는 구현 시그니처에서 `Hexiege.Application.LogLevel` 로 **완전 수식**하고,
  `FileSink`는 `MapLevel`로 1:1 변환한다.
  → **컴파일 미검증 상태에서 가장 먼저 터질 수 있는 자리다**(Plan.md §3-0).

**④ 그 외 확인한 구현 사실**

| 항목 | 구현 내용 |
|------|----------|
| **sink 등록 갈래** | **에디터: `FileSink` 하나만 / 빌드: `ConsoleSink` 하나만.** 둘을 함께 등록하면 `RuntimeLogger`가 파일+콘솔에 동시 출력하므로 콘솔에 같은 줄이 두 번 찍힌다 |
| **sink 0개일 때** | **콘솔로 폴백**한다. 등록 이전에 발생한 로그를 버리면 *"로그가 안 나온다"* 의 원인이 *"로그 시스템이 아직 안 켜졌다"* 인 경우를 추적할 수 없다 |
| **sink 실패 격리** | sink 호출마다 개별 `try-catch`. 하나가 던져도 다음 sink는 계속 진행하고, **게임은 멈추지 않는다** |
| **예외 출력** | `Debug.LogError(e.ToString())`이 아니라 **`Debug.LogException(e)`**. 문자열로 눌러 담으면 크래시 리포터가 예외로 인식하지 못해 **스택 심볼화가 되지 않는다** |
| **민감 데이터 1단** | `GameLog.HashId(rawId)` — SHA-256 **앞 8바이트(16진수 16자리)**. **솔트를 쓰지 않는다** — 실행마다 달라지면 *"같은 사용자가 반복해서 겪나"* 를 판별할 수 없다. 실패 시 `(hash-failed)`, 빈 값이면 `(none)` |
| **민감 데이터 2단** | `GameLog` 내부 `Sanitize()` — 이메일 정규식 감지 시 `[email-redacted]` 로 치환. `@`가 없으면 정규식을 아예 돌리지 않는다. **`Compose` 이전에 걸러 모든 sink가 동일하게 보호된다** |
| **`Event=` 의 위치** | `MergeData()`가 `Event=...` · `ExceptionType=...` 을 **`key=value` 구조화 필드 앞쪽에 병합**한다 — `LogRules.md` **1.4 형식**이 *"`key=value`가 곧 전송 데이터"* 라고 규정하기 때문이다 |
| **`FileSink` 경로** | `Assets/_Project/Docs/_Logs/_editor/{yyyy-MM-dd}/` 아래에 `RuntimeLogger.BeginSession(folderPath, role)` 로 연다. **자기가 연 세션만 자기가 닫는다**(`_sessionOwned` 소유권 가드) |
| **`LogEvent` 현재 멤버** | **`Unknown = 0` 과 `UnhandledException` 둘뿐이다.** `Unknown`은 **의도적으로 사용하지 않는다** — 0번 자리에 의미 있는 키를 두면 값을 빠뜨린 호출이 그 지표로 조용히 섞여 집계를 오염시킨다 |

> **⑤ `LogEvent`가 2개뿐이라는 사실이 남은 작업의 크기를 그대로 보여 준다.**
> 209건 중 축 B = `운영` 으로 판정되는 건마다 **키를 새로 만들어야 한다**(§13-1).
