## 0. 방향 전환 후 확정 계획 (2026-08-13 갱신 시 신설 — **지금 유효한 계획**)

### 0-0. 쉬운 말로 먼저 — 무엇이 달라졌나

**전에는** 게임에 붙어 있는 209장의 쪽지를 보고 *"쓸모없는 94장을 뗀다"* 는 계획이었다.

**지금은** 쪽지를 **뗄지 말지가 아니라, 어느 통로로 보낼지**를 정하는 일이 되었다.
새 통로(`GameLog`)가 만들어졌고, 이 통로는 쪽지를 **두 갈래**로 받는다.

- **개발용 통로** — 출시본에서는 **통로 자체가 사라진다.** 쪽지를 쓰는 비용도 0이 된다.
  → 그래서 **떼지 않아도 떼는 것과 똑같아진다.** 대신 개발 중에는 계속 볼 수 있다.
- **운영용 통로** — 출시본에도 남고, 나중에 **서버로 모아서 셀 수 있게** 이름표(`LogEvent`)를 붙인다.

**결과적으로 "94장을 뗀다"는 목표는 사라졌다.** 대신 **209장 전부를 두 통로 중 하나로 옮긴다.**
작업량은 늘었지만, 잃는 정보가 없다.

| **B — 존속** | **둘 다 "예"** 여야 `운영`<br>① 플레이어 기기에서만 벌어지는가<br>② 이 로그가 없으면 추적 수단이 없는가 | `GameLog.Ops` / `GameLog.Dev` |

**분류 원칙 4가지** (`LogRules.md` **1.3 분류 원칙**) — 축만으로 안 갈리는 경계를 확정한다.

4. **삼킨 예외(`catch { }`)는 반드시 `운영` 로그를 남긴다**

**이벤트 키**(`LogRules.md` **1.5 이벤트 키 — LogEvent**): `enum LogEvent`로만. **`운영` 로그만** 받는다.

## 이 계획이 무엇이고 왜 필요한가 (자연어 설명 — 기술 용어 없이)

> **[보존 — 2026-08-13 07:27 작성 시점의 설명이다. 지금 유효한 설명은 §0-0이다.]**
> 아래는 *"209장 중 94장을 뗀다"* 는 당시 계획을 그대로 담고 있다.
> **확정된 방향은 "떼기"가 아니라 "두 통로로 옮기기"다.**
> 그럼에도 남기는 이유는, *"왜 전부 떼면 안 되는가"* 와 *"왜 한 번에 다 하지 않고 나누는가"* 라는
> 두 판단이 **개정 후에도 그대로 유효**하기 때문이다.

게임의 **접속·방 만들기·로그인** 부분에는 개발자가 붙여 둔 **"지금 여기까지 왔다"는 쪽지가 209장** 있습니다.
사용자가 **"이미 테스트가 끝난 불필요한 쪽지는 떼는 것을 원칙으로 하자"** 고 정했습니다.

**이번 작업은 그 209장 중 94장을 떼는 것입니다.**

### 왜 전부 떼지 않나요

쪽지 중에는 **떼면 안 되는 것**이 섞여 있기 때문입니다.

- **떼는 것 (94장)** — *"건물 만들기 성공"*, *"화면 켜짐"*
  → 건물이 지어졌는지는 **화면을 보면 압니다.** 쪽지가 없어도 아무것도 잃지 않습니다.
- **남기는 것 (77장)** — *"방 만들기 서버가 응답을 안 함"*, *"로그인 실패: (이유)"*
  → 이건 **플레이어 기기에서만 벌어지는 일**입니다. 개발자 컴퓨터에서는 재현되지 않습니다.
  이 쪽지를 떼면 나중에 *"게임이 안 켜져요"* 라는 문의가 왔을 때 **원인을 알아낼 방법이 사라집니다.**
- **먼저 물어볼 것 (38장)** — 판단이 갈리는 것들입니다. **§6에 모아 두었으니 확인해 주세요.**

### 왜 한 번에 다 하지 않고 나누나요

**같은 파일 안에서도 떼는 쪽지와 남기는 쪽지가 섞여 있습니다.**
심한 곳은 **함수 하나 안에 세 종류가 다 들어 있습니다.**
그래서 "이 파일을 통째로 정리" 라는 방식이 통하지 않고, **한 줄씩 판단**해야 합니다.

게다가 **이 환경에는 게임 엔진이 없어서 프로그램이 제대로 컴파일되는지 확인할 수 없습니다.**
94군데를 한 번에 고쳐 놓고 오류가 나면, **어디서 잘못됐는지 찾기가 매우 어렵습니다.**

그래서 **4단계로 쪼갭니다.** 각 단계마다 사용자가 게임을 켜서 확인한 뒤 다음 단계로 넘어갑니다.
문제가 생기면 **그 단계에서 바꾼 것만 보면 됩니다.**

### 왜 어떤 쪽지는 다른 도구로 옮기지 않나요

규칙 문서에는 *"쪽지를 `RuntimeLogger`라는 다른 도구로 옮겨 쓰라"* 고 되어 있습니다.
그런데 조사해 보니 **그 도구는 특정 버그를 쫓는 동안에만 잠깐 켜는 장비**였고,
**지금 프로젝트 어디에서도 쓰이지 않고 있었습니다**(쓰고 나서 다 뗀 상태가 그 도구의 정상 상태입니다).

그 도구로 옮겨 봤자 **평소에는 그냥 원래 쪽지와 똑같이 동작하면서 일만 더 합니다.**
그래서 **떼는 것은 그냥 떼고, 남기는 것은 지금 형태 그대로 둡니다.** (Research.md §6)

### 이번 작업이 바꾸지 않는 것

- **게임 규칙·동작·화면은 하나도 바뀌지 않습니다.** 로그 출력만 줄어듭니다.
- **에러 상황에서 플레이어에게 보여 주는 안내 문구는 건드리지 않습니다.**
- **동시에 진행된 `[DEBUG-TEMP]` 제거 작업의 결과물은 손대지 않습니다.**

> | 근거 | 갱신 후 상태 |

> | **①** 로그는 "비활성화"의 의미가 없다 | **유효.** 이관 시에도 주석으로 남기지 않고 **바로 고쳐 쓴다** |

### 주석 처리가 아니라 제거를 택하는 근거

| 근거 | 상세 |
|------|------|
| **① 로그는 "비활성화"의 의미가 없다** | 로그 호출문은 **다른 코드가 의존하지 않는 말단(leaf) 문장**이다. 주석 처리해도 되살릴 동기가 생기지 않으며, 되살리려면 어차피 그 자리를 다시 판단해야 한다. 반면 주석으로 남기면 **다음 사람이 "이건 왜 꺼져 있지? 다시 켜야 하나?"를 매번 판단**해야 한다 |
| **② 이번 작업의 목적 자체가 "제거"다** | 사용자 결정이 *"이미 테스트가 완료된 불필요한 로그는 삭제하는 것을 원칙으로 하자"* 이다. 주석으로 남기면 **파일에서 눈으로 걸러야 할 줄 수는 그대로**이고, 목적이 달성되지 않는다 |
| **③ 되돌리기 비용이 낮다** | 로그 문구는 이 Plan과 Research.md에 **파일:라인과 함께 전문 인용되어 있다.** 특정 로그를 되살려야 하면 문서를 보고 복원할 수 있다 — **씬 배선처럼 손으로 다시 맞춰야 하는 성격이 아니다** |
| **④ 회귀 표면이 없다** | 제거 대상 94건은 전부 **말단 호출문**이다. Research.md §8 전수 스캔 결과 **제어 흐름과 얽힌 자리는 9곳뿐이고, 그중 5곳(`catch` 본문)은 전부 운영 판정이라 이번 제거 대상이 아니다.** 실제 충돌은 §8-1의 3쌍뿐이며 §3-4에서 개별 처리한다 |

### 제거하지 않는 것 (명시)

- **운영 로그 77건은 한 줄도 건드리지 않는다.** 문구·레벨·위치 전부 현행 유지.
- **`catch` 블록 안의 로그는 어떤 것도 지우지 않는다** — 5곳은 지우면 `catch { }` 가 되어 **예외를 조용히 삼킨다**(Research.md §8-2).
- **`OnError?.Invoke(...)` 등 사용자 통지 코드는 손대지 않는다.**
- **경계 사례 38건은 §6 사용자 확인 전까지 현행 유지한다.**
- **`RuntimeLogger.cs` 자체는 수정하지 않는다** — 향후 디버깅용으로 그대로 둔다(Research.md §6-3 ③).

### 3-4. 특수 처리 — 제어 흐름과 얽힌 3곳 (Research.md §8-1)

#### ① `LobbyManager.cs:271~274` — `if`/`else` 구문 전체 제거

**현재 코드:**
```csharp
                if (lobby != null)
                    Debug.Log($"[Matchmaker] 매칭 Lobby 발견! Name={lobby.Name}, Id={lobby.Id}");
                else
                    Debug.Log($"[Matchmaker] FirstOrDefault null — 비교 실패");

                return lobby?.Id;
```

**처리:** 로그 두 줄만 지우면 `if (lobby != null) else` 가 남아 **컴파일 오류(CS1525)** 다.
**`if`/`else` 구문 4줄을 통째로 제거**한다. `return lobby?.Id;` 는 그대로 둔다.

**안전한 근거:** `if` 블록에 로그 외 문장이 없어 **제거해도 `lobby` 값과 반환값이 달라지지 않는다.**
`lobby` 변수는 바로 다음 줄 `return lobby?.Id;` 에서 계속 사용된다(미사용 변수 경고 발생하지 않음).

#### ② `NetworkGameManager.cs:718~721` · `739~742` — `if`/`else` 반전

**현재 코드 (두 곳 동일 패턴):**
```csharp
            bool result = NetworkManager.Singleton.StartHost();
            if (result)
                Debug.Log("[Network] NetworkManager.StartHost() 성공.");    // ← 진단 (제거)
            else
                Debug.LogError("[Network] NetworkManager.StartHost() 실패."); // ← 운영 (유지)

            return result;
```

**처리:** **한 구문 안에서 분류가 갈린다.** 성공 로그만 지우려면 조건을 반전한다.

```csharp
            bool result = NetworkManager.Singleton.StartHost();

            // 실패했을 때만 신고한다. 성공은 이후 흐름(Heartbeat 시작 · OnHostStarted)으로 확인되므로
            // 별도 로그를 남기지 않는다. (LogRules.md 금지 사항 1 — 진단용 콘솔 로그 제거)
            if (!result)
                Debug.LogError("[Network] NetworkManager.StartHost() 실패.");

            return result;
```

- **`739~742`(`StartClient`)도 동일하게 처리**한다.
- **주석을 반드시 남긴다** — R-7. 로그를 지우면 *"왜 성공 쪽에는 아무것도 없지?"* 라는 의문이 남는다.
- **`return result;` 는 건드리지 않는다** → 호출자 동작 불변.

**안전한 근거:** `if (A) X; else Y;` 에서 `X`를 제거한 `if (!A) Y;` 는 **논리적으로 완전히 동일**하다.
`result`는 로그와 무관하게 `return`에 쓰이므로 변수 사용 여부도 변하지 않는다.
