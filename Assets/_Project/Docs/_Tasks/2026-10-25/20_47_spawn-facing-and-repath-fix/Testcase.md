# 수정 항목 통합 검증 절차

이미 확인한 일반 플레이 결과는 유지하면서, 아직 실제 실행 근거가 부족한 수정 항목을 한 번에 확인한다. 사용자는 아래 순서대로 Editor 검사와 싱글·멀티 테스트를 진행하고, 검사 결과와 양쪽 로그를 전달하면 된다. 내부 요청을 직접 작성하거나 기존 로그 파일을 대량으로 만들 필요는 없다.

- 범위와 코드 전 계획: [Research10](Research.md#10-사용자-확인을-보존한-통합-검증-대상2026-10-26-kst), [Plan8](Plan.md#8-남은-수정-항목의-통합-검증-준비2026-10-26-kst-구현-전-계획).
- 현재 상태: main `f367cb52`까지 병합한 HEAD는`562888d2`다. 진단·검사 준비16경로를 복원하고 새 투사체 경로에 맞춘 실행 전제를 보강했다. 추가분은 미커밋·미푸시이며 실제 새 Unity 컴파일·검사·기기 테스트는 미실행이다. 이 통합 버전을 받은 뒤 새 Development Build로 아래 절차를 사용한다.
- 기존 수용: 사용자가 확인한 당시 컴파일과 일반 플레이는 유지한다. 새 진단 코드를 포함한 버전의 컴파일은 이번에 한 번 확인한다. 피스톨러는 이번 싱글에서 증상이 없었다는 관찰을 유지하며, 기존 방향 문제의 원인을 해결했다고 단정하지 않는다.
- 제외: 인증 전체 재검증, AI 생산시간 배율, 외부 VFX 작업, Profiler 최적화.

## 진행 순서와 준비

1. 이번 진단 코드를 받은 Unity 프로젝트를 열고 컴파일이 끝날 때까지 기다린다. 새 컴파일 오류가 있으면 다음 단계로 넘어가지 말고 오류 내용을 전달한다.
2. Play를 종료한 상태에서 아래 첫 Editor 검사를 실행하고 결과를 먼저 보관한다.
3. 새 코드로 **Development Build**를 만들어 Android 기기에 설치한다. 이전 APK를 그대로 사용하지 않는다.
4. Editor와 기기는 Login부터 정상 진입한다. 기존 로그인·일반 동작을 전부 다시 테스트할 필요는 없다.
5. 싱글 테스트 후 멀티 테스트를 진행한다. 멀티는 **Editor가 Host, Android가 Client**인 전용 테스트 경기를 사용한다. 실제 역할은 개발 로그에서 확인하며 일반 게임 화면에 역할 표시를 추가하지 않는다.
6. 통제 검사 메뉴를 누르는 동안에는 양쪽 모두 조작하지 않는다. 서버 요청 검사는 잠깐 멈췄다가 끝나면 원래 속도로 돌아와야 한다. 보통 수초 내 끝나며 요청별 대기 상한을 모두 합친 최대 시간은36초다. 36초를 넘겨 계속 멈추거나 오류가 나면 다른 검사 메뉴를 반복 실행하지 말고 결과를 보관한다.

Editor의 일반 플레이 로그는 일별로 누적되므로 삭제하지 않는다. 기기 버퍼를 비울 필요가 있다면 기존 필요한 로그를 먼저 저장한 뒤 사용자가 직접 선택한다. 아래 절차에 `Clean Old Editor Logs` 실행은 포함하지 않는다.

## 테스트 케이스

### TC-SINGLE-01: Editor 집중 검사

**전제:** 새 진단 코드를 포함한 프로젝트의 컴파일이 완료됐고 Play가 종료돼 있다. 다른 경기나 네트워크 세션이 실행 중이지 않다.

**동작:**
1. Unity 메뉴에서 **Hexiege > Combat > Diagnostics > Run Refactoring Verification**을 한 번 실행한다.
2. Console 검색창에 `[REFACTOR-VERIFY]`를 입력하고 Collapse를 끈다.
3. 이번 실행의 시작, 항목별 결과, 마지막 요약을 확인한다.
4. 해당 실행의 메시지 전체를 선택해 복사하고 텍스트 편집기에 붙여 **RefactoringVerification.txt**로 저장한다. 전체 Editor.log를 복사하지 않는다.
5. 실행하지 못했다는 안내나 실패가 있으면 이를 지우거나 성공 결과로 바꾸지 않고 그대로 전달한다.

**기댓값:**
- 예약 순서·상한·같은 유닛 번호 재사용, 로그 파일명 소진 시 기존 파일 보존, 이동 단계 해석, 건물 제거 후 경로 갱신, 기존 역할 검사, UI 구독·누르기 수명 검사가 모두 실제 실행된다.
- 각 검사에 결과가 있고 마지막 전체 결과가 통과다.
- 검사 때문에 씬이 저장되거나 기존 사용자 로그가 삭제되지 않는다.

**결과:** 미실행 — 사용자 실행 결과 대기.

### TC-SINGLE-02: 생산 패널 반복 조작과 입력 수명

**전제:** 새 싱글 경기에서 같은 팀의 생산건물 두 개를 사용할 수 있고 생산할 골드와 인구 여유가 있다. 처음에는 자동생산을 꺼 둔다.

**동작:**
1. 첫 번째 생산건물의 패널을 열고 유닛 버튼을 한 번 짧게 눌러 한 번 등록되는지 본다. 표시된 유료 대기 항목을 취소해 한 번만 취소되는지도 본다.
2. 패널을 열고 닫는 조작을 다섯 번 반복한다. 첫 번째와 두 번째 건물의 패널을 번갈아 여는 조작도 다섯 번 반복한다.
3. 다시 짧게 한 번 눌러 한 번만 등록되는지 확인한다.
4. 유닛 버튼을 길게 눌러 자동생산을 켠 뒤 같은 버튼을 눌러 해제한다. 켜기와 해제가 한 번씩 동작하는지 본다.
5. 버튼을 누른 채 패널을 닫거나 다른 건물로 바꾸는 상황은 Editor 집중 검사에서도 확인한다. 기기에서 직접 해볼 수 있다면 자동생산을 끈 상태로 시작해, 닫힌 뒤 추가 입력이나 엉뚱한 건물의 생산이 생기는지만 관찰한다.

**기댓값:**
- 반복해서 열거나 건물을 바꿔도 한 번의 조작이 여러 번 처리되지 않는다.
- 취소한 항목이 다시 등록되거나 다른 건물에 입력이 적용되지 않는다.
- 사용자가 명시적으로 켠 자동생산의 정상 진행과, 닫힌 패널에 남은 잘못된 입력을 혼동하지 않는다.

**결과:** 미실행 — 사용자 관찰과 로그 대기. 앞선 일반 플레이 수용은 유지한다.

### TC-SINGLE-03: 막힌 생산 출구를 연 뒤 생산·이동

**전제:** 새 싱글 경기에서 피스톨러를 생산할 수 있고, 생산건물 주변을 다른 건물로 막을 수 있다. 주변에 적이 없어 출생 직후의 이동을 관찰할 수 있는 위치를 사용한다.

**동작:**
1. 생산건물에 인접한 출구를 막고 피스톨러를 생산한다. 진행률이 가득 찼는데 유닛이 나오지 않는 대기 상태를 확인한다.
2. 주변 건물 하나를 철거하거나 파괴해 실제로 빈 출구를 만든다.
3. 유닛이 생산되고 열린 쪽으로 이동하는지, 이동 중 몸체 방향이 계속 어긋나지 않는지 관찰한다.
4. 가능하면 통로를 여는 순간부터 이동 구간까지 영상으로 남긴다. 전투로 곧바로 멈췄다면 실제로 관찰한 이동 길이만 알려준다.
5. 경기 종료 후 로비로 돌아갔다가 새 싱글 경기를 한 번 시작해 일반 생산이 다시 되는지 확인한다.
6. 확인 후 해당 싱글 경기도 종료하고 로비로 돌아와 다음 멀티 테스트를 준비한다.

**기댓값:**
- 통로가 열리면 대기하던 생산이 진행되고, 이동 가능한 길로 이동한다.
- 이동 중 지속해서 옆이나 뒤를 보는 현상이 없다.
- 새 경기에서 이전 경기의 조작·이벤트가 중복 실행되지 않는다.

**결과:** 미실행 — 이번 새 진단 세대의 관찰과 로그 대기. 이전 싱글의 방향 오류 미재현은 취소하지 않는다.

### TC-MULTI-01: 정상 생산·연구와 서버 요청 검증

**전제:** Editor Host와 Android Client가 새 멀티 테스트 경기에 들어왔다. 양쪽 플레이어가 각자 살아 있는 생산건물과 연구소를 하나 이상 만들었고, 정상 요청을 확인한 다음 통제 검사를 위해 생산과 연구를 다시 시작할 골드·인구 여유가 있다. 이 검사를 마칠 때까지 서로 전투하지 않고 랠리를 자기 기지 근처로 둔다. 비행 중인 투사체나 진행 중인 파도 공격도 없어야 한다. 전투/비행 중이라는 실행 거부 안내가 나오면 해당 공격이 끝난 뒤 생산·연구 전제를 다시 갖춘다.

**동작:**
1. 양쪽에서 각자 정상 생산 등록·대기 항목 취소·랠리 지정·자동생산 켜기와 해제를 한 번씩 해본다.
2. 각자 연구를 시작하고 수동 취소해 정상 요청과 환불을 확인한다. 이후 통제 검사를 위해 양쪽 연구소는 살아 있게 둔다.
3. 양쪽에서 각자 생산건물 한 곳에 유닛을 여러 개 예약해 생산 중으로 둔다. 자동생산은 꺼 두는 것을 권장한다. **검사 전에 큐와 연구를 비우지 않는다.**
4. 마지막으로 양쪽 연구소 한 곳에 연구를 새로 시작하고, 즉시 아래 메뉴를 실행한다. 양쪽 모두 검사 중에는 조작하지 않는다. 생산이나 연구가 먼저 완료됐다면 해당 진행을 다시 준비한다.
5. Editor 메뉴에서 **Hexiege > Combat > Verification > Run Server Request Checks**를 한 번 실행하고 완료를 기다린다.
6. 검사 후 원래 속도로 돌아오는지, 기존 골드·큐·랠리·자동생산·연구 상태가 임의로 바뀌지 않았는지 본다.
7. Console에서 이번 검사의 결과를 확인한다. 전제 부족 안내가 있으면 안내에 적힌 준비만 보완하고 새 실행으로 다시 진행한다.

**기댓값:**
- 양쪽의 정상 요청이 한 번씩 처리된다.
- 통제 검사에서 잘못된 소유권·건물·음수 취소 요청이 실제로 거부되고 검사 전후 상태가 유지된다.
- 검사 결과가 통과이며, 검사가 끝난 뒤 정상 생산·연구를 계속 사용할 수 있다.

**결과:** 미실행 — 사용자 관찰·양쪽 로그·항목별 검사 결과 대기.

### TC-MULTI-02: 포기 종료 뒤 재진입 차단과 최신 통신 확인

**전제:** 앞 멀티 경기에서 살아 있는 유닛과 상대 건물이 남아 있다. 결과 화면에서 검사할 수 있도록 양쪽 앱과 연결을 유지한다. Editor가 Host이며, 아직 로비 복귀나 상대 이탈 판정이 진행되지 않은 결과 화면에서 실행한다.

**동작:**
1. 양쪽 유닛이 이동·전투 중인 상태에서 한쪽 플레이어가 설정의 포기로 경기를 끝낸다.
2. 양쪽 결과 화면이 뜨면 Editor에서 **Hexiege > Combat > Verification > Run Ended Combat Check**를 한 번 실행한다.
3. 이어서 **Hexiege > Combat > Verification > Run Result Heartbeat Check**를 한 번 실행한다. 로비 자동 복귀 전에 실행하며, 실행 전제가 없다는 안내가 나오면 그 결과를 그대로 보관한다.
4. 검사 결과를 확인한 뒤 양쪽에서 재경기를 진행한다.
5. 새 경기에서 생산·이동·공격이 다시 시작되는지 확인한다.

**기댓값:**
- 종료한 경기의 새 전투 진입이 실제로 거부되며 타겟·공격 수명을 다시 열지 않는다.
- 통신 확인을 기다리는 동안 들어온 새 상대 신호를 반영해, 복구된 연결을 잘못 끊지 않는다.
- 두 통제 검사에 각각 통과 결과가 있다.
- 재경기에서는 전투가 정상 시작된다.

**결과:** 미실행 — 종료 검사·통신 검사와 양쪽 종료/재경기 로그 대기.

### TC-MULTI-03: 정상 승패 종료와 최종 로그 수집

**전제:** 재경기에서 양쪽 생산·전투가 정상 동작한다.

**동작:**
1. 이번에는 포기하지 않고 상대 핵심 건물을 파괴해 정상 승패로 경기를 끝낸다.
2. 양쪽 결과 화면이 뜨고 후속 동작이 끝날 때까지 기다린 다음 로비로 돌아간다. 종료 직후 앱이나 Editor Play를 강제로 끄지 않는다.
3. 기기를 USB로 연결한 상태에서 Unity 메뉴 **Hexiege > Logs > Save Device Logs**로 기기 로그를 저장한다.
4. Editor에서 테스트한 날짜의 일별 플레이 로그와 이번 기기 로그, 첫 Editor 집중 검사 결과를 보관한다.
5. 싱글·멀티의 대략적인 테스트 시각, 관찰한 이상 여부, 실행하지 못한 절차가 있으면 함께 적는다.

**기댓값:**
- 정상 승패 뒤 새 전투가 재개되지 않고 결과·로비 복귀가 정상 진행된다.
- Editor와 기기 양쪽에 경기 종료까지의 로그가 남는다.
- 로그 수집 때문에 기존 파일이 덮어써지거나 삭제되지 않는다.

**결과:** 미실행 — 양쪽 로그와 사용자 관찰 대기.

## 전달할 자료

- **RefactoringVerification.txt**: Play 종료 상태의 집중 메뉴를 실행한 이번 Run의 `[REFACTOR-VERIFY]` 메시지 전체. 정지 상태에서는 일별 플레이 로그에 저장된다고 보장하지 않는다.
- **Editor 로그**: `Assets/_Project/Docs/_Logs/_editor/테스트날짜/RuntimeLog.txt` 전체. 날짜가 바뀌었다면 해당 날짜 파일을 모두 포함한다.
- **Android 로그**: 저장 메뉴가 만든 `Assets/_Project/Docs/_Logs/테스트날짜/시각_logcat/RuntimeLog_device.txt` 또는 같은 위치의 번호가 붙은 실제 파일.
- **간단한 관찰 메모**: 테스트 시각, Editor Host/Android Client 구성, 방향·중복 입력·멈춤 등 이상 여부, 실행하지 못한 단계. 영상은 화면 방향 문제가 보였을 때 특히 도움이 된다.

기존 [LogRules](../../../LogRules.md) §1.10의 **private Hexiege-Logs Release ZIP** 공유 방식을 사용한다. main에 추가된 **Hexiege > Logs > Create Log Archive ZIP**에서 작업명을 영문으로 입력하고 시작 날짜를 이번 테스트의 첫날로 지정해 ZIP과 manifest를 만든다. 자정을 넘겼으면 전날도 포함되게 직접 선택한다. 생성된 ZIP과 manifest를 둘 다 기존 private 월별 Release에 올린다.

이 도구가 자동 선택하는 것은 RuntimeLog 원본이다. **RefactoringVerification.txt는 자동 포함되지 않으므로 별도 파일로 함께 첨부해야 한다.** 원시 로그를 소스 저장소에 강제 추가하거나 전체 Editor.log를 공유하지 않는다. 분석 뒤 각 항목은 실제 실행 여부·기댓값·로그·사용자 관찰을 대조해 갱신한다.

공통 식별자는 `[REFACTOR-VERIFY] Generation=refactor-verify-v1`이다. Editor 집중 실행은 Run GUID로 구분하며 중간 case만 잘라 전달하지 않는다. 런타임은 양 peer와 경기 시작·종료를 연결한다. Generation은 Git SHA 보증이 아니다. `NOT_RUN`은 검사가 실행되지 않은 것, `NOT_EXERCISED`는 필요한 조건이 없어 해당 경계를 밟지 못한 것이며 두 상태 모두 PASS가 아니다. 로그 생략·누락·미완료·조건미발생을 오류0만으로 통과 처리하지 않는다.

Editor 원문 확인 기준의 case는 `EDITOR-FIFO`, `EDITOR-LOGCAT`, `EDITOR-ROOT-PARSER`, `EDITOR-BUILDING-REMOVAL`, `EDITOR-BLOOM-NETWORK`, `EDITOR-UI-LIFETIME`, `EDITOR-TICKER-LIFETIME`, `EDITOR-BOOTSTRAP-LIFETIME`이다. 같은 Run의 `BEGIN/STARTED`, 이8개 case의 결과와 `END` 요약이 함께 있어야 한다. 실행 환경이 맞지 않으면 `ENVIRONMENT/NOT_RUN` 및 `END/NOT_RUN`이므로 다시 조건을 갖추기 전에는 해당 항목을 통과 처리하지 않는다.

온라인 부정 요청은 생산4개 소유권·음수취소2개와 연구6개의 합계12개 case다. `RPC-ENQUEUE-OWNER`, `RPC-CANCEL-OWNER`, `RPC-RALLY-OWNER`, `RPC-AUTO-OWNER`, `RPC-CANCEL-NEGATIVE`, `RPC-CANCEL-MINVALUE`, `RPC-RESEARCH-START/CANCEL`의 `OWNER/TYPE/MISSING` 조합을 확인한다. 종료 경계는 `END-LATE-ENTRY`, 최신 통신 경계는 `HB-FRESH-DURING-PROBE`가 각각 실제 실행되고 해당 Run의 END까지 있어야 한다. 일반 런타임 `EVIDENCE` 행 자체는 통제 검사 PASS가 아니다.

**QA 결과:** main 통합 뒤 전문 QA의 추가 blocker 없음과 메인의 C#41개·Editor/Android 개발/Android Release 선택123개 문법 오류0 및 기존 진단 patch 보존 대조를 확인했다. 실제 Unity 컴파일·집중 메뉴·NGO/기기 실행은 미실행이므로 위 case의 PASS 결과는 아직 없다. 사용자 실행 결과와 기존 수용 범위를 구분해 갱신한다.
