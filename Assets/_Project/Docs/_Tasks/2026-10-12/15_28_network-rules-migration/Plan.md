# Plan — 네트워크 동작 규칙 문서 신설과 기술 설계서에서의 이관 (2026-10-12)

> **사용자 승인 원문**: *"신설하고 네트워크 관련된 규칙은 이관시켜 task 문서 작성하고 바로 진행해"* — 이 회차는 **문서만** 다룬다(코드·씬·에셋 변경 0건). `Research.md` 는 쓰지 않는다(조사는 이 문서 안에 필요한 만큼만 담았다 — 직전 회차와 같은 방식이고 사용자 승인 범위다).
> `_Tasks/` 문서는 `Tools/check_docs.py` 의 검사 대상이 아니다(사용자 결정). **그래도 이 문서는 이번 회차의 기록이므로 정확하게 쓴다.**

## 쉬운 말로 (CLAUDE.md 규칙 13)

- **지금 문제**: 이 게임은 두 사람 중 한 명이 서버 역할(Host)을 맡는 구조인데, **플레이어는 자기가 어느 쪽인지 알 수 없다.** 그래서 무슨 일이 있어도 화면도 승패 기록도 역할과 무관하게 같게 동작해야 한다. 사용자가 2026-09-21 에 *"이게 제일 중요하다"* 고 확정한 규정이다. 그런데 이 규정이 **기술 설계서(TDD)** 안에 있었다. 규칙을 찾는 사람은 `GameSystemRules/` 폴더로 가기 때문에, **그 폴더를 다 읽어도 이 규정을 모를 수 있는 배치**였다. 실제로 멀티 최초 경기 맵 준비 실패 안내(규칙 M-2)가 Host 화면에만 뜨게 구현됐고, 사용자가 *"플레이어들이 보는 화면이 호스트와 관계없이 일관성있게 나오냐"* 고 물어서야 위반이 드러났다.
- **하려는 것**: ① `GameSystemRules/` 에 **네트워크 동작 규칙 문서**(`GameSystemRules_Network.md`)를 새로 만든다. ② TDD 의 「🌐 네트워크 설계」 안에서 **「사용자가 확정한 제품 동작 규정」인 세 절**을 **본문 그대로** 새 문서로 옮긴다. ③ TDD 에는 사본을 두지 않고 **옮겼다는 안내(포인터)만** 남긴다. ④ 옮겨서 거짓이 된 **"TDD 의 그 절을 보라"는 안내를 전부 새 위치로 고친다**. ⑤ 문서 인덱스 두 곳(`AGENTS.md` · `GameSystemRules.md`)에 새 문서를 등록한다.
- **옮기지 않는 것**: Netcode 구조·동기화 전략·무작위 맵 데이터 계약·결과 화면 이탈 판정 *구조*·치팅 방어 — 이쪽은 "어떻게 만드는가"라서 TDD 가 맞다.
- **이번 회차의 한계**: 이것은 **문서 배치 문제의 수선**이다. 위반한 코드 자체(Host 전용으로 구현된 M-2 안내)는 이 회차가 고치지 않는다.

## 0. 기존 로직 제거 여부 (WORKFLOW [4] — 문서 최상단 고지)

- **내용 제거 0건 — 이동 3건이다.** TDD 에서 지워지는 세 절(약 159행)은 **새 문서에 먼저 쓰고, 원문과 대조한 뒤에 TDD 에서 지운다**(순서를 거꾸로 하면 중간에 세션이 끊길 때 구멍이 남는다 — 먼저 쓰면 중복이 남고 그건 검사기가 잡는다).
- 지우는 근거: ① 새 문서가 같은 본문을 가진다(대조 수치는 11절) ② 사용자가 승인했다. 이 회차는 `git` 변경 명령을 쓰지 않는다(CLAUDE.md 규칙 5). 대조에 쓴 이관 전 TDD 사본은 `git show HEAD:` 출력을 scratchpad 에 둔 것이라 휘발성이고, **영구한 원본은 git 이력**이다.

## 3. 새 문서의 구조 — `GameSystemRules/GameSystemRules_Network.md`

`.meta` 는 만들지 않는다(Unity 가 다음에 프로젝트를 열 때 생성한다).

```
# Game System Rules — Network            ← 한 줄 설명 + 이관 안내 + 본문 읽는 법
## 🔴 최상위 원칙 …                      ← 번호 없음 (비규칙 H2)
## 네트워크 동작 규칙                    ← 규칙 블록을 감싸는 H2 — 문서당 하나
**규칙 1. 이탈 시 승패 기록 — 규칙 집합 …**
**규칙 2. 인게임 이탈 처리 — `ReconnectionHandler` 정리 …**
```

- **최상위 원칙에는 번호를 주지 않는다.** 이 원칙은 *"개별 규칙이 이 원칙과 충돌하면 고칠 대상은 개별 규칙"* 이라고 스스로 정하는 **규칙들 위의 원칙**이다. 번호를 주면 동급 규칙 중 하나로 읽힌다 → 2026-09-21 에 정한 방침(`doc-conventions.md` §24-2: 원칙은 규칙 번호가 아니라 규칙보다 위 계층에 둔다)을 새 집에서도 지킨다.
- **규칙 1·2 는 이 문서에서 처음 매기는 번호**다(이관 전 TDD 에는 번호가 없었다). 번호를 매기는 이유: 검사기가 `**규칙 N. 제목**` 만 규칙으로 인식하므로, 번호가 없으면 이 문서는 **검사기 눈에 규칙 0개**여서 앞으로 이 문서를 가리키는 참조가 검증되지 않는다. → **9절 A 에서 사용자 확인.**
- 규칙 제목 줄은 **이관 전 절 제목을 그대로** 쓴다(날짜·"사용자 확정 · 미구현" 표기 포함). 그래서 이름으로 가리키던 곳이 이름은 그대로 유지된다.

## 4. 옮기는 방식 — 바꾸는 것 / 바꾸지 않는 것

**바꾸지 않는다**: 날짜 · 사용자 확정 원문 인용 · 근거 · 경고 · 취소선 · 덧붙인 정정 블록 전부(세 절 159행 — 제목 줄 포함 — 을 줄 단위로 그대로 복사하고 이관 후 줄 단위 diff 로 확인한다).

**바꾸는 것 — 네 가지뿐이고 모두 아래에 적는다:**

1. **제목 줄의 서식** — `###`/`####` 제목 → `## `(최상위 원칙) / `**규칙 N. …**`(굵은 글씨). 글자는 그대로다.
2. **상대 링크 3개** — 규칙 2 본문의 `[ROADMAP.md](ROADMAP.md)` ×2 · `[PROJECT_STATUS.md](PROJECT_STATUS.md)` ×1 에 `../` 만 붙인다(폴더가 한 단계 깊어져 링크가 깨지므로. 검사 `[2]` 대상).
3. **새 문서 서두의 "읽는 법" 블록** — 본문에 남은 위치 표현(*위/아래 … 절*)이 이관 후에 무엇을 가리키는지를 **본문을 고치지 않고** 서두 한 곳에서 해설한다. 대상은 8절 ②에 전수 적었다.
4. 위 외의 변경은 없다. 한 글자라도 다르면 11절 대조에서 드러난다.

**TDD 쪽**: 세 절을 지우고 그 자리에 **이관 안내 한 블록**(어디로 갔는지 표 + 사본을 두지 않는다는 문장)만 둔다. 변경 이력 표 맨 위에 0.61.0 행을 더하고(이 표는 **내림차순**이다 — 맨 위가 최신) 머리말의 버전·최종 수정일을 맞춘다.
