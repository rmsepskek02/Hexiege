## 쉬운 말로 (CLAUDE.md 규칙 13)

- **지금(커밋 `cbddf535`)**: 방장(호스트)이 맵을 준비해 상대에게 보내다 실패하면, **방장 화면에만** 「다시하기/로비로」 두 버튼 모달이 뜬다. 상대방(접속한 쪽)에게 실패를 알리는 길이 없어서, 상대방 화면은 접속 때 켠 로딩 화면에 **갇힌 채 남는 것으로 읽힌다**(코드 판독, 실기 미확인).
- **하려는 것**: 맵 준비가 실패하면 **두 사람이 모두 곧바로 방에서 나가 로비 첫 화면으로 돌아가고, 각자 화면에 「경기를 시작할 수 없습니다」라는 안내 창을 띄운다.** 창에는 「확인」 버튼 하나뿐이고, 누르면 창만 닫힌다. 이미 방을 나와 있으므로 창을 누르지 않아도 갇히지 않는다. 다시 하려면 **방을 새로 만들어야 한다**(사용자 결정 — 재시도 버튼은 없어진다).
- **양쪽이 같은 창을 보게 하는 방법**: 호스트가 실패를 상대방에게 알리는 신호를 하나 보내는 것이 기본이다. 그 신호가 못 갈 수도 있으므로(호스트 앱이 죽었거나 회선이 끊긴 경우, 신호를 보내기 전에 실패하는 경우) 접속한 쪽이 **「기다리는 중에 연결이 끊김」과 「60초 자체 타이머」**로 스스로도 같은 결론을 낸다. 세 길이 모두 **같은 한 곳**으로 모여 같은 창을 띄운다.
- **새로 만드는 화면 컴포넌트는 0건**이다 — 이미 있는 알림 팝업 호출(결과 화면이 쓰고 있다)을 그대로 쓴다. 새로 생기는 것은 호스트→상대방 신호 하나(기존 전송 객체에 같은 모양으로 한 개 추가)와 접속한 쪽의 감시 코드다.
- **왜 「접속하지 못했다」가 아니라 「경기를 시작할 수 없습니다」인가**: 접속은 **됐다** — 두 사람이 모여서 맵 준비가 시작됐다. 실패한 것은 맵 준비다. 「접속하지 못했다」고 알려 주면 플레이어는 접속부터 다시 확인하며 **할 수 있는 조치가 없는 곳을 헤맨다.** 사용자가 이 지적을 받아들여 문구를 「경기를 시작할 수 없습니다」로 확정했다. `ROADMAP.md` 의 「끊긴 뒤 상대 화면에 뜨는 문구를 「누가 끊었는가」로 구분한다」 행이 **같은 함정을 이미 적고 있다**(「원인을 반대로 알려 주는 셈이라 플레이어는 할 수 있는 조치를 하지 않는다」) — 이 판은 그 함정을 새로 만들지 않는다.

## 1. 사용자 확정 사양 (최종)

사용자 원문: *"우선 생각해본 바로는 로비씬에서 안내문구로 게임에 접속하지 못했다라는 내용을 전달하고 **확인버튼 하나만 존재하는 모달창**을 띄워서 알려주면 될거같은데"* · *"**「경기를 시작할 수 없습니다」** 로 하고 맵생성에 실패했으면 **방도 나오고 로비에서 있는걸로** 진행하면되겠네"* · *"확인버튼에 방을나가는 기능을 넣어야해? / 그냥 맵생성실패하면 둘다 방나가도록해 그리고 각자 화면에서 모달만 뜨는걸로는 안돼?"*

| 항목 | 확정값 |
|---|---|
| 수단 | **버튼 하나짜리 알림 모달** — 이미 있는 알림 팝업 호출(`UIManager.ShowAlert`, 내부는 `ConfirmPopup.ShowAlert`). 결과 화면(`GameEndUI`)이 이미 쓴다. **새 UI 컴포넌트 0건** |
| 구조·타입 | 규칙 D-5(알림 팝업 구조) · 규칙 8(모달) · 규칙 9(배경 탭으로 닫히지 않는다) |
| 본문 | **「경기를 시작할 수 없습니다」** |
| 실패 시 방 나가기 | 🔴 **실패하면 양쪽이 곧바로 나간다**(사용자 조작 없이) — 연결 종료, 화면은 로비 메인 |
| 「확인」 버튼 | **하나.** 🔴 **모달만 닫는다. 아무 책임도 지지 않는다**(`ShowAlert` 의 클릭 콜백을 비우면 「닫히기만 한다」 — `UIManager.ShowAlert` 매개변수 설명에 있다) |
| 모달의 성격 | **알리기만 한다** |
| 모달의 타이머 | **없음** |
| 양쪽 | 🔴 **호스트와 접속한 쪽이 같은 모달을 본다** |
| 다시 하려면 | **방을 새로 만든다**(재시도 버튼 없음) |

- **타이머가 없어도 되는 근거**: 나가는 길이 늘 열려 있으므로 시간이 사용자를 구조할 필요가 없다. 이 판에서는 근거가 **더 분명해졌다** — 모달이 뜰 때 **이미 방을 나와 있어** 모달을 누르지 않아도 갇히지 않는다. 🔴 **이 논리는 새로 만든 것이 아니다** — `GameEndUI.cs` 의 `ShouldStartAutoReturnCountdown` 주석이 싱글에 타이머를 두지 않는 근거로 규칙 D-3 을 들며 똑같이 적는다(「나가는 길이 늘 열려 있으므로 시간 제한이 사용자를 구조할 필요가 없다」). ⚠️ 같은 주석은 **멀티는 타이머가 그대로 돈다**고도 적는다(「기다릴 상대가 있어」). 이 모달에서는 두 사람이 각자 독립적으로 창을 닫으면 되고 한쪽이 다른 쪽의 응답을 기다리지 않으므로 그 이유가 해당하지 않는다고 **판단**한다 — 판단이지 관측이 아니며, 어차피 타이머 없음은 **사용자 확정**이다.
- **「모달의 타이머 없음」과 「접속한 쪽의 60초 자체 타이머」는 다른 것이다.** 앞의 것은 모달을 닫는 시계가 없다는 뜻이고, 뒤의 것은 **모달을 띄울 시점을 정하는 감시**다(5절).
- **알림 팝업 호출 주의**: 종전에 넘겨받은 표기 `ConfirmPopup.ShowAlert(제목, 본문, 버튼라벨, onClick)` 는 팝업 컴포넌트의 순서이고, 실제로 부르는 `UIManager.ShowAlert` 의 순서는 **(제목, 본문, onClick, 버튼라벨)** 이다(`IUIManager` 선언 확인). 호출은 항상 `UIManager.Instance?.ShowAlert(...)`(규칙 D-5 · L-4).
- ⚠️ **사양에 없는 것 둘 — 채우지 않았다**: ① **모달 제목**(선례: 규칙 D-6 은 `알림`. 제목이 비면 제목 자리가 숨는다) ② **버튼 글자**(사용자 용어는 「확인」이고 `UIManager.ShowAlert` 의 기본값도 「확인」이다). → 11절 2·3번.

| 본문 글자 | 규칙 M-4 가 확정한 싱글 문구 | 🔴 **글자도 다르다 — 「경기를 시작할 수 없습니다」.** 종전에는 세 자리가 같은 글자였으나(이 판의 앞 판까지) 이번에 멀티 쪽이 달라진다. 영향은 아래 「합치지 않는다」 문단과 9절 |
| 방 나가기 | 해당 없음(「로비로」가 씬 전환) | **실패 즉시 양쪽 자동.** 씬 전환이 아니라 연결 종료 + 화면 상태를 로비 메인으로 |
| 누가 보는가 | 혼자 | **양쪽** |
| 재시도 | 있음(횟수 제한 없음 — M-4) | **없음** — 방을 새로 만든다 |
| 로딩 | 모달을 띄운 뒤 같은 맵 로드 절차의 끝이 끈다 | 호스트: 실패 처리의 첫 줄이 끈다(기존). 접속한 쪽: 같은 진입점이 끈다(구현 항목 ⓕ) |
| 모달 닫힘 | 확인/취소는 스스로 먼저 닫고 콜백 | 알림 팝업도 같은 구조. 콜백이 비어 있으면 **닫히기만 한다** |

**「합치지 않는다」 제약(반드시 지킨다)**: `GameBootstrapper.Map.cs` 의 본문 상수 주석과 `BattleViewModel` 의 실패 핸들러 주석에 「세 자리(싱글 모달 · 결과 화면 상태 줄 · 멀티 로비)를 한 상수로 합치지 않는다」는 2026-09-29 판정과 근거(사건이 다르고 규칙 M-2/M-4/D-7 이 따로 개정될 수 있다)가 적혀 있다. 따라서 ① 멀티 본문을 싱글 상수로 가리키지 않는다 ② 새 `const` 로 **올리지도 않는다**(그 주석이 상수화를 합치기의 첫걸음으로 규정한다). 대신 실패 처리 **안의 지역 값 하나**에 글자를 한 번만 두고 오류 텍스트 대입과 모달 본문이 그것을 함께 쓴다 → 글자 리터럴 수가 늘지 않는다. 버튼 글자는 위 판정의 대상이 아니다(라벨은 합치라는 사용자 확정이 있었다 — 단 이번 한 버튼의 글자는 11절 3번).

> **이번에 달라진 한 가지만 덧붙인다 — 제약은 그대로다.** 이번 본문이 **「경기를 시작할 수 없습니다」로 글자가 달라졌으므로**, 종전 주석이 전제하던 「뜻이 거의 같고 **글자까지 같은** 안내가 세 자리에 있다」는 관측은 **멀티 자리에 한해 더 이상 맞지 않는다**(싱글 모달 본문과 결과 화면 상태 줄은 종전 글자 그대로). 글자가 다르니 「같은 문구 세 자리를 모을 것인가」라는 질문 자체는 이 자리에서 **별개의 이야기**가 된다. 🔴 **그렇다고 「합치지 않는다」 제약이 약해지지 않는다** — 그 판정의 근거(사건이 다르다 · 규칙이 따로 개정될 수 있다)는 글자와 무관하다. 구현 시 **세 곳의 주석(`BattleViewModel` 핸들러 · `GameBootstrapper.Map` 본문 상수 · `GameEndUI` 상태 줄 상수)이 「글자가 완전히 같다」고 적은 문장**이 거짓이 되므로 현재 사실로 고쳐야 한다(6절). ⚠️ 그 문장들이 기대는 **규칙 M-4 의 확정 한 칸**(싱글이 멀티 문구를 그대로 쓴다)은 이 판이 건드릴 수 없다 — **9절 ⑤·11절 1번.**

## 4. 「호스트만 먼저」 안은 승인받을 자격이 없었다 (앞 판의 4절을 대체)

앞 판은 상대방 화면 처리를 선택지 A(호스트만, 권고)·B·C 로 나눠 A 를 권고했다. **그 표와 권고, 그 근거 셋을 통째로 걷어냈다 — 남겨 두면 다음 사람이 다시 고른다.** 남기는 것은 그 안이 틀렸던 이유다.

1. **선택지로 존재할 수 없었다.** `GameSystemRules_Network.md` 의 최상위 원칙이 「개별 규칙이 이 원칙과 충돌하면 **고칠 대상은 개별 규칙**」이라 정하고, 「**Host 쪽에만 있는 처리는 그 자체로 이 원칙 위반의 후보다 — Client 쪽에도 같은 판정이 있는지를 먼저 확인한다**」고 정한다. 「호스트만 먼저」는 그 확인을 하지 않고 시작하는 안이다.
2. **쪼갠 근거 둘이 모두 거짓이었다.**
   - ⓐ 「새 `NetworkBehaviour` 경로가 필요하다」 → **거짓.** 실패 처리 쪽이 보낼 통로는 이미 있다. 맵 전송 객체(`NetworkMapTransfer`)가 `Spawn()` 된 **뒤에** 맵 준비를 시작하고(그 위 주석이 「`Spawn()` 을 먼저 해야 한다」), 그 객체는 이미 `ClientRpc` 두 개(준비 시작·조각 전송)를 갖는다. **같은 모양으로 하나 더하는 일이다**(5절).
   - ⓑ 「상대방 화면은 지금과 같고 악화가 아니다」 → **확인하지 않고 적은 문장이었고, 코드로 보면 틀렸다.** 접속한 쪽은 **로딩 화면에 갇힌다.** `BattleViewModel` 의 접속 명령(`JoinGame`)이 로딩을 켜고, **맵 준비 실패 시나리오에서** 로딩을 끄는 자리는 호스트 전용 실패 핸들러(`OnMapTransferFailed`)와 Game 씬에 들어간 뒤의 `GameBootstrapper.Map.cs` 마지막 `ShowLoading(false)` 둘뿐이라 실패 시 **둘 다 돌지 않는다**(다른 끄는 자리는 접속 명령의 예외 처리와 매칭 취소 처리라 이 시나리오에서 돌지 않는다 — 코드 판독. `OnNetworkError` 는 로딩을 끄지 않는다).
3. 앞 판이 남긴 「호스트→상대방 알림은 어느 회차에도 배정되지 않은 채 남는다」는 우려는 **이 판이 이 회차에 흡수해 닫는다.**

## 5. 양쪽이 같은 모달을 보려면 — 흐름과 세 경로

**한 줄 흐름**: 맵 준비 실패 → (호스트가 통보를 보낸다) → **양쪽이 방을 나간다**(연결 종료 · 화면은 로비 메인) → **각자 자기 화면에 「경기를 시작할 수 없습니다」 모달** → 「확인」은 모달만 닫는다.

### 5-1. 호스트

1. (Infrastructure) 실패가 확정되는 자리에서, **방을 나가기 전에** 접속한 쪽에게 실패 `ClientRpc` 를 보낸다. 최초 경기 회차만(아래 5-4).
2. 기존 흐름대로 실패 게이트가 `OnMapTransferFailed` 를 발행한다.
3. (ViewModel) 로딩을 끄고 → **방을 나가고** → 알림 모달을 띄운다. 「방을 나간다」의 실제 처리는 `BattleViewModel.CancelHosting` 본문과 같다 — 화면 상태 초기화(접속중 해제 · 로비 코드 비우기 · 접속 인원 0 · 오류 텍스트 비우기 · 화면을 메인으로)와 `DisconnectAsync()` 호출(결과를 기다리지 않는다)뿐이다(본문을 직접 열어 확인했다). 🔴 **이름만 호스트처럼 보이고 본문은 역할과 무관하다** — 그래서 접속한 쪽도 그대로 쓸 수 있다(로비 코드를 비우는 줄은 접속한 쪽엔 비울 것이 없어 무해하다).

### 5-2. 접속한 쪽 — 세 경로가 **한 진입점**으로 모인다

| 경로 | 언제 | 근거 |
|---|---|---|
| ① 실패 `ClientRpc` 수신 | 통보가 제대로 온 경우 — 가장 빠르다 | 5-3 |
| ② **대기 중 연결 끊김** | 통보가 버려졌거나 호스트가 사라진 경우 | 아래 ⓑ |
| ③ **자체 타이머 60초** | 위 둘 다 없는 경우(전송 객체를 스폰하기 전에 실패한 경우 등 — 5-3 표) | 규칙 17 ① · 아래 |

🔴 **세 경로의 처리를 가르지 않고 한 진입점으로 모은다. 이것은 이미 구현된 재경기 프로세스와 같은 패턴이다.** `GameEndUI.EnterRematchFailedState` 가 재경기 실패 3경로의 공통 진입점이고, 그 주석이 「**세 곳에 같은 코드를 쓰지 않고 전부 이리로 모은다**」라고 적는다. 그 진입점을 부르는 `GameEndUI.OnRematchMapFailed` 의 주석은 「🔴 **두 경로의 처리를 가르지 않는다. 되돌리는 절차는 완전히 같다**(규칙 18). 갈리는 것은 상태 줄 문구 하나뿐」이라고 적는다. 이 판은 같은 선례를 따른다 — 다만 이번에는 **문구도 하나**다(사유로 문구를 가르지 않으므로). 그래서 **호스트의 실패 핸들러·접속한 쪽의 세 경로가 모두 같은 진입점 하나**로 들어가고, 거기서 「로딩 끄기 → 방 나가기 → 알림 모달」을 **한 번만** 한다.

- ⓐ **겹쳐 처리할 코드가 없다**(메인 세션 코드 확인). 연결이 끊기면 `NetworkGameManager.HandleClientDisconnected` 가 `OnServerDisconnected` 를 발행하는데(클라이언트 쪽에서만), **그 이벤트를 구독하는 곳은 `NetworkStatusUI` 하나뿐**(전수 grep)이고 🔴 **그 컴포넌트는 어느 씬에도 배치돼 있지 않다**(스크립트 guid 로 `*.unity`·`*.prefab` 전수 조회 0건 — 이 문서 작업 중 내가 재측정). `ROADMAP.md` 에 「파일은 있는데 화면에 붙어 있지 않아 한 번도 실행된 적이 없다」로 등록돼 있다. **즉 지금 접속한 쪽의 연결이 끊겨도 아무 안내도 뜨지 않고, 이 모달과 충돌할 처리가 없다.** (이 판이 새 구독을 하나 더한다는 뜻이기도 하다.)
- ⓑ **통보가 버려질 위험을 「연결 끊김」이 대신 받는다.** 호스트가 실패 통보를 보낸 직후 연결을 끊으면 그 `ClientRpc` 가 전달되기 전에 버려질 수 있다. ⚠️ **NGO 내부 동작이라 이 환경에서 확인할 수 없다**(패키지 소스가 저장소에 없다 — 추정으로 단정하지 않는다). 그래서 접속한 쪽은 「맵 준비를 기다리는 중에 연결이 끊긴 것」 자체를 실패 신호로 쓴다. 사유로 문구를 가르지 않으므로(규칙 M-1 · RandomMap 규칙 16) 호스트가 일부러 끊었든 회선이 끊겼든 사용자에게는 같은 한 문구다.
- **60초인 근거**: `GameEndUI` 의 `_autoReturnSeconds` 코드 기본값이 60 이다(규칙 D-4 의 60초). 같은 값으로 맞춘다. ⚠️ 값만 같게 맞추는 것이고 **한 상수를 공유하는 것은 아니다** — `GameEndUI` 쪽은 Game 씬에 직렬화되는 값이고 이 감시는 로비 씬 ViewModel 쪽 코드다.
- 🔴 **③은 새 설계가 아니다.** RandomMap 규칙 17 ① 이 「**서버가 판정해 RPC 로 알리는 구조로 만들지 않는다. 양쪽이 각자 같은 감시를 돌린다.** 서버 전용으로 두면 Host 가 사라졌을 때 남은 Client 는 아무 통보도 받지 못한다 … **그것은 상위 원칙 위반이다**」라고 정하고, 같은 자리가 「**자체 감시는 통보가 오지 못한 경우를 받는 그물 — 대체 관계가 아니라 보완 관계**」라고 적는다. 이 판의 ①(통보)과 ②·③(각자 감시)이 정확히 그 관계다 — 하나를 넣었다고 다른 하나를 빼지 않는다.
- **세 경로가 같은 사건을 두 번 결론 내리지 않게 하는 장치가 구현의 필수 요건이다**: 진입점은 **한 번만** 동작하고(이미 처리했으면 무시), 처리하는 순간 ③ 타이머를 멈추며, **스스로 방을 나가는 행위가 일으키는 연결 끊김 이벤트로 ②가 다시 발화하지 않아야 한다.** 이유: `NetworkGameManager.HandleClientDisconnected` 의 주석이 **의도적으로 나갈 때도 이 핸들러가 호출된다**고 적는다(코드 주석 — 정상 종료와 장애가 한 줄을 공유한다). 접속한 쪽이 5-2 의 진입점에서 `DisconnectAsync` 를 부르면 그 끊김이 ②를 다시 부를 수 있다.

### 5-3. 실패 자리 다섯 — `Spawn()` 기준 전수 분류

`NetworkGameManager.BeginMapTransferRound` 의 실패 자리 다섯을 코드로 전수 분류했다(행 번호는 2026-10-12 기준이라 낡을 수 있다 — 사유 이름이 기준이다).

| 행(참고) | 사유 | `Spawn()` | `ClientRpc` | 접속한 쪽에 닿는 길 |
|---|---|---|---|---|
| :945 | `NotServer` | 전 | — | 주석이 「정상 흐름에서는 올 수 없다」고 적는 불변식 위반 |
| :958 | `MapTransferPrefabMissing` | **전** | ❌ | ② 또는 ③ |
| :978 | `MapTransferPrefabMalformed` | **전** | ❌ | ② 또는 ③ |
| :1012 | `BeginHostMapTransferRejected`(맵 준비 실패) | 후 | ✅ | ① (② 보험) |
| :1072 | `MapTransferFailed:<사유>`(전송 실패) | 후 | ✅ | ① (② 보험) |

- **`ClientRpc` 를 보낼 수 있는 근거**: :984 가 전송 객체를 `Spawn()` 하고 **그 뒤** :1003 에서 맵 준비를 시작한다. 스폰 전(:945·:958·:978)에는 보낼 객체가 없다. 🔴 **다른 채널은 없다**: `NetworkGameManager` 는 `MonoBehaviour`(:37)라 스스로 RPC 를 못 보낸다. 메인 세션이 로비 씬 안의 네트워크 스크립트를 guid 로 전수 조회하니 `NetworkGameManager` 하나뿐이고, `ClientRpc` 를 가진 `NetworkGameFlow` 는 `Game.unity` 에만 있다고 한다. ⚠️ **이 문서 작업에서 내가 재측정한 것은 그중 두 건뿐이다** — `NetworkGameFlow` → `Game.unity` 1건(`Lobby.unity` 0건), `NetworkGameManager` → `Lobby.unity` 1건. 로비 씬의 네트워크 스크립트 전수 목록은 재측정하지 않았다. 순서를 바꾸는 것도 불가능하다(없는 프리팹을 먼저 `Spawn()` 할 수 없다).
- :958·:978 은 **에셋·설정 오류**(Inspector 배선 누락·프리팹 컴포넌트 누락)라 정상 프로젝트에서는 나지 않는다. 그래도 **②·③으로 덮인다**(`ClientRpc` 없이도 접속한 쪽이 결론을 낸다).
- **발견 — 구현 시 걸리는 점(코드 판독)**: `HandleMapTransferFailed`(:1072 경로)는 `FailMapTransferGate` 를 부르기 **전에** `CleanupMapTransferSubscription` 으로 활성 전송 객체 참조를 비운다. 실패 통보를 이 참조로 보낸다면 **비우기 전에 보내거나 참조를 미리 잡아 둬야** 한다. :1012 경로는 그 정리를 거치지 않는다(참조가 남아 있다). 두 경로가 서로 다르게 동작하므로 구현자가 먼저 읽어야 한다.

### 5-4. 재경기를 건드리지 않는다

맵 전송 객체는 **최초 경기와 재경기가 공용**이다(RandomMap 규칙 16). 실패 통보를 객체에 더하면 재경기 실패에도 같은 길이 열릴 수 있으므로, **통보는 최초 경기 회차에만 보낸다**(기존 `ClientRpc` 가 이미 회차 종류를 싣는다 — 그것은 로그 표식이고 받는 쪽 동작을 바꾸지 않는다고 적혀 있다). 재경기 실패는 기존 경로(결과 화면 · 규칙 M-3 · 규칙 18)가 그대로 처리한다. 실패 게이트(`FailMapTransferGate`)는 회차의 실패 콜백이 있으면 **그 콜백으로만** 알리고 돌아가며 로비 이벤트는 최초 경기에서만 발행한다 — 이 분기는 수정하지 않는다.

### 5-5. 타이머가 정상 경기에서 발화할 수 없다는 실측

- 보관 로그 전체의 `ElapsedMs=`(맵 준비 소요): **136건 — 최소 0ms · 중앙값 1ms · 최대 59ms**(`Assets/_Project/Docs/_Logs` 하위 23개 파일에서 이 문서 작업 중 내가 재집계했고 인계값과 일치한다).
- `MapPreparationUseCase.cs` 의 진입점 주석이 「최악의 경우 100번의 생성·검증을 **한 프레임 안에서 전부** 돌린다」고 적는다(:305).
- 재경기 맵 **전송**은 별도로 99~134ms 실측(`ForcedMapTransferFailure.cs` 머리말).
- **합쳐도 0.2초가 안 된다** → 60초는 정상 경기를 오판할 여지가 매우 크게 비어 있다. ⚠️ 단 이 계산은 **맵 준비·전송 구간**의 실측이고, 접속한 쪽 타이머를 **언제부터 재는가**(기산점)는 정해지지 않았다 — 7절 ⑦.

## 7. 위험·확인하지 못한 것

**유지하는 위험 (이 판에서도 그대로)**
- 🔴 **`ConfirmPopup` 의 공개 메서드는 `Show` · `ShowAlert` · `Hide` 셋뿐**이고 **떠 있는 동안 본문 글자를 바꾸는 수단이 없다**(메인 세션 확인 — 이 문서 작업 중 `public` 선언을 직접 세어 셋임을 재확인했다). 🔴 **이번 사양은 모달에 타이머가 없어 그 제약에 걸리지 않는다.** 나중에 모달에 초 표시를 넣으려 하면 **팝업에 갱신 수단을 더해야 한다.**
- 모달의 z-order(로비 UI 위에 보이는지) · 상대방 화면의 실제 모습 · 호스트가 나간 뒤의 상대 화면 — **실기 0건.**
- **Unity 컴파일은 이 환경에서 불가.** 구현 후에도 별도 확인이 필요하다.
- 🔴 **랜덤 매칭으로 들어온 경우 매칭 진행 상태 값을 되돌리지 않는다**(메인 세션이 코드로 확인; `cbddf535` 커밋 메시지에도 기록). 방 나가기 처리(`CancelHosting` 본문)에 그 값 되돌리기가 없다. 읽는 곳은 랜덤 매칭 화면의 취소 버튼 표시뿐이라 영향은 작아 보이나 **실기 미확인**이다. 이 판은 방 나가기를 **양쪽 모든 접속 방식**(방 코드·랜덤 매칭)으로 넓히므로 노출이 앞 판보다 크다.
- ⚠️ **메서드 이름이 역할을 암시해 오해를 부른다** — `CancelHosting` 은 본문이 역할과 무관한데 이름은 호스트 전용처럼 읽힌다. **이름 변경은 이번 범위가 아니다**(CLAUDE.md 규칙 6).
- `Spawn()` 앞 실패 두 경로(:958 · :978)는 에셋·설정 오류라 정상 프로젝트에서는 나지 않지만, **②·③으로 덮인다**(5-3).

**새로 생긴 위험 (사용자 지시 반영)**
- ① 🔴 **호스트가 통보를 보낸 직후 끊을 때 그 RPC 가 전달되는지 확인할 수 없다**(NGO 내부 · 패키지 소스 없음). ②가 그 경우를 받으므로 사용자가 안내를 못 받는 일은 없지만, **①이 실제로 동작하는지는 실기로만 알 수 있다.**
- ② 🔴 **「나가기」와 「모달 띄우기」의 순서** — 나가면서 화면이 로비 메인으로 바뀌는데 그 전환이 모달을 가리거나 지우지 않는지. 팝업은 Login 씬의 전역 객체이고 로비 화면 전환은 같은 씬 안의 화면 교체라 괜찮아 보이지만 **실기 미확인**이다(판단).
- ③ 🔴 **②(대기 중 연결 끊김)가 정상 경로를 오판하지 않는지** — 성공해서 전투 씬으로 넘어가는 도중의 전환과 구분돼야 한다. **「아직 맵 준비를 기다리는 중인가」를 무엇으로 판정할지는 판정 불가다** — 접속한 쪽 ViewModel 이 알 수 있는 것은 자신이 접속 명령을 낸 것과 로딩을 켠 것까지이고, 그 상태가 **언제 참에서 거짓이 되는지**(시작 통보 이후? Game 씬 진입?)를 코드로 확인하지 못했다. 필요 조건만 적는다: 거짓이어야 하는 경우 ⓐ 이미 실패 처리를 한 뒤 ⓑ 사용자가 접속 중에 스스로 취소해 나간 경우 ⓒ 성공해 전투 씬으로 넘어가는 중. 판정 수단은 구현자가 정하고 이 Plan 을 갱신한다.
- ④ 🔴 **세 경로가 같은 사건을 두 번 결론 내리는 문제 — 「세 번째 시계」 경고에 걸리는가**: `GameEndUI.cs` 의 주석(재경기 준비 한도 코루틴 필드)이 「이 화면에서 무엇을 판정하는 시계는 이미 두 개(자동 복귀 카운트다운 · 결과 화면 이탈 감시) 있고, **세 번째가 생기면 같은 사건을 서로 다른 시계가 두 번 결론 내리게 된다**」고 경고한다. **판정: 이 경고의 대상이 아니다.** 이번 타이머는 **로비 씬의 `BattleViewModel`** 쪽이고, `GameEndUI` 는 `Game.unity` 에만 있다(guid 로 재측정: `GameEndUI` → `Game.unity` 1건) — 그 경고가 말하는 「이 화면」(결과 화면)과 다른 화면·다른 사건이다. ⚠️ **그러나 경고가 막으려는 모양은 이 판 안에서 별도로 생긴다** — 로비에서 ① 통보 ② 연결 끊김 ③ 타이머가 **같은 사건**을 각자 결론 낼 수 있다. 그래서 5-2 의 「한 진입점 · 한 번만 · 처리 시 타이머 정지」가 필수 요건이다. 선례의 구조(`EnterRematchFailedState` 의 「준비 한도 시계를 멈춘다 — 이미 결론이 났으므로」)도 같다.
- ⑤ **재경기 경로를 건드리지 않는가** — 5-4 대로 건드리지 않게 설계했다. 그러나 **공용 전송 객체에 `ClientRpc` 를 더하는 것은 재경기가 지나는 코드 옆을 수정하는 일**이라 회귀 면적이 앞 판(구독자 쪽만 변경)보다 크다. 재경기 실기 재검증을 구현 뒤 확인 항목에 넣는다.
- ⑥ **이미 구현된 두 버튼 모달은 실기를 거친 적이 없다.** 줄이는 대상 코드가 한 번도 실행된 적 없다는 뜻이므로 「줄였더니 망가졌다」가 아니라 「줄인 결과를 처음 본다」가 된다.
- ⑦ **접속한 쪽 60초 타이머의 기산점이 정해지지 않았다.** 후보(결정하지 않았다): 접속한 쪽이 로딩을 켠 순간 / 접속 완료 순간. 로딩을 켠 뒤 접속 자체가 오래 걸리는 경우(방 입장·릴레이 연결)가 맵 준비 시간에 섞여 들어갈 수 있는지는 확인하지 못했다. 60초 기준이므로 이 불확실성이 정상 경로를 오판시킬 여지는 작아 보이나 **판단이지 관측이 아니다.**
- ⑧ **③이 ②와 겹치는 범위** — 이 판은 호스트가 **모든** 실패(:958·:978 포함)에서 곧바로 방을 나가므로, 호스트가 정상 동작하는 한 스폰 전 실패도 접속한 쪽에는 **연결 끊김(②)으로** 닿을 것으로 **보인다**(판독). 그러면 ③이 홀로 덮는 범위는 「호스트가 앱 사망·정지·회선 끊김으로 연결 종료 이벤트마저 보내지 못하고 전송 계층 타임아웃(`m_DisconnectTimeoutMS: 60000`)이 지나기를 기다리는 경우」에 가까워진다. 사용자가 확정한 것은 「60초 타이머」이므로 **유지하는 것으로 적었고**, 겹침 판정은 11절 4번에서 묻는다.
- ⑨ **모달이 떠 있는 동안 상대가 나가는 경우**의 처리는 없다(이미 둘 다 방을 나온 뒤이므로 영향이 없을 것으로 **보이나** 확인하지 못했다). 접속한 쪽이 방을 나가는 중 `NetworkGameManager` 의 연결 끊김 처리와 겹치는 타이밍도 실기 0건이다.
- ⑩ 🔴 **오류 텍스트 보조 안내가 이 판에서는 보이지 않을 수 있다.** 방 나가기 처리(`CancelHosting` 본문)가 **오류 텍스트를 비우고 화면을 메인으로 돌리는데**, 오류 텍스트를 받는 화면은 방 만들기 대기 화면 하나뿐이라고 `BattleViewModel` 의 2026-10-05 실측 주석이 적는다(이 작업에서 뷰를 다시 열어 재측정하지 않았다). 그러면 모달이 못 뜨는 경우의 보조 안내는 **쓰자마자 지워지거나 보이는 화면이 없다.** 앞 판 구현에서는 방 나가기가 사용자 클릭 뒤였으므로 이 문제가 없었다. → 11절 5번.
- ⑪ 구형 `LobbyUI` 가 지금 로비 씬에 활성인지(접속 2명 시 로비 패널을 숨기는 핸들러가 있다) 확인하지 못했다 — 방 나간 뒤 호스트가 보는 화면이 가정과 다를 수 있다. 연결 끊김 팝업 컴포넌트(`NetworkStatusUI`)는 이번에 guid 로 어느 씬에도 없음을 재확인했다.

## 9. 규칙 M-2 를 개정해야 한다 — 이번에 고치지 않는다 (승인 대기)

### 9-1. 사용자 결정으로 바뀐 **사양 변경**이다
