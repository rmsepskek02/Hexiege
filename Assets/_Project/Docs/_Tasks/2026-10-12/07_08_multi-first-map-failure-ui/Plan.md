# Plan — 멀티플레이 최초 경기 맵 준비 실패 안내 (2026-10-12)

> **이 문서는 사용자 승인 전까지 확정이 아니다.** 승인 없이 코드·씬·규칙 문서를 고치지 않는다(CLAUDE.md 규칙 1·2·11). 이번 회차는 문서뿐이며 Research.md 는 쓰지 않는다(사용자 승인 — 조사는 이 문서 안에 필요한 만큼만 담았다).

## 쉬운 말로 (CLAUDE.md 규칙 13)

- **지금**: 방장(호스트)이 맵을 준비해 상대에게 보내다 실패하면, 로딩 화면이 내려가고 로비에 그대로 남는다. 알려 주는 것은 글자 한 줄뿐인데, 그 글자를 받을 칸이 있는 화면은 **방 만들기 대기 화면 하나**다. 코드로 참가한 쪽과 랜덤 매칭 화면에는 그 칸이 없어 안내가 아예 없다. 그리고 다시 시도할 수단이 없어 방을 새로 만들어야 한다.
- **하려는 것**: 실패하면 싱글플레이의 맵 준비 실패와 **똑같은 모달 팝업**을 띄우고, 버튼 두 개를 준다. 재시도 버튼은 호스트가 맵 준비·전송을 **새 시드부터 처음부터** 다시 하고, 로비 버튼은 연결을 끊고 방에서 나간다.
- **이번 회차의 한계(중요)**: 이 팝업은 **호스트 화면에만** 뜬다. 호스트의 실패를 상대방에게 알리는 네트워크 길이 코드에 없기 때문이다(4절). 규칙 M-2 의 「어느 플레이어든」은 이번에 충족되지 않는다.
- **새로 만드는 컴포넌트·씬 작업·네트워크 경로는 0건**이다(단, 6절 ② 판독 결과에 따라 전송 객체 정리가 조건부로 추가될 수 있다).

## 0. 기존 로직 제거 여부 (WORKFLOW [4] — 문서 최상단 고지)

- **제거 0건.** 맵 전송 실패 핸들러가 하는 일(로딩 끄기 · 접속중 상태 내리기 · 오류 텍스트에 한 줄 쓰기)은 **전부 남기고 모달 호출만 덧붙인다.**
- 오류 텍스트 한 줄을 **남기는 근거**: ① 모달은 `UIManager.Instance` 가 null 이거나 팝업이 배선되지 않으면 **경고만 남기고 조용히 무시**된다(`UIManager.ShowConfirm` 본문 확인). 그때 이 한 줄이 유일한 안내다. ② 덧붙이기만 하면 회귀 면적이 가장 작다.
- 이 줄의 **제거 후보 판정은 모달이 실기에서 확인된 뒤**로 미룬다. 지울 때는 먼저 주석 처리하고, 최종 삭제는 사용자 테스트 통과 후·문서 갱신 전에 한다(WORKFLOW [4]).
- 이번 회차에 **모양이 바뀌는 기존 코드**는 둘이다 — ① 접속 완료 콜백의 「로딩 켜기 + 맵 전송 시작」 두 줄을 공용 private 메서드로 **추출**(본문 동일, 호출 두 곳이 같은 메서드를 부른다) ② 낡아지는 주석 문단 갱신(5절). ①은 최초 경기 성공 경로를 지나므로 위험 6절 ⑥에 둔다.

## 3. 호스트의 재시도 — 진행중 플래그가 막지 않는다 (코드 확인)

실패 통보를 한 곳(`FailMapTransferGate`)이 **이벤트를 내보내기 전에** `_mapTransferInProgress` 를 내리고 `_mapTransferGateSettled` 를 올린다. 새 회차 진입(`BeginMapTransferRound`)은 중복 가드를 통과한 직후 `_mapTransferGateSettled` 를 되돌린다. 즉 모달 콜백(사용자 입력 = 이벤트보다 뒤)에서 진입점을 다시 불러도 거절되지 않는다. 시드는 진입마다 새로 뽑히고 전송 객체도 새로 스폰된다. 중복 클릭은 확인/취소 팝업이 클릭 때 콜백을 비운 뒤 닫아 **1팝업 1호출**이고, 겹쳐 들어와도 가드가 최초 경기에서는 아무 이벤트 없이 무시한다. **남은 의문 하나는 6절 ②.**

## 4. 상대방 화면 — 이번 회차에 정할 것 (사용자 확인 필요)

**사실(코드 확인)**: 맵 전송 실패 통보는 호스트 안의 C# 이벤트뿐이다. 전송 객체의 `ClientRpc` 는 준비 시작·조각 전송 둘뿐이고 실패 결말을 상대에게 보내는 것은 없다. 접속 완료 콜백은 호스트에서만 맵 전송을 시작하며 상대방은 실패 이벤트를 받지 못한다. 상대방 화면은 접속 때 켠 로딩이 그대로 남는 것으로 **읽힌다**(코드 판독, 실기 미확인). → 인계 전제였던 「상대방에게 재시도를 보이게/비활성으로」는 **상대방에게 팝업을 띄울 신호가 없어서 이번 회차에 성립하지 않는다.**

| 선택지 | 내용 | 평가 |
|---|---|---|
| **A (권고)** | 호스트만 모달. 상대방 화면은 지금 그대로 | 새 네트워크 경로 0건. 변경이 호스트 화면 한 곳 |
| B | 호스트→상대방 실패 알림 경로를 이번에 추가하고 상대방에게 로비 버튼 하나뿐인 알림 팝업(규칙 D-5, 공용 알림 호출 존재) | 새 `NetworkBehaviour` 경로(Infrastructure) 필요 — **사용자가 다음 회차로 미룬 종류**이자 RPC 회귀 면적 |
| C | 상대방에게 두 버튼을 보이되 재시도만 비활성 | 확인/취소 팝업에 버튼을 **비활성**으로 보이는 기능이 없다(제목·취소 버튼 숨김만 있다) → 공용 팝업·프리팹 확장 + B 의 경로까지 필요 |

**권고 A 의 근거**: ① B·C 는 전제가 새 네트워크 경로라 사용자가 정한 분할 선을 넘는다. ② 호스트의 두 선택이 모두 상대방을 다음 상태로 보낸다 — 재시도가 성공하면 같은 씬 전환으로 함께 전투 씬에 가고, 로비 버튼은 연결을 끊는다. 모달을 읽는 동안 상대방이 로딩에 있는 것은 **지금과 같고 악화가 아니다.** ③ 회귀 면적 최소. 한계: 호스트가 로비 버튼을 눌러 연결이 끊긴 **뒤의 상대방 화면은 확인하지 못했다**(8절).

**규칙 문서에 범위를 적어야 한다 — 승인 대기(문서는 이번에 고치지 않는다).** M-2 의 「어느 플레이어든 재시도를 누를 수 있다」와 「모달을 표시한다」는 **이번 회차에 호스트에게만 충족**된다. 같은 문장이 RandomMap 규칙 16 에도 있다. 두 곳에 「단계 범위」 표시가 필요하다. 다음 회차 범위가 사용자 결정대로 「상대방 요청 경로 + 중복 한 번 처리」뿐이면 **호스트→상대방 알림은 어느 회차에도 배정되지 않은 채 남는다** → 8절 질문 1.

## 6. 위험 요소

**요청된 세 가지**
1. **재경기 경로를 건드리지 않는가 — 안 건드린다.** `FailMapTransferGate` 는 회차의 실패 콜백이 있으면 **그 콜백으로만** 알리고 돌아가며 로비 이벤트는 실패 콜백이 없는 최초 경기에서만 발행한다. 재경기 진입점은 두 콜백이 모두 있어야 시작한다. 이번 변경은 이 분기를 수정하지 않고(권고 범위 기준) 이벤트 **구독자 쪽**만 바꾼다. 재시도는 최초 경기 종류(`First`)로 들어가 같은 분기를 탄다.
2. **진행중 플래그가 재시도를 막지 않는가 — 플래그는 막지 않는다(3절). 그러나 별개의 미확인 위험이 있다.** 맵 전송이 실패하면 `NetworkGameManager` 는 구독만 풀고 **전송 객체를 Despawn/Destroy 하지 않는다**(`NetworkGameManager`·`NetworkMapTransfer` 두 파일에서 Despawn 호출 0건, Destroy 는 컴포넌트 누락 분기 1건뿐). 재시도는 객체를 **하나 더** 스폰한다. 낡은 객체가 호스트·상대 양쪽에 남은 채 새 객체와 공존해 문제가 되는지(남은 감시 코루틴·연결 끊김 구독·상대 쪽 상태)를 코드로 판정하지 못했다. **구현 착수 전 game-programmer 가 먼저 판독한다.** 문제로 판정되면 5절 조건부 행으로 최초 경기 한정 정리를 넣는다(재경기 분기는 건드리지 않는다).
3. **비동기 연결 종료를 팝업 콜백에서 부르는 처리.** `DisconnectAsync` 는 `Task` 인데 팝업 콜백은 동기 `Action` 이라 await 할 수 없다. 이미 같은 형태의 선례가 있다 — `CancelHosting` 이 화면·상태를 **동기로 먼저** 되돌리고 종료는 `_ = DisconnectAsync()` 로 뒤에서 돌린다. 이를 재사용한다. 팝업은 콜백 전에 먼저 닫히므로 순서 문제는 없다. 위험: (a) 종료 중 예외는 관찰되지 않는다 — 선례와 **같은 노출이고 넓어지지 않는다** (b) 종료가 끝나기 전에 사용자가 새 방을 만들면 겹친다 — 선례와 같고 새 위험이 아니다 (c) 규칙 L-2 는 비동기 작업 시작 시 로딩을 켜라고 하나, 열거된 상황(씬 전환·로그아웃·로비 복귀·재경기)에 이 경우가 없고 선례도 켜지 않는다 → 선례를 따르는 것을 권고, 8절 질문 3.

**추가**
4. **모달이 떴는데 가려지거나 아예 안 뜨는 경우.** 팝업 미배선·`Instance` null 이면 조용히 무시된다(0절의 근거). 로비 화면 위 z-order 는 문서상 모달 대역이 로비 UI 보다 위이나 **실기 미확인**이다.
5. **재시도가 즉시 다시 실패하면 콜백 안에서 모달을 또 띄운다.** 싱글도 같은 모양이나 그 경로가 실기로 확인되었는지는 이 문서 작업에서 확인하지 못했다. 재시도 횟수 제한은 없으나 매번 사용자 클릭이 필요해 무한 루프는 아니다.
6. **접속 완료 콜백의 추출은 정상 최초 경기 경로를 지난다.** 본문이 같아 동작은 같다고 판단하나 판단이며 관측이 아니다. 추출을 하지 않고 두 줄을 복제하는 대안이 있다(복제는 이 프로젝트가 피해 온 방식).
7. **모달이 떠 있는 동안 상대방이 나가는 경우**의 처리는 없다 — 모달이 남는다. 재시도하면 연결 끊김으로 다시 실패한다(RandomMap 규칙 18 의 기존 경로).

## 7. 씬 작업 — 필요 없다

① 팝업은 Login 씬의 공용 UI 관리자가 소유하는 전역 객체이고 싱글 모달이 이미 같은 호출을 쓴다. ② 새 `[SerializeField]` 가 **0건**이다 — 라벨은 코드 상수, 본문은 코드, 호출 대상은 이미 배선된 전역 팝업. 「직렬화 값이 코드 기본값을 이긴다」(`.claude/MEMORY.md` 공통 교훈)는 직렬화 필드를 건드릴 때 걸리는 함정이라 이번에는 해당이 없다. ③ 로비 씬의 `BattleViewModel` 은 순수 C# 이라 컴포넌트 배선이 없다. 이 Plan 의 새 `NetworkBehaviour` 도 0건이다(아키텍처 제약표: `NetworkBehaviour` 는 Infrastructure 에만).

**아키텍처 제약 확인**: `BattleViewModel`(Presentation)은 이미 `NetworkGameManager`(Infrastructure)와 `UIManager`(Presentation)를 쓰고 있어 **새 의존이 없다**(레이어 순서상 Presentation 이 Infrastructure 를 아는 것은 허용 방향). 반대로 `NetworkGameManager` 가 팝업을 부르는 것은 Infrastructure→Presentation 역방향이라 **금지**이고(규칙 L-4 아래 레이어 방향 주석) 그래서 모달 호출은 이벤트 구독자인 ViewModel 에 둔다. Application 은 건드리지 않는다.

## 8. 사용자 결정·승인 대기

1. **상대방 화면(4절)**: 권고 A 로 가도 되는가? 호스트→상대방 실패 알림은 다음 회차 범위에 넣어야 하는가(현재 분할로는 어느 회차에도 없다).
2. **규칙 문서의 단계 범위 표기**(M-2 와 RandomMap 규칙 16) — 승인 대기. 이번에 고치지 않았다.
3. **로비 버튼에서 로딩을 켜는가** — 선례(`CancelHosting`)대로 켜지 않는 것을 권고한다.
4. **재시도 횟수 제한 없음**을 싱글과 같게 적용하는가.
5. **재현 수단**: 기존 1회용 강제 실패 도구(`ForcedMapTransferFailure`)는 **재경기 전용**이라(코드 주석이 최초 경기 비적용을 명시) 이 화면은 정상 경로에서 관측되지 않는다. 최초 경기용 1회 토글 추가는 별도 코드 변경이므로 승인이 필요하다 — 없으면 구현해도 실기 확인이 불가능하다.
6. **오류 텍스트 한 줄의 최종 처분**은 실기 확인 뒤(0절).
