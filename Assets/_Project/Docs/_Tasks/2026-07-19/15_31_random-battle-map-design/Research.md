# Research — 11×21 FlatTop 무작위 대전 맵 기획

## 이 작업이 무엇인지

매 경기 같은 지형을 반복하는 대신 다섯 가지 형태 중 하나를 무작위로 만들되, 어느 진영도 배치 때문에 유리하지 않도록 180도 대칭과 접근성 검증을 강제하는 맵 기획이다. 이번 단계는 구현 전에 확정된 게임 규칙과 용어를 문서의 단일 기준으로 정리하는 작업이다. **모든 내용은 확정 설계이며 아직 구현되지 않았다.**

---

## 확정 범위

- FlatTop 11×21, 중심 `(5,10)`, Red 성 `(5,1)`, Blue 성 `(5,19)`
- 다섯 맵 유형 동일 확률 20%: 완전개방형, 장애물 개방형, 협곡형, 외곽형, 3갈래형
- 타일·광산·지형·건설 불가 구역·장식을 포함한 모든 맵 요소의 정확한 180도 대칭
- 유형별 중립 광산 수, 광산 수별 초기 골드, 시작 공간 10타일
- 국소 건설 불가 구역과 완전 차단 지형의 서로 다른 의미
- 결정적 seed, 100회 재시도, 같은 유형/광산 수의 검증된 폴백, 생성 로그
- 적/아군 건물로 경로가 완전히 막힌 유닛의 후속 동작
- PointyTop은 미사용이며 이번 범위에서 제외
- 완성된 `MapDefinition`을 canonical binary(row-major 231타일, 고정폭 정수, 명시 byte order)로 직렬화하고 SHA-256으로 검증
- 64-bit root seed, 고정 custom PRNG, 선택/지형/광산/장식/attempt별 독립 스트림
- Host 권위 `NetworkMapTransfer`(1KB chunk, 64KB 전체, 10초 대기와 incomplete 한정 1회 재전송)
- 유형별 deterministic base template 5개와 사전 검증 대칭 광산 slot 폴백
- `SameMap`/`NewMap` 재경기 정의 생명주기
- 초기 골드 전용 `GameConfig.MapTestModeEnabled`; ON이면 실제 초기 골드 `5000`, OFF이면 광산 수 표 적용. 멀티플레이에서는 Host 권위의 표식(고정폭 `0`/`1`)과 실제 초기 골드를 canonical bytes 및 SHA-256 입력에 포함

## 기존 문서와의 충돌 및 정정

1. `GameSystemRules_Map.md`의 기존 “각 중립 광산은 양 성까지 개별 동일거리” 규칙은 새 기획과 충돌한다. 중앙 단독 광산만 양 성 거리를 직접 비교하고, 나머지는 180도 대응 광산 쌍의 교차 거리·접근성을 비교하도록 정정한다.
2. 장식은 게임플레이 영향이 없더라도 비대칭 예외가 아니다. 존재·종류·스케일·재질 변형·회전 대응까지 일치시킨다.
3. GDD의 FlatTop 10×29 프로토타입 표와 “중립 광산 2개”는 최신 기획이 아니다. 목표 맵은 11×21이며 유형별로 중립 광산 1~6개다.
4. 세로 방향 전역 보호 통로는 사용하지 않는다. 건설 불가 구역은 협곡 중앙부, 외곽형 통로, 3갈래형 분리 대역처럼 국소 적용한다.

## 문서 구조 판단

- `GameSystemRules_Map.md`: 실제 도입하는 모든 대전 맵에 적용할 대칭·거리·접근성 보편 규칙
- `GameSystemRules_RandomMap.md`: 11×21 FlatTop 생성기의 유형별 수치와 생성·폴백·검증 규칙
- `GameDesignDocument.md`: 플레이어가 경험할 맵·자원·타일·경로 차단 기획
- `CONTEXT.md`: 구현 세부가 없는 확정 용어집

규칙의 양이 많고 유형별 수치가 자주 참조되므로 RandomMap 규칙을 Map 보편 규칙과 분리하는 편이 변경 범위와 책임이 명확하다. 별도 ADR은 이 프로젝트의 기존 관례가 없고 규칙/GDD가 결정과 이유를 충분히 보존하므로 만들지 않는다.

## 구현 전 핵심 위험

- exact 180° 대칭은 맵 좌표뿐 아니라 장식 변형 속성까지 검증해야 한다. 플레이어 소유 성·채굴소·건물·유닛의 외형은 맵 시각 대칭 대상이 아니다.
- 광산 타일을 경로 목표로 직접 사용하면 이동 불가 목표 문제가 생기므로 인접 이동 가능 타일 집합끼리 접근성을 비교해야 한다.
- 장애물 개방형의 장애물 개수 상한이 없어 생성 실패 가능성이 있으므로 재시도와 검증된 폴백이 필수다.
- 초기 소유권의 중복 타일을 단순 합산하면 “고유 10타일” 검증을 잘못 통과할 수 있다.
- 건설 불가 구역과 완전 차단 지형을 같은 플래그/표현으로 취급하면 이동·점령 규칙이 깨진다.
- 건물 경로 차단 대응은 확정 기획이지만 무작위 맵 생성과 별도 구현 범위다.
- 기존 문서와 런타임 참조에는 `HasGoldMine` 같은 중복 상태와 변경 가능한 `IsWalkable` 관념이 남을 수 있다. 목표 모델은 `TerrainKind`·`BuildRule`·`MineKind`·`HasBuilding`을 분리하고 `IsWalkable`을 계산값으로 만든다.
- seed만 Client에 보내 재생성하게 하면 런타임·PRNG 차이에 취약하다. 디버깅 재현성은 seed 계약으로 보장하되 경기 권위는 Host가 검증한 최종 canonical `MapDefinition`이다.
- 맵 바이너리의 임시 `MapVersion=1`은 앱/매치메이킹 호환 버전이 아니다. 전역 `GameProtocolVersion`은 별도 중요 작업으로 남긴다.
- 테스트 모드는 일반적인 개발 치트가 아니다. 초기 골드만 바꾸며, 멀티에서는 Host가 확정한 표식과 실제 골드를 Client가 그대로 적용해야 한다.
