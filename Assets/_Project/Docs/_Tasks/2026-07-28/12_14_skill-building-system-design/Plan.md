# Plan — 스킬 건물 시스템 (기획 확정 + 설계 문서화)

## 이 계획이 무엇인가 (자연어 서두)

이 문서는 스킬 건물 시스템에 대해 **이번 사이클에서 확정한 설계 전체**와, **그 설계를 어떤 문서에 어떻게 반영했는지**를 정리한 계획서입니다.

일반적인 Plan.md는 "앞으로 코드를 이렇게 고치겠다"는 구현 계획이지만, 이번 사이클은 **코드 구현이 아니라 기획 확정 + 문서화가 산출물**입니다. 실제 코드/프리팹은 손대지 않았고(향후 별도 task), 대신 스킬 건물이 앞으로 따라야 할 규칙을 정하고 정식 문서로 남기는 것이 목표였습니다.

따라서 이 Plan은 ① 확정된 설계 내용, ② 그 설계를 담은 문서 작업(이미 수행 완료), ③ 나중에 실제 구현에 들어갈 때 주의할 위험·참고 사항 — 이 세 가지를 다룹니다.

**단일 소스(SSoT):** 확정 설계의 권위 문서는 `Assets/_Project/Docs/GameSystemRules/GameSystemRules_Skills.md`입니다. 이 Plan은 그 문서를 근거로 요약하며, 각 항목이 해당 문서의 어느 규칙에 대응하는지 연결합니다(WORKFLOW [4] 취지 — 각 항목의 근거를 GameSystemRules에 연결).

**구현 상태: 기획 확정 / 미구현.** 구체 스킬 목록·수치는 추후 데이터로 확정.

## 1. 확정된 설계 전체

각 항목 끝의 `→` 는 `GameSystemRules_Skills.md`의 대응 규칙이다.

### 1-1. 공통 규칙

- **자원: 마나 없음, 쿨다운만.** 스킬 사용을 제약하는 유일한 장치는 쿨다운. → 규칙 2
- **건물별 글로벌 쿨다운.** 한 건물에서 스킬 1개를 쓰면 그 건물의 모든 스킬 버튼이 쿨다운 동안 함께 잠긴다(연속·동시 난사 방지). 개별 스킬 쿨다운은 미도입(밸런싱 시 재검토). → 규칙 3
- **건물당 최대 5개 스킬.** → 규칙 4
- **건물 업그레이드 없음.** 건설 즉시 스킬 전부(최대 5개) 사용 가능, 단계별 해금 없음. → 규칙 5
- **종족별 스킬셋 분리.** `MagicSpirit`·`WillowShrine`이 enum `MagicBuilding`을 공유하지만 스킬 로드아웃은 종족(건물)별 데이터로 각각 정의하고 종족 키로 분기. **enum 멤버 분리/개명은 하지 않는다**(직렬화·RPC 안정성). → 규칙 1, 6
- **데이터 주도 설계(ScriptableObject).** 스킬 = {아이콘 / 조준 방식 / 쿨다운 / 타입 / 파라미터}. 코드는 타입별 실행기만 구현, 구체 스킬·수치는 SO로 주입. → 규칙 7
- **UI: 범용 `BuildingActionPanelUI`(3×3 그리드) 재사용.** 슬롯 1~5 = 스킬, 슬롯 6 = 철거(고정), 슬롯 7~9 = 예약(빈 공간, 향후 여유분). → 규칙 8, 9
- **쿨다운 표시.** 버튼 위 반투명 오버레이가 시계방향(clockwise)으로 회전 + 그 위에 남은 초 숫자 텍스트. 글로벌 쿨다운이므로 쿨다운 중 스킬 슬롯 전부에 적용. → 규칙 10
- **건설 비용 200 골드(세 건물 공통).** 권위 소스 `Resources/Config/BuildingStatsConfig.asset`. → 3종 정의 하단 건설 비용 노트

### 1-2. 스킬 메커니즘 3타입 (유틸 타입 제외 → 규칙 14)

| 타입 | 조준 | 대상 | 효과 | 구현 기반 | 대응 규칙 |
|------|------|------|------|----------|----------|
| A. 즉발 범위 피해 | 지점 지정 | 적 | 지정 원형에 1회 피해 | 기존 원형 AoE 판정 재사용 | 규칙 11 |
| B. 범위 지속 피해(장판) | 지점 지정 | 적 | 지정 원형에 지속시간 동안 DoT | 기존 DoT 틱 재사용 | 규칙 12 |
| C. 전역 상태변경 | 전역 즉시(조준 없음) | 아군(긍정)/적(부정) | 지속시간 동안 스탯·상태 변경. 버프·디버프·제어(둔화/빙결=이속0·공격불가)·회복을 하나로 통합 | 기존 HoT 일부 재사용 + 신규 상태변경 시스템 | 규칙 13 |

- 회복(힐)은 우선 전역 즉시로 구현하되, 구현 후 지점 지정형 전환 여부 재결정 가능. → 규칙 13

### 1-3. 발동 경로 2종

- **즉시 발동:** 버튼 탭 = 즉시 발동(타입 C). → 규칙 15
- **지점 지정:** 버튼 → 지도 조준 모드(타입 A·B). → 규칙 16

### 1-4. 모바일 지점 조준 UX

기존 "랠리포인트 설정 모드"(`InputHandler.HandleClick`) 아키텍처 재사용·확장.

- 스킬 버튼을 **누른 채 드래그** → 조준점(범위 원)이 손가락 따라 이동. → 규칙 17
- 조준점을 화면 가장자리로 끌면 그 방향으로 **카메라 자동 팬(엣지 스크롤)**, 부드럽게. → 규칙 18
- **손을 떼면** 그 위치에 발동. → 규칙 19
- 취소: 화면 **하단 중앙 X 버튼(에셋)** 위에서 손을 떼면 취소. → 규칙 20
- **겹침 회피 규칙:** X는 화면 맨 끝보다 살짝 안쪽, 엣지 스크롤은 진짜 가장자리 여백에서만 발동(하단 X와 겹치지 않게). 여백 폭은 구현/테스트에서 조정. → 규칙 21
- **조준 경계 제한:** ① 조준점은 맵 타일 범위 안으로 clamp(맵 밖 불가). ② 엣지 스크롤도 맵 경계에서 정지. → 규칙 22, 23
- 지정 가능 영역: 맵 안 어디든(사거리/시야 제한 없음). → 규칙 24

### 1-5. 멀티플레이 / 서버 권위

- 발동·판정·피해·상태변경은 **서버에서만** 실행. 엣지 스크롤·조준점 이동·범위 미리보기는 로컬 표현. → 규칙 25
- **손 뗀 순간의 조준 좌표만** 서버로 RPC 전송 → 서버가 건물 생존·쿨다운·좌표 유효 타일 재검증 후 발동(클라 입력 불신뢰). 즉시 발동은 좌표 없으므로 생존·쿨다운만 재검증. → 규칙 26

## 3. 향후 구현 시 위험 / 참고 사항

실제 코드 구현(별도 task) 착수 시 유의할 지점.

- **타입 C(전역 상태변경) 시스템이 최대 신규 덩어리.** 버프·디버프·제어·회복을 한 시스템으로 커버하는데, **버프 개념 자체가 게임 내 최초 도입**이다. 스탯·상태 변경의 적용/해제/지속시간 관리 구조를 새로 설계해야 한다(기존 HoT 일부만 재사용 가능).
- **지점 조준용 입력 모드·엣지 스크롤·조준 clamp가 신규.** 기존 랠리포인트 모드를 기반으로 하되, 드래그 추적·카메라 엣지 스크롤(맵 경계 정지)·조준점 타일 clamp·하단 X 취소(겹침 회피)는 새로 구현·튜닝이 필요하다. 여백 폭 등은 실기 조정 대상.
- **서버 권위 RPC 신설.** 스킬 발동 RPC는 좌표만 전송 + 서버 재검증(건물 생존·쿨다운·유효 타일). NetworkBehaviour는 Infrastructure 레이어에만, RPC 메서드명은 `ServerRpc`/`ClientRpc`로 끝나야 하는 아키텍처 제약 준수.
- **종족 분기 데이터 구조.** `MagicSpirit`·`WillowShrine`이 enum을 공유하므로, 스킬 로드아웃 로드는 enum이 아닌 종족 키로 분기해야 한다. enum 멤버 분리는 하지 않는다(필요 시 향후 재검토).
- **개별 스킬 쿨다운은 밸런싱 시 재검토.** 현재는 건물 글로벌 쿨다운만. 데이터 구조는 향후 개별 쿨다운 도입 여지를 열어두는 것이 안전.
- **구체 스킬·수치 미확정.** 각 건물 슬롯 1~5의 스킬 목록, 쿨다운·반경·지속시간·피해량·상태효과 강도는 데이터(ScriptableObject)로 별도 확정.
