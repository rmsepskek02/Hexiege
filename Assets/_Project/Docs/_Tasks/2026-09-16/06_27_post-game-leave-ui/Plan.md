## 1. 이 계획이 무엇을 하는가 (자연어 설명)

경기가 끝난 뒤의 결과 화면에서 **사용자가 갇히지 않게** 만들고, **상대가 사라진 사실을 화면 안에서 알려 주는** 작업입니다.

지금은 「다시하기」를 누르면 다시하기 버튼과 로비 복귀 버튼이 **둘 다 꺼져서** 스스로 나갈 방법이 없고,
상대가 나가도 **내 화면은 아무 말도 해 주지 않습니다.**
그래서 사용자는 영문도 모른 채 기다리다가 시간이 다 되어 로비로 밀려납니다.

이 계획은 그 문제를 이렇게 풉니다.

1. **로비 복귀 버튼은 절대 끄지 않습니다.** 언제든 스스로 나갈 수 있습니다.
2. **상대가 스스로 나가면 나가기 직전에 알려 주고**, 말없이 사라지면 **30초 동안 응답이 없는 것으로 판정**합니다.
3. 그 사실을 **결과 화면의 타이머 자리에 문장으로 띄우고**, 재경기 버튼을 끄고, 남은 시간을 30초로 다시 셉니다.
4. 상대의 재경기 요청을 받아 팝업이 떠 있는데 요청자가 사라진 경우에는 **그 팝업을 닫고 「상대방이 떠났습니다」 알림을 대신 띄웁니다.**

🔴 **이 계획은 새 사양을 만들지 않습니다.** 사양은 2026-09-16 에 이미 규칙 문서에 기록됐고,
이 문서는 **그 규칙을 어떤 순서로 코드에 옮길지**만 정합니다. 그래서 아래 어디에도 사양을 다시 쓰지 않고 **규칙 번호로 가리킵니다.**

## 2. 단계 분할

각 단계는 **그 단계만 끝난 상태에서 독립적으로 검증할 수 있도록** 나눴다.

| 단계 | 내용 | 완료 판정 (기계적) |
|---|---|---|
| **1** | **알림 팝업 신설** — 「타이틀 + 본문 + 버튼 1개」 구조와 `ShowAlert` API. 🔴 **공용 자산을 건드리는 단계라 따로 뗐다** | `ShowAlert` 선언이 `IUIManager` 와 `UIManager` 양쪽에 각 1건. **`ShowConfirm` 실호출처가 변경 전과 같은 5건**이고 `ConfirmPopup` 의 직렬화 필드 6개가 **이름·개수 그대로** |
| **2** | **로비 복귀 버튼 잠금 비활성화** (§0) | `_backToLobbyButton` 을 `false` 로 설정하는 **동작 코드 0줄** (주석은 남아 있어도 된다) |
| **3** | **자동 로비 복귀 카운트다운 60초** — 코드 기본값과 씬 값 **양쪽** | `GameEndUI.cs` 의 `_autoReturnSeconds` 기본값이 `60f` **이고** `Game.unity` 의 직렬화 값이 `60`. **두 자리가 모두 바뀌었을 때만 완료** |
| **4** | **전송 계층 연결 타임아웃 60000** — `Game.unity` · `Lobby.unity` **두 씬** | `m_DisconnectTimeoutMS: 60000` 이 두 씬에서 **각 1건**, `30000` 이 두 씬에서 **각 0건** |
| **5** | **「상대가 나갔다」 채널 신설 + 정상 퇴장 통보** (규칙 17 의 정상 퇴장 갈래) | 새 `GameEvents` 채널 1개가 선언되고, 퇴장 통보 RPC 메서드명이 `ServerRpc` 로 끝난다. `Application` 하위에 `using Unity.Netcode` **동작 코드 0줄** 유지 |
| **6** | **무반응 30초 자체 감시 + 판정 시 연결 종료** (규칙 17 의 무반응 갈래) | 감시 코루틴의 대기 값이 **결과 화면 전용 필드**로 따로 존재하고, `ReconnectionHandler` 의 `_reconnectWaitSeconds` 와 **같은 필드를 공유하지 않는다**. 브로드캐스트 RPC 메서드명이 `ClientRpc` 로 끝난다 |
| **7** | **결과 화면 반영** — 타이머 문구 교체 · 재경기 버튼 비활성 · 카운트다운 30초 재시작 (규칙 D-1 · D-2 · D-4) | 이탈 문구 문자열이 코드에 **1건** 존재하고 평시 문구와 **분기로 갈린다**. 이탈 채널 구독이 `GameEndUI` 에 **1건** |
| **8** | **재경기 요청 응답 전 요청자 이탈 처리** (규칙 D-6) | 이탈 수신 시 재경기 요청 팝업을 닫는 경로 1건 + `ShowAlert` 호출 1건. 별도 타이머 필드를 **추가하지 않았다**(규칙 D-6 3항) |
| **9** | **맵 전송 중 이탈 문구 분기** (규칙 18) | 실패 사유가 `MapTransferErrorCode.Disconnected` 인지로 갈리는 분기 1건. 🔴 **새 `LogEvent` 키 0건 추가 · 새 이벤트 0건 추가** |
| **10** | **맵 준비 실패 알림 팝업 연결** (규칙 M-3 · M-4) | ⚠️ **착수 전 사용자 확정이 필요하다 — 문구와 버튼 라벨이 규칙에서 여전히 미정이다.** 확정 후: 실패 경로에서 `ShowAlert` 호출 1건 |

### 단계 사이의 의존 관계

- **1 → 8 · 10**: 알림 팝업이 없으면 규칙 D-6 과 M-3 · M-4 를 만들 수 없다.
- **5 → 7 → 8**: 채널이 없으면 화면이 반영할 것이 없고, 화면 반영이 없으면 D-6 의 순서를 볼 수 없다.
- **4 는 6 보다 먼저**: 전송 계층 타임아웃이 판정보다 짧으면 **판정이 나기 전에 연결이 끊겨** 통보가 나갈 자리가 사라진다(규칙 17 의 부등호 방향).
- **2 · 3 은 다른 단계와 독립**이며 가장 먼저 넣어도 된다. 🔴 **2 는 단독으로도 「갇힘」을 해소하므로 우선순위가 가장 높다.**

## 5. 위험 요소

| # | 위험 | 왜 위험한가 | 어떻게 다루나 |
|---|---|---|---|
| **R1** | 🔴 **`m_DisconnectTimeoutMS` 를 한 씬만 고치면 갈린다** | 값이 `Game.unity` · `Lobby.unity` 두 곳에 각각 직렬화돼 있다. 한쪽만 고치면 **로비와 인게임의 타임아웃이 서로 다른 값**이 되어, 어느 화면에서 끊겼는지에 따라 동작이 달라진다 | 단계 4 의 완료 판정을 **두 씬 모두 60000 · 30000 이 0건**으로 잡는다 |
| **R2** | 🔴 **`_autoReturnSeconds` 는 코드와 씬 양쪽을 고쳐야 한다** | **Inspector 값이 코드 기본값보다 우선**한다(`.claude/MEMORY.md`). 코드만 60f 로 바꾸면 **실제 동작은 여전히 30초**이고, 바꿨다고 착각한 채로 다음 단계가 얹힌다 | 단계 3 의 완료 판정을 **두 자리가 모두 바뀐 경우에만 완료**로 잡는다 |
| **R3** | 🔴 **통보 RPC 를 보내고 같은 프레임에 `Shutdown()` 하면 메시지가 버려질 수 있다** | `BackToLobby()` 는 Lobby 퇴장 직후 `ShutdownNetworkManager()` 를 부른다. RPC 가 실제로 송신되기 전에 연결이 내려가면 **상대는 아무것도 못 받고**, 정상 퇴장이 무반응 이탈로 떨어져 **30초를 기다리게 된다** | ⚠️ **실기 확인이 필요한 항목이다.** 코드로는 「보냈다」와 「나갔다」를 구분할 수 없다. 실기에서 **정상 퇴장이 즉시 반영되는지**로 확인하고(§7 의 관측 가능 항목), 반영이 늦으면 Shutdown 을 한 프레임 이상 미루는 방안을 별도로 승인받는다 |
| **R4** | 🔴 **30초 시계가 두 개 돈다** | `ReconnectionHandler` 의 재접속 대기(30초)는 결과 화면 위에서도 시작되며, `ForceWin()` 이 `_announced` 가드에 막혀 **아무 일도 하지 않는 죽은 대기**다. 여기에 규칙 17 의 판정 30초가 더해지면 **같은 길이의 시계가 둘**이 된다. 동작은 갈리지 않지만 **로그에서 둘을 같은 것으로 착각하기 쉽다** | 단계 6 에서 **결과 화면 전용 필드를 따로 두고**(`_reconnectWaitSeconds` 를 재사용하지 않는다), 로그에 **어느 시계인지 구분되는 식별자**를 남긴다 |

### 6-1. `grep` 으로 확인되는 것 (리포지토리 루트에서 실행)

```
# 1) 로비 복귀 버튼 잠금 — 동작 코드가 0줄인가 (주석 줄은 걸러낸다)
grep -rn "_backToLobbyButton[[:space:]]*\.[[:space:]]*interactable[[:space:]]*=[[:space:]]*false" \
  Assets/_Project/Scripts --include=*.cs | grep -vE ":[[:space:]]*(//|///|\*)" | wc -l
#   착수 전 실측 = 1 / 단계 2 완료 후 기대 = 0

# 2) ShowConfirm 실호출처가 그대로인가 (선언부와 주석 제외)
grep -rn "ShowConfirm(" Assets/_Project/Scripts --include=*.cs \
  | grep -v "Presentation/UI/UIManager.cs" \
  | grep -v "Presentation/UI/Core/IUIManager.cs" \
  | grep -vE ":[[:space:]]*(//|///|\*)" | wc -l
#   착수 전 실측 = 5 / 단계 1 완료 후 기대 = 5 (변하면 안 된다)

# 3) 전송 계층 타임아웃 — 두 씬 모두인가
grep -c "m_DisconnectTimeoutMS: 60000" Assets/_Project/Scenes/Game.unity Assets/_Project/Scenes/Lobby.unity
grep -c "m_DisconnectTimeoutMS: 30000" Assets/_Project/Scenes/Game.unity Assets/_Project/Scenes/Lobby.unity
#   착수 전 실측 = 60000 각 0건 / 30000 각 1건
#   단계 4 완료 후 기대 = 60000 각 1건 / 30000 각 0건

# 4) 카운트다운 길이 — 코드와 씬 양쪽인가
grep -n "_autoReturnSeconds" Assets/_Project/Scripts/Presentation/UI/GameEndUI.cs Assets/_Project/Scenes/Game.unity
#   착수 전 실측 = 코드 30f · 씬 30 / 단계 3 완료 후 기대 = 코드 60f · 씬 60

# 5) 레이어 경계 — Application 이 Unity.Netcode 를 직접 참조하지 않는가
grep -rn "using Unity.Netcode" Assets/_Project/Scripts/Application --include=*.cs \
  | grep -vE ":[[:space:]]*(//|///|\*)" | wc -l
#   착수 전 실측 = 0 (주석 1건은 걸러진다) / 단계 5 완료 후 기대 = 0

grep -rnE ":[[:space:]]*NetworkBehaviour" \
  Assets/_Project/Scripts/Presentation Assets/_Project/Scripts/Application --include=*.cs | wc -l
#   착수 전 실측 = 0 / 모든 단계 완료 후 기대 = 0
```

🔴 **「`grep` 0건」이라는 문구를 완료 판정에 그대로 쓰지 않는다.**
이 프로젝트는 지운 자리에 **제거 기록 주석**을 남기는 관습이 있어 식별자로만 세면 0 이 되지 않는다
(2026-09-15 에 실제로 그 판정이 문구대로 성립하지 않았다). 위 명령들은 모두 **주석 줄을 걸러낸 뒤** 센다.

### 6-2. Unity 에디터에서만 확인되는 것
