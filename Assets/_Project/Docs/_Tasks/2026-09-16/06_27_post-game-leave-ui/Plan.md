## 1. 이 계획이 무엇을 하는가 (자연어 설명)

경기가 끝난 뒤의 결과 화면에서 **사용자가 갇히지 않게** 만들고, **상대가 사라진 사실을 화면 안에서 알려 주는** 작업입니다.

지금은 「다시하기」를 누르면 다시하기 버튼과 로비 복귀 버튼이 **둘 다 꺼져서** 스스로 나갈 방법이 없고,
상대가 나가도 **내 화면은 아무 말도 해 주지 않습니다.**
그래서 사용자는 영문도 모른 채 기다리다가 시간이 다 되어 로비로 밀려납니다.

이 계획은 그 문제를 이렇게 풉니다.

1. **로비 복귀 버튼은 절대 끄지 않습니다.** 언제든 스스로 나갈 수 있습니다.
2. **상대가 스스로 나가면 나가기 직전에 알려 주고**, 말없이 사라지면 **30초 동안 응답이 없는 것으로 판정**합니다.
3. 그 사실을 **결과 화면의 타이머 자리에 문장으로 띄우고**, 재경기 버튼을 끄고, 남은 시간을 30초로 다시 셉니다.
4. 상대의 재경기 요청을 받아 팝업이 떠 있는데 요청자가 사라진 경우에는 **그 팝업을 닫고 「상대방이 떠났습니다」 알림을 대신 띄웁니다.**

🔴 **이 계획은 새 사양을 만들지 않습니다.** 사양은 2026-09-16 에 이미 규칙 문서에 기록됐고,
이 문서는 **그 규칙을 어떤 순서로 코드에 옮길지**만 정합니다. 그래서 아래 어디에도 사양을 다시 쓰지 않고 **규칙 번호로 가리킵니다.**

## 2. 단계 분할

각 단계는 **그 단계만 끝난 상태에서 독립적으로 검증할 수 있도록** 나눴다.

| 단계 | 내용 | 완료 판정 (기계적) |
|---|---|---|
| **1** | **알림 팝업 신설** — 「타이틀 + 본문 + 버튼 1개」 구조와 `ShowAlert` API. 🔴 **공용 자산을 건드리는 단계라 따로 뗐다** | `ShowAlert` 선언이 `IUIManager` 와 `UIManager` 양쪽에 각 1건. **`ShowConfirm` 실호출처가 변경 전과 같은 5건**이고 `ConfirmPopup` 의 직렬화 필드 6개가 **이름·개수 그대로** |
| **2** | **로비 복귀 버튼 잠금 비활성화** (§0) | `_backToLobbyButton` 을 `false` 로 설정하는 **동작 코드 0줄** (주석은 남아 있어도 된다) |
| **3** | **자동 로비 복귀 카운트다운 60초** — 코드 기본값과 씬 값 **양쪽** | `GameEndUI.cs` 의 `_autoReturnSeconds` 기본값이 `60f` **이고** `Game.unity` 의 직렬화 값이 `60`. **두 자리가 모두 바뀌었을 때만 완료** |
| **4** | **전송 계층 연결 타임아웃 60000** — `Game.unity` · `Lobby.unity` **두 씬** | `m_DisconnectTimeoutMS: 60000` 이 두 씬에서 **각 1건**, `30000` 이 두 씬에서 **각 0건** |
| **5** | **「상대가 나갔다」 채널 신설 + 정상 퇴장 통보** (규칙 17 의 정상 퇴장 갈래) | 새 `GameEvents` 채널 1개가 선언되고, 퇴장 통보 RPC 메서드명이 `ServerRpc` 로 끝난다. `Application` 하위에 `using Unity.Netcode` **동작 코드 0줄** 유지 |
| **6** | **무반응 30초 자체 감시 + 판정 시 연결 종료** (규칙 17 의 무반응 갈래) | 감시 코루틴의 대기 값이 **결과 화면 전용 필드**로 따로 존재하고, `ReconnectionHandler` 의 `_reconnectWaitSeconds` 와 **같은 필드를 공유하지 않는다**. 브로드캐스트 RPC 메서드명이 `ClientRpc` 로 끝난다 **[🔴 2026-09-21 추가 — 이 칸은 한 글자도 지우지 않았다: 이 판정은 「감시가 서버에서 돌고 서버가 상대에게 알린다」를 전제하고 있어 지금 설계와 어긋난다. 어긋난 자리와 보완의 단일 소스는 §2-1]** |
| **7** | **결과 화면 반영** — 타이머 문구 교체 · 재경기 버튼 비활성 · 카운트다운 30초 재시작 (규칙 D-1 · D-2 · D-4) | 이탈 문구 문자열이 코드에 **1건** 존재하고 평시 문구와 **분기로 갈린다**. 이탈 채널 구독이 `GameEndUI` 에 **1건** |
| **8** | **재경기 요청 응답 전 요청자 이탈 처리** (규칙 D-6) | 이탈 수신 시 재경기 요청 팝업을 닫는 경로 1건 + `ShowAlert` 호출 1건. 별도 타이머 필드를 **추가하지 않았다**(규칙 D-6 3항) |
| **9** | **맵 전송 중 이탈 문구 분기** (규칙 18) | 실패 사유가 `MapTransferErrorCode.Disconnected` 인지로 갈리는 분기 1건. 🔴 **새 `LogEvent` 키 0건 추가 · 새 이벤트 0건 추가** |
| **10** | **맵 준비 실패 알림 팝업 연결** (규칙 M-3 · M-4) | ⚠️ **착수 전 사용자 확정이 필요하다 — 문구와 버튼 라벨이 규칙에서 여전히 미정이다.** 확정 후: 실패 경로에서 `ShowAlert` 호출 1건 |

### 단계 사이의 의존 관계

- **1 → 8 · 10**: 알림 팝업이 없으면 규칙 D-6 과 M-3 · M-4 를 만들 수 없다.
- **5 → 7 → 8**: 채널이 없으면 화면이 반영할 것이 없고, 화면 반영이 없으면 D-6 의 순서를 볼 수 없다.
- **4 는 6 보다 먼저**: 전송 계층 타임아웃이 판정보다 짧으면 **판정이 나기 전에 연결이 끊겨** 통보가 나갈 자리가 사라진다(규칙 17 의 부등호 방향).
- **2 · 3 은 다른 단계와 독립**이며 가장 먼저 넣어도 된다. 🔴 **2 는 단독으로도 「갇힘」을 해소하므로 우선순위가 가장 높다.**

### 2-1. 🔴 단계 6 설계 확정 3건 (2026-09-21 추가 — 위 표와 §3 의 줄은 한 글자도 지우지 않았다)

**[쉬운 말로]** 단계 6 은 **「결과 화면에서 상대가 30초 동안 아무 응답이 없으면 나간 것으로 보고 연결을 끊는다」**를 만드는 단계다. 이번에 **① 그 감시를 누가 돌리는가 ② 판정하기 전에 무엇을 먼저 확인하는가 ③ 「응답」을 무엇으로 재는가** 세 가지가 사용자와 확정됐다. 🔴 **구현은 하지 않았다 — 기록만이다.**

🔴 **사양의 단일 소스는 `GameSystemRules/GameSystemRules_RandomMap.md` 규칙 17 의 「2026-09-21 추가 (2차)」 블록**이며 **여기에 규칙 본문을 옮겨 적지 않는다.** 이 절이 적는 것은 **그 확정이 위 표의 단계 6 과 §3 에 무엇을 더하는가**뿐이다.

#### 확정 A — 자체 감시는 **Host 와 Client 가 각자** 돌린다 (서버 전용 금지)

- 🔴 **서버가 판정해 RPC 로 알리는 구조로 만들지 않는다.** 그렇게 두면 **Host 가 결과 화면에서 사라졌을 때 남은 Client 는 아무 통보도 받지 못한다** — 감시할 서버도, 통보를 보낼 RPC 도 **Host 와 함께 사라지기** 때문이다. 이는 **「플레이어는 자신이 Host 인지 Client 인지 알 수 없다」는 상위 원칙 위반**이다(단일 소스는 `TechnicalDesignDocument.md` 「🔴 최상위 원칙 …」 절).
- 🔴 **단계 5 의 정상 퇴장 통보 RPC 는 그대로 둔다.** 정상 퇴장은 **즉시 알리는 것이 맞고**, 자체 감시는 **그 통보가 오지 못한 경우를 받는 그물**이다. **둘은 대체 관계가 아니므로 단계 6 이 단계 5 를 대체하거나 줄이지 않는다.**

#### 확정 B — 판정 **전에** 「내 인터넷이 되는가」를 먼저 확인한다 (도달 확인 **구현도 단계 6 범위**)

```
상대 신호 30초간 없음
  → 내 인터넷 도달 확인
      ├─ 된다    → 상대 이탈 확정 → 연결 종료 → 화면 반영(규칙 D-1 · D-2 · D-4)
      └─ 안 된다 → 내 문제 → 연결을 끊지 않고 복구를 기다린다
```

- 🔴 **왜 이 확인이 없으면 안 되는가** — 규칙 17 이 **「이탈로 판정하면 연결도 함께 종료한다」**고 정하고 있다. 따라서 오판은 **문구가 잘못 뜨는 데서 끝나지 않고, 내가 스스로 연결을 끊어 버린다.** 내 회선이 30초 깜빡였을 뿐인데 **잠깐 끊겼다 돌아올 수 있었던 상황이 되돌릴 수 없는 단절로 확정**되고, **상대는 멀쩡히 있는데 재경기도 불가능해진다.**
- 🔴 **도달 확인을 만드는 것은 이 단계의 범위다 — 전적 기록 작업(별건)으로 미루지 않는다.** 근거는 **오판의 결과가 이 작업의 UI(`GameSystemRules_UI.md` 「공통 UI 규칙」 규칙 D-1 문구 · 규칙 D-2 버튼 잠금)와 연결 종료에 그대로 떨어진다**는 것이다. **전적 기록 작업은 나중에 같은 것을 재사용**한다(`ROADMAP.md` 「전적 기록 연결 + 이탈 시 승패 처리」 행).
- **확인 대상 · 판정표 · 남아 있는 구멍의 단일 소스는 `TechnicalDesignDocument.md` 「이탈 시 승패 기록 — 규칙 집합」 절의 「이탈 판정 절차」**이며 **여기에 표를 옮겨 적지 않는다.** ⚠️ 그 절차는 종전에 **승패 기록 문맥에만** 적혀 있었고, **결과 화면 이탈 판정에도 같은 절차가 적용된다는 것이 이번에 확정**됐다.

#### 확정 C — 「응답」의 측정 수단은 **미확정** (순서만 확정됐다)

| 순위 | 수단 | 상태 |
|---|---|---|
| **1순위** | 이미 있는 RTT — `Infrastructure/Network/NetworkGameManager.cs` 의 `GetCurrentRttMs()` | 현재 이 값을 읽는 곳은 `Presentation/UI/NetworkStatusUI.cs` 의 **핑 표시 한 곳뿐**(문서 작업 중 직접 실측) |
| **2순위** | 결과 화면 전용 하트비트 신설 | **1순위가 불가능할 때만** |

- 🔴 **「RTT 로 한다」를 확정으로 적지 않는다.** **RTT 값으로 「갱신이 멈췄다」를 판별할 수 있는지는 아직 확인되지 않았다**(`CLAUDE.md` 규칙 10). 확정된 것은 **「1순위로 시도하고, 판별이 불가능하면 하트비트로 간다」는 순서**뿐이다.
- **확인 시점은 이 단계 착수 시**이며, **확인 결과와 그 근거는 이 Plan 에 기록**한다.

#### 🔴 위 표의 단계 6 완료 판정이 지금 설계와 어긋나는 자리 — 1건

- **어긋난 것**: 완료 판정의 마지막 조건 *"브로드캐스트 RPC 메서드명이 `ClientRpc` 로 끝난다"* 는 **「서버가 판정하고 그 결과를 상대에게 브로드캐스트한다」는 구조를 전제**하고 있다. **확정 A 로 무반응 갈래는 양쪽이 각자 판정하므로 그 전제가 더 이상 성립하지 않는다.**
- 🔴 **그래도 그 줄을 지우지 않는다** — 지우면 「원래 그렇게 계획했다」가 되어 **전제가 바뀐 경위가 사라진다.**
- ⚠️ **다만 「브로드캐스트를 없앤다」도 확정으로 적지 않는다.** 확정된 것은 **「양쪽이 각자 판정한다」**이고, **단계 5 의 정상 퇴장 통보는 그대로 남으므로 `ClientRpc` 는 그 단계에 여전히 존재**한다. **무반응 갈래에 브로드캐스트를 둘지 말지는 구현 착수 시 정한다**(`CLAUDE.md` 규칙 10).
- **이번 확정으로 단계 6 에 더해지는 완료 판정** (위 표의 기존 판정 중 **대기 값 분리 조건은 그대로 유효**하며 아래가 덧붙는다):
  1. 감시 경로가 **서버 전용 가드 안에 있지 않을 것** — **Host 와 Client 양쪽에서 도는지**가 판정 대상이다.
  2. **인터넷 도달 확인 경로가 존재**하고, **이탈 확정이 그 확인을 통과한 뒤에만** 일어날 것.
  3. **측정 수단(RTT / 하트비트)을 무엇으로 정했는지와 그 근거**가 이 Plan 에 기록되어 있을 것.

#### §3 파일별 변경에 더해지는 것

- `Infrastructure/Network/NetworkGameEndController.cs` (단계 6) — **「서버에서만 도는 감시」가 아니라 양쪽에서 도는 감시**가 된다. ⚠️ **이 파일이 현재 그 감시를 어떤 가드 안에 두는지는 이 문서 작업에서 확인하지 않았다 — 착수 시 확인한다**(`CLAUDE.md` 규칙 10).
- **인터넷 도달 확인** (단계 6, 신규) — ⚠️ **어느 파일에 둘지는 이 Plan 이 정하지 않는다**(추정하지 않는다). 다만 **기존 레이어 경계는 그대로**다 — `NetworkBehaviour` 는 Infrastructure 에만 두고, Application 은 `Unity.Netcode` 를 직접 참조하지 않으며 화면에는 `GameEvents` 를 경유해 전달한다. 🔴 **도달 확인은 현재 구현돼 있지 않다** — 근거(실측)의 단일 소스는 `TechnicalDesignDocument.md` 「이탈 판정 절차」의 실측 항목이다.

## 8. 14-4(실패 경로 실기 검증)를 어떻게 다룰 것인가
