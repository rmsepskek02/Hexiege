## 0. 이 계획이 무엇을 하는가 (자연어 설명 — CLAUDE.md 규칙 13)

에이전트가 자기 기억 노트를 정리하다가 실수로 내용을 지워 버리는 일이 반복됐습니다.
한 번은 378줄이 사라졌는데 **3일 동안 아무도 몰랐고, 발견한 것도 우연이었습니다.**
사람 눈으로는 못 잡습니다. 노트는 겉보기에 멀쩡하고, 없어진 줄이 뭐였는지는
없어진 뒤에는 알 방법이 없기 때문입니다.

그래서 **이미 프로젝트에 있는 문서 검사 도구에게 이 일을 시키기로** 했습니다.
그 도구는 지금 "문서끼리 서로를 잘못 가리키는 곳"을 찾아 주는데,
여기에 **노트를 지키는 검사 세 가지를 더 붙입니다.**

1. **노트가 너무 길어졌는가** — 200줄이 넘으면 넘은 부분은 에이전트에게 아예 안 보입니다.
   글자는 파일에 남아 있으니 지워진 것도 아닙니다. 그래서 더 위험합니다.
   지금 확인해 보니 **세 명의 노트가 이미 넘쳐 있고, 합쳐서 481줄이 보이지 않는 상태**입니다.
2. **미아가 된 상세 노트가 있는가** — 목차에서 링크가 빠지면 그 파일은 있어도 없는 것과 같습니다.
   확인해 보니 **224줄짜리 파일 하나가 실제로 미아**였습니다.
3. **노트 전체 분량이 갑자기 줄지 않았는가** — 내용을 다른 파일로 옮긴 것이라면 총 분량은 그대로여야 합니다.
   파일 개수는 그대로인데 총 분량만 줄었다면, 그건 **옮긴 게 아니라 지워진 것**입니다.
   378줄 사고가 정확히 이 모양이었습니다.

세 번째 검사는 앞의 둘과 성격이 다릅니다. 앞의 둘은 **지금 파일만 보면 판정이 끝나지만**,
세 번째는 **"전보다 줄었는가"를 물어야 해서 이전 분량을 어딘가 적어 둬야** 합니다.
그 기록을 어디에 어떻게 남길지가 이번 계획에서 가장 중요한 결정이고, §4 에서 두 가지 안을 비교합니다.

**이번 작업의 산출물은 이 계획서까지입니다.** 실제 코드는 승인을 받은 뒤
game-programmer 에이전트가 작성합니다(CLAUDE.md 규칙 3).

### 2-2. 임계값 200행의 근거 — 추정이 아니다

🔎 `.claude/agents/` 하위 6개 에이전트 정의 파일 **전부**에 명시돼 있다.

| 파일 | 행 | 문장 |

| `game-design-lead.md` | 109 | 〃 |

| `project-orchestrator.md` | 94 | 〃 |
| `qa-tester.md` | 139 | 〃 |
| `document-manager.md` | 198 | `keep it under 200 lines` |

→ 200은 **시스템 프롬프트에 적힌 값**이며, 도구가 임의로 정한 숫자가 아니다.
에이전트 정의가 바뀌면 이 값도 함께 바꿔야 하므로, 구현 시 **상수 1개로 뽑아 두고
"근거는 `.claude/agents/*.md`" 라는 주석을 단다**(CLAUDE.md 규칙 8 — 초급자도 이해할 주석).

### 2-3. 출력 형식 — 🔴 "몇 행이 잘리는지"를 반드시 함께 낸다

**"502행"이라고만 적으면 사람이 행동하지 않는다.
"302행이 에이전트에게 보이지 않는다"라고 적어야 행동한다.**

출력에 담을 것:
- 파일 경로
- 현재 행수 / 상한 200
- **초과분 = 현재 행수 − 200** ← 이 값이 실제 손실량이다
- (권장) 폴더 내 초과분 합계

예시 형태(문구는 구현자 재량, **초과분 표기는 필수**):
```
  .claude/agent-memory/qa-tester/MEMORY.md : 502행 (상한 200) → 302행이 에이전트에게 보이지 않음
```

### 2-4. 🔴 `[6]` 과 `[7]` 이 겹치는 사례가 실재한다 (🔎 실측)

`qa-tester/MEMORY.md` 는 토픽 2개를 **정상적인 마크다운 링크로 걸고 있다.**

417:- [patterns.md](patterns.md) — 버그 패턴 상세
418:- [qa_history.md](qa_history.md) — 완료된 QA 상세 내역 …

**링크는 존재하지만 200행 밖이라 에이전트 프롬프트에서 잘린다.**
즉 파일 기준으로는 고아가 아닌데, **에이전트가 실제로 보는 것 기준으로는 고아**다.
갱신 규칙 5("링크 없는 토픽은 존재하지 않는 것과 같다")가 노린 상태에 정확히 해당한다.

🔎 전수 확인 결과(모든 에이전트 폴더):

| 상태 | 건수 | 내역 |
|---|---:|---|

- 다만 **보이지 않는다는 사실 자체는 출력에 남겨야** 분산 작업 때 링크 위치를 위로 올리는 걸 잊지 않는다.

### 3-3. 🔴 결정 — 링크로 인정하는 형태는 **마크다운 링크만**

**질문:** `[patterns.md](patterns.md)` 같은 마크다운 링크만 인정할 것인가,
아니면 `` `network-infra.md` `` 같은 **백틱 언급**도 링크로 볼 것인가?

🔎 **실측 확인:** `game-programmer/MEMORY.md` 는 **두 형태를 모두 쓴다.**

| 형태 | 위치 | 성격 |
|---|---|---|
| 마크다운 링크 | 19~54행 (인덱스 절) | **토픽 목록** — 18개 전부 이 형태 |
| 백틱 언급 | 99행 · 101행 | *"상세는 `network-infra.md` 참조"* — 본문 안 상호참조 |

→ **인덱스는 전부 마크다운 링크이고, 백틱은 본문에서 덧붙이는 참조다. 역할이 다르다.**

**결정: 마크다운 링크만 인정한다.**

근거 3가지:
1. **준거 규칙 원문이 "링크"라고 적혀 있다** — `.claude/MEMORY.md` 37행
   *"상세는 토픽 파일로 빼되 **반드시 인덱스에서 링크한다**"* · 38행 *"**링크 없는** 토픽 파일은…"*.
   백틱 언급은 링크가 아니다.
2. **엄격 기준을 써도 현재 정상 상태에 오탐이 0이다** — 🔎 `game-programmer` 토픽 18개,
   `qa-tester` 토픽 2개가 **전부 마크다운 링크를 가지고 있다**(§2-4 표).
   더 엄격한 쪽을 골라도 새 오탐이 생기지 않는다.
3. **백틱을 인정하면 규칙의 취지가 무너진다** — 본문 어딘가에서 지나가듯 한 번 언급됐다는 이유로
   통과하면, "인덱스에서 찾아갈 수 있는가"라는 질문이 "어딘가에 이름이 적혀 있는가"로 바뀐다.
   에이전트는 인덱스를 보고 토픽을 찾는다.

**단, 백틱 언급만 있는 파일은 출력에서 구분 표기한다** —
`고아(언급조차 없음)` 와 `고아(본문 백틱 언급만 있고 인덱스 링크 없음)` 는
사람이 조치할 방향이 다르다(후자는 링크 한 줄만 추가하면 끝난다).
현재 해당 파일은 0건이지만 향후를 위해 형식을 정해 둔다.

## 4. 🔴 검사 `[8]` — 폴더 총합 행수 급감 (이번 계획의 핵심 설계 결정)

### 4-1. 왜 이것만 구조가 다른가

**기존 5종은 전부 「단일 시점」만 본다.** 지금 파일들만 읽으면 판정이 끝난다.
`[8]` 은 **「이전 상태와 비교」**해야 한다 — 도구가 처음으로 **상태를 기억해야 한다.**

그리고 그 기억을 git 에서 가져올 수 없다:
> **CLAUDE.md 규칙 5 — git 명령 절대 금지.**
> (근거: 2026-03-03 `git restore` 무단 실행으로 커밋 안 된 작업 전체 소실, 복구 불가.)

에이전트는 `git log`·`git diff` 를 실행할 수 없다.
→ **기준 행수를 파일에 기록해 두고 대조하는 방식이 불가피하다.**

### 4-2. 판정에 쓰는 값 — 총합만으로는 부족하다

📨 2026-08-17 사고의 결정적 지표는 **"파일 수는 그대로인데 총합만 줄었다"** 였다
(19 → 19 / 2,503 → 2,125). 총합만 보면 이 구분이 안 된다.

> ### 🔴 권장: **안 1 — 감소는 전부 보고한다(임계값 0).**
> 결정적 근거는 **08-20 사고가 폴더 총합 기준 -5행이었다**는 실측값이다.
> 어떤 비율·절대값 임계값을 두든 이 사고는 놓친다. 그런데 이건 **실제로 일어난 사고**다.
> 임계값을 두는 순간 검사는 "큰 사고만 잡는" 도구가 되고, 그러면 08-20 같은 건은 다시 못 잡는다.
>
> 오탐 비용은 낮다 — 정상적인 감소라면 **사람이 확인하고 기준값을 한 줄 갱신하면 끝**이다.
> 오히려 이 절차가 갱신 규칙 3("삭제는 틀렸다고 확인했을 때만, 지운 이유를 남긴다")을
> **기계적으로 강제**하는 효과가 있다. 감소가 검사에 걸리므로 이유 없이 지나갈 수 없다.

### 4-5. 🔴 기준값 갱신 — 누가, 언제, 그리고 **자동 갱신은 금지**

> **자동 갱신하면 검사가 무력해진다.**
> 도구가 실행될 때마다 현재값을 기준값으로 덮어쓰면,
> **감소가 그대로 새 기준이 되어** 다음 실행부터는 아무 문제도 아니게 된다.
> 즉 사고 직후 도구를 한 번 돌리는 것만으로 사고가 지워진다.
> **`check_docs.py` 는 기준값 파일에 절대 쓰지 않는다 — 읽기 전용을 유지한다.**

| 항목 | 결정 |
|---|---|
| 갱신 주체 | **document-manager** (기준값 파일은 데이터 파일이라 코드 위임 불필요) |
| 갱신 시점 | **WORKFLOW [11]** — 메모리 갱신([9])·검토([10]) 가 끝난 뒤, 정합성 검사 직전 |
| 증가 방향 갱신 | 자유롭게 갱신 (정상 성장) |
| **감소 방향 갱신** | 🔴 **사용자 승인 필수.** 감소를 기준값에 반영하는 것은
"이 삭제는 의도된 것"이라는 판단이며, 그 판단은 에이전트가 단독으로 내리지 않는다(규칙 12) |
| 갱신 기록 | 감소 반영 시 **줄어든 행수와 사유를 기준값 파일에 함께 남긴다**(갱신 규칙 3) |

→ 이 절차를 `WORKFLOW.md` [11] 에 명문화할지는 **§12-7 승인 사항**
(WORKFLOW.md 수정은 이번 작업 범위 밖이므로 별도 승인이 필요하다 — 규칙 6).

## 5. 검사 범위 확장 방식 — `.claude/agent-memory/` 를 어떻게 함께 보는가

현재 도구는 `--root`(기본 `Assets/_Project/Docs`)를 받고, 그 아래만 검사한다
(`check_docs.py` 182~183행). `.claude/agent-memory/` 는 **범위 밖**이다.

### 5-1. 🔴 기존 `--root` 재활용은 불가능하다 (실측 근거)

`python3 Tools/check_docs.py --root .claude/agent-memory` 로 돌리면 되지 않을까?
**안 된다.** 🔎 `parse_rule_docs()` 131행:
```python
pattern = os.path.join(root, "GameSystemRules", "*.md")
```
`.claude/agent-memory/GameSystemRules/` 는 존재하지 않으므로 `docs` 딕셔너리가 **빈 채로** 반환되고,
`docs` 에 의존하는 검사 **[1]·[3]·[4]·[5] 가 전부 조용히 "이상 없음"** 을 낸다(201·247·262·297행).
→ **기존 5종을 무력화하지 않고는 `--root` 를 돌려 쓸 수 없다.**

### 5-2. 3안 비교

| 안 | 방식 | 평가 |
|---|---|---|
| ① `--root` 를 복수 인자로 | 기존 인자의 의미를 바꾼다 | 🔴 §5-1 문제 그대로. 기존 5종에 회귀 위험 |
| ② 리포지토리 루트 기준 하드코딩 | `.claude/agent-memory` 를 코드에 고정 | 🟡 동작하지만 검사 범위를 실행 시 조정할 수 없다 |
| ③ **별도 인자 `--memory-root` 신설**(기본값 `.claude/agent-memory`) | 신규 3종 전용 경로 | 🟢 **권장** |

### 5-3. 🔴 권장: 안 ③ `--memory-root` 신설

근거 3가지:
1. **기존 `--root` 의 의미가 그대로다** → 검사 [1]~[5] 에 회귀가 발생할 경로 자체가 없다.
2. **기본값을 주므로 사용법이 안 바뀐다** — `python3 Tools/check_docs.py` 한 줄이 그대로 8종 전부를 돈다.
   WORKFLOW [11]③ 과 `CLAUDE.md` 하단에 적힌 실행 명령을 고칠 필요가 없다.
3. **"루트 밖 파일을 도구가 직접 아는 것"은 이 도구의 기존 관례에 이미 있다** — 🔎 112~115행:
   ```python
   # 리포지토리 루트의 지침 문서도 참조를 담고 있어 함께 본다.
   for extra in ("AGENTS.md", "CLAUDE.md"):
   ```
   리포지토리 루트 기준 상대경로를 기본값으로 두는 것은 새로운 방식이 아니다.

**폴더가 없을 때의 동작:** `--root` 는 없으면 종료 코드 2 로 중단한다(186~189행).
`--memory-root` 는 **없으면 신규 3종을 건너뛰고 그 사실을 출력한다**(중단하지 않는다).
근거: 기존 5종은 메모리 폴더와 무관하므로, 메모리 폴더가 없다고 문서 검사 전체를 못 돌게 만들면 회귀다.

## 6. `_Tasks/` · `_Logs/` 제외 원칙이 새 검사에도 적용되는가

**결론: 적용한다. 단 현재 실효는 없다.**

- 제외 원칙의 이유는 *"이력 기록이라 소급 수정하면 이력이 왜곡된다"*(`check_docs.py` 33~36행).
  이 논리는 경로와 무관하게 유효하므로 신규 3종에도 그대로 적용한다.
- 🔎 **실측: `.claude/agent-memory/` 하위에 `_Tasks/`·`_Logs/` 는 없다.**
  `find .claude/agent-memory -type f` 결과 **총 27개 파일 전부 `.md`**, 하위 디렉터리 0개.
- 따라서 `is_excluded()`(103~105행)를 신규 3종의 파일 수집에도 통과시키되,
  **현재 걸러지는 파일은 0개**다. 앞으로 그런 폴더가 생겨도 자동으로 제외된다.

**단, `[8]` 의 행수 집계에서는 주의가 필요하다.**
집계 대상이 달라지면 총합이 달라져 오탐이 난다.
→ **`[7]` 과 `[8]` 은 반드시 같은 수집 기준을 쓴다**(같은 함수로 목록을 만든다).
서로 다른 기준을 쓰면 "고아는 아닌데 총합에는 안 잡히는 파일" 같은 모순이 생긴다.

## 10. 🔴 후속 작업과의 순서 의존 — `[8]` 이 먼저 있어야 한다

**다음 작업은 200행 초과 3개 에이전트(§9)를 인덱스 + 토픽 구조로 분산하는 것이다.**
그 작업의 성격:

- 대상 합계 **1,081행**(502+325+254)을 여러 파일로 **대량 이동**시킨다.
- 이동은 **"원본에서 지우고 새 파일에 붙이는"** 조작이다.
  → **붙이기가 누락되면 그대로 소실**이고, 겉보기로는 구분이 안 된다.
- 📨 2026-08-17 사고가 **정확히 이 모양**이었다 — 정리처럼 보였지만 총합이 -378행이었다.

**즉 이번 후속 작업은 지금까지 중 가장 큰 이동이며, 가장 큰 손실 위험 구간이다.**

> ### 순서 의존 (역전 금지)
> ```
> [8] 구현 + 기준값 초기화   ←── 반드시 먼저
>            ↓
> 200행 초과 3개 분산 작업   ←── 이동 중 손실이 [8] 에 잡힌다
>            ↓
> [6] 3건 · [7] 1건 해소 확인
> ```
> **`[8]` 없이 분산 작업을 먼저 하면, 이동 중 손실을 검증할 수단이 없다.**
> 갱신 규칙 6 이 *"폴더 전체 행수 합이 줄지 않아야 한다 — 이동과 삭제를 구분하는 **유일한** 검증법"*
> 이라고 못 박은 그대로다. **유일한 검증법을 갖추기 전에 가장 위험한 작업을 하면 안 된다.**

분산 작업 중 활용법: 작업 **전후로 `[8]` 을 실행**해 총합이 유지·증가했는지 확인한다.
§4-2 표의 "파일 수 증가 + 총합 감소" 가 이 작업에서 나올 수 있는 가장 위험한 패턴이다.

## 11. 위험 요소

### 11-1. 🔴 오탐 시 종료 코드 1 이 되어 **다른 문서 작업까지 막힌다** (가장 큰 위험)

WORKFLOW [11]③ 은 *"**0건을 확인한 뒤** [12]로 넘어간다"* 고 규정한다.
그런데 §9 대로 구현 직후 **[6] 3건 + [7] 1건이 즉시 잡히므로 종료 코드가 1** 이 된다.

→ **후속 분산 작업(§10)이 끝나기 전까지, 메모리와 무관한 모든 문서 작업이
"0건 확인" 절차를 통과할 수 없게 된다.** 이건 실제로 발생이 확정된 문제다.

|---|---|---|
| ㉮ | 신규 3종을 **경고 전용**(종료 코드 미반영)으로 둔다 | 🔴 무시되기 쉬워 도구의 존재 이유가 약해진다 |
| ㉯ | **구현과 분산 작업을 한 승인 묶음**으로 처리해 노출 기간을 없앤다 | 🟡 작업량이 커진다(1,081행 분산) |
| ㉰ | 기준값 파일에 **「알려진 미해소 항목(known)」 목록**을 함께 두어, 목록에 있는 항목은 **출력에는 내되 종료 코드에는 넣지 않는다** | 🟢 **권장** |

**권장 ㉰ 의 근거:**
- 흔히 쓰는 baseline 패턴이고, `[8]` 기준값 파일과 **자연스럽게 같은 파일에 들어간다**(§4-3 안 A).

  → 새로 생긴 위반은 절대 조용히 묻히지 않는다.
- 미해소 항목이 **출력에는 계속 보이므로** 잊히지 않는다.

초기 known 목록: `[6]` 3건 + `[7]` 1건 (§9). 분산 작업 완료 시 **비운다.**
→ 이 방식 채택 여부는 §12-6.

### ⓑ `[6]` 폐기 — 이유

**검사 `[6]`(MEMORY.md 200행 초과)을 폐기한다.**

- `[6]` 의 존재 이유는 §2-3 이 못 박은 대로 **"몇 행이 잘리는지"를 알리는 것**이었다. **잘리는 행이 0이므로 검사할 대상이 없다.**
- §2-2 「임계값 200행의 근거 — 추정이 아니다」의 근거는 **에이전트 정의 파일의 `lines after 200 will be truncated` 한 줄**이었다. 그 문장 자체가 거짓이었으므로 **근거가 무너진다.** (그 문장은 2026-08-21에 6개 정의 파일 전부에서 교체됐다 — 잔존 0건)
- 행 수는 이제 **손실 지표가 아니라 품질 지표**다. 새 기준은 `.claude/MEMORY.md` 「🔴 에이전트 메모리 갱신 규칙」 4번 — **1차는 성격**(인덱스 + 매 작업마다 필요한 것만), **2차는 경고선 250행**, **토픽 파일은 상한 없음**(선택적으로 읽으므로 `work-history.md` 819행도 문제가 아니다).
- 따라서 **검사기가 종료 코드 1 로 실패시킬 근거가 못 된다.** §11-1 이 지목한 가장 큰 위험(*"오탐 시 다른 문서 작업까지 막힌다"*)에 정면으로 해당한다.
- 남는 것은 **실제 손실을 잡는 `[7]`(고아 토픽) · `[8]`(총합 급감) 2종**이다. 종전 표기 **「메모리 검사 3종」은 「2종」으로 정정**한다(`ROADMAP.md` 우선순위 표 · `PROJECT_STATUS.md` · `WORK_HISTORY.md` 동시 정정).

**연동 폐기·정정:** §2 전체 · §9 의 `[6]` 3건 · §11-5(200행 임계값 변경 위험) · §13-2 의 `[6]` 구현 · §13-5 의 `[6]` 대조는 **모두 무효**다. §12-10(`[6]`·`[7]` 겹침 처리)은 **`[6]` 이 없어져 겹침 자체가 성립하지 않으므로**, `qa-tester/patterns.md`(링크 417행) · `qa-tester/qa_history.md`(링크 418행)는 **"링크가 200행 밖이라 잘린다"가 아니라 정상 링크**다 — 다만 **부가 표기는 유지**한다(인덱스가 길어 사람이 놓치기 쉽다는 품질 정보로서는 여전히 유효).
