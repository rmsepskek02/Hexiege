# _Tasks 폴더 사용법

이 폴더는 각 작업 진행 시 사전 분석과 설계를 기록하는 공간입니다.

---

## 폴더 구조

```
_Tasks/
└── YYYY-MM-DD
  └── HH_MM_[작업명]/
    ├── research.md    ← 코드 파악, 영향 범위, 현재 상태
    └── plan.md        ← 구현 접근법, 파일별 변경 내용, 위험 요소
```

예시:
```
_Tasks/
└── 2026-03-05
  └── 18_05_network-input-fix/
    ├── research.md
    └── plan.md  
  └── 19_05_attack-direction/
    ├── research.md
    └── plan.md
```

## 전체 작업 사이클

```
[1] 사용자 작업 요청 → 계획 설명
      ↓
[2] 사용자 승인 ("진행해") → "task 문서 작성을 진행할까요?" 반드시 확인
      ↓
[3] research.md 작성
      ↓
[4] plan.md 작성 → 사용자에게 공유 → 명시적 승인 후에만 구현 시작
      ↓
[5] 에이전트 위임 결정 → 컨텍스트 공유 → 구현
      ↓
[6] 구현 내용을 사용자가 테스트하여 작업 완료 여부 확인
(버그 발견 또는 부족한 구현의 경우 재작업)
      ↓
[7] 테스트 완료 확인 즉시 → "문서/메모리 업데이트를 진행할까요?" 반드시 확인
(사용자가 다음 작업으로 넘어가려 해도 이 확인 단계를 생략하지 않음)
      ↓
[8] 에이전트 MEMORY.md 업데이트
      ↓
[9] 업데이트 내용 검토
      ↓
[10] PROJECT_STATUS.md / ROADMAP.md 반영
```

### ⚠️ 절대 금지 사항
- **[2] 승인 후 바로 Edit/Write/Agent 호출 금지** — 반드시 "task 문서 작성할까요?" 먼저 확인
- **[6] 테스트 완료 후 다음 작업 전 [7] 업데이트 확인 생략 금지** — "나중에", "다음 세션에" 불가
- **규모/복잡도 무관 — 한 줄 수정도 포함 — 예외 없음**

### [1] 작업 요청 및 계획 설명
- 사용자 요청 분석 후 작업 범위·접근법 설명
- 승인 전 Edit/Write/Agent 호출 일체 금지

### [2] 사용자 승인 + 문서 작성 여부 확인
- 사용자가 "진행해" 등으로 승인 → 즉시 **"task 문서(research.md / plan.md) 작성을 진행할까요?"** 질문
- 사용자가 명시적으로 "문서 생략해도 돼"라고 말하지 않는 한 반드시 확인

### [3] research.md 작성
- 관련 코드 읽기, 영향 범위 파악
- 현재 버그/상태 분석
- 작업 중 발견한 부가 이슈도 여기에 기록

### [4] plan.md 작성 및 승인
- 구체적인 구현 방법, 수정할 파일 목록
- 예상 위험 요소, 아키텍처 제약 사항
- plan.md 내용을 사용자에게 공유 → **명시적 승인 확인 후에만** 구현 시작
- 계획 변경 시 변경 이유도 추가 기록

### [5] 에이전트 위임 및 구현
아래 **에이전트 위임 기준** 참조.

### [6] 사용자 테스트
- 구현 내용을 사용자가 직접 테스트하여 완료 여부 확인
- 버그 발견 또는 부족한 구현의 경우 재작업

### [7] 문서/메모리 업데이트 확인 ← 절대 생략 불가
- 테스트 완료 확인 즉시 → **"문서/메모리 업데이트를 진행할까요?"** 반드시 질문
- 사용자가 다음 작업을 언급해도 이 확인을 먼저 한 뒤 넘어감

### [8] 에이전트 MEMORY.md 업데이트
아래 **완료 후 업데이트 체크리스트** 참조.

### [9] 업데이트 내용 검토
- 각 에이전트가 작성한 MEMORY.md 변경 내용을 확인
- 잘못 기록된 내용, 누락된 항목 수정

### [10] 문서 반영
- `PROJECT_STATUS.md`: 완료된 시스템/버그 수정 항목 갱신
- `ROADMAP.md`: 완료 마일스톤 추가, 다음 우선순위 조정

| 작업 유형 | 담당 에이전트 | 전달 필수 컨텍스트 |
|----------|-------------|-----------------|
| 코드 구현 / 버그 수정 | **game-programmer** | 관련 파일 경로, 증상, 아키텍처 규칙 |
| 게임플레이 설계 / 밸런스 결정 | **game-design-lead** | 현재 구현 상태, 관련 수치 |
| 구현 후 검증 / 버그 체크 | **qa-tester** | 변경된 파일 목록, 예상 동작 |
| 3D 모델 / Meshy.ai 프롬프트 | **asset-prompt-crafter** | 에셋 스펙, FBX 파이프라인 요구사항 |
| 모든 작업의 계획·조율·검토 | **project-orchestrator** | 전체 컨텍스트 + 각 에이전트 MEMORY 경로 |

## project-orchestrator 역할 상세

### 위치
사용자와 전문 에이전트들 사이의 **중간 관리자**.
직접 코드를 작성하거나 설계를 결정하지 않고, **"무엇을 누구에게 어떤 순서로"** 를 결정한다.

### 주요 책임

**1. 작업 분해 (Task Breakdown)**
- 사용자 요청을 받아 실제로 필요한 하위 작업들을 파악
- 예: "네트워크 이동 버그 수정" → research(코드 파악) → design(수정 방향 결정) → implement(코드) → qa(검증) 순서로 분해

**2. 에이전트 선택 및 컨텍스트 준비**
- 각 하위 작업에 맞는 에이전트를 선택
- 해당 에이전트가 작업에 필요한 모든 정보(파일 경로, MEMORY 경로, 아키텍처 제약)를 받아볼 수 있도록 컨텍스트 정리

**3. 순서 조율**
- 에이전트 간 의존 관계 파악 (설계 결정 전에 코드 작성 불가 등)
- 병렬 가능한 작업과 순차 필요한 작업 구분

**4. 결과 일관성 검토**
- 에이전트가 완료한 결과가 아키텍처 규칙을 지켰는지 확인
- 다른 에이전트의 작업 결과와 충돌하지 않는지 확인

**5. 메모리 업데이트 조율**
- 작업 완료 후 어떤 에이전트의 MEMORY.md를 갱신해야 하는지 결정
- 갱신 내용이 정확한지 검토

### 언제 사용하는가

| 상황 | project-orchestrator 사용 여부 |
|------|-------------------------------|
| 단일 파일 버그 수정 | 선택 (game-programmer 직접 위임 가능) |
| 설계 결정 + 코드 구현이 함께 필요한 경우 | **필수** |
| 3개 이상 파일에 걸친 기능 추가 | **필수** |
| 에이전트 작업 결과 검토가 필요한 경우 | **필수** |
| 전체 프로젝트 현황 파악 및 다음 작업 결정 | **필수** |

### 하지 않는 것
- 직접 코드를 작성하거나 수정하지 않음
- 게임 밸런스 수치를 직접 결정하지 않음
- 에셋 프롬프트를 직접 작성하지 않음
- → 모두 전문 에이전트에게 위임

### 컨텍스트 공유 시 공통 포함 항목
- 관련 파일 절대 경로 (`d:/Dmain/dev/Portfolio/Hexiege/Hexiege/Assets/...`)
- 해당 에이전트의 MEMORY.md 경로 (아래 경로 참조)
- 작업 배경 (왜 이 작업이 필요한지)
- 아키텍처 제약 (Domain → Core 참조 금지, GameBootstrapper 단일 조합 루트 등)

### 에이전트 MEMORY.md 경로

## 규칙

- 작업 폴더는 삭제하지 않음 (히스토리로 보존)
- **계획 단계(research/plan 작성 시)**: 에이전트(Agent) 호출 허용 — 코드 파악, 설계 검토, 의견 수렴에 활용
- **승인 전 금지**: Edit/Write(파일 수정/생성) 일체 금지 — 코드 변경은 반드시 사용자 승인 후에만
- **승인 후 즉시 구현 금지**: 승인 → "task 문서 작성할까요?" 확인 → 문서 작성 → 구현 순서 준수
- **테스트 완료 후 다음 작업 이동 전**: 반드시 "문서/메모리 업데이트를 진행할까요?" 확인 먼저
- project-orchestrator는 단일 에이전트 작업이든 복합 작업이든 계획·조율·검토가 필요할 때 언제든 사용 (위 역할 상세 참조)
- 위 사이클의 어떤 단계도 "간단하니까", "한 줄이니까" 등의 이유로 생략 불가 — 예외 없음
