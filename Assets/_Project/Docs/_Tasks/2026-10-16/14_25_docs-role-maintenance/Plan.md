# 주요 문서 역할 재정리 — 계획

주요 문서에 다시 쌓인 작업 경위와 검증 영수증을 제자리로 옮기고, 현재 규칙·기술·수치·상태·할 일만 명확히 읽히도록 정리한다. 이번 결과뿐 아니라 앞으로 다른 브랜치의 작업을 작성·갱신·병합할 때도 같은 역할 구분을 지키는 기준을 만든다.

**현재 상태: 승인된 2차 본문 재정리·검증 완료 뒤 사용자 결과 검토와 병합 승인을 받아 내용 커밋 `0a676aca`의 main 반영 완료. 푸시는 하지 않았다.** 앞선 1차 판정의 부족을 보완해 주요42문서를 전문 검토하고 역할에 따라 재구성·부분 정돈·유지했다. 결과와 보호 검증은 Research §10, 실제 병합 기록은 §11에 있다. 코드·Unity·새 QA는 변경·실행하지 않았다.

## 1. 범위와 보호 조건

- 대상은 Research §3의 주요 Docs 42파일, 루트 AGENTS 인덱스, 기존 History/ImplementationVerificationHistory다. 파일별 필요성을 판정하며 역할에 맞는 파일은 그대로 둔다.
- 권한·작업 사이클 근거는 CLAUDE와 WORKFLOW [3]~[4], [10]~[12]다. 이번 문서 운영 변경에 대응하는 게임 규칙을 억지로 만들거나 인용하지 않는다.
- 게임 동작을 바꾸지 않는다. 유닛 사건·권위·시간 계약은 Units의 U-ATK-TIMELINE 및 typed marker 계약, Sync의 NET-AUTH/NET-DELIVERY-TIMED 등 현행 규칙을 보존 대상으로 대조한다. UI 프리팹 전제·무작위 맵 runtime 계약도 유지한다.
- 구현 수치·공격값·단위·생산 선택 경계·개별 사용자 수용·실제 미검증은 유지한다. 밸런싱+AI3종 시나리오 재논의는 별건이며 추가 기획 낮은 우선 보류도 유지한다.
- Editor 활성7 C#/17메뉴, runtime·씬·프리팹·설정·맵 bytes·소스코드·검사기 코드는 변경하지 않는다. 문서에서 미실행 Unity/native/기기 검증을 PASS로 올리지 않는다.
- 기존 Task/Log/History 원문을 삭제·재작성하지 않는다. 새 이관 원문은 기존 History에 출처/앵커로 추가하고 대응표를 현재 Task에 기록한다. 메모리·baseline·메타데이터·로그 파일·Git ignore·Git 이력도 변경하지 않는다.

## 2. 역할 안내와 공통 운영 기준의 위치

**상세한 문서별 역할의 단일 원본은 각 문서 머리말이다.** WORKFLOW는 공통 작성·갱신·병합 절차만, AGENTS는 경로+한 줄 역할의 찾기 인덱스만 관리한다. GameSystemRules는 도메인 규칙 찾기 역할을 유지한다. WORKFLOW [11]의 기존 역할표는 필요하면 짧은 유형별 갱신표와 해당 머리말 참조로 정돈하며 42파일의 상세 포함/제외 표를 넣지 않는다. Research 조사표도 중앙 문서에 복제하지 않는다.

AGENTS의 긴 설명·정책 사본은 권위원본 포인터로 간소화하고 WORKFLOW의 중복 설명·상세 작업 이력은 정리해 불필요한 확장을 막는다. 승인 절차·원문 보존·검사기의 형식/한계·LogRules 원본 포인터 같은 필수 조건은 유지한다. 임의 줄 수·문자 수 상한을 새로 정하지 않는다.

### 문서 머리말 공통 양식

- **목적·답하는 질문:** 이 문서에서 무엇을 판단할 수 있는지 구체적으로 설명한다.
- **포함:** 해당 문서가 책임지는 내용과 현재/잠정/이력 등 다루는 축을 적는다.
- **제외·담당 문서:** 담지 않을 내용을 구체적으로 구분하고 정확한 담당 문서에 연결한다.
- **권위원본·주요 참조:** 규범 원본인지 구현값의 미러인지 이력인지 밝히고 우선 대조할 근거를 연결한다.
- **갱신 조건·방법:** 어떤 사실/승인 변화 때 어느 본문을 제자리 수정하는지 적는다. 완료 receipt를 머리말에 누적하지 않는다.

이 머리말은 문서 책임 안내이며 전역 CLAUDE의 권한·승인 규칙을 변경하지 않는다. 기존 제목·앵커·규칙 ID를 유지한다. 이력 문서는 보호 역할과 현행 문서 참조만 필요시 보강하고 기존 원문은 보존한다. 기존 Task/Log는 일괄 머리말 추가에서도 제외한다.

### StatsReference 머리말 예시

> 이 문서는 현재 구현된 유닛·건물 수치의 값과 단위, 잠정·미확정 범위를 찾는 참조표다. 현재 수치와 실제 생산 경로에서 선택되는 타격·주기를 설명하며, 밸런싱 확정을 뜻하지 않는다.
>
> 수치 권위는 실제 Config 자산과 UnitFactory의 생산 연결·선택 클립·소비 경로이고 이 문서는 사람이 읽는 미러다. 저장 fallback과 실제 생산값이 다르거나 선택 순서가 확인되지 않았다면 그 차이와 확인 범위를 함께 표시한다.
>
> 동작·권위·동기화 규칙은 GameSystemRules_Units와 GameSystemRules_UnitCombatSynchronization, 현재 개별 연결·수용은 UnitCombatAssetMatrix, 상세 실행 근거는 기존 Task/History가 담당한다. 이 문서에는 컴파일 결과·해시 manifest·회차별 인계 문단을 쌓지 않는다.
>
> 실제 자산 또는 생산 소비 경로가 변경됐을 때 해당 표의 값·단위·선택 경계와 근거 링크를 제자리 갱신한다. 원래 수치 사본과 날짜별 근거는 이력으로 보존하며 별도 승인 없는 밸런싱을 하지 않는다.

### 작성할 기준

1. **먼저 내용의 역할을 정한다.** 제품 동작→해당 규칙, 구조/데이터/개발 절차→TDD, 현재 값→Stats, 에셋 연결/개별 수용→Matrix·에셋 목록, 시스템 현재 상태→Status, 실제 미완/보류→Roadmap, 완료 마일스톤→WorkHistory, 자세한 실행 근거→기존 Task/Log/History다.
2. **갱신은 해당 본문을 교체한다.** 현행 「미구현/대기/완료」 문장을 제자리에서 고치며 새 날짜 완료 문단을 위아래에 계속 쌓지 않는다. 현행 규범·예외·필요 이유는 본문에 남긴다.
3. **원문 보존과 현행 갱신을 분리한다.** 실제 날짜별 원문은 History로 보존하고 출처/대응 앵커를 연결한다. 기존 Task에 같은 사건이 있다는 이유만으로 중복 판정하지 않는다. 고유 주장·예외·검증 한계와 원문 동일성을 대조해 충분히 보존된 경우에만 기존 근거 링크로 수렴한다. 이관 대상만 가진 고유 문장을 링크만 남기고 지우지 않는다.
4. **완료 갱신은 역할별 차이만 쓴다.** 규칙 변경이 없으면 규칙 문서에 완료 보고를 붙이지 않는다. Status는 상태 전환과 검증 한계, Roadmap은 닫힌 항목 정리와 남은 일, WorkHistory는 짧은 완료 행과 근거 연결이다. 숫자·SHA·실행 시각·회차 목록을 모든 문서에 중복하지 않는다.
5. **다른 브랜치의 변경도 같은 검토를 거친다.** 텍스트 충돌 유무와 별도로 새 완료 블록·중복 상태·규범/이력 혼합을 확인한다. 각 변경 주장마다 역할 원본과 최신 승인 결정/실제 증거를 대조하고, 과거 원문은 보존하면서 현행 본문을 정합화한다. 나중 커밋·가장 긴 문장·과거 PASS를 자동 우선하지 않는다.
6. **판정 불가를 숨기지 않는다.** 최신 승인과 실제 증거가 충돌하거나 확인 범위가 다르면 현재 확인 사실과 미확정 경계를 나눠 남긴다. 범위가 좁은 PASS를 전체 완료로 합치거나 사용자 보류를 새 필수 테스트로 바꾸지 않는다.
7. **기계 검사와 의미 검토를 구분한다.** check_docs는 ID·참조·링크·앵커·메모리 보호 등 명시 범위를 검사한다. 역할 적합성·현재 주장·이관 완전성·증거 범위·병합 의미 충돌은 사람이 별도로 확인한다. 이번에 검사기 코드를 확장하지 않는다.

기존 [11]의 「구현 끝나면 규칙 상태를 완료로」·「실기 검증 0건을 찾아 고침」 안내는 구현·정적·native·실기·사용자 수용의 각 축에 실제 증거가 생긴 경우 해당 상태만 갱신하는 뜻으로 명확히 한다. 구현 완료만으로 실기 완료를 만들지 않으며, 이 정리를 이유로 새로운 gate나 전체 재검증 의무를 추가하지 않는다.

구현·정적 검사·Editor 실행·기기/멀티 실행·사용자 수용은 각각 독립 증거축이다. 각 결과의 실행 리비전·관측 범위·근거 링크를 대조해 실제 바뀐 축만 갱신하며 다른 축의 PASS나 새 전체 재테스트 필요성을 자동으로 만들지 않는다.

LogRules 정책은 위 기준에 복제하지 않고 §1.10/§2 포인터만 둔다. 정확한 로그 실행 권한·private/다운로드/삭제 조건은 그 원본을 따른다.

## 5. 실행 순서

1. **Plan 승인 후 기준 고정:** 실제 대상/기준 Git 상태와 읽기 원문을 확인하고 블록별 원본 경로·제목/앵커·내용·유일성·현재 역할·목적지 대응표를 이 Task에 만든다. 수치/파일 수는 실제 목록에서 재집계한다.
2. **역할 머리말과 공통 절차 정리:** 각 주요 문서 머리말에 §2의 구체 역할 경계를 정리하고 WORKFLOW에는 이를 참조하는 짧은 공통 체크리스트를 반영한다. AGENTS의 한 줄 안내와 GameSystemRules의 도메인 찾기 안내를 대조한다. 상세 역할표를 중앙 문서에 복제하지 않고 중복·작업 이력 축약으로 AGENTS/WORKFLOW의 불필요한 확장을 막는다.
3. **고유 원문부터 보존:** 기존 History 목적지를 확인해 유일한 원문 블록을 그대로 추가하고 출처·앵커를 기록한다. 기존 Task/Log는 이동하지 않는다. 원문과 목적지를 개행 처리 기준을 명시해 대조한 뒤에만 원래 주요 본문의 해당 범위를 치환한다.
4. **현행 본문 복원:** 규칙/설계/수치/연결은 각 원본에, 현재 상태/잔여는 Status·Roadmap에 정리한다. 오래된 상태 도장은 제자리 정정하고 날짜별 진짜 원문은 이력으로 보존한다. 수용·OPEN 범위를 함께 대조한다.
5. **인덱스와 완료 이력 정리:** WorkHistory는 짧은 완료 행과 상세 링크, AGENTS/GameSystemRules는 찾기 요약으로 정리한다. 현재 사용 도구 경로는 운영 안내에서 찾을 수 있도록 연결하되7파일/17메뉴 구현을 변경하지 않는다.
6. **정적·의미 검증:** 아래 gate를 확인하고 변경 파일/이관 대응/남은 불확정을 사용자에게 공유한다. main 병합·커밋·푸시는 이번 Plan 작성 승인에 포함하지 않으며 별도 사용자 지시를 따른다.

## 7. 로그·권한·위험

- LogRules/LogHistory 규범·원문 분리를 유지한다. 보관 정책은 LogRules §1.10/§2로만 연결하며 다른 문서에 복제하지 않는다.
- Log.md·기존 Task·raw txt.meta·CrossAudit 결과는 소스 근거로 보존한다. raw RuntimeLog의 지정 private 월별 ZIP 운영에는 매 업로드 직전 private 검증과 ZIP/manifest 전체 다운로드 검증이 필요하며 추적 해제와 로컬 삭제는 별도 승인이다. 이번에는 업로드·추적 해제·ignore 변경·원본 삭제·자동 정리·history rewrite를 하지 않는다.
- 위험은 유효한 규칙/미검증을 이력으로 잘못 빼는 것과, 원문이 다른 곳에도 있을 것이라 추측하고 소실시키는 것이다. 의무/이유/상태/근거를 나누고 원문 대응 확인을 선행한다.
- 이관 중 새 게임 사양 충돌이나 근거 부족이 나오면 새 답을 만들지 않는다. 가능한 문서 정리는 계속하되 해당 항목은 구체 위치·상충 주장·현재 승인/증거를 보고하고 결정이 필요한 지점만 남긴다.
