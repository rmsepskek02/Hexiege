# Plan — 방어탑 3종 크기 측정 메뉴

## 이 문서는 무엇인가

EMP 스킬로 멈춘 적 방어탑 위에 「무력화됨」 VFX를 탑 크기에 맞게 붙이려면, 먼저 세 종족 탑(인간 CannonTower · 정령 RuneSpire · 초월 VineTower)이 **실제로 얼마나 높고 넓은지** 알아야 한다. 지금은 그 숫자가 어디에도 없다.

이 계획은 Unity 에디터 메뉴에 **「탑 크기 재기」 버튼 하나**를 추가하는 것이다. 사용자가 메뉴를 누르면 탑 프리팹 6개(3종족 × 파랑/빨강 팀)를 하나씩 열어 크기를 재고, 결과를 **Console 창에 글자로만** 보여 준다. 프리팹 · 씬 · 설정 에셋은 하나도 바꾸지 않고, 게임 실행 코드도 손대지 않는다. 크기를 재는 방법은 이미 유닛용으로 만들어 쓰고 있는 측정 기능을 그대로 빌려 쓴다.

사용자가 결과를 알려 주면 그 숫자는 나중에 EMP 스킬 코드 단계(상위 Task 2-B)에서 종족별 VFX 크기 · 위치 값을 정하는 기준이 된다. 이 메뉴 자체가 VFX를 맞추지는 않는다.

현재 상태와 근거(파일 · 행)는 [Research.md](Research.md)에 있다. 상위 Task: [종족별 지원 스킬 기획 Plan](../14_25_race-support-skills-design/Plan.md) 5-1 결정 19. **구현은 이 Plan을 사용자가 승인한 뒤에만 시작한다**(WORKFLOW [4]).

> **현재 상태 (2026-11-02):** 6절 열린 결정 중 U-1 · U-3은 사용자가 정했고(6-1), U-2는 테스트 결과를 보고 정한다(열림). **구현은 사용자 승인 대기** — 아직 코드를 쓰지 않았다.

**표기:** `[확정]` = 사용자 결정 · `[사실]` = Research에서 확인한 것 · `[제안]` = 문서 담당 제안(결정 아님) · `[프로그래머 판단]` = 메인 세션 지시로 구현 담당이 고르는 것 · `[사용자 확인]` = 사용자가 정해야 하는 것.

> **기존 로직 제거 — 없음.** 이 계획은 새 파일 1개를 더하기만 한다. 기존 코드 · 에셋 · 메뉴를 지우거나 끄지 않는다(WORKFLOW [4] 「기존 로직 제거 규칙」 확인). 단 6절 U-1에서 「1회성」을 고르면, 측정이 끝난 뒤 **이 새 메뉴 파일**을 [4]의 비활성화 → 사용자 확인 → 최종 삭제 절차로 정리한다. **[2026-11-02 U-1 결정 — 6-1]** 「1회성」이 아니라 **지원 스킬 VFX 작업이 모두 끝날 때까지 유지(삭제 보류)**로 정해졌다. 그 뒤 삭제 여부를 사용자에게 다시 묻고, 삭제로 정해지면 위 [4] 절차를 따른다.

## 2. 동작

### 2-1. 실행 조건

- Play 모드면 실행하지 않고 안내 창을 띄운다(유닛 도구 103~107행과 같은 방식) — Play 중 프리팹 격리 로드를 피한다.
- **확인 창은 두지 않는다** `[제안]` — 아무것도 저장하지 않으므로 유닛 도구의 「측정 후 저장」 확인(115~119행)이 필요 없다. 끝나면 「결과는 Console 참고」 완료 창 하나만 띄운다(선택 — 프로그래머 판단).

### 2-2. 대상 고르기 — Game 씬 `BuildingFactory` 등록을 따라간다

근거: 「방어 타워 시스템」 머리 안내(0절) · Research 2-1.

- **P1 (추천)** `[제안]`: 유닛 도구의 `ReadProductionPrefabs`(156~198행)와 같은 방식으로 Game 씬을 **미리보기로 열고**, `BuildingFactory`의 `_humanPrefabs` · `_spiritPrefabs` · `_transcendencePrefabs`에서 `type == AutoTower(2)`인 줄의 `blue` · `red`를 읽은 뒤 씬을 닫는다. 실제 게임이 쓰는 프리팹을 재므로 이름 추측이 없다. `BuildingFactory`가 정확히 1개가 아니면 멈추고 경고한다(유닛 도구 185~191행과 같은 안전장치).
- P2: 프리팹 경로 6개를 상수로 적는다. 단순하지만, 씬 등록이 바뀌면 다른 프리팹을 잴 수 있다.
- 비어 있는 칸(`blue`나 `red`가 없음)은 건너뛰고 「없음」을 한 줄 남긴다. 지금은 6칸이 모두 차 있다 `[사실 — Research 2-1]`.

### 2-3. 재기와 출력

근거: 「Human CannonTower 초기 방향」 규칙 11 · LogRules 1.4 / 1.14(0절).

- 각 프리팹에 `UnitRecipientFitMeasureTool.Measure(prefab)`를 부른다(3절 S1). 탑에는 `VisualRoot`가 없어 **프리팹 루트 기준**으로 재고, 메시가 읽기 불가라 **경계 상자 방식**(`Method=BoundsFallback`)이 나올 것이다 `[사실 — Research 2-2 · 2-3 · 2-4]`.
- 한 탑 · 한 팀마다 `GameLog.Dev.Info` 한 줄. 포함할 값 `[제안]`:

| 키 | 뜻 |
|---|---|
| `Race` · `Team` · `Prefab` | 종족 · Blue/Red · 프리팹 이름 |
| `Height` | 최저점 ~ 최고점 높이(미터) |
| `BottomY` · `TopY` | 루트 기준 최저점 · 최고점 y. `TopY = FootOffset.y + Height` |
| `CenterX` · `CenterZ` | 루트 기준 수평 중심 — 0에서 벗어나 있으면 CannonTower 180° 회전 때 방향이 뒤집힌다(Research 2-6) |
| `Radius` | 수평 중심에서 가장 먼 점까지 거리. 경계 상자 방식이면 **상한값**(Research 2-5) |
| `Renderers` · `Method` | 잰 렌더러 수 · 측정 방식 |
| `Pivot` | `PrefabRoot`(고정 문자열 — 무엇을 기준으로 쟀는지 명시) |

- 숫자는 `CultureInfo.InvariantCulture`, 소수 셋째 자리(유닛 도구 442~446행과 같은 형식). 값 안에 `", "`를 넣지 않는다.
- 측정 실패(`Ok == false`)는 `GameLog.Dev.Warn`으로 사유(`Failure`)와 함께 한 줄.
- 같은 종족의 Blue와 Red 높이가 5% 넘게 다르면 경고 한 줄(유닛 도구 `WarnIfTeamsDiffer` 401~403행과 같은 기준) — 지금은 같은 메시 · 배치라 같아야 한다 `[사실 — Research 2-2]`.
- 마지막에 요약 한 줄: 대상 수 · 성공 · 실패.
- **유닛 이상값 기준(`IsImplausible`)은 쓰지 않는다** — 유닛용 기준이라 정상 탑도 경고될 수 있다(Research 2-4 · 4절).
- 로그 카테고리는 LogRules 「카테고리 규칙」에 맞게 프로그래머가 고른다(유닛 도구는 `Combat`).
- 에디터에서는 이 줄이 런타임 로그 파일에도 남는다(LogRules 1.10). 에셋에는 아무것도 쓰지 않는다 `[사실 — Research 2-8]`.

### 2-4. 주석

CLAUDE.md 규칙 8에 따라 유니티 초급 개발자도 읽을 수 있게 쓴다. 최소한: 파일 머리에 「무엇을 왜 재는가(EMP 무력화 VFX 기준)」, 「아무것도 저장하지 않는다」, 「경계 상자 방식이면 반경은 상한값」, 「언제 다시 실행하나(탑 모델을 바꿨을 때)」, 상위 Task 경로.

## 3. `Measure` 공유 방식 `[프로그래머 판단]`

메인 세션 지시에 따라 구현 담당이 고른다. 선택지와 장단점:

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| **S1** | 새 파일에서 `UnitRecipientFitMeasureTool.Measure`를 **직접 호출**(`internal`, 같은 에디터 어셈블리 — Research 2-4) | 기존 파일 무변경 → 회귀 스위트 영향 없음. 코드가 가장 적다 | 결과 구조에 X · Z 반폭이 없다(최고점은 계산 가능). 탑 도구가 「유닛 도구」에 기대는 이름이 된다 |
| S2 | 측정 부분을 공용 도우미로 **분리**하고 두 도구가 같이 씀 | 이름이 정직해지고 반폭 같은 값을 더하기 쉽다 | 기존 도구와 회귀 검사(`RunUnitActionSelfValidation.VfxConnections.cs` 593~603행)가 부르는 코드를 옮긴다 → 유닛 측정 결과가 그대로인지 확인 필요. 수정 파일이 늘어난다 |
| S3 | 측정 코드를 새 파일에 **복사** | 기존 파일 무변경 | 같은 코드 두 벌 — 한쪽을 고칠 때 다른 쪽이 조용히 어긋난다(2026-10-13 스케일 버그 같은 수정이 한쪽에만 들어갈 수 있다) |

- 문서 담당 의견 `[제안]`: 이번 목적(1회 측정, 출력만)에는 **S1**이 범위가 가장 작다. S2를 고르면 Plan을 고쳐 바뀐 파일 목록 · 회귀 확인을 추가한다(WORKFLOW [4] 「계획 변경 시 변경 이유도 추가 기록」).
- 정확한 몸통 반경이 필요하면(6절 U-2) 정점을 읽어야 한다. 읽기 불가 메시의 정점을 에디터에서 읽을 수 있는 방법이 있는지는 **확인하지 않았다** `[미확인]`. 임포트 설정(Read/Write)을 바꾸는 방식은 **에셋 변경이라 이번 범위 밖**이다.

**결과 점검표** — 맞지 않으면 측정 기준이나 대상이 틀렸을 가능성이 있다:

- `Method`가 세 탑 모두 `BoundsFallback`이다(메시 읽기 불가 — Research 2-3). 다르면 그 이유를 확인한다.
- 같은 종족의 Blue · Red 값이 같다(Research 2-2).
- CannonTower `TopY`가 포구 높이 0.405보다 크다 — 포구가 메시 위에 있고 포신 반지름이 약 0.026이기 때문(「타워 발사 연출」 2026-10-21, Research 2-5) `[추정 — 포신이 탑 최고점이 아닐 수 있어 「크다」만 본다]`.
- `BottomY`가 0 근처다(모델이 루트 바닥에서 시작) `[추정 — 메시 원점 위치를 확인하지 않았다]`. 크게 벗어나면 VFX 위치 보정에 그 값을 반영해야 한다.

**회귀 스위트(`Hexiege/Combat/Run Full Regression Suite`):** S1이면 기존 파일을 고치지 않아 영향이 없다고 본다 — 회귀 검사가 쓰는 `Measure` · 이상값 상수(Research 2-4)를 바꾸지 않고, 새 파일은 메뉴 하나만 더하기 때문이다 `[판단]`. 사용자가 평소대로 돌린다면 WORKFLOW [6] 규칙(사용자가 문제를 말하지 않으면 PASS, 결과 파일 없음 · Console만 · 에이전트 미관측 주석)으로 기록한다. S2를 고르면 회귀 스위트 실행이 **필수**다(유닛 측정 경로를 옮기므로).

Testcase.md는 사용자 지시가 있을 때만 만든다(WORKFLOW [5] — TC · QA는 지시가 있을 때만).
