# 현재 PC 매칭 환경 차이 진단 계획

저장된 에디터/기기 실패와 SDK/환경을 대조한 뒤, 사용자 승인에 따라 익명 명시 로그아웃과 매칭 실패 복구를 최소 교정한다. 같은 Task에서 구현・빌드 시도까지 진행하고 실제 사용자 확인 절차를 안내한다. 진단 근거・정책 승인・코드 결과・빌드/실기 성공은 구분한다.

> **기존 로직 교체 경계:** 명시적 익명 로그아웃의 기본 UGS SignOut은 자격을 남겨 다음 새 게스트 요구와 충돌하고, 매칭 catch의 로그만 남기는 처리는 상위 실패 복구를 막는다는 소스 근거로 필요한 부분만 대체했다. 기존 처리 원문은 비활성화 주석으로 보존했다. 최신 랜덤 매칭 수용 뒤에도 이번 문서 갱신에서 소스 최종 삭제는 실행하지 않는다. 자동 Bridge/앱 재실행・실계정 OIDC・진행도・기존 요청 계약은 보존한다.

- 작업 시작: 2026-10-20 12:19 KST
- 근거: [Research.md](Research.md)
- 승인 범위: 최초 진단 뒤 같은 Task 계획 갱신・최소 코드 구현・빌드 시도・테스트 절차 안내까지 사용자 명시 승인
- 상태: 2026-10-21 정상 진입・상대 인터넷 단절 시 Host 30초 복구・복구 후 재매칭의 사용자 수용 완료. 이번 랜덤 매칭 교정은 종료하며 인증/취소 등 별도 미관측을 전체 PASS로 확대하지 않음. 최신 판정은 12절
- 구현 경계: 6절의 기존 익명/매칭 교정을 보존하고 후속 11절의 접속 준비 30초・실패 즉시 복구를 적용. SDK 교체・전체 profile migration・계정/서버 데이터 삭제・네트워크 설정 변경은 제외

## 3. 가설과 오판 방지

Editor timeout은 Android의 21999/응답 역직렬화 예외와 별도 현상으로 시작한다. SDK가 보여주는 일반 오류 번호・뒤따른 ArgumentNullException만으로 원래 서비스 오류를 확정하지 않는다. AndroidResolver 설정 차이 하나로 Editor와 Android 실패 전체를 설명하지 않는다. 다른 PC 정상 보고는 중요한 비교 조건이지만 정확한 환경/산출물 동일성을 대신하지 않는다.

원인이 미확정인 상태에서 SDK 교체・Resolver 원복・서비스 큐 수정・재시도 시간 변경・오류 UI 수정은 실행하지 않는다. 필요한 경우 구현 담당자의 읽기 분석을 받아 영향/근거와 별도 승인 범위를 제시한다. 원시 로그를 새 폴더로 복사하거나 공개 전송하지 않는다.

## 4. 인계와 완료 기준

이번 단계 인계는 확정 사실/미확정 목록, 각 실행의 실패 단계, 환경 대조 결과, 다음에 필요한 최소 근거 또는 계측 제안이다. 로그 확인 완료를 매칭 해결 완료로 보고하지 않는다. 실제 원인 교정・원래 실패 시나리오 재확인・회귀가 필요한 단계는 추가 승인 후 별도 증거로 기록한다.

현재 변경은 이 Task Research/Plan 두 파일뿐이다. 코드/씬/SDK/설정・메모리・상시 규칙・Testcase・QA・Git은 수정하지 않는다. 메타는 수동 생성하지 않으며 Unity 자동 생성 가능성과 제품 수정은 구분한다. 문서의 로컬 링크/의미는 직접 검수하고 기존 Python 실행 불가・`_Tasks/` 기계 검사 제외 한계를 유지한다.

## 5. 후속 근거에 따른 비교 계획 — 미실행

12:06 Editor/기기의 UGS 해시 일치와 Firebase 해시 차이, salt 없는 제한 길이 해시 구현을 대조해 동일 UGS identity 경합을 우선한다. 원본 식별자/해시는 복제하지 않고 해시 충돌 가능성을 제거한 확정 표현도 피한다. 상세 시각・SDK map/예외 변환・4개 순위 후보/반증 조건은 Research 6절을 따른다. 공식 초당 1회/player ID 제한은 문서 근거이며 실제 429는 아직 관측하지 못했다.

먼저 사용자가 실패한 매칭 조합을 확인한다. 최소 비교 후보는 Editor를 완전히 중지한 뒤 문제 기기와 정상 PC를 사용하는 것으로, 계정/데이터 삭제 없이 중복 identity 동시 polling을 분리하는 방향이다. 아직 새 실서버 대조 요청은 실행하지 않았다. identity 경합을 제거해도 남는 실패는 원 HTTP 상태와 큐/서비스 조건을 별도로 확인한다. Editor 서비스 Timeout 응답을 앱의 10분 타이머로 해석하거나 Android Unknown 21999를 원 HTTP 코드로 취급하지 않는다.

NetworkGameManager가 실패를 로그만 남기고 삼켜 BattleViewModel의 실패 정리가 실행되지 않는 소스 전달 결함은 별도 확인됐다. 매칭 최초 원인과 UI 잔류를 분리하고, 이 확인을 제품 수정 승인으로 확대하지 않는다. 원 응답 계측/오류 전달 수정/SDK 업데이트/세션 삭제/설정 변경은 사용자 추가 승인 전 실행하지 않는다. 현재 원인 후보 좁힘 단계이며 해결/회귀 PASS가 아니다.

## 6. 사용자 승인된 최소 구현・빌드 진행안

위 1~5절은 진단 당시 기록이다. 이후 사용자가 구현/빌드까지 승인했으며 최신 범위는 이 절을 따른다. 추가 로그・명시 로그아웃 후 익명 재시도 실패와 세션 복원 소스는 Research 7~8절에 기록했다.

| 순서・수정 | 구현 기준 | 원본/근거 |
|---|---|---|
| A. 명시적 익명 로그아웃 | SignOutAsync에서 익명 여부를 종료 전에 확인하고 익명 로그아웃에만 UGS 저장 자격 정리. 다음 익명 시작은 Firebase/UGS 새 게스트, 이전 닉네임/전적 미승계 | [AuthSystemRules](../../../AuthSystemRules.md#로그아웃) 「로그아웃」 규칙 2~3 사용자 승인 정책. 단순 재실행・자동 Bridge・실계정 진행도 보존 |
| B. 매칭 실패 전달 | NetworkGameManager에서 실패를 상위로 전달, BattleViewModel의 대기/타이머/로딩 복구와 재시도 경로 확인 | [Network](../../../GameSystemRules/GameSystemRules_Network.md) 역할 독립성, 기존 화면 상태/로그 계약. 맵 준비 실패 규칙을 새 티켓 오류 규칙으로 대체하지 않음 |
| C. 회차/취소 정리 | 요청 회차 식별, 취소 중 티켓 생성 완료/늦은 응답이 새 회차를 덮지 않도록 최소 정리. 남은 이전 티켓/상태를 소유 회차로 구분 | 기존 매칭 취소/준비 수명 보존, [MatchFlow](../../../GameSystemRules/GameSystemRules_MatchFlow.md)와 [네트워크 TDD](../../../TechnicalDesignDocument_Network.md)의 단계 구분 |
| D. 검사・빌드 시도 | 구현 담당자의 근거 검토 뒤 메인이 Unity 컴파일 상태와 빌드 시도를 확인. 성공/실패/미완을 실제 관측대로 기록 | WORKFLOW의 구현/실기 증거 분리. 빌드 클릭을 완료나 기기 성공으로 판정하지 않음 |

예상 관련 파일은 LoginUseCase・NetworkGameManager・BattleViewModel 및 취소/회차 정리에 직접 필요한 기존 매칭 코드다. 정확한 실제 파일/수치는 구현 인계 뒤 확정한다. AuthSystemRules에는 승인된 로그아웃 정책만 반영하고 Status/메모리/기존 UI Task/새 TC는 변경하지 않는다. 원HTTP 계측이 추가 필요하면 별도 범위를 공유하며 429 확정은 주장하지 않는다.

## 7. 사용자 확인 절차 — 수정본 확보 뒤 한 번에 안내

아래는 사용자용 조작 절차이며 별도 Testcase 생성/QA 실행이 아니다. 아직 새 빌드 성공/배포・실기 수용은 없고 실제 수정본 인계 뒤 절차를 확정한다. 계정 삭제・앱 데이터 삭제・session 수동 삭제・개발 profile 변경은 하지 않는다.

1. **익명 로그아웃:** 수정본에서 기존 게스트의 닉네임/전적을 확인한 뒤 로비 로그아웃을 명시적으로 누른다. 익명으로 다시 시작하면 신규 게스트의 기본 상태이며 이전 닉네임/전적을 잇지 않아야 한다. 기존 익명 흐름처럼 닉네임 설정 화면은 거치지 않으며 새 화면을 요구하지 않는다. 이 정책상 기존 게스트를 다시 이어가려는 계정으로 시험하지 않는다.
2. **단순 재실행:** 새 게스트로 시작한 뒤 로그아웃을 누르지 않고 앱을 닫았다 다시 연다. 같은 게스트 상태를 유지해야 한다. 단순 재실행만으로 다른 새 게스트가 되면 실패다.
3. **실계정 보존:** 사용 가능한 기존 실계정으로 명시 로그아웃/재로그인한다. 같은 닉네임/진행도를 유지해야 한다. 자격증명 입력은 사용자가 직접 하고 대화/로그에 비밀번호를 남기지 않는다.
4. **매칭:** 현재 PC Editor와 문제 기기의 수정본으로 서로 다른 게스트 상태에서 랜덤 매칭한다. 필요하면 Editor를 완전히 중지하고 문제 기기↔정상 PC 조합도 비교한다. 같은 project/environment/queue 조건을 맞추고 내부 identity 비교는 보호된 로그로 확인한다. 실제 연결/경기 진입까지 확인해야 매칭 성공이다.
5. **실패/재시도:** 실패가 발생하면 오류 안내와 대기/타이머/로딩 종료 후 다시 시도할 수 있는지 확인한다. 실패를 만들기 위한 임의 서버 설정/데이터 삭제는 하지 않는다. 실패가 발생하지 않은 실행에서 오류 복구 실기까지 통과했다고 보고하지 않는다.
6. **취소/다시 시작:** 매칭을 취소한 뒤 새 매칭을 시작했을 때 이전 결과가 새 대기 화면을 닫거나 잘못 연결하지 않아야 한다. 빠른 반복은 필요한 취소 경계 확인만 수행하고 무제한 서버 요청을 하지 않는다.

정상/실패 결과는 실행 조합・화면 증상・시각으로 알려주면 기존 private 로그와 대조한다. 원시 계정/티켓 값은 문서에 복제하지 않는다. 기존 입력 수용・UI 패널 크기/슬롯/여백 합의는 그대로 유지하며 제품 기능을 추가하지 않는다.

승인된 문서 갱신 뒤 자동 검사를 한 번 시도했으나 기존 Python ResourceUnavailable로 본문 실행은 실패했다. runtime 추가 탐색이나 자동 PASS 주장은 하지 않았고 Task 로컬 링크와 Auth 로그아웃 원본/변경 범위를 직접 확인했다. 소스・검사・빌드 결과는 후속 인계 뒤 이 Task에 추가한다.

## 8. 구현 중간 인계와 빌드 미시작

소스 3개 교정과 실제 메서드 추출 RED 3개/GREEN 19개 PASS, 초기 전체 Runtime errors 0/warnings 23은 담당자 인계다. 추가 보강 뒤 전체 컴파일은 진행 중이므로 초기 검사를 최종 완료로 취급하지 않는다. 최종 파일・검사 근거는 후속 결과를 받아 갱신한다.

Unity Build Profiles는 Android/APK(AAB 해제)・Development 유지까지 준비했지만 Computer Use의 Escape 중단 신호로 조작을 중단했다. 실제 Build/파일 선택 전이라 빌드는 미시작이고 APK 산출물도 없다. 사용자 테스트 절차는 수정본 확보 뒤 적용하며 현재 빌드 성공이나 기기 수용으로 안내하지 않는다. 문서 담당자의 추가 UI 조작・빌드 재시작・원시 로그/식별자 복제는 없었다.

## 9. 최종 검사 확인과 사용자 빌드 인계

최종 Runtime errors 0/warnings 23, 실제 메서드 추출 GREEN 19 PASS를 인계받고 문서 담당자도 임시 로그를 직접 확인했다. 이후 소스 변경은 없다는 인계이며 정확한 경계/근거는 Research 10절을 따른다. static/대체환경 결과를 서비스/기기 성공으로 확대하지 않는다.

사용자가 빌드를 직접 시작했으며 메인은 Editor.log에서 Android BuildPlayerAndRun 및 bee/UnityLinker 진행을 확인했다. 8절의 미시작/APK 없음은 에이전트 UI 중단 당시 기록으로 보존하고 현재는 **사용자 빌드 진행 중/성공・산출물 미확정**으로 갱신한다. 실제 빌드 결과 인계 뒤 7절 사용자 절차를 적용하고 실기 수용은 별도 기록한다. 원시 로그・식별자 복제와 추가 제품 변경은 하지 않았다.

## 10. 사용자 매칭 수용과 남은 확인

새 빌드 기기↔Editor 양쪽에서 명시 로그아웃 뒤 익명으로 시작해 실제 매칭에 성공했다는 사용자 보고를 수용했다. 로그 저장/문서 갱신도 승인됐다. 메인 최신 로그 대조는 기기 identity 전환・현재 양쪽 identity 분리・동일 매치/Host-Client/게임 시작을 확인한다. Editor는 이전 identity를 유지하므로 양쪽 모두 새 ID 생성이 로그로 입증됐다고 확대하지 않는다. 매칭/로그아웃 오류가 새 구간에서 없더라도 별도 UAS-MOVE-AUTH ERROR가 있어 전체 오류 0으로 표현하지 않는다. 정확한 범위는 [Research 11절](Research.md#11-원래-실패-조합의-사용자-매칭-수용)을 따르며 원 HTTP 429는 미확정이다.

당시 7절 중 원래 실패 조합의 새 게스트 매칭은 수용됐지만 단순 재실행・실계정/진행도 보존・이전 닉네임/전적 미승계・취소 재시작/늦은 결과・실패 안내/로딩 복구/재시도는 아직 실기 미확인이다. 기확인 최종 컴파일과 19개 메서드 검사는 해당 분기의 사용자 실기 수용을 대신하지 않는다. 이를 남은 검증으로 관리하고 legacy 주석 삭제는 아직 하지 않는다.

이번 승인은 Task와 관련 상태/로드맵/마일스톤・공용/관련 programmer/QA 메모리의 최소 동기화다. 소스・원시 로그・이전 UI 문서・Git은 변경하지 않고 새 TC/QA 파일을 만들지 않는다.

원래 실패 조합만 수용하고 Task 전체를 닫거나 추가 테스트를 요구하지 않는다. 10개 기존 문서/메모리의 수용 범위・신규 링크/앵커와 저장본을 직접 검수했고 변경 형식 검사는 exit 0이다. 마지막 자동 검사/메모리 증가 baseline 갱신 시도는 Python 프로세스 실행 불가로 본문이 실행되지 않아 PASS가 아니며 baseline 수동 변경은 하지 않았다. 기존 legacy 소스 주석도 보존했다.

## 11. 승인된 최초 접속 준비 30초 교정

후속 실계정 Editor↔익명 기기 정상 2회 뒤 기기 오프라인 상태 조회/티켓 정리 실패가 발생했다. 온라인 Editor는 Found/Host 시작 뒤 Client가 오지 않아 접속중 로딩에 남았다. 상세 근거는 Research 12절이며 기존 맵 timeout보다 앞선 대기 공백으로 구분한다. 기존 익명/Auth 교정과 정상 매칭 수용은 철회하지 않는다.

| 시작/종료/상한 | Found에서 접속중 로딩을 켠 순간 시작, Game 씬 전환을 시작할 때 종료. 최대 30초 | [MatchFlow](../../../GameSystemRules/GameSystemRules_MatchFlow.md#매칭-성립-후-최초-접속-준비-상한) 「무작위 맵 생성 규칙」 규칙 16의 접속 준비 절 |

메인 검토 후 구현 착수 범위는 NetworkGameManager・BattleViewModel 두 파일이다. 최종 실제 파일/검사는 인계 뒤 확정한다. 새 패키지/SDK 변경이나 별도 기능을 추가하지 않으며 기존 10초 맵 응답/재전송・매칭 티켓 대기・결과/재경기/이탈 시간은 바꾸지 않는다. 제거/교체 지점은 상단의 주석 보존/검증 경계를 따른다.

Lobby/RelayManager의 SDK await 후 공유 상태 쓰기는 늦은 결과 무시만으로 보호되지 않으므로 이전 준비 회차 SDK 종료/정리가 끝나기 전 다음 session 생성이 시작되지 않도록 barrier를 둔다. 커스텀 생성/참가에도 이 안전 대기만 적용하고 기존 커스텀 대기/timeout 정책은 그대로 둔다. 새 서버 데이터/heartbeat 없이 기존 실패 RPC/NGO disconnect를 사용하며 미접속 상대에게 전달 불가하면 각자 30초 상한을 따른다.

감시 종료는 Host의 NGO LoadScene Started 반환과 Client의 Game SceneEvent.Load 관측이 기준이다. StartHost 성공・RPC 송신/로드 요청만으로 종료하지 않는다. 실패/timeout UI는 즉시 복구하되 이전 공유 SDK 정리가 끝나기 전에 새 생성/참가가 시작되지 않게 하는 두 책임을 분리한다.

실행 결과가 오면 실제 파일・검사・빌드/실기 범위를 추가한다. 후속 확인은 정상 매칭 유지, 실패 인지 시 즉시 복구, 상대 미접속/미전달 시 최대 30초, 씬 전환 뒤 이전 timer 무효화의 경계로 정리하되 지금 새 TC/QA를 만들거나 통과로 기록하지 않는다. 이번 계획 승인 자체가 구현/모든 회귀 완료는 아니다.

### 최종 적용・검사와 실행 한계

NetworkGameManager・BattleViewModel 두 파일을 교정했고 Task 두 문서/규범 두 문서를 합한 이번 범위는 6개다. 실제 Found 회차의 deadline・Host/Client 씬 시작 종료・한 번 실패 알림・즉시 ViewModel 복구・이전 SDK/cleanup static barrier・원 NGO 소유권/scene verifier 보존・늦은 Game 거부・cleanup 실패 시 새 SDK 차단을 반영했다. custom 생성/참가는 안전 대기만 적용하고 기존 정책을 유지한다. 정확한 소스/근거는 Research 12절 최종 인계를 따른다.

최종 Runtime errors 0/warnings 23, Android 조건 정적 errors 0/warnings 30이며 추출된 실제 메서드의 SDK/clock/NGO 대역 회귀 31개 PASS를 확인했다. 두 소스 manifest 일치도 문서 담당자가 대조했다. 컴파일 DLL은 scratch만 출력하고 기존 Library는 바꾸지 않았다. 이 최종 정적 인계 당시 native/실서버/Android APK 실행은 없었으며 기존 기기 앱은 이 교정 전 빌드다. 사용자 수용・원 429・Task 전체 완료로 확대하지 않는다.

### 수정본 확보 뒤 묶어서 확인할 절차

별도 Testcase/QA 파일은 생성하지 않는다. 이번 교정이 포함된 Editor/기기 수정본 확보 뒤 아래 경계를 한 번에 확인하는 안내다. 기존 익명 정책/정상 매칭 수용을 취소하거나 이전 앱 결과를 30초 교정의 수용으로 바꾸지 않는다.

1. 정상 온라인 양쪽으로 매칭해 게임 씬 진입이 유지되는지 확인한다. 접속 준비 중 로딩이 켜진 시점을 기준으로 보고, 매칭 상대를 찾는 대기 시간과 혼동하지 않는다.
2. 이전 문제가 난 상대 오프라인 조건을 재확인한다. 실패를 알게 된 쪽은 즉시 로딩/대기를 닫고 알림/로비로 돌아와야 한다. 이미 Found로 접속 준비에 들어간 온라인 쪽은 상대 통보가 없어도 로딩 시작부터 최대 30초 안에 실패 안내/복구해야 한다. Found가 안 된 티켓 대기에 30초를 적용했다고 판정하지 않는다.
3. 복구 뒤 네트워크를 정상으로 돌리고 새 매칭을 시도한다. 이전 SDK 정리 중이면 안전 대기하고, 이전 결과/cleanup이 새 회차의 로딩/연결을 지우지 않아야 한다. 정리 자체가 실패하면 새 연결을 무리하게 생성하지 않고 실패 복구를 유지해야 한다.
4. 정상 Game 씬 전환이 시작된 회차는 이전 로딩 기준 30초가 지나도 뒤늦은 준비 실패로 닫히지 않아야 한다. 필요할 때 같은 재시도 흐름에서 확인하며 별도 무제한 반복 요청은 하지 않는다.

관측 결과는 양쪽 실행 조건・로딩 시작/종료 시각・화면만 알려주고 계정/티켓 식별자는 옮기지 않는다. 취소된 새 요청/새 SDK 안전 대기 등 통제하기 어려운 경계를 실기에서 못 보았다면 대역 검사와 미관측을 구분해 남긴다. legacy 최종 삭제・상태/메모리 확대 갱신은 이번 새 구현 실기 수용 전 실행하지 않는다.

최종 문서 검사 1회는 기존 ResourceUnavailable로 본문 실행 불가였다. 자동 PASS로 보고하지 않고 로컬 링크/앵커・저장 의미를 직접 확인했다. 이번 6개 정확 목록과 검사 범위는 Research 12절의 최종 인계를 따른다. 새 TC/QA・이전 UI/Auth・Status/메모리・원시 로그・Git은 이번에 변경하지 않았다.

## 12. 최신 수용 판정과 종료 범위 — 2026-10-21

사용자는 정상 매칭 → 상대 인터넷 단절 시 복구 → 인터넷 복구 뒤 재매칭의 안내된 세 단계를 확인했다. 메인 로그 대조로 Editor Host・기기 Client의 정상/재매칭 양쪽 동일 매치와 시작 RPC, 온라인 Host의 준비 deadline 30.006초 뒤 M-2 UI/Disconnect를 확인했다. 첫 정상 씬은 Found 약 6초 후 전환을 시작하므로 경기 시작 RPC가 약 30초 후라는 이유로 준비 상한 실패로 판정하지 않는다. 정확한 시각/범위는 [Research 13절](Research.md#13-랜덤-매칭-세-단계-사용자-수용-완료--2026-10-21)을 따른다.

11절의 수정본 확보 뒤 절차는 당시 안내 기록이며 이번 사용자 실행으로 정상・단절 복구・재매칭과 성공 후 준비 오류 미재발 범위를 수용했다. **이번 랜덤 매칭 교정은 구현과 사용자 확인까지 완료**다. 기기 Found 전 티켓 실패에 준비 30초를 적용한 것으로 확대하지 않는다. 정확한 APK 해시/빌드 실행 로그는 미제공이며 소스 정적 검사/대역 31 PASS와 사용자 실기는 서로 다른 근거다.

기기 기존 게스트 자동복원은 로그 확인됐으며, 재실행 전후 닉네임/전적 상세 보존・실계정 진행도/익명 이전 진행도・취소 직후 경쟁/늦은 결과・Host/Client 역할 교환은 별도 미관측으로 보존한다. 원 429 원인은 미확정이다. 이 목록은 이번 교정을 다시 열거나 같은 세 단계를 반복시키는 필수 관문이 아니다. 기존 입력필드 수용과 UI 고정 프레임/슬롯/여백 합의도 유지한다. 이번 변경은 Task/상태/로드맵/이력/관련 메모리의 기록뿐이며 legacy 소스 삭제나 새 구현・규칙・TC/QA・원시 로그/Git 수정은 하지 않는다.
