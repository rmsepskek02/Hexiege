## §1. 이 조사가 무엇을 왜 하는가 (자연어 설명 — `CLAUDE.md` 규칙 13)

지도를 쓰는 일은 **두 단계**입니다.

1. **만든다(준비)** — 이번 판의 지형과 광산 자리를 계산해 «설계도»를 뽑는다.
2. **격자에 새긴다(투영)** — 그 설계도를 실제 타일판에 대입한다.

**싱글플레이**에서는 2026-09-29 에 **두 단계 어디에서 실패해도 안내가 뜨도록** 구현이 끝났습니다.
맵을 만들다 실패해도, 만든 맵을 새기다 실패해도, 사용자는 **맵 준비가 실패했다는 뜻의 안내 한 줄**과
「다시하기」·「로비로」 두 버튼을 받습니다. ⚠️ **그 안내의 실제 글자는 이 문서에 적지 않습니다** —
그 값의 단일 소스는 `Assets/_Project/Docs/GameSystemRules/GameSystemRules_UI.md` 「공통 UI 규칙」
규칙 M-2·M-4 이고, 🔴 **글자를 옮겨 적으면 「그 문구가 코드에 몇 곳 있는가」를 세는 검증이 오염됩니다.**

**멀티플레이는 그렇지 않습니다.** 멀티에서는 맵을 **로비에서** 만들어 상대에게 보내고,
양쪽이 같은 맵임을 확인한 뒤에야 전투 화면으로 넘어갑니다. 그 **로비 단계**(만들기·보내기)의
실패는 이미 처리되어 있습니다. 그런데 전투 화면에 들어온 뒤의 **새기기 단계**가 실패하면
**아무 안내도 없습니다** — 로그 한 줄만 남고, 사용자는 그 사실을 알 방법이 없습니다.

**이 조사가 답하려는 것**은 다섯 가지입니다.

| # | 질문 |
|---|---|
| 1 | 멀티에서 새기기가 실패하면 **지금 정확히 무슨 일이 일어나는가** (화면·로그·이후 절차) |
| 2 | **Host 와 Client 각각** 어떻게 되는가. 한쪽만 실패할 수 있는가 |
| 3 | **최초 경기와 재경기**가 같은 자리를 지나는가 |
| 4 | 기존 멀티 실패 안내가 **실제로 화면에 무엇을 띄우는가** |
| 5 | 이 실패를 **일부러 만들어 볼 수단이 있는가** |

🔴 **이 문서는 「어떻게 고칠 것인가」를 정하지 않습니다.** 어느 규칙이 이 실패를 규정하는지,
무엇을 어떻게 알릴지는 [Plan.md](Plan.md) 가 후보와 권고를 제시하고 **확정은 사용자가** 합니다
(`CLAUDE.md` 규칙 6·12).

## §4. 질문 1 — 멀티에서 투영이 실패하면 지금 정확히 무슨 일이 일어나는가

### §4-1. 코드 경로 (✅ 전부 코드 실측)

```
NetworkGameFlow.StartGameClientRpc       ← 🔴 ClientRpc — Host·Client 가 각자 로컬에서 실행한다
  → GameBootstrapper.StartNetworkGame(localTeam)
      → GameBootstrapper.LoadMap(FlatTop)
          … 3. 격자 생성: new HexGrid(11, 21, FlatTop)
          → 3-A. PrepareAndProjectMap()
                   · _mapPreparation = null / _mapProjection = null   (먼저 비운다)
                   · if (IsNetworkMode()) → ProjectHandedOverMap(); return;   ← 멀티는 여기서 갈라진다
                         · MapHandoff.TryTake(out handedOver)  실패 → 로그 한 줄 + return   (§9 별건)
                         · _mapPreparation = handedOver
                         · ProjectMap(handedOver);            ← 🔴 반환값을 버린다
                                · MapProjectionUseCase.Project(...)
                                · _mapProjection = projected
                                · if (!projected.IsSucceeded) → GameLog.Ops.Error(MapProjectionFailed, …); return false;
          … 4. UseCase 생성        ← 🔴 실패해도 그대로 계속 진행한다
          … 5. 타일 렌더링 _gridRenderer.RenderGrid(_grid)
          … 6~10. 카메라 · 입력 · 건물 · 생산 · HUD · 결과 화면 초기화 …
          … 마지막 줄에서 전역 로딩 표시를 끈다
```

🔴 **핵심은 두 가지다.**

1. **`ProjectMap` 은 이제 `bool` 을 돌려준다** — 2026-09-29 에 싱글 때문에 `void → bool` 이 됐다.
   🔴 **그런데 멀티 호출부(`ProjectHandedOverMap`)는 그 값을 받지 않고 버린다.** C# 은 반환값을
   쓰지 않아도 컴파일되므로, **멀티는 실패를 알 수 있는 값이 눈앞에 있는데도 읽지 않는 상태**다.
   (그 함수의 XML 주석이 *「이 값을 실제로 「읽는」 호출부는 싱글 경로 하나뿐이다」* 라고 명시한다.)
2. **실패해도 `LoadMap` 은 끝까지 진행한다** — 실패 자리에서 되돌아가거나 씬을 닫지 않는다.
   그래서 전역 로딩 표시는 **정상적으로 꺼진다.** 🔴 **즉 사용자에게는 「로딩이 끝나고 전투 화면에
   도착한」 것으로 보인다.**

### §4-2. 로그에 무엇이 남는가 (✅ 코드 실측)

- **한 줄**이다 — `GameLog.Ops.Error(LogEvent.MapProjectionFailed, …)`.
  message 는 `"맵 투영 실패 — 성/광산을 배치하지 않는다: " + 사유`, 구조화 필드는
  `BuildMapProjectionLogData(prepared)`(어느 판인가 = MapVersion/Seed/Hash + 격자 크기).
- 🔴 **화면 쪽으로 나가는 신호는 0건이다** — 이 블록에는 이벤트 발행도 RPC 도 UI 호출도 없다.
  주석이 그 이유를 *「이 메서드는 싱글·멀티가 함께 쓰는 자리라, 안내를 이 안에 넣으면 멀티에서도
  발화한다」* 고 적어 둔다. 🔴 **즉 지금의 「안내 0건」은 사고가 아니라 의도적으로 비워 둔 자리**이고,
  그 자리를 **부르는 쪽이 채우기로 한 계약**인데 멀티 호출부만 채우지 않았다.

### §4-3. 화면에 무엇이 남는가 — ⚠️ **여기부터는 구조 추론이다. 관측이 아니다**

🔴 **호출 세션의 「빈 전투 화면」이라는 표현을 그대로 옮기지 않는다** — 코드를 따라가면 그보다
구체적이고, **한 조각은 그 표현과 어긋난다.**

| 화면 요소 | 어떻게 되는가 | 근거 |
|---|---|---|
| **타일판** | 🔴 **그려진다 — 「비어 있지」 않다.** 5번 단계가 `RenderGrid(_grid)` 를 그대로 부르고, 격자는 3번 단계에서 막 만들어졌다. `HexTile` 의 기본값이 `TileKind.Normal` · `MineKind.None` 이므로 **막힌 칸도 구멍도 광산도 없는 11×21 균일한 평지**가 그려진다 | ✅ 코드 실측(`Domain/Hex/HexTile.cs` 의 두 프로퍼티 초기값) + ⚠️ 렌더 결과는 추론 |
| **성 2채** | 🔴 **없다.** `PlaceCastles()` 가 맨 앞에서 `if (_mapProjection == null \|\| !_mapProjection.IsSucceeded) return;` 으로 되돌아간다 | ✅ 코드 실측 |
| **시작 채굴소 2채** | 🔴 **없다.** `PlaceGoldMines()` 에 같은 가드가 있다 | ✅ 코드 실측 |
| **HUD · 설정 버튼** | **있다.** 10번 단계가 HUD 를 초기화하고, HUD 의 설정 버튼이 인게임 설정 메뉴를 연다 | ✅ 코드 실측 |
| **로딩 표시** | **꺼진다**(정상 종료) | ✅ 코드 실측 |
| **안내 문구·팝업** | 🔴 **0건** | ✅ 코드 실측 |

⚠️ **그래서 정확한 표현은 「빈 화면」이 아니라 「성도 광산도 없는 균일한 평지 + 정상 HUD」다.**
🔴 **이것이 왜 중요한가 — 「비어 있다」보다 **나쁘다.** 화면이 텅 비면 사용자는 고장을 의심하지만,
멀쩡해 보이는 판이 그려져 있으면 **이번 판이 성립하지 않았다는 사실 자체를 알 수 없다.**
(같은 위험을 `ProjectHandedOverMap` 의 주석이 인계 누락에 대해 *「화면에는 멀쩡한 맵이 뜨고 경기도
굴러가므로 아무도 이상을 눈치채지 못하는데, 그것이 규칙 16 을 어기는 가장 조용한 방식이다」* 라고
이미 적어 두었다.)

### §4-4. 이후 절차 — 사용자가 빠져나갈 길이 있는가

⚠️ **싱글 최초 경기와 다르다 — 갇히지는 않는 것으로 보인다(추론).**

- HUD 우상단 **설정 버튼 → 인게임 설정 메뉴 → 「포기」** 경로가 살아 있다
  (✅ `Presentation/UI/GameHudUI.cs` 의 설정 버튼 → `InGameSettingsUI.Show()`,
  `InGameSettingsUI` 의 포기 버튼 → 확인 팝업 → `IForfeitService.RequestForfeit()`,
  멀티에서는 `NetworkGameEndController` 가 그 서비스다).
- 포기가 성립하면 결과 화면이 뜨고 그 화면의 「로비로」로 나갈 수 있다.
- ⚠️ **확인하지 못한 것 — 성이 없는 판에서 포기가 실제로 성립하는지는 확인하지 않았다.**
  승패 판정이 성 파괴를 전제하는 코드와 얽힐 수 있다. 🔴 **「나갈 수 있다」고 단정하지 않는다.**

## §5. 질문 2 — Host 와 Client 각각 어떻게 되는가

### §5-1. 🔴 대전제 (단일 소스: `TechnicalDesignDocument.md` 「🔴 최상위 원칙 — 플레이어는 자신이 Host 인지 Client 인지 알 수 없다」)

그 절이 정하는 것을 그대로 적는다 — **화면(UI/UX) · 승패 기록 · 이탈·종료 처리 셋 중 어느 하나라도
역할에 따라 갈리면 그것은 결함**이고, **개별 규칙이 이 원칙과 충돌하면 고칠 대상은 개별 규칙**이다.
🔴 **「Host 쪽에만 있는 처리」는 그 자체로 위반 후보**다.

### §5-2. 투영은 🔴 **양쪽이 각자 로컬에서** 돌린다 (✅ 코드 실측)

- 진입점이 **`[ClientRpc] StartGameClientRpc`** 다 → **Host 와 Client 가 각자 자기 기기에서**
  `StartNetworkGame → LoadMap → ProjectHandedOverMap → ProjectMap` 을 실행한다.
- ✅ **이 구조 자체는 최상위 원칙에 맞다** — 서버 전용 처리가 아니고, 두 역할이 같은 코드를 탄다.
- 🔴 **그러나 실패했을 때의 처리가 「없음」이므로, 원칙을 만족하는지는 지금 물을 수 있는 질문이 아니다.**
  없는 처리는 갈리지도 않는다. **원칙이 걸리는 자리는 「안내를 붙일 때」**이며 그것이 Plan 의 판정 항목이다.

### §5-3. 🔴 한쪽만 실패할 수 있는가 — **그렇다**

투영이 실패하는 사유 8자리는 **전부 「받은 설계도 vs 내 로컬 격자」의 불일치**다
(맵 정의 null · 격자 null · **맵 크기와 격자 크기 불일치** · 타일 배열 길이 불일치 ·
**맵이 가리키는 칸이 격자에 없다(헥스 방향 불일치)** · 성 목록 무효 · 시작 광산 목록 무효 ·
중립 광산 타일 번호 범위 밖 — ✅ 재확인은 §3).

- **설계도는 양쪽이 같다** — 씬 전환 전에 해시가 일치해야만 넘어온다
  (`GameSystemRules/GameSystemRules_RandomMap.md` 규칙 16 의 *「Host와 Client의 최종 맵 데이터 해시가
  같을 때만 전투 씬 전환을 시작한다」*).
- 🔴 **그러나 격자는 각자 자기 로컬 설정에서 만든다** — `LoadMap` 이 `_config`(`GameConfig` 에셋)의
  `FlatTop.GridWidth/GridHeight` 로 `new HexGrid(...)` 를 만든다. ✅ 코드 실측.
- 🔴 **따라서 두 기기의 `GameConfig` 격자 크기나 orientation 이 다르면 한쪽만 실패한다.**
  현실적인 경우는 **서로 다른 빌드가 붙은 경우**(에디터 vs 기기 · 구 버전 APK)다.
- ⚠️ **「실제로 그렇게 어긋난 기록」은 0건이다** — 아래 §8 이 적는 대로 진짜 투영 실패의 발생 기록이
  싱글·멀티 모두 0건이다. 🔴 **즉 한쪽만 실패하는 경우가 현실에서 일어난 적이 있는지는 알 수 없다.**

### §5-4. 🔴 한쪽만 안내가 뜨면 어떻게 보이는가 (⚠️ 추론 — 아직 안내가 없으므로 관측 대상이 존재하지 않는다)

**전제**: 실패는 로컬 사건이고 **상대에게 알리는 경로가 0건**이다(§4-2).

| 누가 실패했나 | 실패한 쪽 화면 | 상대 화면 |
|---|---|---|
| 한쪽만 실패 | (안내를 붙인다면) 실패 안내 | 🔴 **완전히 정상인 전투 화면.** 성·광산·HUD 모두 정상이고 **안내는 0건** |
| 양쪽 실패 | 실패 안내 | 실패 안내 (양쪽 같다) |

🔴 **그래서 「한쪽만 뜬다」는 상태는 역할 비대칭이 아니라 «실패한 쪽 vs 실패하지 않은 쪽» 비대칭이다.**
⚠️ **이 구분을 흐리면 안 된다** — 최상위 원칙이 금지하는 것은 **역할(Host/Client)에 따라 갈리는 것**이고,
**실제로 실패한 기기에만 안내가 뜨는 것은 원칙 위반이 아니다.** 오히려 **로컬 통보는 구조적으로
역할 대칭**이다(누가 실패해도 같은 코드가 같은 화면을 띄운다).

🔴 **반대로, 상대에게 RPC 로 알리는 설계는 최상위 원칙과 충돌할 위험을 새로 들인다** —
실패한 쪽이 Client 면 서버로 올려 다시 브로드캐스트해야 하고, 실패한 쪽이 **Host** 면
그 판정·중계 주체가 실패한 기기 자신이 된다. 🔴 **이것은 「결과 화면 이탈 감시를 서버 전용으로 두면
Host 가 사라졌을 때 남은 Client 가 통보받을 길이 함께 사라진다」는 이유로 2026-09-21 에 뒤집힌 판단과
같은 모양**이다(단일 소스: `TechnicalDesignDocument.md` 「🔴 최상위 원칙」과 그 절이 가리키는
「결과 화면 이탈 판정·통보 구조」). ⚠️ **이 조사는 그것을 판정하지 않는다 — Plan 의 위험 항목으로 넘긴다.**

⚠️ **남는 질문(이 조사가 답하지 못한 것)** — 실패하지 않은 쪽은 **상대가 아무것도 하지 않는 판**에
남는다. 그 쪽이 언제 어떻게 빠져나가는지는 **인게임 이탈 처리**의 범위이고, 그 계통에는
**이미 문서화된 역할 비대칭**(`ReconnectionHandler` 가 서버 전용)이 있다
(단일 소스: `TechnicalDesignDocument.md` 「🔴 최상위 원칙」의 실측 예와 「인게임 이탈 처리」 절).
🔴 **이 조사는 그 자리를 건드리지 않는다.**

## §6. 질문 3 — 최초 경기와 재경기가 같은 자리를 지나는가

### §6-1. ✅ **지난다 — 멀티는 두 회차가 완전히 같은 자리를 탄다** (코드 실측)

| 회차 | 경로 |
|---|---|
| **최초 경기** | 로비에서 전송 성공 → `NetworkGameManager` 가 `SceneManager.LoadScene("Game", LoadSceneMode.Single)` → `NetworkGameFlow` 가 양쪽 준비 확인 → `StartGameClientRpc` → `StartNetworkGame` → `LoadMap` → `ProjectHandedOverMap` → `ProjectMap` |
| **재경기** | 결과 화면에서 양측 동의 → 맵 재전송 성공 → `NetworkGameEndController.StartRematch()` 가 `SceneManager.LoadScene("Game", LoadSceneMode.Single)` → **이하 최초 경기와 같은 줄** |

🔴 **즉 갈라야 할 자리는 하나뿐이고, 싱글처럼 「지금이 다시하기인가」를 가르는 깃발이 필요하지 않다.**

### §6-2. 🔴 그런데 **싱글과 결정적으로 다른 점**이 있다 — 씬이 이미 새로 로드됐다

| | 싱글 | 멀티 |
|---|---|---|
| **재경기 때 씬을 다시 불러오는가** | ❌ **아니다.** 결과 화면(`GameEndUI.OnRestartClicked`)이 **같은 씬에서** `GameBootstrapper.LoadMap()` 을 직접 부른다 | ✅ **그렇다.** `LoadSceneMode.Single` 로 Game 씬을 통째로 다시 불러온다 |
| **투영 시점에 결과 화면이 살아 있는가** | ✅ **있다** — `Hide()` 된 채 그 자리에 있어 **되살릴 수 있다** | 🔴 **없다** — 옛 씬과 함께 파괴됐고, 지금 있는 것은 **아직 한 번도 뜬 적 없는 새 인스턴스**다 |
| **투영 시점에 로비가 살아 있는가** | (해당 없음) | 🔴 **없다** — `LoadSceneMode.Single` 이라 로비 씬은 이미 내려갔다 |
| **되돌릴 「이전 맵 정의」가 있는가** | (해당 없음) | 🔴 **없다** — 규칙 16 대로 **양측 검증 성공 시 새 정의를 원자적으로 교체한 뒤** 씬을 재로드한다. 투영은 그 **교체가 끝난 뒤**다 |
| **「지금이 다시하기인가」 깃발이 필요한가** | ✅ 필요했다(`_restartMapLoadInProgress`) | ❌ **불필요** — 두 회차가 도착하는 상태가 같다 |

🔴 **이것이 이 조사에서 가장 중요한 발견이다.** 기존 멀티 실패 규칙 둘이 요구하는 **복구 동작이
투영 실패 시점에는 구조적으로 실행 불가능**하다.

| 규칙 | 요구하는 복구 | 투영 실패 시점에 가능한가 |
|---|---|---|
| `GameSystemRules_UI.md` 「공통 UI 규칙」 규칙 M-2 (멀티 최초 경기) | *「loading UI를 닫고 **기존 로비와 network connection을 유지**한다」* · `Retry` 는 *「새 root seed부터 맵 관련 추첨·생성·전송을 다시 시작」* | 🔴 **불가능.** 로비 씬이 이미 내려갔고, 전투 씬 안에서는 로비의 전송 기구를 그대로 다시 돌릴 자리가 없다 |
| 같은 문서 규칙 M-3 (멀티 재경기) | *「**이전 `MapDefinition`과 결과 화면을 유지**하고 rematch pending 상태를 초기화한다」* · *「결과 화면의 기존 선택지를 모두 복원한다」* | 🔴 **불가능.** 결과 화면은 씬과 함께 파괴됐고, 이전 맵 정의는 이미 새 정의로 교체됐다 |

⚠️ **그러므로 「규칙 M-2·M-3 에 투영 단계를 포함시킨다」는 해석 확장은 싱글에서 규칙 M-4 에 한 것과
같은 모양이 **아니다.** 규칙 M-4 는 확장해도 **복구 동작이 그대로 성립**했다(싱글 최초 경기는 모달을
띄울 자리가 전투 씬 안에 있고, 싱글 재경기는 결과 화면이 같은 씬에 살아 있었다). 🔴 **멀티는 그렇지 않다.**
**이 차이가 Plan 의 핵심 질문(어느 규칙이 규정하는가)의 실제 쟁점이다.**

## §7. 질문 4 — 기존 멀티 실패 UI 가 실제로 무엇을 띄우는가

### §7-1. 규칙 M-2 (멀티 최초 경기) — 🔴 **규정은 「모달 + 버튼 2개」인데 코드는 「텍스트 한 줄」이다**

✅ **코드 실측**:

- 발화 경로: `Infrastructure/Network/NetworkGameManager` 의 `FailMapTransferGate(...)` → `OnMapTransferFailed?.Invoke(reason)`
  → `Presentation/UI/ViewModels/BattleViewModel.OnMapTransferFailed(string)`(정의 **335행**, 구독 등록 **133행**).
- 그 핸들러가 하는 일은 **셋**이다 — ① 전역 로딩 표시를 끈다 ② `IsConnecting` 을 내린다
  ③ `ErrorMessage.Value` 에 문구 한 줄을 넣는다.
- 🔴 **모달도 `Retry` 도 `Leave Match` 도 없다.** 그 핸들러의 주석이 스스로
  *「실패 팝업·재시도 버튼은 이번 범위가 아니다 … 그래서 지금 플레이어에게 가는 안내는 아래
  ErrorMessage 한 줄뿐이다」* 라고 적는다.
- 🔴 **그 한 줄을 화면에 꺼내는 곳도 한 곳뿐이다** — `Presentation/UI/Views/Lobby/Battle/CustomHostView.cs`
  가 `vm.ErrorMessage` 를 구독해 텍스트로 찍는다. ✅ **프로젝트 전체에서 `vm.ErrorMessage` 구독은 그 1건**이다
  (다른 1건은 같은 파일 머리말 주석이다).
- ⚠️ **그래서 이 안내는 「방을 만든 쪽 화면」에서만 보인다** — 참가한 쪽 화면(`CustomJoinView`)에는
  그 구독이 없다. 🔴 **이것은 역할에 따라 화면이 갈리는 상태이므로 최상위 원칙의 위반 후보다.**
  ⚠️ **다만 이것은 「전투 씬에 들어가기 전(접속·전송 단계)」의 자리이고 이번 작업 범위가 아니다** —
  **고치지 않고 기록만 한다**(`CLAUDE.md` 규칙 6). Plan 의 「범위 밖」 절에 옮겨 적었다.

🔴 **결론 — 이 자리는 「접속·전송 단계」의 로비 화면 자리라 전투 씬 안의 투영 실패를 받을 수 없다.**
인계표가 적은 그대로이며 ✅ **재확인됐다.** 그 사건 구분은 이미 규칙 문서에 판정으로 못 박혀 있다
(`GameSystemRules_UI.md` 「공통 UI 규칙」 규칙 M-4 끝의 2026-09-29 (4차) 판정 블록 근거 ⓑ —
*「③ 은 전투 씬에 들어가기 전 … ①·② 는 전투 씬 안」*).

### §7-2. 규칙 M-3 (멀티 재경기) — ✅ **규정대로 「상태 줄」이다** (팝업이 아니다)

✅ **코드 실측**:

  **발행 2곳**(`Infrastructure/Network/NetworkGameEndController.cs` 863 · 996행) ·
  **구독 1곳**(`Presentation/UI/GameEndUI.cs` 880행 → `OnRematchMapFailed(e.Cause)`).

  카운트다운은 전체 길이로 다시 시작한다. 🔴 **알림 팝업을 띄우지 않는다** — 그 개정의 단일 소스는
  `GameSystemRules_UI.md` 「공통 UI 규칙」 규칙 M-3 의 2026-09-22 (2차) 개정 블록이다.
- 🔴 **이 채널은 「결과 화면이 떠 있는 동안」을 전제한다.** 그래서 §6-2 대로 **씬이 재로드된 뒤의
  투영 실패는 이 채널로 받을 수 없다** — 받을 화면이 없다. ✅ **인계표가 적은 그대로 재확인됐다.**

### §7-3. 요약 — 🔴 멀티의 맵 실패 안내 자리는 **전부 전투 씬 진입 전**이다

## §8. 질문 5 — 재현 수단이 있는가

### §8-1. ✅ 현재 있는 강제 실패 도구는 **4개**다 (코드 실측)

### §8-2. 🔴 결론 — **멀티 투영 실패를 재현할 수단은 0개다**

- 싱글 투영 토글이 **가장 가까운데도** 닿지 않는다 — 그 토글의 소비 자리가
  `if (!IsNetworkMode() && ForcedMapProjectionFailure.TryConsume())` 이고,
  C# 의 단락 평가 때문에 **멀티에서는 토글을 읽지도 않는다**(✅ 코드 실측).
  🔴 **그것은 버그가 아니라 2026-09-29 에 「멀티를 건드리지 않는다」는 범위 한정을 지키려고
  일부러 그렇게 둔 것**이다(단일 소스: `_Tasks/2026-09-28/11_50_single-map-failure-ui/Plan.md` §15-H-3 의 3).
- 🔴 **정상 경로로는 관측할 수 없다** — 투영 실패 사유 8가지가 전부 **격자 설정 불일치**라
  정상 빌드에서는 나지 않는다. ✅ **진짜 투영 실패의 발생 기록은 싱글·멀티 모두 0건**이다
  (단일 소스: `GameSystemRules_UI.md` 「공통 UI 규칙」 규칙 M-4 의 2026-09-29 (3차) 블록 —
  이번까지 관측된 2회는 **전부 강제 실패 도구가 만든 것**이다).

### §8-3. ⚠️ 🔴 그리고 **도구를 만들어도 한쪽밖에 태울 수 없다** — 테스트 설계의 제약

- 기존 4개는 전부 **에디터 전용 컴파일 가드 안**에 있고 저장소도 에디터 환경설정이다
  (✅ 파일 머리말과 `#if UNITY_EDITOR` 실측).
- 🔴 **멀티 실기는 「에디터 1대 + 기기 빌드 1대」 구성이다** — 즉 **에디터 쪽(= 보통 Host)만** 예약할 수 있고
  **기기 빌드 쪽에서는 강제 실패를 켤 수 없다.**
- ⚠️ **그러므로 「Client 쪽만 투영이 실패한 경우」는 에디터 전용 도구로는 만들 수 없다.**
  🔴 **§5-3 이 보여 준 「한쪽만 실패한다」가 실제로 가장 알고 싶은 경우인데, 바로 그 경우가
  재현 난이도가 가장 높다.** 이것을 어떻게 다룰지는 Plan 의 판정 항목이다.
  ⚠️ **「에디터를 Client 로 두면 된다」는 회피책이 성립하는지는 확인하지 않았다** —
  기존 도구 절차가 *「에디터를 Host 로 둘 것」* 을 전제로 쓰여 있다(전달값: 위 TDD 절의 사용 절차).

## §9. 곁가지 발견 — 🔴 인계표에 없던 **세 번째 실패 자리**

✅ **코드 실측**: `ProjectHandedOverMap()` 에는 투영보다 **앞선** 실패 분기가 하나 더 있다 —
`if (!MapHandoff.TryTake(out handedOver))`, 즉 **로비에서 확정된 맵이 전투 씬으로 인계되지 않은 경우**다.

- 그 블록이 하는 일도 **로그 한 줄**(`LogEvent.MapPreparationFailed`, 필드 `Reason=MapHandoffEmpty`)**뿐**이고
  **화면 안내는 0건**이며 **그대로 `return`** 한다.
- 🔴 **결과 화면은 투영 실패와 똑같다** — 성·광산이 배치되지 않고(같은 `_mapProjection` 가드에 걸린다)
  타일판만 그려진다.
- ⚠️ **이 자리는 인계표에 없다.** 🔴 **범위에 넣을지는 Plan 이 판정해야 하며 이 문서가 정하지 않는다.**
  판정에 필요한 사실만 적는다 — **사용자가 겪는 것은 투영 실패와 구별되지 않고**(§4-3 의 화면이 같다),
  **로그 키는 다르다**(`MapPreparationFailed` + `Reason=MapHandoffEmpty` vs `MapProjectionFailed`).
  🔴 **키가 다른 것은 의도된 설계다** — 그 블록의 주석이 키 선택 근거를 길게 적어 두었고
  *「MapProjectionFailed 는 쓰지 않는다: 그 키는 「맵은 있는데 격자에 못 새겼다」는 설정 계통 지표다」* 라고 못 박는다.
