# Android 최적화 재개 — 계획

먼저 남은 후보를 작은 범위로 비교하고, 실제 비용을 줄일 근거와 기존 기능 보존 방법이 분명한 작업을 고른다. 과거 이동 교정 이력을 계속 늘리는 대신 이번 선택과 구현의 목적·범위·종료 기준을 이 문서에서 명확히 한다.

**문서 역할**
- 목적·질문: 조사 결과로 무엇을 왜 진행하고 언제 완료/중단할지 정한다.
- 포함: 선택 기준, 구체 수정·검증·예상 작업량과 승인 상태.
- 제외·담당: 소스 조사 근거는 [Research](Research.md), 과거 작업 이력은 기존 Task.
- 원본·갱신: 이번 실행 계획 원본이며 후보 선정·범위/승인 변경 때 현행 상태를 갱신한다.

## 1. 현재 단계

사용자는 최적화 재개·새 Task 작성을 승인했다. 핵심8~9파일의 제한 읽기 조사와1차 분류를 마쳤으나, 작업별 소스·기존 문서·구현/검증 한계를 연결하는 정식 재감사를 [Research4절](Research.md#4-작업별-소스문서-검수-장부--2026-11-24)에 기록했다. 이는 현재까지 확인한 작업 단위의 검수이며 전체 프로젝트 최적화 완료 선언이 아니다. 구체적인 추가3후보 중 공간 후보 축소의 국소 실현 가능성 설계·검증을 먼저 제안한다. 제품 구현안은 아직 승인·착수하지 않았다. 이번 작성은 계획 준비이며 새 제품 수정·빌드·실기 실행은 없다.

## 2. 후보를 고르는 기준

1. 관측 비용에서 실제로 제거 가능한 부분과 빈도를 확인한다. 근거 없는 절감 수치는 만들지 않는다.
2. 예상 실제 비용 절감을 우선하고 비슷하면 구현·검증 작업량이 작은 쪽을 고른다.
3. 기존 동작·출력·소유권·권위 계약을 보존할 방법과 위험을 함께 제시한다.
4. 실제 프로젝트 진도에 맞는 예상 작업량과 완료/중단 기준을 정하고 구체안을 공유한다.

공간 후보의 구체 구현 파일/알고리즘·규칙 근거·검증 대응은 다음 국소 설계 결과로 정한다. 완료 구현·추가 후보·단순 조사 분야는 [Research2절](Research.md#2-완료추가-후보조사-분야의-구분)처럼 구분하며, 분야 전체를 미완 작업으로 세지 않는다. 기존 로직 변경이 필요하면 검증 전에는 주석 비활성화 보존 원칙을 적용하고, 완료한 최적화는 반복 구현하지 않는다.

## 3. 범위와 종료 기준 준비

기존 완료 목록과 이동 잔여 범위는 [Research2절](Research.md#2-완료추가-후보조사-분야의-구분)을 따른다. 기존 이동 교정을 이번 후보로 다시 선정하지 않는다. 조사 단계는 후보별 근거·감소 가능 작업·대략 작업량·검증 부담을 비교하고 하나의 실행안 또는 근거 부족 보류 결론을 내리면 마감한다. 구현 완료·성능 PASS는 별도 실제 검증 전 선언하지 않는다.

후보 비교와 조사 단계 완료·중단 기준은 아래와 같으며 구체 구현은 공유 후 사용자 승인을 받아야 한다. 새 Testcase·메모리·Git 작업은 하지 않는다.

## 4. 첫 제안: 공간 후보 제한의 국소 실현 가능성 검증

비용 우선 기준에서 가장 큰 잠재 반복 구조인 최근접/Detect 전수 탐색부터 검토한다. 이것은 구현 승인이 아니라 후보 누락 없이 같은 결과를 낼 수 있는지 확인하는 설계 검증이다. 실제 K분포·발생 빈도·ms/FPS가 없으므로 최대 절감률을 가정하지 않는다. 밀집/장거리 검색은 전체 후보와 같아져 효과0일 수 있다.

예상 범위는 핵심3~4파일과 아래3단계다. 시간이 검증되지 않았으므로 몇 시간/며칠 같은 견적 대신 중간 규모의 포함 범위·순서·수명 검증 부담으로 설명한다.

1. 보수적 포함 bound: 실제 Root/논리 tile·terminal contact·건물 반경/후보 소유권과 순서를 읽고, 모든 기존 유효 target이 포함되는 범위를 설계한다. 기존 logical index/첫 유닛 조회를 그대로 사용하지 않는다.
2. 실제 소스 동일 입력 비교: 기존 private 하네스를 재사용해 target·동률·존재 여부·범위 결과를 비교하고 후보 검사 수를 확인한다. 새 측정 framework를 만들지 않는다.
3. 수명·SDK: spawn/death·이동/index 갱신·동기 재진입·역할/초기화 계약과 현재 source의 SDK 컴파일 범위를 확인한다. 제품 적용은 구체안 공유·승인 뒤 별도 단계다.

완료 기준은 동일 target/동률/범위 결과, 같은 입력 상태에서 후보 검사 감소를 입증한 자료, 실제 source와 검증 연결이다. 이것을 전체 FPS PASS로 바꾸지 않는다. 보수적 포함·순서 보존을 증명할 수 없거나 일반 입력에서 검사 감소가 없으면 중단/보류한다. 큰 공간 인덱스·새 계측 틀·이동 규칙 수정이 필요하면 조용히 확장하지 않고 사용자에게 범위 판단을 다시 보고한다.

힐러 bool early-exit와 AI count 병합은 후순위 대안으로 남긴다. 두 후보도 기존 target/힐/AI 의사결정 출력 보존이 전제이며 조사에서 작업이 작다는 이유만으로 먼저 구현하지 않는다. 현재 작업별 재감사·후보 비교와 계획 제안을 마쳤고, 공간 후보 제한의 구체 설계·승인은 다음 단계다. 이후 사용자 요청으로 물리·발열까지 읽기 조사 범위를 확장했고 추가 후보11개와 산정 불가 범위를 Research5절에 기록했다. 제품/새 테스트/빌드/Git 변경0이다.

## 5. 확장 조사 결과의 다음 판단

[Research5절](Research.md#5-물리발열을-포함한-확장-비용-조사--2026-11-24)의11개 후보는 앞3개를 포함한 현재 후보 목록이다. 완료25개를 다시 구현하거나 넓은 분야를 미완 개수로 더하지 않는다. 숨겨진 preview camera gate는 작은 범위의 불필요 GPU 반복 제거 후보, 전투 공간 후보 제한은 큰 잠재 규모와 높은 안전 검증 부담이 있는 후보로 병기한다. 절대 절감 ms/FPS 순위는 미확정이며 이 확장 조사는 구현 승인이 아니다.

구현 전에는 활성 조건/빈도·0효과 조건·소유권/재진입/참조 교체·동일 출력 검증을 구체안으로 공유한다. 타일 collider는 외부 참조·기존 입력 계약 확인 전 삭제하지 않는다. 화질·FPS 저하 선택이나 열 정책을 임의 도입하지 않으며, 열/전력 절감은 연속 실측 없이 수치화하지 않는다. 현재는 읽기 조사·문서 정리만 완료했고 제품·새 테스트·빌드·Git 변경0이다.
