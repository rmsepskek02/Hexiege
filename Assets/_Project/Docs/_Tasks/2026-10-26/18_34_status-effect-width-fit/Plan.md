# Plan — 상태 이펙트(화상) 몸통 폭 맞춤

## 이 문서는 무엇인가

곰전사·탱크·대포수레처럼 몸이 넓은 유닛에 붙는 화상 불꽃이 잘 보이지 않는 문제를 고치는 계획이다. 사용자가 고른 방향(안 1)대로, **불꽃 한 장의 크기는 지금처럼 키에 맞추고, 불꽃이 피어오르는 범위를 몸통 폭만큼 넓히고, 몸이 넓을수록 불꽃 개수를 늘린다.** 몸이 좁은 유닛은 계산상 불꽃 1장이 되어 지금과 똑같이 보인다.

화면 표현만 바뀌고 피해량·지속시간·서버 판정·멀티플레이 동기화는 바뀌지 않는다. 독·힐은 이번에 **지금 동작을 그대로** 두고, 나중에 프리셋에서 켤 수 있는 구조를 어디까지 넣을지는 사용자 결정 항목(D1)이다.

현재 구조·수치·대안 비교는 [Research.md](Research.md)에 있다. **구현은 이 Plan을 사용자가 승인한 뒤에만 시작한다**(WORKFLOW [4]).

**후속 단계(2026-10-26 추가) — 불꽃을 몸 앞에 그리기.** 폭 맞춤 뒤 실기에서 곰전사 불꽃이 2장으로 나왔지만 "몸 안에 가려져 잘 안 보인다"는 사용자 확인이 있었다. 불꽃이 몸 한가운데에 그려져 몸 앞부분에 덮이기 때문이다. 그래서 불꽃을 **카메라 쪽으로 몸 두께만큼 당겨** 몸 앞에 그려지게 한다. 이 게임 카메라는 원근이 없는 직교 카메라라서, 당겨도 화면에서 불꽃의 위치·크기·모양은 그대로이고 "몸 앞에 보이는지"만 바뀐다. 이번에도 화상만 켜고, 독·힐은 같은 옵션 구조만 두고 꺼 둔다. 계획은 [8절](#8-d7-후속-상태-이펙트를-몸-앞에-그리기가려짐-해소), 조사는 [Research 9·10절](Research.md#10-d7-후속-상태-이펙트를-몸-앞에-그리기가려짐-해소).

**다음 단계(2026-10-26 22:21 실기 뒤 추가) — 새 화상 이펙트(v2)로 교체.** 몸 앞에 그리기까지 넣은 뒤 실기에서, 사용자는 화상이 "타오르는 불"이 아니라 "물건이 붙어 있는" 것처럼 보이고 "좌우로 빠르게 튄다"고 했다. 지금 화상은 큰 불꽃 그림 한 장이 움직임 없이 서 있는 구조라 코드 조정으로는 한계가 있다고 보고, 사용자는 **화상 이펙트를 새로 만들기로** 했다(작은 불꽃 여러 개가 몸 둘레에서 일렁이며 올라가는 모양). 새 이펙트는 이미 만들어졌고, 이 단계는 그것을 **화상에 연결**한다. 새 이펙트가 스스로 몸 둘레에서 불꽃을 내므로 앞 단계의 "폭 맞춤"과 "몸 앞으로 당기기"는 화상에서 **끈다.** 코드는 지우지 않고 옵션으로 남기며, 기존 화상 이펙트 파일도 되돌리기용으로 남긴다. 이번에도 화상만 바꾸고 독·힐은 그대로다. 계획은 [9절](#9-새-화상-vfx-v2-교체연결), 조사는 [Research 11절](Research.md#11-새-화상-vfx-v2-교체연결-plan-9절).

**다음 단계(2026-10-27 00:40 실기 뒤 추가) — 뒤집힌 Client에서 이펙트가 회전 중 옆으로 튀는 문제 고치기.** v2 연결(9절, 커밋 `5dd22db7`) 뒤 멀티 실기에서 사용자는 "화상이 어느 정도 만들어졌는데, 유닛 범위를 벗어나 잠깐씩 빠르게 옆으로 튄다"고 했다. 코드를 읽어 찾은 유력한 원인(확정 아님)은, 화면이 뒤집혀 보이는 Client에서 유닛의 "보이는 몸"이 실제 위치와 맵 반대편에 따로 그려지는데, 유닛이 **방향을 트는 프레임**에 화상 이펙트가 그 보이는 몸 위치가 **바로잡히기 전** 값을 읽어 1~2 m 옆으로 따라가는 것이다. 그래서 이펙트가 **따라가기 직전에 보이는 몸 위치를 먼저 바로잡게** 한다. Host·싱글은 결과가 바뀌지 않는다. 화상과 같은 코드를 쓰는 독도 함께 고쳐지며, 같은 구조인 힐은 사용자가 "문제 없었던 것 같다"고 해 이번에는 빼고 작업 뒤 따로 확인한다. 계획은 [10절](#10-뒤집힌-client에서-상태-이펙트가-회전-중-옆으로-튐--따라가기-직전-위치-바로잡기), 조사는 [Research 12절](Research.md#12-뒤집힌-client에서-상태-이펙트가-회전-중-옆으로-튐-plan-10절).

**완료(2026-10-27 04:15 실기 뒤 추가) — 사용자 테스트 PASS.** 튐 수정(10절, 커밋 `ec621589`) 뒤 멀티 실기에서 사용자는 「특별히 문제 발견되지 않음」이라고 했고, 로그로도 뒤집힌 Client에서만 바로잡기가 일어났다(Research 13절). 회귀 스위트는 사용자가 문제를 말하지 않아 PASS로 본다(2026-10-27 사용자 결정 — WORKFLOW 「[6] 사용자 테스트」). 힐은 육안 문제가 없어 같은 수정을 넣지 않는다. 사용자 지시 「작업 완료됐으니 메인에 병합」에 따라 `origin/main`에 병합됐다(`0a47f37f`). 「세 이펙트가 아주 눈에 띄지는 않는다」는 의견은 후속 작업 「지속 효과 이펙트 가시성 강화」로 ROADMAP에 남겼다. 완료 처리는 [10-10절](#10-10-실기-결과와-완료-처리-2026-10-27).

> **기존 로직 제거: 없음.** 이 계획은 기존 크기 계산(프리팹 원본 × 프리셋 배율 × 키 기반 맞춤 배율)과 프리팹 모양을 그대로 두고, 그 위에 "방출 범위·개수 맞춤"을 프리셋 옵션으로 **덧붙인다.** 지우거나 주석 처리하는 기존 코드는 없다.
>
> **8절 후속 단계도 기존 로직 제거: 없음.** 기존 위치 계산(대상 pose + 대상 회전 × 위치 보정)은 그대로 두고, 그 결과에 "카메라 쪽 당김"을 프리셋 옵션(기본 0 = 꺼짐)으로 **더하기만** 한다. 재질·셰이더·프리팹은 바꾸지 않는다.
>
> **9절 v2 교체도 기존 로직 제거: 없음 — 비활성화만 한다.** 폭 맞춤(1~3절)·카메라 쪽 당김(8절) 코드는 지우지 않고, 화상 프리셋에서 값만 끈다(폭 맞춤 0·당김 비율 0). 근거: v2 프리팹은 스스로 몸 둘레에서 방출하므로 폭 맞춤이 그 방출 모양을 덮어쓰면 구조가 깨지고 입자가 최대 3배가 되며, 당김은 뒤쪽 불꽃이 몸에 가려져 생기는 "감싸는" 입체감을 없앤다(Research 11-5). 기존 화상 프리팹 `vfx_infernospirit_burn.prefab`도 롤백용으로 **보존**한다(사용자 승인 — 7절).
>
> **10절 튐 수정도 기존 로직 제거: 없음.** 기존 따라가기 계산(`FollowTimedDamage`의 위치 식)은 그대로 두고, 그 호출 **직전에** 보이는 몸 위치 바로잡기(`ProjectNow()`) 한 번을 **더한다.** `VisualRootProjector`의 정기 바로잡기(`LateUpdate`)도 그대로 둔다.

## 3. 단계별 구현 항목 (담당: game-programmer)

파일 경로는 모두 `Assets/_Project/` 기준. 필드·변수 이름은 game-programmer가 정한다(아래 이름은 설명용).

### 3-1. 몸통 반경을 재생 코드까지 전달 — `Scripts/Presentation/Effects/UnitEffectConfig.cs`

- `RecipientFit`에 몸통 반경 값을 추가한다. 기본값(Identity)은 0 = "반경 모름 → 폭 맞춤 안 함".
- `TryGetRecipientFit`이 표의 `radius`를 채운다. 0 이하·NaN·무한대면 0.
- 기존 생성자(배율, 발밑 보정)는 그대로 쓸 수 있게 둔다(자체 검증 fixture가 사용 중 `[사실]`).
- `radius` Tooltip과 `RecipientReferenceRadius` 주석의 "배율 계산에 쓰지 않음·참고용"을 사실에 맞게 고친다(배율에는 여전히 안 쓰지만 방출 범위에 쓰임).
- 근거: 2절 "균등 배율 유지"(배율 계산은 바꾸지 않음).

### 3-2. 프리셋 옵션 — `Scripts/Presentation/Effects/EffectPreset.cs`

- **폭 맞춤 켜기**(기본 꺼짐) · **최대 개수**(기본 = D2 결정값) 두 칸을 추가한다.
- 기본이 꺼짐이므로 기존 프리셋 전부(독·힐 포함)는 값을 넣지 않아도 지금과 같다.
- 근거: D1 · 2절 규칙 34(독·힐 기존 동작 보존).

### 3-3. 재생 시 범위·개수 설정 — `Scripts/Presentation/Effects/VfxPoolItem.TimedDamage.cs` (D1 (a)면 `VfxPoolItem.cs`의 힐 재생도)

1. 각 파티클 시스템의 **원본 값**(방출 모양 켜짐·모양 반경·초당 개수·최대 입자 수)을 처음 한 번 저장한다(지금 `_originalLocalScale`을 처음 한 번 저장하는 것과 같은 방식).
2. 재생 시작마다 **먼저 원본 값으로 되돌린 뒤** 아래를 적용한다.
3. 프리셋 옵션이 켜져 있고 몸통 반경이 0보다 크면 1절 공식으로 N과 R을 계산한다. **N이 1이면 아무것도 바꾸지 않는다.**
4. N이 2 이상이면 **방출이 켜진 시스템**에만 적용한다 — 방출 모양을 원(Circle)으로 켜고 반경 = R ÷ (그 오브젝트에 걸린 배율), 초당 개수 ×N, 최대 입자 ×N. 화상은 해당 시스템이 `Flame_Haze` 하나다 `[사실]`.
   - 반경을 배율로 나누는 이유: Scaling Mode Hierarchy라 모양 반경도 배율에 곱해진다(Research 2-4).
   - `Flame_Haze`의 원래 모양 설정(Circle·X축 −90°)은 수평 원판이라 그대로 쓴다. 원래 `radiusThickness` 0.5(원판 바깥쪽 절반에서만 방출)를 유지할지 1(원판 전체)로 할지는 육안 확인 후 정한다 `[제안: 1]`.
   - 독·힐처럼 오라 레이어가 섞인 프리팹에 나중에 켤 때 "방출이 켜진 시스템 전부"가 맞는지는 그때 다시 정한다(Research 6-1). 이번에는 화상만 켜므로 영향 없음.
5. 재생 기록 줄에 N과 R을 덧붙인다(예: 기존 `FitScale=` 옆). 로그로 "곰 2장·탱크 3장"을 확인할 수 있게 한다.
6. 같은 대상 갱신(`RefreshTimedDamage`)은 아무것도 다시 계산하지 않는다(지금과 같음).

- 근거: 2절 규칙 34·40(재생 시작 때 1번, burst 미변경), VFXSFXGuide 2번(시작 속도 0 유지).

### 3-4. 풀 반환 시 원복 — 같은 두 파일

- 자연 반환(`Return`), 재생 실패 거부(`RejectTimedDamageAcquire`), 강제 정리(`OnDisable`) 세 경로 모두 원본 값으로 되돌린다.
- 3-3의 "재생 시작마다 먼저 원본으로" 덕분에 한 경로에서 원복이 빠져도 다음 재생은 깨끗하게 시작한다(이중 안전장치).
- 근거: Research 2-5·6-4(풀은 프리팹 단위로 다른 유닛에 재사용).

### 3-5. 화상 프리셋에서 켜기 — `Resources/Config/EffectPresets/EffectPreset_InfernoSpirit_Burn.asset`

- 폭 맞춤 켜기 ON, 최대 개수 = D2.
- D5 (b)를 고르면 이 단계에 프리팹 `Prefabs/VFX/Units/vfx_infernospirit_burn.prefab` 수정이 추가된다.
- Inspector 작업이 필요하면 WORKFLOW [5-2] — 1회성 에디터 스크립트 또는 사용자 Inspector 작업 — 를 따른다. 에셋 YAML을 직접 고칠지 Inspector로 할지는 game-programmer가 제안한다.

### 3-6. 자체 검증 추가 (D6) — `Assets/Editor/Tools/Combat/RunUnitActionSelfValidation.VfxConnections.cs`

`ValidateDamageParticles` 계열에 다음을 확인하는 항목을 추가한다.

- 폭 맞춤이 켜진 화상 프리셋 + 넓은 대상(반경이 커서 N ≥ 2) → 대상 시스템의 모양 반경·초당 개수·최대 입자가 공식대로 설정되고, N이 상한을 넘지 않는다.
- 같은 프리셋 + 좁은 대상(N = 1) 또는 반경 0(Identity) → 모든 값이 원본 그대로.
- 옵션이 꺼진 독 프리셋 → 넓은 대상이어도 원본 그대로.
- 자연 반환 뒤, 그리고 넓은 대상 → 좁은 대상 순서로 같은 아이템을 재사용했을 때 → 원본 값 복원.
- 기존 항목(크기·위치·갱신 유지·반환 시 크기 복원)은 그대로 통과해야 한다. 기존 fixture가 입자를 강제로 1개 내보내고(`Emit(1)`) 시뮬레이션으로 비우는 단계는 최대 입자 수가 늘어도 영향이 없을 것으로 본다 `[추정 — 실행으로 확인]`.
- 도구 존재·정적 검사는 실제 메뉴 실행 PASS가 아니다(WORKFLOW [5-2]). 사용자 메뉴 실행 결과로만 통과를 기록한다.

### 3-7. 하지 않는 것

- 불꽃 한 장의 크기·모양·색·높이 변경(D-3 유지).
- 독·힐 프리셋 옵션 켜기.
- 가려짐 대응(카메라 쪽 당기기·렌더 정렬) — D7. *(2026-10-26: 후속 단계로 착수 — 8절)*

## 8. D7 후속: 상태 이펙트를 몸 앞에 그리기(가려짐 해소)

### 8-1. 무엇을 왜 하는가

폭 맞춤으로 곰전사 불꽃은 계산대로 2장이 되어 몸 폭을 꽉 채웠다. 그런데 불꽃은 몸 **한가운데**에 세워진 얇은 판처럼 그려지고, 유닛 몸은 불투명해서 카메라 쪽에 있는 몸 앞부분이 불꽃의 아래·가운데 대부분을 덮는다(Research 10-1·10-5). 사용자는 이것을 "몸 안에 가려져서 안 보인다"고 확인했다.

그래서 불꽃을 **카메라 쪽으로 몸 두께만큼 당긴다.** 이 게임의 카메라는 원근이 없는 직교 카메라(55° 기울기)라서, 카메라 쪽으로 물체를 옮기면 화면에서의 위치·크기·모양은 전혀 바뀌지 않고 **무엇의 앞에 그려지는지만** 바뀐다(Research 10-2). 즉 사용자가 보는 불꽃 모양은 그대로이고, 몸에 덮이던 부분만 몸 앞에 드러난다.

이번에도 **화면 표현만** 바뀐다. 피해·지속시간·서버 판정·멀티 동기화는 바뀌지 않는다. 재질·셰이더·프리팹도 바꾸지 않는다. 폭 맞춤(D1)과 같은 방식으로 **화상만 켜고**, 독·힐은 같은 옵션 구조만 두고 꺼 둔다.

**표기:** 1절과 같다. `[구현 시 확인]` = 문서 담당이 확정하지 못해 game-programmer가 구현하면서 확인할 것.

4. **카메라 쪽 방향을 얻는 방법** `[구현 시 확인]`

   - 어디서 카메라를 얻을지(`Camera.main`을 재생 시작 때 읽기 / `EffectManager`가 넘겨주기 등)는 game-programmer가 정한다. 에디터 자체 검증에서 카메라가 없을 수 있으므로, 카메라를 구하지 못하면 당김 0으로 두고 예외를 내지 않는다. 검사가 시험용 방향을 넣을 수 있는 통로가 필요한지도 함께 정한다.
   - 주석에 전제를 적는다: "직교 카메라라서 화면 위치가 안 바뀐다. 원근 카메라로 바뀌면 당김이 화면 위치를 조금 바꾼다", "기본 비율 1.75는 기울기 55°에서 나온 값(1 ÷ cos 55°)이다" — CLAUDE.md 규칙 8(초급자도 이해하는 주석).

5. **화상 프리셋에서 켜기** — `Resources/Config/EffectPresets/EffectPreset_InfernoSpirit_Burn.asset`
   - 카메라 쪽 당김 비율 = **1.75**(D7-2). 프리팹 `vfx_infernospirit_burn.prefab`과 재질 `Mat_VFX_Flame.mat`은 수정하지 않는다.
   - Inspector 작업이 필요하면 WORKFLOW [5-2](1회성 에디터 스크립트 또는 사용자 Inspector 작업)를 따른다. YAML 직접 수정 여부는 game-programmer가 제안한다.

6. **자체 검증 추가 (D7-4)** — `Assets/Editor/Tools/Combat/RunUnitActionSelfValidation.VfxConnections.cs`
   - 비율 0(독 프리셋) + 반경이 있는 맞춤 → 위치가 지금 공식 그대로.
   - 비율 > 0(화상) + 반경 r + 시험용 직교 카메라(55°) → 위치 = 지금 공식 + 카메라 쪽 방향 × 비율 × r. 그리고 **카메라 화면 기준 좌표(오른쪽·위쪽 성분)가 당기기 전과 같다.**
   - 같은 대상 갱신·따라붙기 뒤에도 당김이 유지되고, 대상 pose 회전을 바꿔도 당김 방향이 바뀌지 않는다.
   - 반경 0인 기존 fixture(801~808행 「Timed damage recipient fit applies uniform scale and foot offset at Play.」)는 값이 바뀌지 않고 그대로 통과해야 한다 `[계산 — 실행으로 확인]`.
   - 넓은 대상 → 반경 0 대상 순서로 같은 아이템을 재사용하면 당김이 0으로 돌아온다.
   - 카메라가 없을 때 당김 0, 예외 없음.
   - 도구 존재·정적 검사는 실제 메뉴 실행 PASS가 아니다(WORKFLOW [5-2]). 사용자 메뉴 실행 결과로만 통과를 기록한다.

## 9. 새 화상 VFX v2 교체·연결

### 9-1. 무엇을 왜 하는가

8절까지 넣은 뒤 22:21 실기에서, 로그로는 곰전사 불꽃이 계산대로 2장·몸 앞으로 당겨져 나왔다(Research 11-1). 그러나 사용자는 "타오르는 느낌보다 물건이 붙어 있는 느낌", "좌우로 빠르게 튄다", "더 키워 몸을 감싸는 느낌"을 원한다고 했다. 기존 화상은 큰 불꽃 그림 한 장이 움직임 없이 서 있는 구조라, 폭 맞춤으로 그 큰 그림이 원판 안 무작위 위치에 번갈아 생기면 튀어 보이고, 코드 조정으로는 "타오르는" 모습을 만들기 어렵다고 본다(Research 11-2 `[추정]`).

그래서 사용자는 화상 이펙트를 **새로 만들었다(v2)** — 작은 불꽃 혀 여러 개가 몸 둘레 원 가장자리에서 일렁이며 올라가고, 불씨·발밑 빛·옅은 연기가 함께 나오는 모양이다(Research 11-4). 이 단계는 v2를 **화상 프리셋에 연결**하고, v2와 맞지 않는 앞 단계 옵션(폭 맞춤·카메라 쪽 당김)을 **화상에서 끈다.** 코드와 기존 프리팹은 지우지 않는다.

이번에도 **화면 표현만** 바뀐다. 피해·지속시간·서버 판정·멀티 동기화는 바뀌지 않는다. 독·힐은 그대로다.

## 10. 뒤집힌 Client에서 상태 이펙트가 회전 중 옆으로 튐 — 따라가기 직전 위치 바로잡기

### 10-1. 무엇을 왜 하는가

v2 연결 뒤 00:40 멀티 실기에서, 로그로는 v2가 Host·Client 모두에서 쓰였고(`RecursivePS=5`) 폭 맞춤·당김은 꺼져 있었으며 오류도 없었다(Research 12-2). 그러나 사용자는 화상이 "유닛 범위를 벗어나 잠깐씩 빠르게 옆으로 튄다"고 했다.

game-programmer의 읽기 전용 진단으로 찾은 유력한 원인은 이렇다(Research 12-4 — **추정, 확정 아님**). 멀티에서 화면이 뒤집혀 보이는 Client는 유닛의 **보이는 몸**(VisualRoot)을 실제 위치와 맵 중심 반대편에 그린다. 보이는 몸은 실제 위치 오브젝트의 자식이라, 실제 위치 쪽이 그 프레임에 돌면 보이는 몸도 함께 돌아 **바로잡기 전까지 틀린 자리**에 있다. 바로잡기(`VisualRootProjector`)와 화상 이펙트의 따라가기(`TimedDamageEffectPresenter`)는 실행 순서가 정해져 있지 않아서, 따라가기가 먼저 돌면 이펙트가 그 틀린 자리로 간다. 실제·화면 위치가 13.7 m 떨어진 유닛이 초당 270°로 돌면 한 프레임에 1~2 m 옆이다 — 몸 폭의 몇 배다.

그래서 **따라가기 직전에 그 유닛의 보이는 몸 위치를 먼저 바로잡는다.** 바로잡기는 같은 입력에 같은 결과를 내므로(멱등) 한 프레임에 여러 번 해도 문제가 없고, 화면이 뒤집히지 않는 Host·싱글에서는 원래부터 실제 위치와 같아 결과가 바뀌지 않는다. 화상과 독은 같은 코드를 쓰므로 함께 고쳐진다. 같은 구조인 힐은 이번에 넣지 않는다.

이번에도 **화면 표현만** 바뀐다. 피해·지속시간·서버 판정·멀티 동기화·프리팹·프리셋은 바뀌지 않는다.

**표기:** 1절과 같다. `[구현 시 결정]` = 사용자가 game-programmer에게 맡긴 선택.

### 10-4. 단계별 구현 항목 (담당: game-programmer)

파일 경로는 `Assets/_Project/` 기준.

1. **따라가기 직전 바로잡기** — `Scripts/Presentation/Effects/TimedDamageEffectPresenter.cs`
   - `LateUpdate`의 `owner.Item.FollowTimedDamage(owner.Lease, owner.Pose)`(114행 `[사실]`) **직전에** 그 유닛의 `VisualRootProjector.ProjectNow()`가 실행되게 한다. 방법은 J4 `[구현 시 결정]`.

   - projector가 없는 경우(Visual Root 없는 유닛·사망 대역으로 떼어진 뒤 등)에는 지금과 같이 저장된 Transform을 그대로 쓴다. `ProjectNow()`는 `_visualRoot`가 없으면 아무것도 하지 않는다(`VisualRootProjector.cs` 88~89 `[사실]`).
