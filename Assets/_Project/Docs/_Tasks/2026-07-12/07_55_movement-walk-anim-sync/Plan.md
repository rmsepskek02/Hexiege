## 이 계획은 무엇을 하려는가 (비개발자용 설명)

Research에서 확인했듯, 지금 게임은 걷기·공격 같은 애니메이션 상태를 **"바뀌는 순간 한 번 쏘는 신호"** 로만 상대 화면에 전달합니다. 이 방식은 신호가 도착하는 순간 유닛이 아직 준비되지 않았으면 신호를 놓치고, 그 뒤로는 바로잡을 방법이 없다는 약점이 있습니다. 갓 생산된 유닛에서 걷기 모션이 안 나오는 문제가 여기서 나옵니다.

이 계획은 세 단계로 진행합니다.

- **1단계(계측):** 먼저 코드에 임시 기록 장치를 넣어, 신호가 실제로 어디서·왜 유실되는지, 그리고 "뒤로 밀림"이 어느 화면에서 왜 생기는지 **숫자로 확인**합니다. 추측이 아니라 근거를 확보하는 단계입니다.
- **2단계(근본 수정):** 애니메이션 상태를 "신호 한 번"이 아니라 **"현재 상태 값 그 자체"** 로 공유하도록 바꿉니다. 값을 공유하면 유닛이 늦게 준비되어도 준비되는 순간 서버의 현재 값을 자동으로 받아 올바른 애니메이션을 재생하므로, 신호를 놓칠 수가 없습니다. 이 구조는 걷기 미재생과 잔여 지연(2.7%)을 함께 없앨 것으로 기대합니다.
- **3단계(이동 보정):** 1단계에서 "뒤로 밀림"의 원인이 확정되면, 이동 재개 출발점을 바로잡습니다. 이 단계는 계측 결과에 따라 내용을 확정하는 조건부 단계입니다.

각 단계는 만들어 놓고 검증하기 전까지 **기존 코드를 지우지 않고 "비활성화(주석 처리)"** 로 남겨, 문제가 생기면 즉시 되돌릴 수 있게 합니다.

## Phase 2 — 애니메이션 상태 레벨 동기화 (근본 수정, 사용자 승인 방향 B)

**핵심:** 유닛 애니메이션 상태를 서버가 쓰는 **NetworkVariable**로 단일화한다. 클라이언트는 값 변경(`OnValueChanged`) + **스폰 시 현재 값 자동 수신**으로 적용한다. → 스폰 레이스 구조적 소멸, 신호 유실 불가능.

### 2-1. 상태 값 정의 (Infrastructure — NetworkUnit)
- `NetworkUnit`에 애니메이션 상태용 NetworkVariable 추가(예: `NetworkVariable<UnitAnimState>` 또는 byte 인코딩). 상태 열거: 최소 `Walk`, `Attack`. (사망은 기존 `IsDead` bool + Despawn 경로 유지, 이번 범위 밖.)
- 권한: `_unitId`와 동일하게 ReadPermission=Everyone / WritePermission=Server (NetworkUnit.cs 67~71줄 패턴 재사용).
- 레이어 준수: NetworkVariable 선언·서버 쓰기는 **Infrastructure(NetworkUnit)** 에 둔다(NGO 허용 위치). Animator 적용은 **Presentation(UnitView)**.

### 2-2. 서버 쓰기 지점
- 서버가 상태를 바꾸는 실제 지점에서 NetworkVariable 값을 갱신:
  - `MoveAlongPathV3` Walk 진입 시 → `Walk`
  - 전투 진입(`OnUnitEnteredCombatHandler` / 공격 시작) 시 → `Attack`
  - 전투 종료 후 이동 재개 시 → `Walk`
- 서버(호스트)는 기존처럼 로컬에서 Animator를 직접 제어하므로, 값 쓰기가 호스트 자신에게 중복 적용되지 않도록 한다(기존 `StartWalkAnimationClientRpc`의 `if (IsServer) return` 취지 계승).

### 2-3. 클라이언트 적용 지점 (레이어 연결)
- 클라이언트는 `OnValueChanged`로 상태 변화를 받고, **스폰 시(`OnNetworkSpawn` 또는 구독 완료 시) 현재 값**을 읽어 즉시 적용한다(`_unitId` 등록 패턴과 동일한 자동 수신).
- **Infrastructure→Presentation 연결 방식은 기존 관례를 확인해 결정한다.** 두 후보:
  - (a) 기존 패턴 유지 — NetworkUnit이 상태 변화를 `GameEvents`로 발행하고 UnitView가 구독(현행 RPC→GameEvents→UnitView 흐름과 일관). 단, 이 경우도 **값 기반**이라 스폰 시 현재 값 재적용이 가능해 유실이 없다.
  - (b) NetworkUnit이 같은 GameObject의 `IUnitView`(또는 UnitView)를 `GetComponent`로 잡아 직접 호출(NetworkUnit이 이미 `GetComponent<UnitView>()`를 OnNetworkDespawn에서 사용 중 — NetworkUnit.cs 179줄).
  - → **결정은 구현 착수 시 game-programmer가 기존 코드 관례(레이어 규칙: Presentation은 Unity.Netcode 직접 참조 금지, NetworkContext만 사용)를 재확인한 뒤 확정**한다. 어느 쪽이든 "값 기반 + 스폰 시 현재 값 적용"이 핵심 요건이다.

### 2-4. 애니메이션과 분리 유지할 것 (제거 대상 아님)
- **조준 회전(타겟 추적):** `StartCombatAnimation`/`ChangeTarget`이 저장하는 `_combatTargetTransform`·`_combatTargetId`와 `Update()`의 매 프레임 회전(UnitView.cs 266~303줄)은 **애니메이션 상태가 아니라 조준 로직**이다. 타겟 Id 전달 경로는 유지한다(레벨 상태값에는 타겟 회전 정보를 싣지 않는다). 규칙 12·15(전투/공격 중 타겟 방향 회전) 준수.
- **데미지 판정:** 서버 권위 `TickCombat`과 무관하게 유지(규칙 18). 애니메이션 상태값에 데미지를 종속시키지 않는다.
- **피격 표현 큐:** 선행 태스크 규칙 19의 큐 방출(공격자 로컬 `OnAttackHit`)은 유지한다. 레벨 동기화로 클라이언트 Attack 루프가 안정화되면 규칙 19의 타격 프레임 방출이 정상 작동해 **잔여 타임아웃 2.7%(증상 4) 소멸이 기대**된다.

### 2-5. 기존 엣지 로직 비활성화
- 위 "제거(비활성화) 대상" 표의 A·B·C·D를 주석 처리한다. 삭제는 [6] 통과 후.

**기대 효과:** 증상 1(Walk 미재생) 소멸, 증상 4(잔여 타임아웃 2.7%) 소멸, 스폰 레이스로 인한 애니메이션 유실 불가능화.

**전제:** Phase 1 계측에서 "뒤로 밀림"의 원인(정렬 Lerp의 forwardTile이 현재 transform보다 뒤, 규칙 11 위반)이 실증되면 진행한다. 실증 결과에 따라 아래 후보 중 확정하고 **본 Plan을 갱신한 뒤** 구현한다.

**후보 A — 이동 재개 출발점 통일:**
- 재경로/이동 재개 시 출발점을 "도메인 타일(`_unitData.Position`)"이 아니라 **"현재 `transform` 기준 전방 타일"** 로 통일한다. 이미 존재하는 `FindForwardClosestTile`(UnitView.cs 947줄)을 재사용해, 정렬 목적지가 항상 진행 방향 앞쪽이 되도록 보장(규칙 11 강제).

**후보 B — 보간 설정 검토:**
- `NetworkTransform` 보간 파라미터가 짧은 정렬 이동에서 오버슈트/되감김을 만드는지 검토한다.

**표기:** 본 Phase는 **조건부**다. Phase 1 결과가 가설을 뒷받침하지 않으면(예: 뒤로 밀림이 클라이언트 보간 문제) 후보를 재선정한다.

## 검증 계획

**재현 시나리오:**
1. **갓 생산 + 즉시 전투**: 생산 랠리 지점 근처에 적을 배치해, 갓 생산된 유닛이 나오자마자 사거리 내 적을 만나도록 구성 → 증상 1 재현.
2. **밀집 교전**: 다수 유닛이 좁은 지역에서 타겟 전환을 빈번히 하도록 구성 → 증상 2·4 재현.
- 두 시나리오 모두 **에디터(Host) + 빌드(Client)** 구성으로 host/client 화면을 각각 확인한다.

**로그 판정 수렴 기준:**
- 유실 RPC(구독 전 수신) → **0** (레벨 동기화로 구조적 0).
- 역방향(뒤로) 이동 벡터 → **0**.
- 타임아웃 방출 → **0으로 수렴**(선행 2.7% 잔여 소멸).

**QA/Testcase:** 이번 태스크는 사용자 지시에 따라 **Research.md / Plan.md만 작성**한다. Testcase.md 및 QA 진행은 사용자가 명시적으로 지시하기 전까지 만들지 않는다(WORKFLOW [5-1]~[5-3] 준수).

## 위험 요소 / 아키텍처 제약

- **레이어 규칙:** NetworkVariable·NGO 참조는 Infrastructure(NetworkUnit)에만. Presentation(UnitView)은 `Unity.Netcode` 직접 참조 금지 — `NetworkContext` 정적 홀더만 사용(UnitView.cs 290줄 등 기존 관례). Phase 2-3의 연결 방식이 이 규칙을 위반하지 않도록 검토.
- **싱글플레이 회귀 방지:** 싱글플레이는 RPC 없이 로컬 Animator 제어 + `GameEvents.OnCombatStarted` 직접 구독 경로다. Phase 2 변경이 싱글플레이 경로를 건드리지 않도록 멀티플레이 분기 내에서만 구조를 바꾼다.
- **데미지/피격 큐 불변:** 서버 권위 데미지(규칙 18)와 피격 표현 큐(규칙 19)는 애니메이션 상태값과 분리 유지. 이번 작업은 **순수 시각/애니메이션 동기화**로 승패에 영향을 주지 않는다.
- **비활성화 우선:** A~D 제거 대상은 [6] 통과 전까지 주석 처리로만 남긴다(WORKFLOW 기존 로직 제거 규칙).
- **구현 위임:** 코드 구현은 game-programmer 에이전트, 계측/재현 검증은 필요 시 qa-tester에게 위임(CLAUDE.md 규칙 3). 이 문서는 계획 단계 산출물이며, **사용자 명시적 승인 후에만** 구현을 시작한다(WORKFLOW [4]).

### Phase 3 (위치 보정) — 조건부 → **확정**
- Research 6-2절 실증으로 **후보 A(이동 재개 출발점 통일)로 확정**한다. 역방향 이동 WARN 282건이 전부 서버 파일이고 그중 281건이 "새 경로 발급 직후 첫 타일 스텝"에서 발생했으며, 전투 종료 정렬 Lerp는 460건 전부 정방향(무죄)이었다. 따라서 가설이던 정렬 Lerp forwardTile 후위설은 기각되고, 원인은 **재경로 출발점 좌표계 불일치**로 확정됐다.
- **확정 수정 내용:** 재경로/이동 재시작 시 경로 출발점을 뒤처진 도메인 타일(`_unitData.Position`)이 아니라 **현재 `transform` 기준 전방 타일(`FindForwardClosestTile`)로 통일**한다. 후보 B(NetworkTransform 보간 파라미터 검토)는 클라이언트 WARN 0건으로 보간 무죄가 확정됐으므로 **철회**한다.
- **근거(규칙 11):** 재경로 첫 스텝이 목적지 역방향으로 향하는 것은 규칙 11("뒤쪽 타일로 복귀 금지, 현재 월드 위치 기준 앞쪽 타일") 위반이다. 본 수정은 규칙 11을 강제한다.
- **판정 지표:** "새 경로 발급 직후 첫 스텝 역방향" 281건이 판정 지표다. 수정 후 재계측에서 **0으로 수렴**하는 것이 목표.
