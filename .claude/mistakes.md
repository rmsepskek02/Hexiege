# AI 실수 기록

이 파일은 **AI가 이 프로젝트에서 실제로 저지른 실수를 누적해 두는 곳**이다.
같은 실수가 반복되는 것을 막는 것이 유일한 목적이며, 그 외의 용도(성과 기록·설계 논의)는 담지 않는다.

## 이 파일을 읽는 법

- **자동으로 주입되지 않는다.** 필요할 때 직접 열어야 한다.
- **전문을 읽지 않는다.** 아래 「목차」를 훑고, 이번 작업과 성격이 비슷한 항목만 본문에서 펼쳐 읽는다.
  목차는 한 건당 한 줄이라 100건이 쌓여도 100줄이다 — 훑는 비용이 작다.
- 「성격이 비슷하다」의 기준은 기술 분야가 아니라 **실수의 모양**이다.
  예: 숫자를 인계하는 작업이면 「인계 수치」 항목을, 정리·이관 작업이면 「소실」 항목을 본다.

## 이 파일에 적는 법

- **실수를 인지하면 바로 적는다.** 미루면 경위가 흐려지고, 흐려진 경위는 교훈을 못 만든다.
- **사건을 지우지 않는다.** 누적 기록이다. 나중에 사소해 보여도 남긴다.
- 교훈이 검사기·도구·규칙으로 승격되면 **그 사실을 항목에 덧붙이되 항목 자체는 남긴다.**
  도구는 되돌려질 수 있고, 그때 왜 그 도구가 생겼는지 아는 것은 이 기록뿐이다.
- 각 항목은 **무엇을 틀렸나 / 왜 그랬나 / 어떻게 드러났나 / 교훈** 네 칸으로 적는다.
- **교훈은 실행 가능한 행동으로 적는다.** "조심한다" · "유의한다" 는 아무것도 바꾸지 못한다.
  대신 "무엇을 · 언제 · 어떻게 확인하라"를 적는다.
- 목차 줄은 **`- YYYY-MM-DD  제목`** 형식으로 통일한다(목차만 뽑아 쓸 수 있어야 한다).
  기간에 걸친 사건은 **최초 발생일**을 목차 날짜로 쓰고, 전체 기간은 본문에 적는다.
- 항목은 **시간 오름차순**(오래된 것이 위)으로 쌓는다. 새 항목은 목차와 본문 **양쪽 맨 아래**에 덧붙인다.

## 2026-08-17  에이전트 메모리 -378행 소실 — 프롬프트에 하드코딩된 거짓 상태

**무엇을 틀렸나**
`game-programmer` 가 자기 `MEMORY.md` 를 갱신하라는 지시를 받고 `Edit` 이 아니라 `Write` 를 골라
파일을 통째로 다시 썼다. 커밋 `675203ae` 에서 **-450/+72 = -378행**.

**왜 그랬나**
`.claude/agents/*.md` 6개 전부에 `Your MEMORY.md is currently empty.` 라는 문장이 하드코딩돼 있었다.
파일은 실제로 **502행**이었지만 에이전트는 매 호출마다 "비어 있다"고 **믿은 채 시작**했고,
비어 있는 파일을 채우는 데는 `Write` 가 맞는 도구다.
**오작동이 아니라 지시대로 행동한 결과다** — 잘못은 에이전트가 아니라 프롬프트에 있었다.
같은 파일에 박혀 있던 **존재하지 않는 윈도우 절대경로** 때문에 기존 파일을 찾아 그 문장을 반증할 수도 없었다.

**어떻게 드러났나**
폴더 파일 수는 19 → 19 로 그대로인데 **폴더 총합 행수가 정확히 -378** 이었다 — 이동이 아니라 소실이라는 증거.
**3일간 발견되지 않았고, 발견도 우연이었다.**

**교훈**
- **프롬프트에 「현재 상태」를 사실로 못 박지 말고 「절차」로 적는다.**
  "비어 있다"(상태, 시간이 지나면 거짓이 됨)가 아니라 **"먼저 읽어서 확인하라"**(절차, 낡지 않음).
- 메모리 갱신은 **`Read` → `Edit`**. `Write` 로 파일 전체를 다시 쓰지 않는다.
- **이동인지 삭제인지는 폴더 총합 행수로 판정한다** — 옮겼다면 총합이 줄지 않는다.

**이후 조치**
`.claude/agents/*.md` 6개에서 두 줄을 모두 제거·교체했고, 규칙 원문은
`.claude/MEMORY.md` 「🔴 에이전트 메모리 갱신 규칙」 절에 두었다.
> ※ 근거 구분: 커밋 해시·증감 행수는 **당시 호출 세션이 측정한 값**이다(git 명령 금지 규칙 때문에 이 파일에서 재검증하지 않았다).
> 이 문서 작성 시점에 **직접 확인한 것**은 `.claude/agents/` 하위에 `currently empty` 문구가 남아 있지 않다는 사실뿐이다.

## 2026-09-27  🔴 로그에 흔적이 남지 않는 것(에디터의 Error Pause 설정)을 회차별로 단정했다

**무엇을 틀렸나**
같은 날의 실기 로그를 분석하면서 **「회차 A(20:57)는 Unity 의 Error Pause 가 켜져 있었고, 회차 B(21:16)는 껐다」고 단정해 문서 작업에 넘겼다.**
🔴 **그렇게 쓸 근거가 없다 — Error Pause 는 에디터 설정이라 런타임 로그에 아무 흔적도 남지 않는다.** 사용자가 지적해 **철회**했다.

**왜 그랬나**
- **바로 앞에서 얻은 결론이 맞았기 때문에 그 결론을 넓혀 버렸다.** *「강제 실패의 결말 줄이 `[ERROR]` 라 Error Pause 가 켜져 있으면 에디터가 멈춘다」* 는 **참이고 사용자 보고로 확인된 것**이다.
  그런데 거기서 **「그러므로 이 회차는 켜져 있었고 저 회차는 꺼져 있었다」로 한 발 더 나갔다** — 🔴 **앞은 기전이고 뒤는 각 회차의 설정값이다. 뒤쪽은 재지 않았다.**
- **로그가 두 회차에서 다르게 보인 것을 설정 차이로 설명했다.** 회차 A 는 67.3초가 지났는데 만료 로그가 없고, 회차 B 는 60.25초에 정상 만료했다.
  🔴 **「다르게 보인다」에서 「원인이 이것이다」로 가는 사이에 확인 단계가 없었다.**
- 🔴 **같은 날 위 항목과 원인이 정반대다.** 그쪽은 **환경을 용의자 목록에서 빼놓아** 코드를 의심했고, 이쪽은 **환경을 근거 없이 단정했다.**
  즉 **「환경을 다룰 때의 근거 기준」이 양방향으로 흔들렸다.**

**어떻게 드러났나**
사용자 지적. 그리고 문서 작업 중 로그를 다시 읽어 **그 두 회차 사이에 플레이 세션 경계(`[Bootstrap/LoginBootstrapper]`)가 있다는 것까지는 확인됐지만
「설정을 바꿨다」는 기록은 어디에도 없다**는 것이 확인됐다 — **바꿀 기회가 있었다는 사실은 바꿨다는 증거가 아니다.**

**교훈**
- 🔴 **테스트 환경에 대해 무엇을 주장하기 전에 「그것이 로그에 남는가」를 먼저 묻는다.** 남지 않으면 **주장하지 않고 사용자에게 묻는다**(`CLAUDE.md` 규칙 10 · 12).
  남지 않는 것의 예 — **에디터의 Error Pause / Console 필터 · 버튼의 활성 상태와 색 · 글자의 줄 수와 위치 · 버튼에 적힌 문구.**
- 🔴 **맞는 기전을 각 회차의 설정값으로 번역하지 않는다.** 「A 면 B 가 된다」가 참이어도 **「이 회차에 A 였다」는 별도의 측정**이다.
  적는 방식은 **「로그로 확인된 것」 표 + 「그래서 원인은 미확정」 한 줄**이다. 그 형태의 예가 `Assets/_Project/Docs/_Tasks/2026-09-16/06_27_post-game-leave-ui/Plan.md` **§15-11-4** 다.
- 🔴 **철회는 문서에 남긴다.** 그 절은 *「확인 전에는 이 항목을 ✅ 로 적지 않는다」* 와 **닫는 방법**(Error Pause 를 껐음을 확인한 상태에서 강제 실패 ①을 2~3회 반복)까지 함께 적어 두었고,
  **2026-09-28 회차에도 그 조건이 충족되지 않아 등급이 유지됐다**(같은 Plan **§15-12-9**). ✅ **닫는 조건을 적어 둔 것이 그 판단을 가능하게 했다 — 조건 없이 「미확정」만 적으면 다음 사람이 무엇을 해야 할지 모른다.**

## 2026-09-28  🔴 테스트 절차를 「내가 아는 것」 전제로 써서 사용자가 절반을 시행하지 못했다

**무엇을 틀렸나**
사용자가 실기 테스트 절차를 달라고 했는데, **아는 사람만 따라올 수 있는 문장으로 적었다.** 그 결과 **테스트 4건 중 1~3 만 시행되고 나머지는 시행되지 못했다.**
사용자 보고 — *"나머지는 테스트 방식을 제대로 안알려줘서 시행 못했으니"*. 지적 — *"대충 알려주는건 정확히 파악이 안돼 / 아무것도 몰라도 테스트 절차대로 진행할수있어야하는데 니 기준에서 적어두니까 제대로 할수가없어"*.

틀린 것은 **3건**이다.

| # | 무엇을 틀렸나 | 왜 그것이 문제인가 |
|---|------|------|
| 1 | 절차를 **「내가 아는 것」 전제**로 썼다 — 예: *"결과 화면에서 상대 앱 강제 종료"* · *"경기 종료 후 방치"* | **무엇을 어떻게 눌러야 하는지가 빠졌다.** 화면의 버튼 라벨·팝업 문구를 모르는 사람은 그 문장으로 아무것도 할 수 없다 |
| 2 | **번호를 재부여**해 테스트가 늘어난 것처럼 보이게 했다 — 5→(5,6) · 3→7 · 미결 관찰→8 | **새 항목은 0개인데 목록이 길어졌다.** 읽는 쪽은 할 일이 늘었다고 읽는다 |
| 3 | 🔴 **이미 통과한 테스트(거절 경로)를 새 번호로 다시 내보냈다** | 통과한 것을 다시 시키는 것은 **시간 낭비이고 통과 기록을 흐린다** |

**왜 그랬나**
- **절차를 쓰는 사람과 읽는 사람의 사전 지식이 같다고 가정했다.** 코드와 로그를 방금 읽은 쪽에게는 *"상대 앱 강제 종료"* 가 한 동작이지만, **화면 앞에 있는 사람에게는 「어느 기기에서 · 어느 화면에서 · 무엇을 눌러서」가 전부 빠진 문장**이다.
- **UI 경로를 확인하지 않고 절차를 썼다.** 메뉴 이름·버튼 라벨·팝업 문구는 **코드·씬에 실재하는 문자열**인데 그것을 찾지 않고 기억으로 적었다.
- **목록을 「정리」하려다 번호를 손댔다.** 항목이 바뀌지 않았는데 번호를 다시 매기면 **변화가 없는데 변화가 있는 것처럼 보인다.**

**어떻게 드러났나**
사용자가 테스트 결과를 보고하면서 **「1~3 은 했고 나머지는 못 했다」고 말하고 그 이유를 지적했다.**
🔴 **로그로는 드러나지 않는다** — 시행되지 않은 테스트는 아무 줄도 남기지 않으므로, **「안 했다」와 「했는데 아무 일도 없었다」가 로그에서 같게 보인다.**

**교훈**
- 🔴 **테스트 절차는 「어느 기기에서 / 무엇을 누르고 / 무엇을 볼 것인가」 세 칸으로 쓴다.** 한 칸이라도 비면 그 절차는 전달되지 않는다.
- 🔴 **버튼 라벨·메뉴 경로·팝업 문구는 반드시 코드나 씬에서 찾아 그대로 인용한다.** 기억으로 적지 않는다.
  ⚠️ **두 버튼 중 하나를 누르는 절차라면 나머지 버튼의 라벨도 적는다** — 어느 것을 누르는지 모르면 절차가 성립하지 않는다.

- 🔴 **번호를 재사용하거나 이어 붙이지 않는다. 이미 통과한 항목은 다시 내지 않는다.** 남은 것만 적고 **「이것이 남은 전부다」를 명시한다.**
- ⚠️ **다른 실수와 무엇이 다른가** — 2026-09-09 는 **체크리스트 항목이 그 조건에서 애초에 관측 불가능**했고, 2026-09-22 는 **씬 배치를 확인하지 않아 검증 불가능한 테스트를 요청**했다.
